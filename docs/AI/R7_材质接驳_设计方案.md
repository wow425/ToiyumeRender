## 0. 结论摘要

> **状态：✅ 已拍板（2026-10-27），P0 施工中。**
> 拍板结果：D1 =(a) linear ｜ **D2 = (b) P0 就上 GGX** ｜ D3 = (a) 只 BaseColor ｜ D4 = (a) alpha test 留 P2 ｜ D5 = 采纳 `-R7Test` ｜ D6 = 方案 A 施工、方案 B 留作演进。

现状**不是「贴图采样参数写错」，而是「贴图通路根本不存在」**：ClosestHit 里的 albedo 是硬编码的中性灰 `(0.8,0.8,0.8)`，每实例数据里没有材质索引、没有 UV 偏移，全局根签名里没有任何 SRV / Sampler 描述符表。三处缺一不可，因此不可能「调一下参数就好」。

分三阶段推进，**每阶段独立可验收、可回滚**：

| 阶段 | 交付 | 新增每实例字段 | 改 RTPSO | 可独立验收 |
|---|---|---|---|---|
| **P0 最小可见色** | BaseColor 贴图 × `baseColorFactor` + **GGX/Cook-Torrance 直射与环境项** | UvOffset / VertexFlags / MaterialIndex / SrvTableOffset / 材质标量 | 否 | 是 |

## 1. 现状取证（为什么看起来是白模）

### 1.1 着色侧的硬编码

`Engine/Shader/07_RayTracing/RayTracing.hlsl`（R6 现版 468 行）：

- `:428` `const float3 albedo = float3(0.8f, 0.8f, 0.8f);   // D3 未接材质，用中性灰`
- `:400` `const float3 albedoSecondary = float3(0.8f, 0.8f, 0.8f);`（反射递归闸门分支的次要着色）

### 1.5 光栅侧是怎么消费这些贴图的（必须对齐）

`Engine/Shader/02_Deferred/GBufferPS.hlsl`：

```hlsl
Texture2D<float4> baseColorTexture : register(t0);
Texture2D<float3> metallicRoughnessTexture : register(t1);
Texture2D<float1> occlusionTexture : register(t2);
Texture2D<float3> emissiveTexture : register(t3);

    float4 baseColorFactor; float3 emissiveFactor; float normalTextureScale;
    float metallicFactor; float roughnessFactor; uint flags;

```

槽位顺序由 `Engine/03_AssetSystem/Assets/Constants/ConstantBuffers.h` 的
`enum { kBaseColor, kMetallicRoughness, kOcclusion, kEmissive, kNormal, kNumTextures };` 固定，`kNumTextures = 5`。

描述符来源（`Engine/05_Scene/Model/ModelLoader.cpp:95-230`）：

- 每材质 `Renderer::s_TextureHeap.Alloc(5)` 拿 5 个连续槽位，`CopyDescriptors` 从真实纹理或默认纹理拷过去
- 默认纹理表：`{ kWhiteOpaque2D, kWhiteOpaque2D, kWhiteOpaque2D, kBlackOpaque2D, kDefaultNormalMap }`
- `Material::SRVTable` / `Material::SamplerTable` 存的是**堆内偏移**（`DescriptorHeap::GetOffsetOfHandle` 的结果），不是句柄
- `Material::MaterialCBV` 是 `model->m_MaterialConstants` 的 GPU VA + `sizeof(MaterialConstants) * matIdx`（`MaterialConstants` 是 `alignas(256)`，步长 256）
- `mesh.materialSlotIdx` 是查材质的唯一入口（赋值点唯一：`ModelConvert.cpp:112`）

### 1.6 sRGB 现状（重要，但**不是**本方案要改的）

`TextureManager::LoadDDSFromFile(path, fallback, bool sRGB = false)`，而 `ModelLoader.cpp:87` 的调用是
`TextureManager::LoadDDSFromFile(ddsFile)` —— **没传 sRGB，恒 false**。
`merlin.ty` 的 `textureOptions` 里 13 张贴图有 8 张带 `kSRGB = 1` 位，但**这个位在加载时被丢弃**。

→ 即 **光栅路径当前也是「linear 读取 sRGB 编码数据」**。这是 R0–R6 一直存在的既有缺陷，不是 R6 引入的。

**决策见 §6 / D1：P0 刻意与光栅保持一致（都 linear），以保证两条路径逐像素可比。修 sRGB 会影响光栅基线，应单独立项。**

## 2. 三条硬约束（决定了方案形状）

这三条都是 D3D12 的机制限制，不是本项目的设计选择，绕不过去：

### C1：一次 `DispatchRays` 只能绑一套描述符表

DispatchRays 是一次派发，整个屏幕所有像素在**同一个** draw call 里跑完。
不同实例命中不同材质 → 需要不同 SRV 表基址，但**无法在派发中途 `SetDescriptorTable`**。

三条出路：
1. **无界 SRV 表 + 着色器内动态索引**（推荐）
2. **SBT 每材质一条 hit group 记录 + 本地根签名**（重量级但最正统）
3. 每材质一次 DispatchRays —— **直接否决**：会重复着色已写过的像素，语义错误

### C2：一个命令列表同时只能绑一个 `CBV_SRV_UAV` 堆

`CommandContext::SetDescriptorHeap(Type, HeapPtr)` 是替换绑定，不是追加。
`RayTracingRenderer.cpp:452` 目前绑的是 `m_DescriptorHeap`（只有输出 UAV 一个槽）。
→ **贴图 SRV 必须与输出 UAV 同一个堆**，否则绑了贴图堆就丢了输出 UAV。

### C3：一个命令列表同时只能绑一个 `SAMPLER` 堆

15 个材质的 `SamplerTable` 偏移各不相同（虽然实测值恰好都落在同一组 5 个槽上，因为 `g_SamplerPermutations` 按 `addressModes` 缓存复用）。
→ **采样器走根签名的静态采样器（static sampler）**，彻底绕开"每材质采样器表"的问题。
代价：失去 per-material `addressModes` 保真度（实测全部 WRAP/WRAP，暂无损）。

## 3. 方案对比

### 方案 A（推荐）：无界 SRV 表 + 着色器内动态索引 + 静态采样器

- 根签名新增一个**无界 SRV 描述符表** `range(NumDescriptors = UINT_MAX, BaseShaderRegister = 3)`，绑定到 `s_TextureHeap` 的**堆首** GPU 地址
- HLSL 声明 `Texture2D g_Textures[] : register(t3);`，用 `NonUniformResourceIndex(instance.SrvTableOffset + slot)` 取具体贴图
- 采样器用 5 个 `StaticSampler`（s0..s4，各向异性 16x / WRAP）写进根签名
- 每实例数据里只存 **1 个 uint32**（`SrvTableOffset`）+ 材质标量

**优点**：改动集中、无 SBT 变更、无 RTPSO 变更、任意数量材质/模型都能工作、可增量演进到 P1/P2。
**缺点**：依赖「无界范围 + 动态索引」，需要一次最小验证（见 §7 风险 R1）。

### 方案 B：SBT 每材质一条 hit group + 本地根签名

每个材质一条 SBT hit 记录，记录的 local root argument 里带该材质的描述符表基址，用 `InstanceContributionToHitGroupIndex` 选中。

**优点**：最正统，为将来「每材质不同着色模型 / 不同 shader」铺路；不依赖动态索引。
**缺点**：要引入 local root signature、要按材质重建 SBT（材质数变化要重建）、SBT 记录尺寸从 32 B 涨到 32+data，且 `InstanceContributionToHitGroupIndex` 只有 24 位。
**结论**：本轮不做，但**保留为 P1 之后的演进项**（如果将来材质需要不同的着色逻辑）。

### 方案 C：每材质一次 DispatchRays

否决。像素会被多材质重复写，且没有深度合成机制。

**推荐 A。**

## 4. 推荐方案的具体改动（P0）

### 4.1 每实例数据结构：32 B → 96 B

`Engine/04_Renderer/Renderer/RayTracing/RaytracingScene.h`：

```cpp
struct RaytracingInstanceData {
    // 0..31   几何寻址（R5/R6 既有）
    uint32_t VertexOffset, IndexOffset, VertexStride, IndexFormat,
             StartIndex, BaseVertex, PrimitiveCount, InstanceId;
    // 32..47  材质寻址（R7 新增）
    uint32_t UvOffset;          // 32: UV0 在顶点记录内的字节偏移
    uint32_t VertexFlags;       // 36: Renderer::kVertex_* 位图
    uint32_t MaterialIndex;     // 40: 语义用（日志 / 调试）
    uint32_t SrvTableOffset;    // 44: s_TextureHeap 堆内偏移（5 个槽起始）
    // 48..91  材质标量（直接内联 MaterialConstantData 的 44 字节，避免再绑 per-model CB）
    float    baseColorFactor[4];   // 48
    float    emissiveFactor[3];    // 64
    float    normalTextureScale;   // 76
    float    metallicFactor;       // 80
    float    roughnessFactor;      // 84
    uint32_t materialFlags;        // 88
    // 92..95  填充
    uint32_t _pad;
};
static_assert(sizeof(RaytracingInstanceData) == 96, "HLSL 侧 INSTANCE_STRIDE_BYTES 必须同步");
```

**为什么内联材质标量而不是绑 `m_MaterialConstants`**：`Model::m_MaterialConstants` 是**每个模型各自一块**的 GPU 资源，HLSL 无法用裸 GPU VA 解引用；多模型场景下还得每模型绑一次（又回到 C1）。内联 44 字节后这一整类问题消失。15 实例 × 96 B = 1,440 B，代价可忽略。

**为什么 stride 取 96**：96 = 6×16，保证每条记录 16 字节对齐，`baseColorFactor`（`float4`）落在 48 偏移即可安全 `Load<float4>`。

### 4.2 UV 偏移的通用算法

不要硬编码 20。由 `Mesh::vertexFlags` 推出（`MeshConvert.cpp:308-330` 的元素顺序固定）：

```
offset = 12                      // POSITION, R32G32B32_FLOAT
if (flags & kVertex_Normal)  offset += 4    // R10G10B10A2
offset += 4                                  // NORMAL 恒存在，实际写法见下
if (flags & kVertex_Tangent) offset += 4    // R10G10B10A2
offset 即为 TEXCOORD0 偏移
```

写成：

```cpp
static uint32_t ComputeUv0Offset(uint32_t vertexFlags)
{
    uint32_t offset = 12;                                   // POSITION
    if (vertexFlags & Renderer::kVertex_Normal)  offset += 4;
    if (vertexFlags & Renderer::kVertex_Tangent) offset += 4;
    return offset;                                          // merlin: 12+4+4 = 20
}
```

`RaytracingScene.cpp` 在填 `RaytracingInstanceData` 时顺手写 `UvOffset` / `VertexFlags` / `MaterialIndex` / `SrvTableOffset` / 材质标量。
材质查找路径：`model->m_MeshData` 转 `const Mesh*`（`m_MeshData` 是 `unique_ptr<uint8_t[]>`，可直接 `reinterpret_cast`）→ `mesh.materialSlotIdx` → `model->m_Materials[slot].SRVTable`。

### 4.3 根签名：新增 1 个无界 SRV 表 + 5 个静态采样器

`RayTracingRenderer.cpp`：

```cpp
enum GlobalRootBindings {
    kGlobalRootScene = 0,
    kGlobalRootSceneData,
    kGlobalRootInstanceData,
    kGlobalRootTextureTable,    // t3  无界 SRV 表（R7 新增）
    kGlobalRootOutputTable,     // u0
    kGlobalRootConstants,       // b0
    kNumGlobalRootBindings
};
```

`BuildRootSignature()` 内：

```cpp
// 贴图表：无界（NumDescriptors = UINT_MAX），覆盖整个 s_TextureHeap
// 注意：无界范围必须是表中最后一个 range，且 HLSL 侧必须声明为无界数组
m_GlobalRootSig[kGlobalRootTextureTable].InitAsDescriptorRange(
    D3D12_DESCRIPTOR_RANGE_TYPE_SRV, /*Register=*/3, /*Count=*/UINT_MAX,
    D3D12_SHADER_VISIBILITY_ALL);
```

`Reset(kNumGlobalRootBindings, 5)` 并把 5 个静态采样器写好：

```cpp
SamplerDesc sampler;                       // 默认各向异性 16x / WRAP / LOD 全范围
sampler.MaxAnisotropy = 16;
m_GlobalRootSig.InitStaticSampler(0, sampler, D3D12_SHADER_VISIBILITY_ALL);  // s0 BaseColor
m_GlobalRootSig.InitStaticSampler(1, sampler, D3D12_SHADER_VISIBILITY_ALL);  // s1 MR
m_GlobalRootSig.InitStaticSampler(2, sampler, D3D12_SHADER_VISIBILITY_ALL);  // s2 Occlusion
m_GlobalRootSig.InitStaticSampler(3, sampler, D3D12_SHADER_VISIBILITY_ALL);  // s3 Emissive
m_GlobalRootSig.InitStaticSampler(4, sampler, D3D12_SHADER_VISIBILITY_ALL);  // s4 Normal
```

> 注：`RootSignature::Finalize` 用的是 `D3D12SerializeRootSignature`（v1.0 序列化器，`RootSignature.cpp:153`），静态采样器与无界范围都在 v1 能力内，无需改序列化器。

### 4.4 描述符堆：合并成一个 CBV_SRV_UAV 堆（解决 C2）

**现状**：`m_DescriptorHeap`（输出 UAV，1 槽）+ `s_TextureHeap`（贴图 SRV，4096）两个堆，但同一时刻只能绑一个。

**改动**：把输出 UAV 也放进 `Renderer::s_TextureHeap`，然后全程只绑 `s_TextureHeap`：

- `RayTracingRenderer` 删掉成员 `DescriptorHeap m_DescriptorHeap`，改成 `uint32_t m_OutputUavOffset = 0;`
- `Initialize()` 中 `s_TextureHeap.Create(...)` **之后**再 `m_OutputUavOffset = s_TextureHeap.GetOffsetOfHandle(s_TextureHeap.Alloc(1));`（此时堆空，恒为 0）
- `RefreshDescriptorHeap()` 往 `s_TextureHeap[m_OutputUavOffset]` 写 UAV 描述符
- `Render()` 里 `context.SetDescriptorHeap(CBV_SRV_UAV, s_TextureHeap.GetHeapPointer())`，并
  - `compute.SetDescriptorTable(kGlobalRootTextureTable, (D3D12_GPU_DESCRIPTOR_HANDLE)s_TextureHeap[0])` —— 堆首，无界表覆盖整个堆
  - `compute.SetDescriptorTable(kGlobalRootOutputTable, (D3D12_GPU_DESCRIPTOR_HANDLE)s_TextureHeap[m_OutputUavOffset])` —— 1 个 UAV

> 副作用：堆里 index 0 是 UAV，贴图从 index ≥ 1 开始。无界 SRV 表会把 index 0 也当 SRV 看待，但我们永远不索引它，无害。**在代码里写清这条**，否则后来人会困惑。

### 4.5 HLSL 改动

`Engine/Shader/07_RayTracing/RayTracing.hlsl`：

```hlsl
// R7：贴图。注意寄存器与 GBufferPS 不同 —— t0/t1/t2 已被根级 SRV 占用
Texture2D<float4> g_Textures[] : register(t3);   // 无界数组，索引 = SrvTableOffset + slot
SamplerState g_BaseColorSampler : register(s0);

#define INSTANCE_STRIDE_BYTES 96   // 32 → 96
#define INSTANCE_UV_OFFSET          32
#define INSTANCE_VERTEX_FLAGS       36
#define INSTANCE_MATERIAL_INDEX     40
#define INSTANCE_SRV_TABLE_OFFSET   44
#define INSTANCE_BASECOLOR_FACTOR   48
#define INSTANCE_MATERIAL_FLAGS     88

float2 LoadVertexUv(uint vertexOffsetInScene, uint uvOffsetInVertex)
{
    const uint addr = vertexOffsetInScene + uvOffsetInVertex;
    return Load<float2>(addr);          // R16G16_FLOAT，Load<float2> 内部按 half2 解
}
```

`ClosestHit` 内替换 `:428`：

```hlsl
const uint instBase = InstanceID() * INSTANCE_STRIDE_BYTES;
const float4 baseColorFactor = Load<float4>(instBase + INSTANCE_BASECOLOR_FACTOR);
const uint   vertexFlags     = Load<uint>(instBase + INSTANCE_VERTEX_FLAGS);
const uint   uvOffset        = Load<uint>(instBase + INSTANCE_UV_OFFSET);
const uint   srvBase         = Load<uint>(instBase + INSTANCE_SRV_TABLE_OFFSET);

float4 baseColor = baseColorFactor;
if (vertexFlags & kVertex_UV0)
{
    const float2 uv = LoadVertexUv(instBase_vertex..., uvOffset);   // 具体写法见实现
    baseColor *= g_Textures[NonUniformResourceIndex(srvBase + kBaseColorSlot)]
                     .SampleLevel(g_BaseColorSampler, uv, 0.0f);
}
const float3 albedo = baseColor.rgb;
```

**三个必须写对的点**：

1. **`NonUniformResourceIndex()`** —— 索引逐像素不同（不同材质），不加会触发未定义行为 / 校验错误
2. **`SampleLevel(..., 0.0f)`** —— 光追里没有像素级 quad 导数，`Sample` 会算错 mip；必须显式给 LOD。P0 先固定 LOD 0（与光栅近景一致），需要时再按 RayCone 算
3. **寄存器重编号** —— 贴图不能再用 t0..t4（已被 TLAS / SceneData / InstanceData 占住），必须是 t3..t7 或换 register space。这是最容易踩的坑

### 4.6 新增调试通道 `BaseColor`

### 4.7 D2 拍板 (b) 后的增量：GGX/Cook-Torrance

D2 已拍板为 **(b) P0 就上 GGX**。相对 §4.5 的 Lambert 版本，增量如下。

**新增两个独立开关**（`Engine/04_Renderer/RenderParams.h`）：

```cpp
bool  EnableMaterialTextures = true;    // 关掉 = 回到 R6 的 albedo=(0.8,0.8,0.8)
bool  EnableGGX              = true;    // 关掉 = 回到 R6 的 Lambert
```

两个开关正交，构成 §5 的 2×2 对照矩阵（A5a/A5b/A5c）。

**GGX 所需的额外每实例字段**：`metallicFactor` / `roughnessFactor` 已在 §4.1 的 96 B 结构里，无需再扩。

**HLSL 侧**（`RayTracing.hlsl` 内新增，替换 §4.5 的 `diffuse + albedo*ambient` 三行）：

```hlsl
// 与 GBufferPS/LightingPS 用同一套 BRDF 常数，保证两条路径可比
static const float kPI = 3.14159265359f;
static const float kMinRoughness = 0.045f;   // 避免 alpha=0 时 GGX 除零

float DistributionGGX(float nDotH, float alpha)
{
    const float a2 = alpha * alpha;
    const float d  = nDotH * nDotH * (a2 - 1.0f) + 1.0f;
    return a2 / max(kPI * d * d, 1e-7f);
}

float VisibilitySmithGGXCorrelated(float nDotV, float nDotL, float alpha)
{
    // 用「可见性」项（已含 1/(4·nDotV·nDotL)），避免单独写 G 再除的老式写法出错
    const float a2 = alpha * alpha;
    const float gv = nDotL * sqrt(nDotV * nDotV * (1.0f - a2) + a2);
    const float gl = nDotV * sqrt(nDotL * nDotL * (1.0f - a2) + a2);
    return 0.5f / max(gv + gl, 1e-7f);
}

float3 FresnelSchlick(float vDotH, float3 f0)
{
    return f0 + (1.0f - f0) * pow(saturate(1.0f - vDotH), 5.0f);
}
```

着色主体（在 `ClosestHit` 内，`albedo` 已由 §4.5 求出）。

> **与 D3（只做 BaseColor）的对齐**：GGX 需要 metallic / roughness，但**不采样 MetallicRoughness 贴图** —— 只用 §4.1 内联的 `metallicFactor` / `roughnessFactor` 标量。这样：
> - 仍然只接 1 张贴图（BaseColor），符合 D3；
> - GGX 有真实的 per-material 参数（实测 mat7/mat11 的 `metallicFactor=1.0`，其余 0.0，`roughnessFactor` 全 0.5）；
> - 贴图版 MR 留给 P1，届时只多一次采样，不动染色路径。
>
> 代价：本场景 15 个材质的 roughness 全是 0.5 → 金属/粗糙的**空间变化**看不出来，只有金属度在 mat7/mat11 上有跳变。这是 D3 决定的必然结果，写进日志与文档，不作为缺陷。

```hlsl
// 只用标量 —— P0 不采样 MR 贴图（D3：只做 BaseColor）
const float metallic  = saturate(metallicFactor);
const float roughness = clamp(roughnessFactor, kMinRoughness, 1.0f);
const float alpha     = roughness * roughness;

const float3 v = -incoming;
const float  nDotV = max(dot(n, v), 1e-4f);
const float3 h = normalize(toLight + v);
const float  nDotL = saturate(dot(n, toLight));
const float  nDotH = saturate(dot(n, h));
const float  vDotH = saturate(dot(v, h));

const float3 f0 = lerp(float3(0.04f, 0.04f, 0.04f), albedo, metallic);
const float3 F  = FresnelSchlick(vDotH, f0);
const float  D  = DistributionGGX(nDotH, alpha);
const float  Vis = VisibilitySmithGGXCorrelated(nDotV, nDotL, alpha);

// 直射项：注意 G 已并入 Vis，不再乘 1/(4·nDotL·nDotV)
const float3 specular = (D * Vis) * F;
const float3 kd = (1.0f - F) * (1.0f - metallic);
const float3 diffuseBRDF = kd * albedo / kPI;

const float3 direct = (diffuseBRDF + specular) * lightRadiance * nDotL * visibility;

// 环境项：D3 没有 IBL，用 SkyColor 作为"单色环境"的粗代理
// 不乘 albedo 的部分是镜面反射，乘 albedo 的部分是漫反射
const float3 ambientSpec = SkyColor(reflect(-v, n)) * F * (1.0f - roughness * 0.7f);
const float3 ambientDiff = albedo * SkyColor(n) * 0.35f;
float3 shaded = direct + lerp(ambientDiff, ambientSpec + ambientDiff, metallic);
```

> **为什么用「相关式 Smith 可见性」而不是 G**：`VisibilitySmithGGXCorrelated` 已把 `1/(4·nDotL·nDotV)` 折进去，调用点不再除分母 —— 少一个除法、少一处常见错误（项目内如果将来有人照抄 G 的写法，会重复除一次，直接对比 A5b/A5c 就能看出异常）。

**`EnableGGX == false` 时**回退到 R6 的 `diffuse + albedo*ambient` 三行，且 **`EnableMaterialTextures == false` 时 albedo 恒为 `(0.8,0.8,0.8)`** —— 两者都关时，代码路径与 R6 逐指令等价（这也是 A5a 要求 md5 相同的前提；只允许 `g_RTParams2.w` 这个新开关位参与，不影响输出）。

**反射项与 GGX 的关系**：R6 的单次反射（`TraceReflectionRay` + Schlick 菲涅尔）保持不变，`EnableGGX` 只影响直射/环境项。反射强度仍由 `RTReflectionIntensity` 控制。这是刻意的 —— 反射已经是简化模型，本轮不把它改成 GGX 追踪。

## 9. 与路线图的关系

`docs/AI/ToiyumeRender_升级路线图_2026-10-24.md` §8 D3 要求「每个算法都应有可比较的光栅/光追场景、明确采样与偏差策略、性能统计和开关」。本方案：

- **可比较场景**：`BaseColor` 调试通道双向对照（A4）
- **采样策略**：P0 固定 LOD 0 并写明理由；P1 起按 RayCone 或固定 LOD 偏置
- **偏差策略**：沿用 R6 的 `RTShadowNormalBias`（唯一旋钮），贴图接驳不引入新偏差
- **性能统计**：沿用 `RayTracingFrameStats`（射线发射数），P0 新增「贴图采样次数」可选
- **开关**：新增 `EnableMaterialTextures`（默认开），关掉能回到 R6 白模 —— 这本身就是 A5 的验收手段
