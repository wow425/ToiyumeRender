| 维度 | 实现 | 证据 |
|---|---|---|
| 数据结构 | 每队列一池：`vector<ID3D12CommandAllocator*> m_AllocatorPool`（只增）+ `queue<pair<uint64_t,ID3D12CommandAllocator*>> m_ReadyAllocators`（fence 值 ↔ 分配器） | `Engine/02_RHI/Command/CommandAllocatorPool.h:26-32` |

| 调用点 | `RequestAllocator`：`CommandContext.cpp:199`（Reset 复用）、`CommandListManager.cpp:96/98/99`（CreateNewCommandList）；`DiscardAllocator`：`CommandContext.cpp:135`（Finish） | — |
| 池是否收缩 | **不收缩**，`m_AllocatorPool` 只 `push_back`，仅 `Shutdown()` 整体 Release | `CommandAllocatorPool.cpp:21-28` |

### 2.2 为什么需要池（代码依据）

1. **DX12 硬规则**：一个 allocator 不能在两处同时录制；重置一个仍被 GPU 执行的 allocator 是 UB。代码把"allocator 可用"与"fence 已完成"绑定：`CommandAllocatorPool.cpp:40` `if (AllocatorPair.first <= CompletedFenceValue)`。
2. `CommandContext::Reset` 断言 `m_CurrentAllocator == nullptr`（`CommandContext.cpp:198`），说明 allocator 是"单独借贷、单独归还"的资源，必须由池统一托管。
3. 归还时机精确绑在**本次提交的 fence 值**上：`FenceValue = Queue.ExecuteCommandList(...)` → `Queue.DiscardAllocator(FenceValue, m_CurrentAllocator)`（`CommandContext.cpp:134-135`），保证"GPU 处理完这一批才允许复位"。
4. `CompletedFenceValue` 来源：`m_pFence->GetCompletedValue()`（`CommandListManager.cpp:183-188` 的 RequestAllocator 转发），不是靠 CPU 阻塞等待。

### 2.3 池的局限（实测）

| 局限 | 影响 | 证据 |
|---|---|---|
| 只检查队首 | 队首 fence 未完成时，后面已完成的 allocator 也拿不到 → 无谓新建 | `CommandAllocatorPool.cpp:37-46` |
| 与 DynamicDescriptorHeap / LinearAllocator 同构的"只查队首"写法 | 三处一致，属体系性写法而非孤立缺陷 | `DynamicDescriptorHeap.cpp:21`、`LinearAllocator.cpp:30`、`CommandAllocatorPool.cpp:39` |
| 无容量上限 | 极端落后情况下 allocator 数量随在飞帧线性增长（受 DXGI 队列深度约束，实际很小，INFERRED） | 无容量检查，`CommandAllocatorPool.cpp:48-55` |

## 5. UploadBuffer / ReadbackBuffer / LinearAllocator 的复用策略与风险

### 5.1 三者的定位

| 类型 | 堆类型 / 初始状态 | 复用策略 | 证据 |
|---|---|---|---|
| `UploadBuffer` | `HEAP_TYPE_UPLOAD` / `GENERIC_READ`（**但代码从不给 m_UsageState 赋值**，保持默认 COMMON） | **无复用机制**。`Create` 建资源、`Map`/`Unmap` 由调用者负责；无 fence、无帧槽位 | `Engine/02_RHI/Resource/Heap/UploadBuffer.cpp:9-46`（`:17` Destroy、`:37` CreateCommittedResource）；`:49-57` Map（`:54` `CD3DX12_RANGE readRange(0,0)`）；`:59-63` Unmap（`:61` `std::min(end,m_BufferSize)`） |
| `ReadbackBuffer` | `HEAP_TYPE_READBACK` / `COPY_DEST`（此处**有**赋值） | 无复用机制；Map 全程可读 | `Engine/02_RHI/Resource/Heap/ReadbackBuffer.cpp:7-48`（`:15` `m_UsageState=COPY_DEST`）、`:50-56` Map（`:53` range(0,m_BufferSize)）、`:58-62` Unmap |
| `LinearAllocator` | CPU 页 UPLOAD / GPU 页 DEFAULT+ALLOW_UAV | **有完整复用**：页管理器 + fence 退休队列 | 见 §5.2 |

> 注：`UploadBuffer` 不写 `m_UsageState` 与真实状态（GENERIC_READ）不符，但 `TransitionResource` 在 `CommandContext.cpp:430-438` 对 UPLOAD 堆直接校正状态并 return，**不会发出非法屏障**，故当前无害（潜在一致性隐患，INFERRED）。

### 5.2 LinearAllocator 的复用链（唯一真正"帧级环形"的部分）

| 环节 | 实现 | 证据 |
|---|---|---|
| 页大小 | GPU 64KB / CPU 2MB | `Engine/02_RHI/Memory/LinearAllocator.h:46-50`（`kGpuAllocatorPageSize=0x10000`、`:49` `kCpuAllocatorPageSize=0x200000`） |

### 5.3 逐帧动态常量缓冲的实际路径

| 路径 | 事实 | 证据 |
|---|---|---|
| UI 之外的每帧 CB | `SetDynamicConstantBufferView` → `m_CpuLinearAllocator.Allocate(BufferSize)` → `memcpy` → `SetGraphicsRootConstantBufferView` | `CommandContext.h:486-493`（`:490` Allocate、`:492` memcpy） |

### 6.1 最值得关注的一条（展开）

**R-04：屏障缓冲 16 槽在 Release 下会静默越界。**

- 机制：`CommandContext.h:200` 定义 `D3D12_RESOURCE_BARRIER m_ResourceBarrierBuffer[16]`；`CommandContext.cpp:452` 先取引用 `D3D12_RESOURCE_BARRIER& BarrierDesc = m_ResourceBarrierBuffer[m_NumBarriersToFlush++]`，**断言在 `:451` 只是 `ASSERT`**，而 `Utility.h:158-163` 的 Release 分支把 `ASSERT` 展开为 `(void)(isTrue)`。
- 触发条件：在**同一次 FlushResourceBarriers 之前**累计第 17 个不同的资源状态转换。当前主渲染路径每次 Draw 前都会 Flush（`CommandContext.h:723/732`），所以正常达不到 16；但 `TransitionResource` 支持 `FlushImmediate=false` 批量累积，任何"批量转换 >16 个资源"的新代码都会命中。
- 后果：Debug 下 `__debugbreak`（`Utility.h:169-176`）；Release 下写穿数组，破坏 `m_NumBarriersToFlush` 邻接成员与栈帧 → 随机崩溃或更糟的静默错误。
