### 4.2.3 与 `Engine/Engine.md` 自述依赖方向的差异（必须说明）

`Engine/Engine.md` 自述推荐方向为 `Application → Renderer → RenderFeatures → RenderPasses → RenderGraph → ResourceSystem → GPUInfrastructure → RHI → Core` `[实测]`。本文的差异与理由：

| Engine.md 中的层 | 本文对应 | 差异与理由 |
|---|---|---|
| RenderGraph | **无（暂缓）** | 项目当前 pass 数量（Z/GBuffer/Lighting/透明）不足以摊薄 RenderGraph 的抽象成本；引入会让「同步关系」更隐蔽，与原则⑤冲突。触发条件见 4.6 |
| ResourceSystem / GPUInfrastructure | **并入 L4 Shared** | 项目现有 `BufferManager`/`PipelineStateCache`/`ShaderLibrary` 体量小，单列一层会造成只有 1–2 个文件却要走跨层头文件路径的空层 |
| RenderFeatures / RenderPasses 两层 | **合并为 L4** | WE 的 `wi::renderer` 把「功能」与「pass 组织」放在同一命名空间（`DrawScene` 内部自组织 pass）`[实测]`，证明两者可合并；拆两层会产生「Feature 与 Pass 谁持有 RT」的重复定义 |

## 4.4 边界契约 B1–B6（本文核心）

### B1 应用层 ↔ 渲染路径（原则①）

**机制**：应用层只做「一帧一次」的 `path->Render(frameContext)` 调用；路径内部完成 shadow→（Z/GBuffer）→lighting→透明→后处理的全链。**取消**现有 `BaseRenderer` 的「按 pass 分次调用」形态（`Render(context, frame, pass, batchType)`），因为它把 pass 调度权交给了应用层——这是 MiniEngine `GameCore` 形态的遗留，是原则①的直接违反。

现状证据：`BaseRenderer.h` 声明 `virtual void Render(GraphicsContext&, const RenderFrameDesc&, DrawPass pass, BatchType batchType = kDefault) = 0;`，即**外部**决定画哪个 pass `[实测]`。

**目标接口草案**（在现有 `BaseRenderer` 上演化，命名可讨论）：

`@cpp
namespace Renderer {

// 帧输入：由应用层构造，路径只读
struct FrameContext {
    const Scene::Scene* scene = nullptr;        // 取代现有裸指针列表（现状：注释掉的 scene + std::vector<ModelInstance*>）
    const Scene::Camera::Camera* camera = nullptr;
    const Scene::Camera::Camera* shadowCamera = nullptr;
    float deltaTime = 0.0f;                     // 修正现状拼写 delatT
    uint64_t frameIndex = 0;                    // 帧资源环与 TAA 需要
    RenderSettings settings;                    // 由命令行/UI 驱动，取代编译期 GetFeatures()
};

class RenderPath {
public:
    virtual ~RenderPath() = default;
    virtual std::wstring GetName() const = 0;
    virtual bool Initialize(const PathCreateDesc& desc) = 0;   // 取代 RendererCreateDesc（补 RT 格式/帧数）
    virtual void Shutdown() = 0;
    virtual void OnResize(uint32_t width, uint32_t height) = 0;
    virtual void Render(FrameContext& frame, GraphicsContext& gfx) = 0;   // 单入口，全链
    // 结果暴露：取代 WE 的 public RT 成员，用 getter 明确语义（链后续的 UI/后处理/多路径共享）
    virtual const ColorBuffer* GetFinalLDR() const = 0;   // 交换链格式，UI 之前的最终颜色
    virtual const ColorBuffer* GetSceneHDR() const = 0;   // 线性 HDR
    virtual const DepthBuffer* GetSceneDepth() const = 0;
    // 声明本路径支持什么（不驱动调度）
    virtual PathFeature GetSupportedFeatures() const = 0;
};

} // namespace Renderer
`@

**应用层侧约束**：`IGameApp` **保留**（形态合理），但 `RenderScene()` 的实现体必须退化为「构造 `FrameContext` → `path->Render`」。渲染 handle、pass、RT 不得出现在 `Demos/*` 中。

**@[实测]` 现状对照**：`IGameApp` 现有 `Startup/Cleanup/IsDone/Update(float)/RenderScene()/RenderUI(GraphicsContext&)/RequiresRaytracingSupport()`（Engine/01_Application/GameCore.h:16-31）——只需把 `RenderScene()` 的实现外包给路径，**接口本身不动**，改动量可控。

### B2 渲染路径 ↔ 公共渲染功能（原则②，本文最关键的决策）

**问题陈述（作者自己的话）**：`BaseRenderer.h:1-8` 注释记载：「miniengine 的 pso 绑定设计成一个全局方法……问题是这方法写在 renderer 模块里，还跟 renderer 的 cpp 文件里的数据有联系，想要设计成抽象 renderer 类与具体实现 renderer 类，这方法得分离开来，留在抽象类里缺乏数据没法实现，又因为是通用方法，放在具体类里又不合适」`[实测]`。

**正解**：这条困境的精确定位是——**「按 mesh+material 生成并绑定 PSO 并绘制」是一个公共渲染功能，它需要 Scene/材质数据，但不需要路径身份**。因此把它提取到 L4，作为 `DrawScene` 功能，输入显式包含它需要的数据，从而同时解决「抽象类缺数据」和「具体类不该放通用方法」两个矛盾。

**目标形态**（@[实测]` 对齐 WE `wi::renderer::DrawScene(CameraComponent&, wi::scene::Scene&, uint32_t flags)` 的显式参数风格）：

`@cpp
namespace Renderer::Features {

enum class DrawSceneFlags : uint32_t {
    None = 0, DepthPrepass = 1u<<0, Opaque = 1u<<1, Transparent = 1u<<2,
    Shadow = 1u<<3, GBuffer = 1u<<4, Forward = 1u<<5, // 路径选择用哪个几何输出通道
};

// 公共渲染功能：显式声明读写资源，不自己创建 RT、不自己提交换链
void DrawScene(GraphicsContext& gfx,
               const Scene::Scene& scene,          // 只读世界
               const Scene::Camera::Camera& camera,
               const Scope& scope,                 // 视锥/可见性（避免每次重算）
               const SceneDrawTargets& targets,    // 由路径传入：GBuffer SRV 槽/深度/颜色
               PSOFactory& psoFactory,             // PSO 解析责任在此，不在路径
               DrawSceneFlags flags);

void DrawShadowmaps(GraphicsContext&, const Scene::Scene&, const ShadowScope&, const ShadowTargets&, PSOFactory&);
void DrawSkyBox(GraphicsContext&, const Scene::Scene&, const Scene::Camera::Camera&, const ColorBuffer* target, PSOFactory&);

} // namespace Renderer::Features
`@

**责任划分（本边界最容易被做错的地方，逐条写明）**：

| 关注点 | RenderPath | RenderFeatures | 理由 |
|---|---|---|---|
| RT 的创建/尺寸/格式 | **拥有** | 不感知 | 原则④：输入输出约定由路径装配 |
| barrier / 资源状态转换 | **声明并执行** | 只声明读写意图 | 原则⑤：**禁止用抽象隐藏同步关系** |
| pass 顺序 | **决定** | 提供能力 | 原则② |
| mesh 排序（MeshSorter） | 不参与 | **拥有** | 它是绘制细节 |
| PipelineDesc→PSO 解析 | 不参与 | **拥有**（PSOFactory） | **正是自述困境的正解**：通用且需要材质数据 |
| 材质 CB 上传与纹理描述符 | 不参与 | **拥有** | 同上 |
| 相机/光照数据读取 | 传入 FrameContext | **只读** Scene | 原则③ |
| 提交命令列表 | **拥有** | 不拥有 | 应用与交换链耦合点只在路径。**注意**：WE 反其道而行——全帧唯一提交在 `wiApplication.cpp:388 SubmitCommandLists`，路径内部无提交无 fence（`01A` §6.3）`[实测]`。本项目**不照搬**此点：路径自己提交，应用层不碰命令列表，这样「一帧一次调用」的边界才成立 |

**现有 `BaseRenderer` 虚函数的去向（可施工级映射）**：

| 现有成员 | 去向 |
|---|---|
| `Initialize/Shutdown/OnResize/GetName` | 保留到 `RenderPath` |
| `BeginFrame/EndFrame` | 并入 `Render(FrameContext&)` 的前后段 |
| `Update(frame, gfx)` | 拆成：`RenderPath::Render` 内的 pass 循环 + `Features::DrawScene` |
| `Render(ctx, frame, pass, batchType)` | **删除**（pass 调度权收回路径） |
| `GetPSO(PipelineDesc)` | **迁出**到 `PSOFactory`/`MaterialShaderMap` |
| `BindRenderState` | **迁出**到 `DrawScene` |
| `BindMaterial` | **迁出**到 `DrawScene` + MaterialShaderMap |
| `GetFeatures()` | 改为 `GetSupportedFeatures()`，返回值由 `RenderSettings` 配置驱动 |
| `MeshSorter` | **整类迁入** L4（它是绘制功能的一部分） |
| `RootBindings` 枚举 | 迁入 L4 `Shared`（根签名布局是公共渲染约定，不是路径私有） |
| `s_TextureHeap/s_SamplerHeap` 全局堆 | 迁入 L4 `Shared` 的 `DescriptorAllocator`，**去掉裸 `extern` 全局**（改显式传入或单例访问器，保留可测性） |

**原则②的例外条款必须显式写进实现约定**（约束文档明确允许「不强迫所有算法共用不合理接口」）：PathTracing 的 SBT/shader binding、Neural/3DGS 的专用管线**允许**绕过 `DrawScene` 专用实现；但必须：(a) 仍由 L5 路径暴露结果；(b) 仍使用 L1 的帧资源环与具名 Transition；(c) 在代码注释标注「专用实现，不共享公共接口」并说明理由。

### B3 场景/材质 ↔ RHI（原则③）

**缺口**：项目**没有 Scene 类**（S5）。这是原则③与「场景与资产系统」完成标准的**结构性**缺口，不是泄漏问题，是缺失问题。

**目标**：新增 `Scene::Scene` 轻量世界容器（**不引入完整 ECS**，理由见 4.6）：

`@cpp
namespace Scene {
class Scene {
public:
    Camera::Camera& GetMainCamera();
    Camera::Camera& GetSunCamera();
    LightingSystem& GetLighting();
    const std::vector<ModelInstance>& GetInstances() const;   // 取代应用层每帧手传的 vector<ModelInstance*>
    EnvironmentDesc& GetEnvironment();                        // IBL/天空/曝光
    // 变更通知（原则③：GPU 侧资源跟着 CPU 侧变更走，而非每帧重建）
    uint32_t GetRevision() const;
    void MarkMaterialDirty(MaterialHandle);
};
}
`@

**材质的分裂（关键）**：现在 `Scene::Material::Material` 同时承担「数据」与「给 GPU 绑定」两种职责。目标拆成：

| 侧 | 类型 | 归属层 | 职责 |
|---|---|---|---|
| CPU 数据 | `Scene::Material::Material` | L3 | 参数值 + 纹理句柄（**无 PSO、无根签名、无描述符**） |
| GPU 映射 | `Renderer::MaterialShaderMap` | L4 | 材质→(shader/PSO/输入布局) 的解析与缓存，按 revision 失效 |

**允许泄漏的边界（本文的取舍，必须说明）**：目标是**收敛**而非消灭 D3D12 类型。规则：

| 层 | 允许出现的类型 | 禁止 |
|---|---|---|
| L3 Scene | `Texture`/`GpuBuffer`/`DescriptorHandle` 等 **RHI 资源包装类** | `ID3D12*`、命令列表、barrier、`D3D12_ROOT_SIGNATURE_DESC` |
| L4 Features | `D3D12_GPU_VIRTUAL_ADDRESS` 等**在内层实现与排序结构**中出现 | 在上层接口（路径/应用可见的签名）中出现裸 D3D12 类型 |
| L5 Path | 无（对外接口只用 RHI 类与自定义 POD） | `D3D12_VIEWPORT`/`D3D12_CPU_DESCRIPTOR_HANDLE` 出现在 public 签名 |

**现状违反清单（02 号审计需逐条确认并计数）**：`MeshSorter::SortObject` 的 `D3D12_GPU_VIRTUAL_ADDRESS`（BaseRenderer.h:190-196）；`BaseRenderer::GetMainViewport()` 返回 `D3D12_VIEWPORT`；`DeferredRenderer::m_CPUGBuffers[]` 与 `m_GBufferSRV`（DeferredRenderer.h:145-147）`[实测]`。

### B4 后处理与 HDR/LDR 约定（原则④）

**约定的核心是「语义表 + 显式绑定」**，不是某个具体特效。

**RT 语义表（目标）**：

| 语义 | 格式建议 | 写入者 | 读取者 | 备注 |
|---|---|---|---|---|
| `SceneHDR`（场景颜色） | R16G16B16A16_FLOAT | lighting pass（延迟）/ forward pass | 后处理、TAA | **线性 HDR** |
| `Depth`（场景深度） | D32_FLOAT（+stencil 按需） | Z/GBuffer pass | 阴影、SSAO、后处理、PathTracing(可选) | 现状已有 `ShadowBuffer`（深度 VB 偏移不递增是 P0 bug）`[待02复核]` |
| `Velocity` | R16G16_FLOAT | 几何 pass | TAA/运动模糊 | 现状 `DeferredBuffer::VelocityBuffer` 已声明 `[实测]` |
| `PostA/PostB` | 与 `SceneHDR` 同格式 | 后处理 ping-pong | 下个效果 | **两个，按需 ping-pong** |
| `SceneLDR` | 交换链格式（如 R10G10B10A2 / R8G8B8A8） | **tonemapping** | UI 合成 | **LDR 起点**：tonemap 之后禁止再引入 HDR 语义 |

**三类不可混淆**：HDR（线性、可 >1、可运算）→ Tonemapping（**唯一跨界点**）→ LDR（[0,1]、仅供显示与 UI）。约定：任何效果的签名参数类型即声明其语义域；`PostProcess::Effect` 的输入输出必须显式标注 HDR 或 LDR。

**Ping-Pong 规则**：

- 每个效果的签名形如 `void Render(GraphicsContext&, const ColorBuffer& src, ColorBuffer& dst, const Params&)`，**禁止无参 `Render()`**（MiniEngine `namespace PostEffects { void Render(void); }` 形态 **明确拒绝**——它内部用全局后缓冲，输入输出不可见）`[实测]`。
- 允许 `src == &dst` 的效果必须在注释中声明 in-place 安全性；否则由链负责交换 A/B。
- 链由 **路径拥有**（`PostProcess::Chain` 成员），效果是纯函数式调用，不持有 RT。
- 时序效果（TAA）需要历史资源：历史 RT 归**效果**持有但由路径在 `OnResize` 时统一重建（生命周期归属要在工作包里写死，避免现状的 resize 断链 bug 重演）。

**现状与约束的冲突处理**：项目当前无后处理链（S8），而约束要求「架构迁移完成前禁止大规模新增无关渲染特效」。因此本阶段后处理的工作包**只做**：(a) 语义表与接口约定；(b) 把已有的 tonemap / TAA（`04_PostProcess/TAACS.hlsl`）**归位到新链框架**，不新增新特效。

### B5 资源生命周期与 GPU 同步（原则⑤）

**禁止用抽象隐藏同步关系**是硬约束，因此本边界不给「自动同步」，只给**显式的帧资源环 + 显式状态转换 + 显式延迟销毁**。

**帧资源环（目标）**：

`@text
FrameResource[kFrameCount]   // 建议 3，可配置
  ├─ CommandAllocator        （每帧一组的分配器池）
  ├─ UploadBuffer 线性区      （每帧重置，供 CB/IB/VB 上传）
  ├─ 该帧引用的资源清单        （用于延迟销毁）
  └─ FenceValue              （提交完成值）

Render(frameIndex):
  1. 若 FrameResource[frameIndex].FenceValue 未完成 → CPU 等待（阻塞点显式可见）
  2. 用该帧分配器录制；上传走该帧线性区
  3. 资源状态转换用**具名 API**：Transition(cmd, resource, before, after)
  4. 提交后记录 fence 值；被销毁资源登记到该帧的延迟销毁队列
  5. 回收：仅当对应 fence 完成才真正 Release
`@

**必须写进工作包的协议（现状风险对应）**：

| 场景 | 协议 | 对应现状风险 |
|---|---|---|
| resize | ①等待 GPU 空闲 → ②按依赖倒序销毁尺寸相关 RT → ③重建 → ④重建描述符 → ⑤恢复 | 旧审计记为「resize 断链致必崩」`[待02复核]` |
| 最小化（0×0） | 跳过渲染但**不跳过帧推进**，且不创建 0 尺寸资源 | 旧审计记为「最小化 0 尺寸」`[待02复核]` |
| shutdown | 等待所有在飞帧 → 销毁 RT → 销毁 PSO/根签名 → 销毁堆 → 退出调试层 | 顺序错误是经典崩溃源 |
| 上传堆 | 线性分配器按帧重置；禁止跨帧复用未 fence 的映射内存 | 原则⑤ |
| 描述符 | 每帧分配区按帧重置；静态描述符（纹理/IBL）持久 | 现状全局堆 `s_TextureHeap` 需区分持久/瞬态 |

**可验证证据（工作包验收用）**：调试层零 warning；PIX 每个 pass 有 `PIXBeginEvent`；帧资源环的 fence 计数可日志化；resize/最小化/关闭三个用例手动测试通过。

### B6 扩展性（原则⑥）

| 未来管线 | 接入方式 | 是否需要改 RHI | 是否需要改公共功能接口 |
|---|---|---|---|
| Forward 路径 | 新增 `ForwardPath : RenderPath`；复用 `Features::DrawScene`（`DrawSceneFlags::Forward`）与阴影/IBL/后处理功能 | 否 | 否（这正是 B2 拆分的收益） |
| Deferred 路径 | 由现有 `DeferredRenderer` 演化 | 否 | 否 |
| DXR PathTracing | 新增 `PathTracingPath : RenderPath`；**允许专用实现**（SBT/加速结构）；复用 Scene/RHI/帧资源环/后处理 LDR 输出约定 | 需要（加速结构、DXR PSO） | 否（走例外条款） |
| Neural / 3D Gaussian Splatting | **独立 Demo + 独立路径**；初期只依赖 L1 + 只读 L3；**不进公共渲染功能**、不与光栅路径共享后处理 | 需要（可选 compute 管线） | 否 |

**接入新路径的固定步骤（写成文档给未来自己）**：①实现 `RenderPath` 子类并只做「RT 装配 + pass 顺序 + barrier + 提交」；②在应用层 `ActivatePath` 处注册/切换；③补一条路径级验收测试（构建 + 该路径下画面与 `GetFinalLDR()` 非空 + 调试层零 warning）。

## 4.6 明确不做 / 暂缓的事（防止过度设计）

| 项 | 结论 | 理由 | 触发条件（何时重新评估） |
|---|---|---|---|
| 多后端 RHI（Vulkan/Metal） | **不做** | WE 的 `wiGraphicsDevice` 服务于跨平台发行；本项目是 DX12 学习项目，抽象会淹没学习目标，且与「禁止用抽象隐藏同步关系」冲突 | 出现明确跨平台需求时 |

## 4.7 可机检的边界规则（给工作包验收用）

把边界变成**可执行的检查命令**，避免「写了规则但没人守」：

`@bash
