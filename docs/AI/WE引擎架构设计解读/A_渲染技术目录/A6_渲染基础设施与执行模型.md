## §1 本卷在管线中的位置

```
                    ┌──────────────────────── CPU 每帧 ────────────────────────┐
                    │ BeginCommandList(QUEUE_GRAPHICS / QUEUE_COMPUTE)          │
                    │        │                                                  │
                    │        ├─ AllocateGPU(帧线性分配器)  ── 每帧临时实例/CB     │
                    │        ├─ RenderPassBegin(LoadOp/StoreOp) ── 通道边界       │
                    │        ├─ BindPipelineState(PSO key 含 renderpass_hash)    │
                    │        ├─ BindResource / GetDescriptorIndex(bindless 堆)   │
                    │        ├─ PushBarrier(...) → FlushBarriers(批量提交)       │
                    │        ├─ DrawIndexedInstanced / Dispatch / *Indirect      │
                    │        └─ QueryBegin/QueryEnd(遮挡剔除、GPU 计时)          │
                    │ SubmitCommandLists()  →  ID3D12CommandQueue               │
                    └────────────────────────────┬────────────────────────────┘
                                                 ▼
      GPU：QUEUE_GRAPHICS ── WaitCommandList ─→ QUEUE_COMPUTE（异步：蒙皮/粒子/海洋/湿痕）
           GPU：AliasingAllocator 别名堆 → rtPostprocess / rtPrimitiveID / rtSceneCopy 共用同一块显存
```

A1–A5 的每个 pass 都嵌入在这张图的 `BindPipelineState … Draw` 区间里；`RenderPassBegin` 之外的状态转换、`Aliasing` 切换、`PushBarrier` 批处理**必须由调用方手写** —— 这正是 WE 反复踩坑、也是本项目最需要先立规矩的地方。

## §3 逐项详解

### A6-01 队列类型与命令列表生命周期 —— **必需**
- **功能**：定义四条队列 `QUEUE_GRAPHICS/QUEUE_COMPUTE/QUEUE_COPY/QUEUE_VIDEO_DECODE`（`wiGraphicsDevice.h:59-68` [实测]）。命令列表由 `BeginCommandList(queue)` 获得（`:122`），注释明确「**非线程安全，一条命令列表同一时间只能一个线程录制**」（`:207-212` [实测]）。
- **结构**：CPU 录制 → `Close()` → `SubmitCommandLists`（`wiGraphicsDevice_DX12.cpp:5388` [实测]）。命令列表**不是立即执行**，要等提交。
- **取舍**：本项目只做单后端，可以砍掉 VIDEO_DECODE；但**必须保留 COMPUTE 队列**，否则 A6-23 的异步并行做不了，粒子/蒙皮只能挤在图形队列里。

### A6-02 队列间等待 —— **必需**
- **功能**：`WaitCommandList(cmd, wait_for)`（`wiGraphicsDevice.h:215` [实测]，注释说明粒度「至少是列表开始等待另一列表结束」）。WE 的所有跨队列依赖都靠它，不用全设备 fence。
- **结构**：`wiRenderPath3D.cpp:883-889` [实测] 先 `BeginCommandList(QUEUE_COMPUTE)`，再 `WaitCommandList(async, graphics)`，随后异步录制 `UpdateRenderDataAsync`（`wiRenderer.cpp:5434` [实测]）。
- **取舍**：本项目 WP4 帧资源环必须提供同名 API。**不要**用 `WaitForGPU()`（`wiGraphicsDevice.h:128`）代替 —— 那是全同步，会掩盖生命周期 bug 且直接杀掉并行，`05_迁移顺序与工作包.md:143` 已明确否决该替代方案。

### A6-03 提交模型 —— **必需**
- **功能**：一帧内所有录制好的命令列表在 `SubmitCommandLists()` 里统一 Close + Execute（`wiGraphicsDevice_DX12.cpp:5388-5408` [实测]）。
- **结构**：`cmd_count` 计数归零 → 逐条 Close → 按队列 Execute → 帧末 fence signal。
- **取舍**：教学项目最容易写错成「每个 pass 一次 ExecuteCommandLists」，那会让 GPU 频繁空转；必须照抄「**一帧一提交**」这个粒度。

### A6-04 帧资源环 —— **必需**
- **功能**：`BUFFERCOUNT = 2`（`wiGraphicsDevice.h:72` [实测]），`:145 GetBufferCount()` 对外暴露。帧资源（上传缓冲、回读缓冲、查询结果）按帧索引轮转。
- **结构**：`wiScene.h:149` [实测] 的 `textureStreamingFeedbackBuffer_readback[GetBufferCount()]` 就是典型用法 —— 每帧一份回读缓冲，避免 CPU 读正在被 GPU 写的内存。
- **取舍**：本项目 WP4 必须先把「帧索引 + 完成值」立起来，A6-25 的流送回读才有地方落。

### A6-05 RenderPass 抽象 —— **必需**
- **功能**：`RenderPassImage` 声明 `type`（RENDERTARGET/DEPTH_STENCIL/RESOLVE/RESOLVE_DEPTH/SHADING_RATE_SOURCE）、`loadop`（LOAD/CLEAR/DONTCARE）、`storeop`（`wiGraphics.h:960-985` [实测]）+ `layout_before/layout/layout_after` 三态（`:983-985` [实测]）。
- **结构**：DX12 后端把这些映射成 `D3D12_RENDER_PASS_BEGINNING_ACCESS_TYPE_PRESERVE/CLEAR/DISCARD`（`wiGraphicsDevice_DX12.cpp:6126-6131` [实测]），并自动生成 barrier —— 即 **pass 内的状态转换不用调用方写**。
- **取舍**：这是 WE「两边责任划分」的关键：pass **内**自动、pass **外**手动（见 A6-07）。本项目若不做 RenderPass 抽象，就得每处手写 barrier，那是 A1–A5 所有 pass 的重复劳动。

### A6-06 PSO 缓存键含通道哈希 —— **必需**
- **功能**：`PipelineHash{ const PipelineState* pso; uint64_t renderpass_hash; }`（`wiGraphics.h:1330-1350` [实测]）；`get_hash()` 实为 `(pso_hasher.value ^ (renderpass_hash << 1)) >> 1`（`:1339-1349` [实测]）—— **注意 renderpass_hash 左移后被右移截掉了最高位**，即只有 63 位有效。
- **结构**：绑定时 `pipeline_hash.renderpass_hash = commandlist.renderpass_info.get_hash()`（`wiGraphicsDevice_DX12.cpp:6808` [实测]）—— 同一 PSO 在不同 RT 格式组合下会得到不同内部 PSO。
- **取舍**：**本项目 09 决策 D7 已对齐**。这是最容易被忽略的坑：D3D12 的 PSO 与 RT 格式绑定，不哈希就会「换了 G-Buffer 格式后画面错但无报错」。

### A6-07 屏障四态与批量提交 —— **必需**
- **功能**：`GPUBarrier` 有 MEMORY（UAV 依赖）/IMAGE（布局转换）/BUFFER（状态转换）/ALIASING（别名切换）四类（`wiGraphics.h:683-762` [实测]，四个工厂 `Memory/Image/Buffer/Aliasing`）。
- **结构**：`wiRenderer.cpp:91` [实测] `static thread_local wi::vector<GPUBarrier> barrier_stack` 累积；`:99-106 PushBarrier` 只对 **BUFFER 与 IMAGE 两类**做 `before==after` 去重（`:101-104`），MEMORY/ALIASING 直接入栈；最后由 `FlushBarriers(cmd)`（`:92-98`）一次 `device->Barrier(...)` 提交并清空。
- **取舍**：本项目应照抄「累积 + 去重 + 批量」三件套。**责任边界直接引用 `08_RB5_同步与资源生命周期.md:234-260` 的结论**：「pass 边界上的 RTV/DSV 布局归框架，资源作为 SRV/UAV/COPY 的角色与内存依赖归调用者」；框架只做 `before != after` 的机械转换，不做跨 pass 语义推导。教学项目在此基础上再加一条 WE 没有的：`assert(current_state == expected)`（WE 是「记不住就静默跳」，漏写在 Debug 层不报、只在 Release 花屏）。

### A6-08 内存别名 —— 可选
- **功能**：`AliasingAllocator`（`wiGraphicsDevice.h:449-498` [实测]）用 `Add(desc)` 计算偏移、`Add({多张 desc})` 把多张 RT 叠在同一偏移、`Commit()` 出一块带 `ALIASING_TEXTURE_RT_DS` 标志的堆。
- **结构**：`wiRenderPath3D.cpp:108-167` [实测] `offset_rtPostprocess = offset_rtPrimitiveID = offset_rtSceneCopy = aliasing_allocator.Add({...})`（`:164`） —— 后处理 RT、primitiveID、场景拷贝三张共用一块内存；切换时 `GPUBarrier::Aliasing(&rtPostprocess, &rtPrimitiveID)`（`:876` [实测]）。
- **取舍**：**`08_RB5_同步与资源生命周期.md:286` 已判定为「规模不匹配」**（依赖项里没有 heap 复用/别名调用方，引入即引入一整类难查 bug）。本卷同意该判定：**WP4 明确不做**；若将来显存实测超标再启，前提是先有 RenderPass（A6-05）把切换点唯一化。

### A6-09 帧线性分配器 —— **必需**
- **功能**：`GPULinearAllocator{buffer, offset, alignment, reset()}`（`wiGraphicsDevice.h:331-341` [实测]）+ `AllocateGPU(size, cmd)` 返回 `{data, buffer, offset}`（`:355` [实测]），注释 `:353-354` 写明「**只活一帧，之后自动失效**」。
- **结构**：空间不足时新开一块 UPLOAD buffer 并 `size = (old+need)*2`（`:360-374` [实测]），即几何增长。
- **取舍**：本项目实例/常量上传路径散落在 AssetSystem。应集中到「每帧一个线性分配器」，这是 WP4 最有性价比的一项：消灭 per-draw `memcpy + Map/Unmap`。

### A6-10 Bindless 描述符堆 —— 可选
- **功能**：`GetDescriptorIndex(resource, type, subresource)` 返回常量索引（`wiGraphicsDevice.h:109-110` [实测]）；堆本体 `DescriptorHeapGPU` 内嵌 **GPU 端 fence**（`wiGraphicsDevice_DX12.h:474-497` [实测]），用 `allocationOffset` 原子计数 + `SignalGPU` 让 GPU 与 CPU 的分配进度对齐。
- **结构**：资源创建时把 SRV 复制到 `descriptorheap_res.start_cpu` 下的 bindless 区（`wiGraphicsDevice_DX12.cpp:1277-1283` [实测]）。
- **取舍**：本项目 `Engine/04_Renderer/Renderer/Base/BaseRenderer.h:46-47` 已有 `extern DescriptorHeap s_TextureHeap / s_SamplerHeap` 全局泄漏（`02_架构现状审计_audit-tooiyume.md:567` 记录为「原则③：两个全局堆外露等于广播 RHI 实现」，`04_目标架构与模块边界.md:251` 已定为迁入 L4 `DescriptorAllocator`）。**要么彻底 bindless，要么彻底槽位绑定**，不要两套并存 —— WE 自己也是靠 `TEXTURE_SLOT_*` 宏 + `Texture2D textures[]` 统一入口（`shaders/ShaderInterop_Renderer.h:159-163` [实测]）。

### A6-11 空描述符兜底 —— **必需**
- **功能**：`nulldescriptorheap_cbv_srv_uav` / `nulldescriptorheap_sampler` + `nullCBV/nullSRV/nullUAV/nullSAM` 四个句柄（`wiGraphicsDevice_DX12.h:86-92` [实测]）。
- **结构**：未绑定的槽在根参数里填 null 句柄，而不是留垃圾。
- **取舍**：**这是 Debug Layer 最常见的 ERROR 来源**（本项目已多次踩）。WP2 的 PSO/RootSignature 工厂必须内置这组兜底。

### A6-12 根签名来自 DXIL —— **必需**
- **功能**：`CreateShader` 用 `D3D12CreateVersionedRootSignatureDeserializer` 从着色器字节码里读出根签名描述，强转 1.1 版本后 `CreateRootSignature`（`wiGraphicsDevice_DX12.cpp:3888-3920` [实测]）。
- **结构**：`rootsig_deserializer → rootsig_desc → rootSignature`，CS/LIB 还额外 init `rootsig_optimizer`（`:3921-3926` [实测]）。
- **取舍**：这是 `08_RB4` 的核心结论之一 —— **根签名只有一个真相源（HLSL 里的 `[RootSignature(...)]`），C++ 不能手写第二份**。本项目现状是**双真相**：`Engine/02_RHI/Pipeline/RootSignature.cpp:86-156` 手填 `D3D12_ROOT_SIGNATURE_DESC` 后 `SerializeRootSignature`（c++ 侧），而 `Engine/04_Renderer/Pipeline/PSOBuilder.cpp` 目前是 **0 行空壳**（`PSOBuilder.h` 亦为 0 行），即「新管线尚未成型」。施工时必须先定：**要么让 DXC 编译时内嵌根签名（WE 路线），要么把 `RootSignature` 当唯一真相并禁止 HLSL 写 `[RootSignature]`**；两者不可并存。

### A6-13 Push Constant —— **必需**
- **功能**：`PUSH_CONSTANT_COUNT = 22`（`wiGraphicsDevice.h:49` [实测]，注释原文 “The number indicates how many 32 bit values can be set for common shaders”，`:45-48`）个 32bit 常量直推，即 **88 字节总预算**（Vulkan 后端按 `sizeof(uint32_t) * PUSH_CONSTANT_COUNT` 开 push range，`wiGraphicsDevice_Vulkan.cpp:1501` [实测]）；HLSL 侧 `#define PUSHCONSTANT(name, type) ConstantBuffer<type> name : register(b999)`（`shaders/ShaderInterop.h:50` [实测]，Vulkan 分支则是 `[[vk::push_constant]]`，`:48`）。
- **结构**：调用方 `device->PushConstants(&postprocess, sizeof(postprocess), cmd)`（接口在 `wiGraphicsDevice.h:260`，注释已给出 `offset` 参数但 WE 渲染路径未用 [实测]）。
- **取舍**：22 个 DWORD 是**跨全部 push constant 的总预算**，单个 shader 只能有一个 `b999` 槽 —— `aerialPerspectiveCS.hlsl:7-11` 用 `#ifdef AERIALPERSPECTIVE_CAPTURE` **二选一**（`AerialPerspectiveCapturePushConstants` 或 `PostProcess`），不是叠加；全仓 20+ 个 shader 各用一个 push 结构，**实测最大者是 `SkinningPushConstants`（`ShaderInterop_Renderer.h:1726-1748`，20 DWORD = **80 字节**，`float3` 后必须补 1 个 DWORD 才能对齐到 4 的倍数），只剩 8 字节余量**；其次是 `PaintTexturePushConstants`（`:1698-1713`，12 DWORD = 48 字节）。**这就是 22 的来历：给蒙皮这条最大的结构留够并向上取整。**`PostProcess`（`shaders/ShaderInterop_Postprocess.h:9-15`：`uint2` 分辨率 + `float2` 倒数 + 2×`float4` = **48 字节 / 12 DWORD**）单独用时只占一半，**余量是给「同一 shader 叠加第二结构」留的**。本项目若只抄 `PostProcess` 会低估上限。

### A6-14 静态采样器 —— **必需**
- **功能**：`STATIC_SAMPLER_SLOT_BEGIN = 100`、`STATIC_SAMPLER_COUNT = 10`（`wiGraphicsDevice.h:56-57` [实测]）；着色器侧 `SamplerState sampler_linear_clamp : register(s100)` … `sampler_cmp_depth : register(s109)`（`shaders/globals.hlsli:345-354` [实测]）。
- **结构**：全部进根签名 static sampler 表，**运行时一次 BindSampler 都不需要**。
- **取舍**：本项目直接照抄这 10 个即可覆盖 99% 需求；`sampler_cmp_depth` 是阴影 PCF 专用，必须留。

### A6-15 帧常量与相机 CB —— **必需**
- **功能**：`UpdatePerFrameData(scene, visibility, frameCB, dt)`（`wiRenderer.cpp:4179` [实测]）每帧写一次全局 FrameCB；`BindCommonResources` 只绑 `buffers[BUFFERTYPE_FRAMECB]` 到 `CBSLOT_RENDERER_FRAME`（`:11210-11213` [实测]，HLSL 端 `CONSTANTBUFFER(g_xFrame, FrameCB, CBSLOT_RENDERER_FRAME)` 在 `shaders/ShaderInterop_Renderer.h:1610` [实测]）。
- **结构**：`BindCameraCB(camera, camera_previous, camera_reflection, cmd)`（`:11215` [实测]）写三个相机：当前帧（TAA 抖动用）、上帧（reprojection）、反射相机（平面反射）。大量派生量预计算（`z_near_rcp / z_range / far_mul_near_mul_2 …`，`:11241-11252` [实测]）。
- **取舍**：**派生量在 CPU 算、不在 GPU 算**是 WE 的明确风格。本项目若在 shader 里反复 `1/z`，是白烧 ALU。

### A6-16 批次结构 + 64 位排序键 —— **必需**
- **功能**：`RenderBatch` 16 字节对齐（`wiRenderer.cpp:207` [实测]），两种极性比较：不透明 `operator<` 位序 `distance:16 | lod:8 | meshIndex:16 | sort_bits:24`（`:243-265` [实测]），透明 `operator>` 位序 `lod:8 | meshIndex:16 | sort_bits:24 | distance:16`（`:274-296` [实测]）。断言 `sizeof(RenderBatch)==16`（`:302` [实测]）。
- **结构**：`RenderQueue` 只有 `add / sort_opaque / sort_transparent`，`thread_local` 两份（`:306-338`、`:337-338` [实测]）。
- **取舍**：`08_RB2` 决策 M9 建议**退化为显式 lambda 比较 + static_assert 保护**（位域上限 65536 网格会静默错序）。本项目教学优先，采 M9 的后半段。

### A6-17 视锥剔除与流式压缩 —— **必需**
- **功能**：`UpdateVisibility` 并行视锥剔除（`wiRenderer.cpp:3619-3631` [实测]，注释写明 shared memory 分组写回以减少原子与保持列表相干）。
- **结构**：`object_counter/light_counter` 原子追加 → 末尾 `visibleObjects.resize(counter)`（`:3991-3992` [实测]）。
- **取舍**：共享内存分组写回是「教学项目也值得抄」的少数多线程技巧 —— 它同时解决正确性（相干）与性能（原子少）。

### A6-18 遮挡剔除 —— 可选
- **功能**：上帧把每个对象 AABB 画成 14 顶点三角带立方体（`shaders/occludeeVS.hlsl:14-18` [实测]，`vertexID_create_cube(vID)*2-1` 直接生成，无 VB），用 `PSO_occlusionquery`（声明 `wiRenderer.cpp:679`、创建 `:1381`、绑定 `:5842` [实测]）在 `:5834 OcclusionCulling_Render` 里 QueryBegin/Draw(14,0)/QueryEnd。
- **结构**：`QueryResolve` 到回读缓冲（`:5952-5969` [实测]），下帧 CPU 读结果剔对象；query 数按场景上限动态扩容（`wiScene.cpp:224-229` [实测]）。
- **取舍**：收益取决于场景规模。本项目现阶段（教学场景）**不要做**；但 A6-21 的查询堆 API 必须存在，否则以后做不了。

### A6-19 间接绘制/派发与命令签名 —— **必需**
- **功能**：`DispatchIndirect(args, offset, cmd)`（`wiGraphicsDevice.h:245` [实测]）等一族；DX12 后端有 6 种命令签名，且分「不带 count buffer」（`wiGraphicsDevice_DX12.cpp:6898,6905,6936` [实测]）与「带 count buffer / 带 max_count」（`:6914,6923,6958` [实测]）两套。
- **结构**：参数缓冲必须是 `ResourceState::INDIRECT_ARGUMENT`（`wiRenderer.cpp:5395` [实测] 的 `SHADER_RESOURCE | INDIRECT_ARGUMENT` 组合就是典型）。
- **取舍**：**带 count buffer 的间接**是 GPU 驱动裁剪（impostor/meshlet/粒子）的必需品；本项目 WP5 分 PassType 后若要上 GPU 裁剪，必须先有这套签名。

### A6-20 GPU 排序 —— 可选
- **功能**：`radix_sortCS.hlsl` 有 6 个 permutation：`FPS_COUNT / FPS_COUNT_REDUCE / FPS_SCAN / FPS_SCAN_ADD / FPS_SCATTER / FPS_INDIRECT`（`offlineshadercompiler.cpp:129-135` [实测]）；`GPUSortLib::Sort`（`wiGPUSortLib.cpp:78` [实测]）。
- **结构**：5 段式并行基数排序（count → scan → scan-add → scatter，可迭代多趟），最后一趟用间接参数。**实测调用点 3 处**：粒子按距离排序 `wiEmittedParticle.cpp:786`、3DGS 按距离排序 `wiGaussianSplatModel.cpp:465`、自建 BVH 的 Morton 码排序 `wiGPUBVH.cpp:257` —— 三处都把排序结果直接写成 `InstanceCount`（`offsetof(IndirectDrawArgsInstanced, InstanceCount)`），即**排序与间接参数在同一次 dispatch 里完成**。
- **取舍**：本项目只有透明排序（CPU `std::sort` 足够）。**等粒子/GI 真需要再引**；但 `radix_sortCS` 的 6 permutation 命名方式是「一个 shader 多个 entry」的好范例（见 A6-12 的根签名复用）。

### A6-21 查询堆与 GPU 计时 —— **必需**
- **功能**：`GPUQueryHeapDesc{ GpuQueryType type; uint32_t query_count; }`（`wiGraphics.h:658-662` [实测]）；`QueryBegin/QueryEnd/QueryResolve`（`wiGraphicsDevice.h:252-254` [实测]）。
- **结构**：Resolve 目标必须是 CPU 可映射缓冲；`GPUQueryHeap` 本体在 `wiGraphics.h:1158` [实测]。
- **取舍**：**这是「画面只认 GPU 回读」验收规则的底层能力**（本项目 `AGENTS.md:20` 第 4 条：`-Screenshot <dir>` / `-ResizeTest`）。WP4 必须提供，否则验收第 4 条的人肉项无法自动化，pass 计时也做不了。

### A6-22 Profiler 双通道 —— 可选
- **功能**：`wi::profiler` 用同一套 `range_id` 同时管 CPU 计时（`wi::Timer`）与 GPU 时间戳（`gpuBegin/gpuEnd` 数组），20 帧滑窗平均（`wiProfiler.cpp:47-63` [实测]）。
- **结构**：`BeginFrame/EndFrame(cmd)`（`wiProfiler.h:25-28` [实测]）+ `BeginRangeCPU / BeginRangeGPU / ScopedRangeGPU`（`:31-51` [实测]）。
- **取舍**：`wiRenderer.cpp` 全文有 **64 处** `BeginRangeGPU/ScopedRangeGPU` [实测]。本项目应做「`ScopedRange` RAII + pass 名常量表」，而不是每处手写 Begin/End。

### A6-23 异步计算与并行录制 —— **必需**
- **功能**：`wiRenderPath3D.cpp:883-899` [实测] 注释直说「async compute parallel with depth prepass」：开 COMPUTE 列表、等待图形列表、在 job 里录 `UpdateRenderDataAsync`（`wiRenderer.cpp:5434`）。
- **结构**：并行内容是**蒙皮 / 粒子 GPGPU / 海洋 FFT / 湿痕**（`:881-899` 内 wetmap 分支）。用 `wi::jobsystem::Execute`（`wiJobSystem.h:58` [实测]）把录制铺到线程池。
- **取舍**：`08_RB2` 已指出 `RenderMeshes` 因 `thread_local` 批次**不可重入** —— 异步录制的每一步都必须独占自己的 command list。本项目若照搬，要先解决「批次缓冲的归属」。

### A6-24 VRS —— 可选
- **功能**：`shadingRateClassificationCS.hlsl` 64 线程/组，用 `groupshared tile_rate` 把瓦片内速度幅值聚合成一个着色率（`:14` 声明、`:38-45` 按 `magnitude > 0.1f` 判 4X4 [实测]）；C++ 侧 `ComputeShadingRateClassification`（`wiRenderer.cpp:11520-11544` [实测]）写 7 种 rate 的 D3D12 编码值。
- **结构**：调用点在 AO 之后、SSR 之前（`wiRenderPath3D.cpp:1093-1101` [实测]），且要求 `VARIABLE_RATE_SHADING_TIER2`（该能力位在 `wiGraphics.h:435` [实测]）。材质可覆写 `material.shadingRate`（`wiRenderer.cpp:3369` [实测]，字段定义 `wiScene_Components.h:210` [实测]）。
- **取舍**：教学场景无收益。**但注意**：WE 在每帧多处显式 `BindShadingRate(RATE_1X1)` 复位（`wiRenderer.cpp:6061,7197,7279` [实测]）—— 这类「状态泄漏复位」是 VRS 唯一的坑，记录下来即可。

### A6-25 纹理流送 —— **规模不匹配**
- **功能**：UAV 反馈缓冲记录被采样的 mip → 每帧 `CopyResource` 到回读缓冲（`wiRenderer.cpp:5646-5660` [实测]）→ CPU 映射读（`wiScene.h:150` [实测]）决定驻留。
- **结构**：`textureStreamingFeedbackBuffer_readback[GetBufferCount()]`（A6-04 的帧环）+ `COPY_SRC` 屏障。
- **取舍**：依赖资产系统整体支持 mip 按需加载，本项目资产层（WP3）尚未到这一步。**登记为后续候选，不进 WP1–WP8**。

### A6-26 延迟执行登记（MIP / BC 压缩）—— 可选
- **功能**：`AddDeferredMIPGen(texture, preserve_coverage)`（`wiRenderer.cpp:19360` [实测]）与 `AddDeferredBlockCompression(src, bc)`（`:19366` [实测]）只**登记**，帧内统一刷。着色器侧 `generateMIPChain2DCS_float4.hlsl:10-11` [实测]（`GENERATEMIPCHAIN_2D_BLOCK_SIZE` 组）。
- **结构**：登记队列 → 帧内取用 → 生成完成 → 才允许被采样；`GenerateMipChain` 本体在 `:10266` 起 [实测]。
- **取舍**：登记端只有 `deferredMIPGenLock.lock() → push_back → unlock()`（`wiRenderer.cpp:19360-19372` [实测]，BC 压缩共用同一把锁与同一帧首刷），执行端是 `GenerateMipChain`（`:10266` [实测]，全文另有 7 处直接调用，说明「登记」是**可选路径而非常态**）。**这是 09 §WP8 推荐的「登记-执行分离」原型**：本项目资产导入（WP3）可先做「只登记」，等帧资源环（WP4）到位再接执行。

### A6-27 稀疏资源与跨帧异步拷贝 —— **规模不匹配**
- **功能**：`SparseUpdate(queue, commands, count)`（`wiGraphicsDevice.h:196` [实测]）把稀疏页映射到 tile 池；`CopyBufferAsync(commands, count, name)`（`:200` [实测]）注释写明「**立即提交到独立 COPY 队列，可跨帧边界**，其余队列会同步到它完成」。
- **结构**：两者默认空实现（`{}`），只有支持的平台覆盖。
- **取舍**：本项目单机教学，不碰稀疏。**但 `CopyBufferAsync` 的「跨帧边界拷贝」语义值得记住** —— 它说明 WE 的 fence 模型允许非帧同步的拷贝。

### A6-28 半精度策略 —— 可选
- **功能**：`#define half min16float`（`shaders/globals.hlsli:10-16` [实测]）—— 把 half 统一映射到 min16float，保证 DX/Vulkan/Metal 一致。
- **结构**：`Surface` 里 baseColor/albedo/f0/roughness/occlusion/opacity 全是 half（`shaders/surfaceHF.hlsli:73-82` [实测]），位置/法线/视线是 float（`:69-71` [实测]）。
- **取舍**：本项目若在 HLSL 里直接写 `half`（DXC 下是 `float16_t`），移动端/其他后端会不一致。**照抄这 7 行宏**，代价为零。

## §4 数据流总图（一帧的 CPU 侧）

```
 frame N
   │
   ├─ device->BeginFrame()                       // 帧索引 + 完成值
   │
   ├─ cmd_graphics = BeginCommandList(QUEUE_GRAPHICS)          [A6-01]
   │     ├─ RenderPassBegin(images, count, occlusionQueries, cmd)  [A6-05]  // 自动 barrier（`:218` 重载）
   │     ├─ BindPipelineState(PSO)      key=(pso, renderpass_hash)[A6-06]
   │     ├─ BindConstantBuffer(g_xFrame) / PushConstants        [A6-15][A6-13]
   │     ├─ BindResource(slot) 或 bindless GetDescriptorIndex   [A6-10]
   │     ├─ alloc = AllocateGPU(size)  写实例/粒子               [A6-09]
   │     ├─ DrawIndexedInstanced / DrawXxxIndirect              [A6-19]
   │     ├─ QueryBegin/End(occlusion, timestamp)                [A6-18][A6-21]
   │     ├─ PushBarrier(Image 布局)  累积                       [A6-07]
   │     ├─ RenderPassEnd()  自动 store barrier                  [A6-05]
   │     └─ FlushBarriers(cmd)  一次提交所有非 pass 内屏障       [A6-07]
   │
   ├─ cmd_async = BeginCommandList(QUEUE_COMPUTE)               [A6-23]
   │     └─ WaitCommandList(async, graphics)                    [A6-02]
   │
   ├─ SubmitCommandLists()  Close + 按队列 Execute               [A6-03]
   │
   └─ （别名堆在这一帧内被 rtPostprocess→rtPrimitiveID 反复切换）[A6-08]
```

**时序约束（三条，都有实测支撑）**：
1. `RenderPassBegin` **内**的屏障由后端生成，`RenderPassEnd` **外**的必须调用方写（`wiGraphicsDevice_DX12.cpp:6108-6140` + `wiRenderPath3D.cpp:874-877`）。
2. `AllocateGPU` 的内存**只活一帧**（`wiGraphicsDevice.h:353-354` 注释原文 “It is only alive for one frame and automatically invalidated after that”，函数在 `:355`），跨帧引用必然野指针。
3. `WaitCommandList` 只保证「列表 A 开始等待列表 B 结束」，不保证中间点同步；录制顺序 ≠ 执行顺序（`wiGraphicsDevice.h:213-215`，注释原文 “The granularity of this is at least that the beginning of the command list will wait for the end of the other command list”；PS5 等平台可在插入点精确等待，DX12 不行）。

## §6 未确认项

1. **后处理链各步与队列边界的精确对应关系未逐行核对**。本卷只用到了 `wiRenderPath3D.cpp:882-889`（异步预通道，注释原文 “async compute parallel with depth prepass”）与 `:1093-1101`（VRS 调用点）两处；若要判定「哪几步必须同队列、哪几步可以并行」，需读后处理链全段并对照 `WaitCommandList` 的插入位置（链本身的顺序见 `A3_后处理链.md:290`【§4 后处理链的真实顺序】，本卷不重复）。**需读 `wiRenderPath3D.cpp` 后处理链全段**。
2. **Bindless 的真正使用范围未穷举**。本卷只读到 `GetDescriptorIndex`（`wiGraphicsDevice.h:109-110`）与堆分配路径（`wiGraphicsDevice_DX12.cpp:1277-1283`）；着色器端通过 `Texture2D textures[]` + `TEXTURE_SLOT_*` 宏（`shaders/ShaderInterop_Renderer.h:159-163`）访问，但 `BINDLESS_RESOURCE_CAPACITY` 的实际数值与其在根签名里的展开方式未读。**需读 `wiGraphicsDevice_DX12.h:1-120` 与 `wiGraphicsDevice_DX12.cpp:3926-3990`**。
3. **`GPUBarrier` 的 `before` 状态由谁维护未确认**。`PushBarrier` 只对 BUFFER/IMAGE 两类跳过 `before==after`（`wiRenderer.cpp:99-106`），说明调用方要自己记住当前状态；但 `Texture::desc.layout` 与后端内部状态是否始终一致，未逐路径核对。**需读 `wiGraphicsDevice_DX12.cpp` 中 `Barrier(...)` 实现与 `desc.layout` 的写入点**。
4. **`wiGPUSortLib` 的调用点已确认存在，但排序质量未验证**。调用点实测 3 处（`A6-20` 已列）：粒子距离排序（`wiEmittedParticle.cpp:786`）、3DGS 实例排序（`wiGaussianSplatModel.cpp:465`）、自建 BVH 的 Morton 排序（`wiGPUBVH.cpp:257`）[实测]。**但 `Sort` 内部对「已排序比例」的自适应趟数未读**，若要做「按帧预算可中断的排序」需读 `wiGPUSortLib.cpp:78-140`。
5. **VRS 的 7 种 rate 编码与服务端支持矩阵未读**。`ComputeShadingRateClassification` 里 `WriteShadingRateValue` 逐个写 **7 种** `RATE_1X1/1X2/2X1/2X2/2X4/4X2/4X4`（`wiRenderer.cpp:11544-11550` [实测]，随后 `:11551` 整结构体 `PushConstants`），与 `ShadingRateClassification` 结构体的 `SHADING_RATE_*` 字段一一对应（`A6-24`）。**未读**：`device->WriteShadingRateValue` 在各后端的取值映射（DX12 是 `D3D12_SHADING_RATE` 枚举加权），以及 Tier2 以下的降级行为。**需读 `wiGraphicsDevice_DX12.cpp` 中 `WriteShadingRateValue` 实现**。
