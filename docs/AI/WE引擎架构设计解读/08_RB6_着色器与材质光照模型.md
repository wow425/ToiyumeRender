## 摘要（先读这 10 条）

1. **材质模型是「半精度打包的 384B POD」**：`ShaderMaterial` 固定 384 字节，主体是 10 组 `uint2`（half2x2 打包）+ 15 个 16B 纹理槽 + 一块 `float4` 乘加。CPU 侧 `static_assert(sizeof(ShaderMaterial) == 384)` 在编译期钉死布局（`WE/shaders/ShaderInterop_Renderer.h:393`、`:513`） [实测]。
2. **材质不进 CB，进 StructuredBuffer**：材质以 bindless SRV 索引的 `StructuredBuffer<ShaderMaterial>` 供给所有着色器，着色器用 `load_material(index)` 拉取（`WE/shaders/globals.hlsli:589`）；每次 Draw 只推 16 字节 push constant（`ObjectPushConstants`，`WE/shaders/ShaderInterop_Renderer.h:835-844`） [实测]。
3. **光照只有一条公式链**：`Surface`（表面描述）→ `SurfaceToLight`（逐光几何项）→ `BRDF_GetDiffuse/GetSpecular`（D·Vis·F）→ `Lighting{direct,indirect}` 累加 → `ApplyLighting` 合成（`WE/shaders/lightingHF.hlsli:41-55`） [实测]。
4. **IBL 不是三项 LUT 拼接，而是「解析 DFG 近似 + 预过滤 cubemap」两项**：漫反射用 `GetAmbient`（最低 mip 采样，`lightingHF.hlsli:516-538`），镜面用 `EnvironmentReflection_Global`（`roughness × mipcount` 选 mip，乘 `surface.F`，`lightingHF.hlsli:543-570`）；`F` 本身来自 `EnvBRDFApprox` 解析近似（`surfaceHF.hlsli:21-29`），**没有独立的 BRDF LUT 纹理**（对比本项目现有 `brdfLUT`） [实测]。
5. **变体机制 = 编译期宏 + 多入口 + 文件名后缀缓存**：12 个 SHADERTYPE 各自对应一组 define（`WE/wiScene_Components.h:162-176`），对同一份 `objectPS.hlsl` 编译 12+12 次（不透明/透明）（`WE/wiRenderer.cpp:1238-1262`），二进制按 `_PLANARREFLECTION_TRANSPARENT.cso` 之类的后缀命名缓存（`WE/wiRenderer.cpp:800-811`） [实测]。
6. **一份公共代码被 4 类 pass 复用**：`objectHF.hlsli` 通过 `OBJECTSHADER_COMPILE_VS/PS` + `OBJECTSHADER_LAYOUT_*` + 特性宏三组开关，从同一个文件产出 VS/PS、prepass/shadow/common 布局（`WE/shaders/objectHF.hlsli:61-132`） [实测]。
7. **Surface 是「大而全结构 + 宏裁剪」**：PBR/透明/头发/皮肤共用同一个 `Surface`（`surfaceHF.hlsli:66-124`），sheen/clearcoat/aniso 是 `#ifdef` 附加子结构；无继承、无模板特化 [实测]。
8. **TiledLighting 剔除在 CS 里做，PS 里只做位图遍历**：CS 每 32x32 tile 建 frustum+AABB，输出「每实体 1 bit」的 8 桶位图（`WE/shaders/lightCullingCS.hlsl:410-418`）；PS 侧 `TiledLighting` 用 `firstbitlow` 逐位取灯（`shadingHF.hlsli:226-251`） [实测]。
9. **对本项目最该抄的两件事**：①「材质 POD + 编译期 static_assert 钉大小」的契约模式；②「Surface 中间层」——它把材质采样与光照解算彻底分开，正是本项目 `GBufferPS`/`LightingPS` 直接对读 GBuffer 所缺的那一层。
10. **最不该抄的两件事**：① 15 槽全量纹理（本项目只要 5 槽）；② TiledLighting（本项目单方向光 + 少量点光，直接前向遍历即可）。

#### 2.1.3 半精度打包的位级约定

CPU 侧：`WE/wiMath.h:594-604` `pack_half4` [实测]
```
inline XMUINT2 pack_half4(float x, float y, float z, float w)
{
    return XMUINT2(
        f32tof16(x) | (f32tof16(y) << 16u),   // .x = (x, y)
        f32tof16(z) | (f32tof16(w) << 16u)    // .y = (z, w)
    );
}
```
Shader 侧：`WE/shaders/globals.hlsli:155-163` `unpack_half4` [实测] —— 逐位对应，`value.x` 低位→`.x`，高位→`.y`，`value.y` 低位→`.z`，高位→`.w`。

**排布规律总结（可直接抄的结论）**：所有 `uint2` 材质字段都是「`(a,b)` 打进 `.x`，`(c,d)` 打进 `.y`」，即 **xy 一组、zw 一组**，而不是 xz/yw。原因见 `:594` 的移位写法 [实测]。这一点若不照抄会在解包时全错位。

**精度取舍的实际后果**：`baseColor` 用 half 存储意味着 albedo 在 [0,1] 内精度约 1e-3（half 相对精度 2^-11）[推断]；`texMulAdd` 显式保持 fp32（`:405` 声明为 `float4`），因为它是 UV 乘加，half 会在大 UV 下产生可见接缝 [推断]。

> **这套断言的完整逻辑（可直接照抄的范式）**：
> 1. **精确等值**用于「被当作数组元素 / 被 memcpy / 被 GPU 按固定 stride 读取」的结构——布局错一个字节就是整批数据错位。`ShaderMaterial` 正是这一类（`WE/wiScene_Components.cpp:444` 的 `std::memcpy(dest, &material, sizeof(ShaderMaterial))`）[实测]。
> 2. **上界**用于 CB，因为 D3D12 单 CBV 上限 64KB，超了要改结构而不是改断言。
> 3. **表驱动同步**（`SHADERTYPE_COUNT == arraysize(shaderTypeDefines)`）是最有价值的一条：新增一个材质类型时，若忘了加 define 表项，**编译期直接失败**，而不是运行期 shader 编译失败。本项目应引入同等机制（§7.2 建议 2）。
>
> **缺口**：`ShaderMaterial` 内部的位域语义（`options_stencilref` 的低 24/高 8 划分、`uvset_aniso_lodclamp` 的 bit0/1-7/16-31 划分）**完全没有断言保护**，只有注释与 getter [实测]（`ShaderInterop_Renderer.h:204-210` 只有 getter，无断言）。这是 WE 的真实弱点，见 §8 U3。

| 重载 | 位置 | 谁用 |
|---|---|---|
| `create(ShaderMaterial)` | `surfaceHF.hlsli:185-191` | 只从材质拿 SSS/shadow 开关，**不碰贴图** [实测] |
| `create(material, baseColor, surfaceMap, specularMap=1)` | `:193-248` | 主路径：算 f0/albedo/roughness/opacity |
| `create(material, color, surfacemap_simple)` | 由上重载的默认参数形式调用 | 简化光照（粒子/头发），见 `hairparticlePS.hlsl:42` [实测] |

**`create` 里的两条工作流分支**（`:221-241`）[实测]：
```
[branch]
if (material.IsUsingSpecularGlossinessWorkflow()) {
    roughness = material.GetRoughness() * saturate(1 - surfaceMap.a);
    f0 *= surfaceMap.rgb;
    albedo = baseColor.rgb;
} else {                            // Metallic-roughness（默认）
    if (material.IsOcclusionEnabled_Primary()) occlusion *= surfaceMap.r;
    roughness = surfaceMap.g;
    const half metalness  = surfaceMap.b;
    const half reflectance = surfaceMap.a;
    albedo = baseColor.rgb * (1 - max(reflectance, metalness));
    f0 *= lerp(reflectance.xxx, baseColor.rgb, metalness);
}
```
> **这是整个材质模型最核心的 5 行**（`:236-240`）：
> - `albedo = baseColor * (1 - max(reflectance, metalness))` —— 金属没有漫反射；
> - `f0 = f0_material * lerp(reflectance, baseColor, metalness)` —— 电介质 F0≈0.04（由 reflectance 给），金属 F0=baseColor。
> 本项目 `LightingPS.hlsl:101-102` 已有等价的 F0 逻辑（`F0 = 0.16*specular²; F0 = lerp(F0, baseColor, metallic)`）[实测]，但**缺少 `albedo *= (1-metalness)` 这一步**，导致金属同时有高光与漫反射，能量不守恒。这是 §7.2 建议 4 的直接依据。

#### 2.4.3 简化光照的「常量 surfacemap」

`WE/shaders/surfaceHF.hlsli:10` `static const half4 surfacemap_simple = half4(1, 1, 0, 0);` [实测]，注释 `:5-9` 说明含义：occlusion=1, roughness=1, metalness=0, reflectance=0。
在 `:682-685` 处当 `simple_lighting`（头发/粒子）时整体替换 `surfaceMap` [实测]。

> **可迁移点**：这是一个「用**常量数据**代替特化代码」的廉价技巧——不需要为粒子单独写一套 Surface 初始化，只要喂一个常量 surfaceMap。本项目粒子若走同一套光照，可直接用。

| 用法 | 位置 | 填充方式 |

**L1 契约层的核心技巧**（`WE/shaders/ShaderInterop.h:4-53`）[实测]：

```
#ifdef __cplusplus
  // C++ 侧：把 HLSL 类型映射到 DirectXMath，把 CBUFFER 宏变成 struct 声明
  using float4 = XMFLOAT4;
  #define CBUFFER(name, slot) static const int CB_GETBINDSLOT(name) = slot; struct alignas(16) name
  #define CONSTANTBUFFER(name, type, slot)
  #define PUSHCONSTANT(name, type)
#else
  // HLSL 侧：同样的宏变成 cbuffer/ConstantBuffer 声明
  #define alignas(x)
  #define CBUFFER(name, slot) cbuffer name : register(b##slot)
  #define CONSTANTBUFFER(name, type, slot) ConstantBuffer<type> name : register(b##slot)
  #define PUSHCONSTANT(name, type) ConstantBuffer<type> name : register(b999)
#endif
```

> **这是整个着色器体系里最值得抄的 30 行**。它让**同一份头文件既是 C++ 结构体定义、又是 HLSL cbuffer 声明**，从根本上消灭「C++ 改了字段忘了改 HLSL」这类 bug。具体机制：
> - `CBUFFER(name, slot)` 在 C++ 展开成「一个带名字的 struct + 一个记录槽位的常量」；在 HLSL 展开成 `cbuffer name : register(b<slot>)`。
> - `CONSTANTBUFFER(name, type, slot)` 在 C++ 展开成**空**（因为 struct 已由别处定义）；在 HLSL 展开成 `ConstantBuffer<type>`（即 `type` 可以单独定义、单独复用）。
> - `PUSHCONSTANT` 在 HLSL 走 `register(b999)`（`ShaderInterop.h:50`）[实测]，即**所有 push constant 都占同一个"伪槽"**，靠 D3D12 根签名的 32 位常量参数区分，而非靠 register。
> - `#define alignas(x)` 在 HLSL 侧定义为空（`:38`）[实测]——因为 HLSL 的 cbuffer 打包规则由编译器决定，写 alignas 无意义。

## §4 算法与公式

### 4.1 直接光：GGX / Smith / Schlick 的完整展开

#### 4.1.1 法线分布 D_GGX

`WE/shaders/brdf.hlsli:8-17` [实测]：

```
half D_GGX(half roughness, highp float NoH, const float3 h)
{
    half oneMinusNoHSquared = 1.0 - NoH * NoH;
    half a = NoH * roughness;
    half k = roughness / (oneMinusNoHSquared + a * a);
    half d = k * k * (1.0 / PI);
    return saturateMediump(d);
}
```

数学形式（注释标注来源 Walter et al. 2007，`:10`）：

$$D_{GGX}(N,H) = \frac{\alpha^2}{\pi\left((N\cdot H)^2(\alpha^2-1)+1\right)^2}$$

WE 的写法是**代数等价形式**：令 $k = \frac{\alpha}{(1-(N\cdot H)^2) + (N\cdot H)^2\alpha^2}$，则 $D = \frac{k^2}{\pi}$ [推断]（把 $k$ 平方展开即得标准式分母）。

> **注意传入的 `roughness` 已经是 $\alpha = \text{perceptualRoughness}^2$**：调用点 `brdf.hlsli:163` `half roughnessBRDF = sqr(clamp(surface.roughness, min_roughness, 1));` [实测]。若直接把 perceptual roughness 传进 `D_GGX` 会得到错误的高光宽度——**这是移植时最常见的错误**。

#### 4.1.2 可见性项 V_SmithGGXCorrelated（已含 1/(4 NoL NoV)）

`WE/shaders/brdf.hlsli:42-54` [实测]：

```
half V_SmithGGXCorrelated(half roughness, half NoV, half NoL)
{
    half a2 = roughness * roughness;
    half lambdaV = NoL * sqrt((NoV - a2 * NoV) * NoV + a2);
    half lambdaL = NoV * sqrt((NoL - a2 * NoL) * NoL + a2);
    half v = 0.5 / (lambdaV + lambdaL);
    return saturateMediump(v);
}
```

标准形式（Heitz 2014，注释 `:44`）：

$$V = \frac{0.5}{\Lambda_V + \Lambda_L},\quad \Lambda_V = N_oL\sqrt{(N_oV - \alpha^2 N_oV)N_oV + \alpha^2}$$

> **关键**：这个 $V$ **已经把分母 $4 N_oL N_oV$ 吃进去了**。证据是注释 `:50`「a2=0 => v = 1/(4*NoL*NoV) => min=1/4」[实测]。所以最终 specular 是 `D * Vis * F`（`brdf.hlsli:168`）[实测]，**不再除 $4N_oLN_oV$**。
>
> **对比本项目现状**：`BRDF.hlsl:175` 写的是 `float3 specularBRDF = (D * G * F) / max(4.0 * NdotV * NdotL, 0.0001);` [实测] —— 用的是**分离式 Schlick-GGX**（`BRDFHelp.hlsl:15-26`）[实测] 且显式除 $4N_oLN_oV$。两种写法在数学上都正确，但 WE 的 correlated Smith 在掠射角更准确，且省一次除法。本项目若要升级，只需把 `BRDFHelp.hlsl:20-26` 的 `GeometrySmith` 换成 correlated 形式并去掉 `/ (4 NdotV NdotL)`——**两者必须同时改**，否则会双重计入（见 §7.2 建议 7）。

#### 4.1.3 菲涅尔 F_Schlick（带 f90 修正）

`WE/shaders/surfaceHF.hlsli:13-18` [实测]：

```
half3 F_Schlick(const half3 f0, half VoH)
{
    half f90 = saturate(50.0 * dot(f0, 0.33));   // reflectance at grazing angle
    return f0 + (f90 - f0) * pow5(1.0 - VoH);
}
```

$$F = f_0 + (f_{90} - f_0)(1 - V_oH)^5,\quad f_{90} = \text{saturate}(50 \cdot \langle f_0, (0.33,0.33,0.33)\rangle)$$

> **这个 $f_{90}$ 修正很重要且常被漏掉**：标准 Schlick 用 $f_{90}=1$，WE 用 $f_{90}=\text{saturate}(50\cdot \text{mean}(f_0))$（`:16`）[实测]。物理意义：粗糙金属在掠射角的反射率达不到 1，用 $f_0$ 的均值缩放 $f_{90}$ 更接近测量值 [推断]。本项目 `BRDFHelp.hlsl:28-31` 用的是 $f_{90}=1$ 的标准式 [实测]——对本项目的教学定位来说标准式更易解释，可保留，但应在注释里说明差异。

#### 4.1.4 逐光几何项 SurfaceToLight

`WE/shaders/brdf.hlsli:90-151` [实测]。`create()` 里逐项：

| 量 | 公式 | 行号 |
|---|---|---|
| `L` | 传入的归一化光向量 | `:110` |
| `H` | $\text{normalize}(L + V)$ | `:111` |
| `NdotL` | $\langle L, N\rangle$（可加 `BRDF_NDOTL_BIAS`） | `:113-117` |
| `NdotL_sss` | $\text{saturate}\big((N_oL + sss_{rgb}) \cdot sss^{-1}_{rgb}\big)$ ← **次表面 wrap 光照** | `:119`、`:149` |
| `NdotH` | $\text{saturate}\langle N, H\rangle$ | `:121` |
| `LdotH` | $\text{saturate}\langle L, H\rangle$ | `:122` |

**Cartoon 特化**（`:134-146`）[实测]：把 `NdotL`/`NdotL_sss`/`NdotH` 全部过 `smoothstep(0.005, 0.05, x)` 做硬边，且 SSS 分两段（先单色 wrap、再染色）。**这是唯一一处用宏改写 BRDF 几何项而非只裁剪的地方**。

#### 4.1.5 最终 BRDF 组合

`WE/shaders/brdf.hlsli:156-188` [实测]：

```
half3 BRDF_GetSpecular(in Surface surface, in SurfaceToLight stl)
{
  // (1) 主瓣
  half roughnessBRDF = sqr(clamp(surface.roughness, min_roughness, 1));
  half D   = D_GGX(roughnessBRDF, stl.NdotH, stl.H);
  half Vis = V_SmithGGXCorrelated(roughnessBRDF, surface.NdotV, stl.NdotL);
  half3 specular = D * Vis * stl.F;

  // (2) SHEEN 叠加（布料的绒毛瓣）
  specular *= surface.sheen.albedoScaling;
  half Dc = D_Charlie(sheen_roughnessBRDF, stl.NdotH);
  half Vc = V_Neubelt(surface.NdotV, stl.NdotL);
  specular += Dc * Vc * surface.sheen.color;

  // (3) CLEARCOAT 叠加（车漆的清漆层）
  specular *= 1 - surface.clearcoat.F;                 // 主瓣被清漆遮挡
  specular += D_GGX(cc_rough, NdotH_cc, H) * V_Kelemen(stl.LdotH) * surface.clearcoat.F;

  return specular * stl.NdotL;                          // (4) 乘 N·L
}
```

**逐项对应公式**：

| 项 | 公式 | 定义位置 |
|---|---|---|
| Sheen D | $D_{Charlie} = \frac{(2+\frac{1}{\alpha})\sin^{(\alpha/2)}(N_oH)}{2\pi}$，$\sin^2 h = \max(1-N_oH^2, 2^{-7})$ | `brdf.hlsli:33-40` [实测] |
| Sheen V | $V_{Neubelt} = \frac{1}{4(N_oL + N_oV - N_oL \cdot N_oV)}$ | `brdf.hlsli:73-77` [实测] |
| Clearcoat V | $V_{Kelemen} = \frac{0.25}{(L_oH)^2}$ | `brdf.hlsli:67-71` [实测] |
| Clearcoat 能量 | 主瓣乘 $1-F_{cc}$ | `brdf.hlsli:179` [实测] |
| **最终乘 $N_oL$** | `return specular * stl.NdotL` | `brdf.hlsli:187` [实测] |

`BRDF_GetDiffuse`（`:189-204`）[实测]：

$$f_d = \big(1 - \text{lerp}(F, 0, \text{saturate}(sss_a))\big) \cdot [1-F_{cc}] \cdot \text{albedoScaling} \cdot N_oL_{sss}$$

> **逐行要点**：
> - `:193` `half3 diffuse = (1 - lerp(surface_to_light.F, 0, saturate(surface.sss.a)));` —— **SSS 会把菲涅尔淡出**，注释 `:191-192` 解释原因：「否则背面 wrap 处会有 artifact」[实测]。这是 SSS 与能量守恒的正确耦合方式，很多引擎漏掉。
> - `:203` 用的是 **`NdotL_sss` 而不是 `NdotL`** —— 即漫反射用 wrap 后的 N·L，镜面用原始 N·L。**两者不同是 SSS 效果的核心**。
> - 注意 `BRDF_GetDiffuse` 返回的**不含 `albedo` 也不含 $1/\pi$** —— albedo 在 `ApplyLighting` 乘（`lightingHF.hlsli:51`），$1/\pi$ 在 `lightingHF.hlsli:49` 除 [实测]。

#### 4.1.6 四类灯的差异

| 灯型 | 入口 | 衰减 | 位置 |
|---|---|---|---|
| Directional | `light_directional` | 无衰减；有 **CSM 级联选择 + 边缘混合** | `lightingHF.hlsli:58-148` [实测] |
| Point | `light_point` | `attenuation_pointlight` | `lightingHF.hlsli:160-267` [实测] |
| Spot | `light_spot` | point × 角度衰减 | `lightingHF.hlsli:277-366` [实测] |
| Rect | `light_rect` | **立体角（Frostbite 2014）** | `lightingHF.hlsli:368-511` [实测] |

**点光衰减**（`lightingHF.hlsli:150-159`）[实测]：

$$A(d) = \frac{\text{saturate}\left(1 - \left(\frac{d^2}{r^2}\right)^2\right)}{\max(d^2, 10^{-4})} = \frac{\text{saturate}\left(1 - \frac{d^4}{r^4}\right)}{d^2}$$

注释 `:152-155` 说明这是 glTF KHR_lights_punctual 推荐式，且**故意不用 `pow`**：`dist2 * range2_rcp` 再自乘即得 4 次方 [实测]。这是一个纯粹的 ALU 优化。

**聚光角度衰减**（`lightingHF.hlsli:269-276`）[实测]：

$$A_{spot} = A_{point} \cdot \text{saturate}\big(\text{mad}(s, \text{angleScale}, \text{angleOffset})\big)^2,\quad s = \langle L, \text{lightDir}\rangle$$

`angleScale`/`angleOffset` 由 CPU 预计算（编码在 `ShaderEntity.remap`，`ShaderInterop_Renderer.h:951-958` 的 `GetAngleScale/GetAngleOffset`）[实测]。**预计算使得 shader 里只有一次 mad + 一次平方**。

**面光立体角**（`lightingHF.hlsli:413-419`）[实测]：注释明确引用 Frostbite 2014 "Moving Frostbite to PBR"，用矩形四角构造 4 个方向再求立体角。这是 4 种灯里唯一**没有解析式**、必须几何近似的。

**面光的球形代表点**（`lightingHF.hlsli:246-253`、`:347-357`）[实测]：

```
float3 centerToRay = mad(dot(Lunnormalized, surface.R), surface.R, -Lunnormalized);
Lunnormalized = mad(centerToRay, saturate(light.GetRadius() / length(centerToRay)), Lunnormalized);
if (light.GetRadius() > 0) light_color /= max(1, sphere_volume(light.GetRadius()));  // 能量守恒
```

即把光源球投影到反射射线上取最近点，再按球体积做能量守恒（`:252`）[实测]。**这是「面光源高光」的标准做法**（Karis 2013）。

### 4.2 IBL：三项合成的真相

**RB6 任务书假设「IBL 三项（irradiance / prefiltered specular / BRDF LUT）」，但 WE 实测只有两项半**：

| 项 | WE 的做法 | 位置 |
|---|---|---|

#### 4.2.1 漫反射：GetAmbient

`WE/shaders/lightingHF.hlsli:516-538` [实测]：

```
inline half3 GetAmbient(in float3 N)
{
    half3 ambient;
    [branch]
    if (GetScene().globalprobe >= 0) {
        TextureCube<half4> cubemap = bindless_cubemaps_half4[descriptor_index(GetScene().globalprobe)];
        uint2 dim; uint mipcount;
        cubemap.GetDimensions(0, dim.x, dim.y, mipcount);
        ambient = cubemap.SampleLevel(sampler_linear_clamp, N, mipcount);   // ← 最后一 mip
    }
#ifndef NO_FLAT_AMBIENT
    ambient += GetAmbientColor();     // ← 加一个常量环境色兜底
#endif
    return ambient;
}
```

$$L_{diffuse}^{IBL} = \text{cubemap.SampleLevel}(N,\ \text{mip}_{max}) + C_{ambient}$$

> **这是「穷人的 irradiance」**：cubemap 的最高 mip 在预过滤过程中已经近似成半球平均，直接当 irradiance 用。优点是零额外纹理、零额外卷积 pass；缺点是**低频精度差**（mip 链是盒式降采样，不是余弦加权卷积）[推断]。
>
> **注释 `:531-533` 承认了这一点**：「This is not entirely correct if we have probes, because it shouldn't be added twice. However, it is not correct if we leave it out from probes, because if we render a scene with dark sky but ambient, we still want some visible result.」[实测] —— 即 **WE 自己知道这里不物理正确，是工程折衷**。本项目当前有专门的 `irradianceConvolutionCS.hlsl` [实测]（`Engine/Shader/06_Environment/irradianceConvolutionCS.hlsl`），**比 WE 更正确**，不应倒退回去抄 WE 的做法。

#### 4.2.2 镜面：EnvironmentReflection_Global

`WE/shaders/lightingHF.hlsli:543-570` [实测]：

```
inline half3 EnvironmentReflection_Global(in Surface surface)
{
    if (GetScene().globalprobe < 0) return 0;
    TextureCube<half4> cubemap = bindless_cubemaps_half4[descriptor_index(GetScene().globalprobe)];
    const half mipcount16f = half(f16tof32(GetScene().globalprobe_mipcount16f));
    half MIP = surface.roughness * mipcount16f;
    half3 envColor = cubemap.SampleLevel(sampler_linear_clamp, surface.R, MIP).rgb * surface.F;
    // SHEEN / CLEARCOAT 各再采一次（见下）
    return envColor;
}
```

$$L_{spec}^{IBL} = \text{cubemap.SampleLevel}(R,\ \text{roughness}\cdot \text{mipCount}) \cdot F$$

**关键点**：
1. **`R` 在 `Surface::update()` 里算好**：`surfaceHF.hlsli:273` `R = -reflect(V, N);` [实测]（注意是 `-reflect`）。
2. **`F` 是 `EnvBRDFApprox` 的结果**（`surfaceHF.hlsli:270` `F = EnvBRDFApprox(f0, roughness, NdotV);`）[实测]，**不是** `F_Schlick(f0, NdotV)`。只有 CARTOON 分支才用 `F_Schlick`（`:268`）[实测]。
3. **`mipcount16f` 用 half 存储**（`ShaderScene.globalprobe_mipcount16f`，`ShaderInterop_Renderer.h:19`），CPU 侧 `wiScene.cpp:958` `f32tof16(float(mip_levels))` [实测]——**省 2 字节，且强制 shader 侧用 half 计算 mip**。

**Sheen / Clearcoat 各再采一次**（`:557-567`）[实测]：sheen 用自己粗糙度采一次乘 `sheen.DFG`；clearcoat 用自己反射向量 `clearcoat.R` 采一次乘 `clearcoat.F`，且主瓣先乘 $(1-clearcoat.F)$。

#### 4.2.3 BRDF LUT 的替代：EnvBRDFApprox

`WE/shaders/surfaceHF.hlsli:21-29` [实测]：

```
// https://www.unrealengine.com/en-US/blog/physically-based-shading-on-mobile
half3 EnvBRDFApprox(half3 SpecularColor, half Roughness, half NoV)
{
    const half4 c0 = { -1, -0.0275, -0.572, 0.022 };
    const half4 c1 = {  1,  0.0425, 1.04, -0.04 };
    half4 r = Roughness * c0 + c1;
    half a004 = min(r.x * r.x, exp2(-9.28 * NoV)) * r.x + r.y;
    half2 AB = half2(-1.04, 1.04) * a004 + r.zw;
    return SpecularColor * AB.x + AB.y;
}
```

这是 Unreal 的移动端 DFG 拟合，返回 **$F_0 \cdot A + B$** —— 即已经乘过 F0 的完整结果，所以 IBL 里直接 `* surface.F` 即可（`:555`）[实测]，不需要再乘一次 $(F_0 A+B)$。

> **与 LUT 方案的对比**：
>
> | 方案 | 存储 | 精度 | 本项目适用性 |
> |---|---|---|---|
> | BRDF LUT 纹理（本项目当前） | 1 张 2D 纹理 + 1 次采样 | 高（卷积无拟合误差） | 已有 `BRDFLUTCS.hlsl`，**保留** |
> | EnvBRDFApprox（WE） | 0 存储，约 10 ALU | 中（拟合误差约 2%） | 可选，但**没有必要换** |
>
> [推断] 结论：**本项目已有 LUT 不应改回解析近似**。理由见 §6 判定 J5。

#### 4.2.4 局部反射探针（parallax-corrected OBB）

`WE/shaders/lightingHF.hlsli:578-620` `EnvironmentReflection_Local` [实测]：

```

half3 SecondPlaneIntersect = (-1 - clipSpacePos) / RayLS;
half3 FurthestPlane = max(FirstPlaneIntersect, SecondPlaneIntersect);

这是标准的 **box-projected cubemap**：把反射射线与 OBB 求交，用交点重定向采样方向；`edgeBlend` 在靠近盒面时淡出（`:617`）[实测]。

即**按"剩余可见度"做前向 over 合成**，循环终止条件 `envmapAccumulation.a < 0.99`（`:79`）[实测]。注释 `:97-98` 提示「探针按上到下排序，但混合按下到上」[实测]。

最后若 $\alpha < 0.99$ 用全局探针填补（`:110-113`）[实测]：

### 4.3 能量守恒与最终输出（ApplyLighting）

`WE/shaders/lightingHF.hlsli:41-55` [实测] —— **这是全块最重要的 15 行**：

```
inline void ApplyLighting(in Surface surface, in Lighting lighting, inout half4 color)
{
    if (GetFrame().options & OPTION_BIT_FORCE_UNLIT) { color.rgb = surface.albedo; return; }

    half3 diffuse  = lighting.direct.diffuse / PI
                   + lighting.indirect.diffuse * GetGIBoost() * (1 - surface.F) * surface.occlusion
                   + surface.ssgi;

    half3 specular = lighting.direct.specular
                   + lighting.indirect.specular * surface.occlusion;

    color.rgb  = lerp(surface.albedo * diffuse, surface.refraction.rgb * (1 - surface.F), surface.refraction.a);
    color.rgb += specular;
    color.rgb += surface.emissiveColor;
    color.rgb  = saturateMediump(color.rgb);
}
```

**逐项公式**：

$$L_{out} = \underbrace{\text{lerp}\Big(A \cdot \big[\tfrac{L^{dir}_{diff}}{\pi} + L^{ind}_{diff}\cdot g_{boost}(1-F_{N_oV})\cdot AO + L_{ssgi}\big],\ R_{refr}(1-F),\ a_{refr}\Big)}_{\text{漫反射/折射混合}} + \underbrace{\big(L^{dir}_{spec} + L^{ind}_{spec}\cdot AO\big)}_{\text{镜面}} + E$$

各项位置的精确对应：

| 项 | 表达式 | 行号 | 为什么 |
|---|---|---|---|
| 直接漫反射除 $\pi$ | `lighting.direct.diffuse / PI` | `:49` | BRDF 返回的是 $f_d \cdot N_oL$，缺 $1/\pi$ 归一化 |
| 间接漫反射不除 $\pi$ | `lighting.indirect.diffuse * ...` | `:49` | irradiance 已经是「半球积分后的辐射度」，本身含 $\pi$ 归一 |
| 间接漫反射乘 $(1-F)$ | `* (1 - surface.F)` | `:49` | 能量守恒：镜面反射掉的能量不再参与漫反射（**kD 项**） |
| 间接漫反射乘 AO | `* surface.occlusion` | `:49` | 环境光遮蔽只作用于间接光 |
| GI boost | `* GetGIBoost()` | `:49` | 美术可调的环境光强度（`ShaderInterop_Renderer.h:1280` 打包成 half） [实测] |
| 直接镜面 **不乘 AO** | `lighting.direct.specular` | `:50` | AO 是环境遮蔽，不应遮蔽直接光 |
| 间接镜面乘 AO | `* surface.occlusion` | `:50` | 同上 |
| **无法对整体间接镜面乘 F** | 注释 | `:50` | 注释原文「multiple layers have separate fresnels (sheen, clearcoat)」[实测] |
| 折射混合 | `lerp(albedo*diffuse, refraction.rgb*(1-F), refraction.a)` | `:51` | $\alpha$ 控制不透明↔折射插值 |
| 发光 | `+= surface.emissiveColor` | `:53` | 发光不参与能量守恒（额外能源） |
| 上界 | `saturateMediump` = `clamp(x, 0, 65504)` | `:54` | half 上界，见 `globals.hlsli:800,831` [实测] |

> **能量守恒的完整论证**（这是回答「光照怎么算」的核心）：
>
> 1. **单条光线上**：$f_{spec} + f_{diff}$ 通过 $k_D = 1-F$ 保证不超 1 ——
>    - $f_{diff}$ 里含 $(1-F)$（`brdf.hlsli:193`）[实测]；
>    - $f_{spec}$ 含 $F$（`brdf.hlsli:125`）[实测]；
>    - 二者相加不大于 1（在 $F\in[0,1]$ 且 albedo 不大于 1 时）[推断]。
> 2. **直接光 vs 间接光**：直接光在 BRDF 里已含 $(1-F)$，间接光在 `ApplyLighting:49` 再乘一次 $(1-F)$ —— **两者在 shader 的不同层各自乘，不是漏了也不是乘了两次**。判据：`lighting.direct.diffuse` 由 `BRDF_GetDiffuse`（含 $1-\text{lerp}(F,0,sss)$）产生，`lighting.indirect.diffuse` 是裸 irradiance（无 F），所以在 `:49` 补乘。
> 3. **Sheen/Clearcoat 的额外守恒**：sheen 用 `albedoScaling = 1 - max3(sheen.color)*DFG`（`surfaceHF.hlsli:278`）[实测] 削减主瓣；clearcoat 用 `specular *= 1 - clearcoat.F`（`brdf.hlsli:179`）与 `diffuse *= 1 - clearcoat.F`（`brdf.hlsli:200`）[实测]。
> 4. **SSS 的守恒**：$f_d$ 里的 $F$ 被 `lerp(F, 0, sss.a)` 淡出（`brdf.hlsli:193`），因为 wrap 光照会照到背面，此时菲涅尔无意义 [实测]。

### 4.4 为什么 direct.diffuse 要除 PI 而 indirect 不用（易错点专题）

这是本块**最容易移植错的一处**，单独成节。

- `BRDF_GetDiffuse` 返回 $f_d = (1-F)\cdot N_oL$，**量纲是「无」**。
- 物理上漫反射 BRDF 是 $\frac{\rho}{\pi}$，所以积分 $\int f_d\, d\omega = \rho$ 需要 $1/\pi$。
- 直接光：$L_o = f_r \cdot E_\perp \cdot N_oL$。BRDF 里的 $1/\pi$ 必须在 $f_r$ 里 → WE 把它提到 `ApplyLighting` 统一除（`:49`），因为**所有直接光项都需要它**，逐个除反而费 ALU。
- 间接光：irradiance map 存的是 $\int L_i \cos\theta\, d\omega$，已经积分过；再乘 $\rho/\pi$ 才是出射辐射度。但 WE 的 `GetAmbient` 返回的是 **cubemap 采样值 × 某种预过滤**，注释 `:531-533` 承认「不完全正确」[实测]。**因此 WE 的 indirect 不打 PI 是「因为预过滤阶段已经除过/隐含了」而不是「物理上不需要」** [推断]。

> **本项目的正确做法**：`irradianceConvolutionCS.hlsl` 若严格实现了 $\frac{1}{\pi}\int L\cos\theta\,d\omega$，则 `indirectDiffuse = irradiance * albedo` 就够（不再乘 albedo/π）；若只做了 $\int L\cos\theta\,d\omega$ 未除 π，则要乘 $\rho/\pi$。**必须先确认自己的卷积 shader 归一到哪一步**——这是 §8 未确认项 U5。

## §5 资源与同步

### 5.1 材质数据的三段式生命周期

这是本块对 WP4（帧资源环）最直接的一条输入：**材质数据不是 CB，而是"CPU 映射上传缓冲 → 拷贝 → GPU 只读 SRV"的三段式**。

| 阶段 | 资源 | 位置 | 说明 |
|---|---|---|---|
| ① CPU 写 | `materialUploadBuffer[frame]` | `WE/wiScene.cpp:188-195` | `Usage::UPLOAD`，`mapped_data` 直接 memcpy；`materialArrayMapped` 就是它的指针（`:195`） [实测] |
| ② 逐材质填 | `materialArrayMapped + jobIndex` | `WE/wiScene.cpp:4352` | job 并行填（`RunMaterialUpdateSystem`，`:4298-4300`） [实测] |
| ③ 拷贝 | `materialUploadBuffer → materialBuffer` | `WE/wiScene.cpp:1093-1099` | `GPUBufferCopyCommand`，size = `materialArraySize * sizeof(ShaderMaterial)` [实测] |
| ④ 绑定 | `shaderscene.materialbuffer = GetDescriptorIndex(&materialBuffer[frame], SRV)` | `WE/wiScene.cpp:938` | 非 UMA 用独立 Default buffer；UMA 直接用 upload buffer（`:932`） [实测] |

**双缓冲**：`materialUploadBuffer[GraphicsDevice::GetBufferCount()]`（`WE/wiScene.h:144`），`GetBufferCount()` = `BUFFERCOUNT = 2`（`WE/wiGraphicsDevice.h:72,145`）[实测]。索引来自 `device->GetBufferIndex()`（`WE/wiScene.cpp:37`）[实测]。

> **三个对本项目有价值的结论**：
> 1. **材质用 StructuredBuffer 而不是 CB** 的根本理由是**规模**：WE 单场景可达数千材质，CB 只有 64KB（约 170 个 ShaderMaterial）。本项目模型材质数在几十到几百量级，**用 CB 数组或 StructuredBuffer 都可行**，但 StructuredBuffer 更省根签名槽（一个 SRV 覆盖全部材质）。
> 2. **双缓冲是必需的**：CPU 在第 N 帧写 upload buffer 时，GPU 可能还在读第 N-1 帧的 default buffer。本项目 WP4 的帧资源环必须覆盖材质缓冲，否则会出现「改材质参数后一帧花屏」[推断]。
> 3. **增长策略是 `×2` 预留**（`WE/wiScene.cpp:171` `desc.size = desc.stride * materialArraySize * 2; // *2 to grow fast`）[实测]——避免每加一个材质就重建 buffer。本项目可直接照抄这个 2 倍策略。

### 5.2 纹理走 bindless，不走 per-draw 描述符表

| 事实 | 位置 | 说明 |
|---|---|---|
| 15 类 bindless 资源句柄以「类静态常量」形式声明 | `WE/shaders/globals.hlsli:373-410`（SM6.6 路径）、`:481-512`（space 路径） | 每种类型一个数组 [实测] |
| 每种类型占一个独立的 `space` | `WE/shaders/globals.hlsli:481-512` | 例如 `bindless_textures_half4 : register(space24)`（`:506`） [实测] |
| `descriptor_index(x)` = `max(0, x)` | `globals.hlsli:26` | **索引 0 恒为 null 描述符**，注释 `:22-25` 说明理由：「shader compiler sometimes incorrectly loads descriptor outside of safety branch」[实测] |
| 采样器容量 256（8 位可索引） | `WE/wiGraphicsDevice.h:45` `BINDLESS_SAMPLER_CAPACITY = 256` | push constant 里 `samplerIndex` 只给 8 位（`ShaderInterop_Renderer.h:838`）[实测] |
| 材质采样器优先从 push constant 取 | `objectHF.hlsli:59` `#define sampler_objectshader bindless_samplers[descriptor_index(push.samplerIndex)]` | 注释 `:58` 说明：比从 material 结构里取更快 [实测] |

> **`descriptor_index(x) = max(0, x)` 是一个「防御性 null」模式**：所有 -1（无效）索引自动指向 0 号 null 描述符，从而让 `if (IsValid())` 分支即使被编译器错误地"穿透"也不会越界。这是 WE 在真实驱动 bug 上踩出来的补丁 [推断]（注释只说 "sometimes incorrectly"）。
>
> **对本项目的含义**：本项目若引入 bindless（WP2 的 DescriptorAllocator），**必须保留 0 号槽为 null 描述符**，否则 -1 索引会读到随机资源。这是一条低成本高收益的约定。

## §6 可迁移性判定（逐项，三选一 + 理由 + 替代方案）

判定口径：**必需** = 不做就无法实现 PBR 材质与光照；**可选** = 有更好但非阻塞；**规模不匹配** = 在 1-3 万行/单 D3D12/教学定位下收益为负。

### J1 384B 半精度打包的 ShaderMaterial

**判定：可选（建议采纳「打包思想」但换尺寸与字段集）**

- **理由**：半精度打包把 10 组参数压到 80 字节，对**每像素都要读一次材质**的前向渲染是真实的带宽收益。但 384B 中 240B 是 15 个纹理槽（`ShaderInterop_Renderer.h:128-368`）[实测]，本项目只要 5 槽 → 实际需要约 80+80 = 160B。
- **不采纳的部分**：① 15 槽（用不到）；② `userdata`/`layerMask`/`sampler_descriptor`（本项目无自定义 shader/分层/材质级采样器）；③ **stencil ref 与选项位挤一个 uint**（`wiScene_Components.cpp:395`）[实测]——这会让每个新增选项都要动 stencil 语义。
- **替代方案**：见 §7.1 的 `MaterialData` 草案（约 160B，5 槽，选项位独立 uint）。
- **规模适配性**：适配。半精度打包的**实现成本**只是一对 `pack/unpack` 函数（约 30 行，可直接抄 `wiMath.h:594-628` 与 `globals.hlsli:118-163` [实测]），收益是材质带宽减半。教学价值也高——学生能直观看到「精度是有价格的」。

### J2 bindless 纹理槽（15 槽 → 任意数量纹理走 heap 索引）

**判定：规模不匹配（本项目用固定 5 槽描述符表）**

- **理由**：bindless 的收益在「材质数 × 纹理数」很大时才显现。WE 的收益点：① 一个 SRV 数组覆盖全场景纹理，draw 之间不换描述符表；② 材质数组里只存 int 索引（`ShaderInterop_Renderer.h:205` `texture_descriptor`）[实测]。
- **本项目的实际规模**：5 槽/材质（`ConstantBuffers.h:34-42`）+ 每 draw 一次描述符表绑定。当前架构（`Common.hlsli:14-16` 的 `DescriptorTable(SRV(t0, numDescriptors=10))` 两段 [实测]）已经能覆盖。
- **引入 bindless 的真实代价**（本项目承担不起）：
  - 需要 SM 6.6 的 `ResourceDescriptorHeap` 或 space-based bindless（`globals.hlsli:481-512` 用 space1..space30）[实测]，对本项目 D3D12 教学代码是显著复杂度；
  - 需要 null 描述符兜底约定（`globals.hlsli:22-26`）[实测]；
  - 需要 CB 里携带 count 做越界保护（`surfaceHF.hlsli:345`）[实测]；
  - Debug Layer 对 bindless 越界的报错极其晦涩 [推断]。
- **替代方案**：**保留固定 5 槽 + 每 draw 绑描述符表**。若要减少绑定次数，把 5 个 SRV 打进一张 DescriptorTable（本项目已是如此，`Common.hlsli:14`）[实测]，用 `t0..t4` 连续寄存器（`GBufferPS.hlsl:3-7`）[实测]。这是「5 槽的 bindless 等价物」，成本几乎为零。
- **规模适配性**：不匹配。1-3 万行教学项目引入 bindless 会把「材质采样」这一件简单事变成「索引安全 + 描述符生命周期 + 平台分支」三件难事。

### J3 interop 头模式（同一份 .h 被 C++ 与 HLSL 同时 include）

**判定：必需（这是本块价值最高的一项，且实现成本极低）**

- **理由**：本项目当前存在**真实的双份定义**：
  - `ConstantBuffers.h:48-77` `MaterialConstants`（C++） [实测]
  - `GBufferPS.hlsl:15-25` `cbuffer MaterialConstants`（HLSL） [实测]
  - `ConstantBuffers.h:96-102` `GlobalConstants`（C++） [实测]
  - `GBufferPS.hlsl:30-36` `cbuffer GlobalConstants`（HLSL） [实测]
  - 而 `DefaultPS.hlsl:25-29` 的 `GlobalConstants` 只有 `ViewProj + ViewerPos`，**与 `GBufferPS.hlsl` 的 4 字段版本不一致** [实测]！
- **这条不一致是实测证据**：同一个项目里两个 PS 对同一个 b1 槽声明了**不同布局**的 `GlobalConstants`。若两者用同一个 CBV 绑定，必有一个读错。这说明「双份定义」已经在制造 bug。
- **替代方案**：引入一个 `Engine/Shader/ShaderInterop.h`，把 `CBUFFER/CONSTANTBUFFER/PUSHCONSTANT` 三个宏按 WE 的方式定义（`ShaderInterop.h:4-53`）[实测]，然后让 `ConstantBuffers.h` 用它声明结构。**改动量约 60 行，收益是消灭整类错位 bug。**
- **注意**：WE 的做法有一个前置依赖——C++ 侧的 `float4/float3/uint2` 需要映射到 `XMFLOAT4/XMFLOAT3/XMUINT2`（`ShaderInterop.h:13-24`）[实测]。本项目用 `Math::Vector4`/`Math::Matrix4`（`ConstantBuffers.h:99-101`），需要写对应的 `using` 别名，或改用 DirectXMath 基础类型。
- **规模适配性**：**高度适配**。这是「小改动、结构性收益」的典型。

### J4 公共 hlsli 复用（globals / surfaceHF / brdf / lightingHF 分层）

**判定：必需（但只抄 brdf.hlsli + surfaceHF 的 create/update，约 350 行）**

- **理由**：本项目的 BRDF 代码当前有**三份**：
  - `BRDFHelp.hlsl:1-35`（`DistributionGGX/GeometrySmith/FresnelSchlick/FresnelSchlickRoughness`） [实测]
  - `DeferredCommon.hlsli:56-129`（`DistributionGGX/GeometrySmith/FresnelSchlick/EvaluateCookTorranceLight`） [实测]
  - `BRDF.hlsl:170-206`（直接调前两者的函数再算 IBL） [实测] 三份的 `DistributionGGX` 实现细节不同：`BRDFHelp.hlsl:12` 有 `max(..., 0.0000001)`，`DeferredCommon.hlsli:74` 有 `max(denom, 0.0001)` —— **两个不同的 epsilon** [实测]。这必然导致两处画面亮度不一致。
- **抄什么**：
  - `brdf.hlsli` 全部 206 行（D_GGX / V_SmithGGXCorrelated / F_Schlick / SurfaceToLight / BRDF_GetSpecular / BRDF_GetDiffuse）；
  - `surfaceHF.hlsli` 的 `Surface` 结构 + `init/create/update`（`:66-311`，约 150 行有效代码，跳过 700 行的 `load_internal`）。
- **不抄什么**：`shadingHF.hlsli`（653 行；实测构成：`TiledLighting` 函数体 `:51-406` 共 **356 行**、`TiledDecals` `:408-534` 共 **127 行**，两者占 74%；其余是 `LightMapping`/`PlanarReflection`/`ApplyFog`/`ApplyAerialPerspective`/`AlphaToCoverage`/`InteriorMapping`）[实测]，本项目不需要这部分（见 J6）。`objectHF.hlsli` 的 1152 行也不需要——它绑定的是 WE 的 meshlet/provoking index/LOD 体系。
- **替代方案**：新建 `Engine/Shader/Shared/Brdf.hlsli` + `Surface.hlsli`，两者都 include 一个 `ShaderInterop.h`。Deferred 与 Forward 两条路径共用这两份。这正好落在 **WP5（DrawScene 提取）** 的范围内。
- **规模适配性**：**高度适配**。350 行换取「两条路径光照一致 + 消除三份重复」。

### J5 BRDF LUT vs EnvBRDFApprox 解析近似

**判定：规模不匹配（保留现有 LUT，不换成 WE 的解析近似）**

- **理由**：本项目**已经有**完整的 LUT 生成链：
  - `BRDFLUTCS.hlsl:15-40` 的 `IntegrateBRDF`（Hammersley + ImportanceSampleGGX + GeometrySmith_IBL）[实测]
  - `EnvironmentLightingManager.h:40-47` `EnvironmentMapTextures` 含 `BRDFLUTTexture` [实测]
  - `LightingPS.hlsl:155` `BRDFLUT.Sample(...)` [实测]
- **换成 EnvBRDFApprox 的收益**：省一张纹理 + 一次采样；**代价**：引入约 2% 的拟合误差，且**丢掉一个教学上极有价值的资产**（LUT 积分是 PBR 课程的核心内容）。
- **替代方案**：**保留 LUT**。若担心启动耗时，把 LUT 预烘焙成资源文件（`EnvironmentLightingManager` 已有烘焙路径）。
- **规模适配性**：不匹配。WE 用解析近似是因为它要跑移动端/主机，纹理预算紧张；本项目是教学，**LUT 的可解释性 > 2% 的性能**。

### J6 TiledLighting 的具体剔除逻辑

**判定：规模不匹配（本项目用直接前向遍历）**

- **理由**：WE 的 tiled 剔除由三部分组成，每部分都有显著成本：

  **(a) CS 侧（`lightCullingCS.hlsl:194-443`，250 行）** [实测]：
  - 每 32×32 tile 一个 8×8 线程组（`:194`，`TILED_CULLING_THREADSIZE=8` 出自 `ShaderInterop_Renderer.h:1224`） [实测]
  - 每线程读 16 个深度像素做 min/max（`:231-238`）
  - 建 4 个视锥平面（`:289-297`）
  - 建 tile AABB（视空间 + 世界空间）（`:301-314`）
  - 可选 32 层深度切片掩码（`ADVANCED` 变体，`:320-345`）
  - 每实体一次 sphere-frustum + 一次 AABB 测试（`:353-406`）
  - 写 8 个 uint 桶到全局（`:414-418`）

  **(b) PS 侧（`shadingHF.hlsli:211-341`，130 行 × 4 类灯）** [实测]：
  - 每类灯一次 bucket 循环
  - **wave 标量化**：`bucket_bits = WaveReadLaneFirst(WaveActiveBitOr(bucket_bits))`（`:223` 等 5 处）[实测]，注释 `:74-75` 引用 "Improved Culling, Siggraph 2017 [Michal Drobot]"
  - `firstbitlow` 逐位取（`:230`）
  - 每灯一次 `load_entity` + 阴影采样 + BRDF

  **(c) CPU 侧（`wiRenderer.cpp:10158-10228`）** [实测]：buffer 分配、barrier×2、dispatch、空场景快速路径。

- **总成本量化**：tile buffer 大小 = `tileCount.x × tileCount.y × 4B × 8桶 × 2(opaque/transparent) × cameraCount`（`wiRenderer.cpp:10165-10166`）[实测]。1080p 下 tileCount = 60×34（`GetEntityCullingTileCount`，`wiRenderer.h:46-52`）→ 60×34×4×8×2 ≈ **130KB/相机** [推断]。
- **本项目的实际需求**：单方向光（`GlobalConstants.SunDirection/SunIntensity`，`ConstantBuffers.h:100-101`）+ `NUM_DIR_LIGHTS 3` 上限（`BRDF.hlsl:2`）+ 1 个点光（`LightingPS.hlsl:122-139` 只有 1 个点光字段）。**3 个灯做 tiled 剔除是纯负收益**。 [实测]
- **替代方案**：在 PS 里直接 for 循环 3 个方向光 + 1 个点光（本项目 `LightingPS.hlsl:162-188` 已经是这样）[实测]。**若将来要上几十个灯**，先做「光列表 + 每物体灯索引」的 CPU 侧剔除（成本约 50 行），再考虑 tiled。
- **规模适配性**：不匹配。tiled 剔除的代码量（250+130 = 380 行）超过本项目整个光照模块的预算。

### J7 Surface 中间层（表面描述结构）

**判定：必需（这是本块第二重要的可迁移项）**

- **理由**：本项目当前的材质解算分散在三个地方，且**互相不一致**：
  - `GBufferPS.hlsl` 写 GBuffer（采样 5 张贴图，打包 baseColor+AO / oct-normal / metallic+roughness+specular / emission）
  - `LightingPS.hlsl:101-102` 从 GBuffer 读回并**重算 F0**：`F0 = 0.16*specular²; F0 = lerp(F0, baseColor, metallic)` [实测]
  - `DeferredCommon.hlsli:109-110` 在 `EvaluateCookTorranceLight` 里**又算一次 F0**：`F0 = float3(0.04); F0 = lerp(F0, baseColor, metallic)` [实测] **同一个像素的 F0 被算了两次，且公式不同**（一个是 $0.16s^2$ 起手，一个是常数 0.04 起手）。这就是缺少 Surface 层的直接后果。
- **替代方案**：引入 `Surface` 结构（只保留本项目需要的字段，约 18 个），提供两个构造入口：
  - `Surface::FromMaterial(materialCB, uv, ...)` —— 前向路径用
  - `Surface::FromGBuffer(gb0, gb1, gb2, gb3, ...)` —— 延迟路径用
  两者保证产出**同一个结构**，后续 `ApplyLighting` 只认结构、不认来源。
- **规模适配性**：**高度适配**。约 120 行，直接消除「F0 算两次」这类跨 pass 不一致。

### J8 变体机制（宏 + 多入口 + 文件名后缀缓存）

**判定：可选（采纳「宏组合」思想，拒绝「12×2 编译」规模）**

- **理由**：
  - WE 的变体数 = 12 种类型 × 2（不透明/透明）= 24 个 PS，再乘 renderpass/alphatest/blend/cull/tessellation/mesh_shader 等 PSO 维度（`wiRenderer.cpp:352-359`）[实测]。
  - 本项目当前变体机制是 `PipelineDesc{VertexFlags, MaterialFlags, PassType}`（`PipelineDesc.h:37-48`）[实测] + `SortKey.psoIdx : 12`（`BaseRenderer.h:124`）[实测]，即**最多 4096 个 PSO**，实际组合由 `MaterialFlags`（`Material.h:14-20`：AlphaBlend/AlphaTest/DoubleSided/None）[实测] 决定。
- **抄什么**：
  - **「变体 = 正交宏的组合」**：例如 `SHEEN + CLEARCOAT` 是两个独立宏（`wiScene_Components.h:170`）[实测]，不需要 4 个枚举。本项目若将来加 clearcoat，只需加一个 `CLEARCOAT` 宏，而不是加 2 个枚举值。
  - **「枚举 ↔ define 表 + static_assert 同步」**：`static_assert(SHADERTYPE_COUNT == arraysize(shaderTypeDefines))`（`wiScene_Components.h:176`）[实测]。
- **不抄什么**：
  - 12 种材质类型（本项目只需 PBR / Unlit / Transparent 三种）；
  - 文件名后缀缓存（本项目 shader 编译走离线 .cso，不需要运行时拼名）。
- **替代方案**：本项目定义 3 个 shader 类型（`PBR / UNLIT / TRANSPARENT`）+ 3 个正交特性宏（`ALPHATEST / DOUBLE_SIDED / NORMALMAP`），共 3×2³ = 24 个组合，但**只编译实际用到的**（用 `PipelineDesc` 做惰性编译，本项目 `PipelineStateCache` 已经是这个模式 [推断]）。
- **规模适配性**：部分适配。思想可抄，规模需砍到 1/4。

### J9 objectHF.hlsli 的「一份代码多 pass」组织

**判定：规模不匹配（本项目用"一个 pass 一个文件 + 共享 hlsli"）**

- **理由**：WE 的 `objectHF.hlsli`（1152 行）通过 `OBJECTSHADER_COMPILE_VS/PS` + `OBJECTSHADER_LAYOUT_{SHADOW,SHADOW_TEX,PREPASS,PREPASS_TEX,COMMON}` + 13 个 `OBJECTSHADER_USE_*` 特性宏（`objectHF.hlsli:61-87`）[实测]，从**同一个文件**产出：
  - VS（`objectVS_common.hlsl:1-3` 只有 3 行） [实测]
  - PS 的 4 种布局 × 12 种材质 × 2 种透明性
  - HS/DS/MS 变体（`objectHS_*.hlsl`、`objectDS_*.hlsl`、`objectMS_*.hlsl`）
- **这个设计的代价**：1152 行里有 **约 250 行是 `#ifdef/#endif`**（实测：`grep -c "^\\s*#if|#else|#endif|#elif"` 得 252 条，252/1152 = 21.9%）[实测]。新人读这个文件基本无法线性理解。
- **替代方案**：**「一个 pass 一个文件 + 共享 hlsli」**，即：
  - `Shared/Surface.hlsli` + `Shared/Brdf.hlsli` + `ShaderInterop.h`（J3/J4/J7）
  - `Deferred/GBufferPS.hlsl`（写 GBuffer）
  - `Deferred/LightingPS.hlsl`（读 GBuffer + 调 Brdf.hlsli）
  - `Forward/ForwardPS.hlsl`（采样 + 调 Surface + Brdf）——**新增，WP7**
  - `Shadow/ShadowPS.hlsl`
  文件数从 WE 的 1 个巨型 hlsli + 40 个薄壳，变成 4 个独立 PS + 3 个共享 hlsli。**重复代码靠 hlsli 消除，不靠宏消除。**
- **规模适配性**：不匹配。WE 需要「一份代码 40 个变体」是因为它有 305 个 pass；本项目 4-6 个 pass 用宏生成反而更难维护。

### J10 后处理 PostProcess 万能 CB（params0/params1 + 宏重命名）

**判定：可选（建议采纳，但补 CPU 侧镜像 + static_assert）**

- **理由**：56 个后处理 shader 共用 32B 的 `PostProcess`（`ShaderInterop_Postprocess.h:9-15`）[实测]，根签名只需一个 push constant 范围。本项目后处理（TAA/ACES/bloom）参数各不相同，但总参数少。
- **收益**：根签名从 N 个 CBV 降为 1 个 32 位常量块；shader 侧零额外绑定代码。
- **风险**：宏名与字段的对应关系**不可机检**（`ssao_range` → `params0.x`，改字段顺序全崩，编译器不报错）[实测]（实测 `sed -n '22,76p' ShaderInterop_Postprocess.h | grep -c '^#define'` = **33 条**宏） [实测]。
- **替代方案**：采纳 32B 结构，但**同时**在 C++ 侧定义一个同名 struct 并按效果写 setter 函数（`SetSSAO(range, power, count)`），用 `static_assert(sizeof(PostProcess) == 32)` 固定。这样"字段语义"由 setter 保证，不靠宏。
- **规模适配性**：适配。

### J11 FrameCB 内联实体数组（256 × ShaderEntity + 256 × matrix + 256 × Sphere）

**判定：规模不匹配**

- **理由**：占约 36KB（见 §2.2.2）[推断]，直接逼近 64KB 上限。本项目的灯数量在 1-4 个，矩阵数在百级（但矩阵可以按需 push，不需要内联）。
- **替代方案**：灯用「小 CBV（4 灯 × 64B = 256B）」；矩阵用 StructuredBuffer（若需要）。见 §7.3。
- **规模适配性**：不匹配。

### J12 变体→define 表驱动 + static_assert

**判定：必需（成本 5 行，收益是消灭一类静默错位）**

- **理由**：见 §2.3 的「表驱动同步」条。本项目 `MaterialFlags`（`Material.h:14-20`）与 `GBufferPS.hlsl` 的 `flags` 位域（`ConstantBuffers.h:55-76`）之间**当前没有任何一致性检查** [实测]。
- **替代方案**：定义 `static constexpr const char* kMaterialFlagDefines[] = {...}` + `static_assert(arraysize(...) == kMaterialFlagCount)`。
- **规模适配性**：高度适配。

#### 7.1.2 草案 A：最小改动版（推荐先做，落在 WP3）

**目标**：保持现有字段集不变，只修 P1/P2/P3/P4。改动量约 80 行。

`Engine/Shader/ShaderInterop.h`（新建，约 55 行）：
```
#pragma once
#ifdef __cplusplus
  #include "00_Core/Math/Matrix4.h"
  #include "00_Core/Math/Vector4.h"
  #include <cstdint>
  using float4   = Math::Vector4;
  using float4x4 = Math::Matrix4;
  using uint     = uint32_t;
  #define CBUFFER(name, slot)      struct alignas(16) name
  #define CBV_SLOT(name, slot)     static constexpr uint32_t kSlot_##name = slot
  #define PUSHCONSTANT(name, type)
#else
  #define CBUFFER(name, slot)      cbuffer name : register(b##slot)
  #define CBV_SLOT(name, slot)
  #define PUSHCONSTANT(name, type) ConstantBuffer<type> name : register(b999)
#endif
```

`Engine/Shader/Shared/MaterialCB.h`（新建，被 C++ 与 HLSL 同时 include，约 45 行）：
```
#pragma once
#include "../ShaderInterop.h"

// 与 GBufferPS/LightingPS/ForwardPS 的共同契约。改这里就同时改了 C++ 与 HLSL。
// 注意：本结构按 16B 对齐排布，避免 HLSL 的 float3 16B 规则歧义。
CBUFFER(MaterialConstants, 0)
{
    float4  baseColorFactor;      // offset   0  rgb=albedo, a=opacity
    float4  emissiveFactor;       // offset  16  rgb=emissive, a=strength
    float4  texMulAdd;            // offset  32  xy=UV mul, zw=UV add
    float   metallicFactor;       // offset  48
    float   roughnessFactor;      // offset  52
    float   normalTextureScale;   // offset  56  (unused in PS today, kept for VS/PS parity)
    float   reflectance;          // offset  60  取代硬编码 0.04；glTF 无此字段时填 0.04
    uint    flags;                // offset  64  kMatFlag_*（见下）
    float   alphaRef;             // offset  68  [0,1]，仅 ALPHATEST 有效
    uint2   _pad;                 // offset  72  补齐到 80
};

// 位定义必须与 C++ 侧 kMatFlag_* 同步；两边都在本文件，天然同源。
#define kMatFlag_AlphaBlend   (1u << 0)
#define kMatFlag_AlphaTest    (1u << 1)
#define kMatFlag_DoubleSided  (1u << 2)
#define kMatFlag_Unlit        (1u << 3)
```

C++ 侧（改 `ConstantBuffers.h`，删掉原有 `MaterialConstants` / `GlobalConstants` 定义，改为 include）：
```
// ConstantBuffers.h 改为：
#include "Engine/Shader/Shared/MaterialCB.h"

{

#### 7.1.3 草案 B：ShaderMaterial 风格（若 WP3 决定上 StructuredBuffer，则用此）

**只在做完草案 A 且确认「材质数 > 500」或「需要 bindless」时才建议启动。** 字段集合按 §2.1 的判定裁剪：

| # | 字段 | 类型 | 打包 | 语义 | 相对 WE 的裁剪理由 |
|---|---|---|---|---|---|
| 1 | `baseColor` | `uint2` | half4 | rgb=albedo(线性)，a=opacity | 保留 |
| 2 | `emissive_strength` | `uint2` | half4 | rgb=emissive，a=strength | 保留（WE 的 cloak 换成 strength） |
| 3 | `roughness_reflectance_metalness_unused` | `uint2` | half4 | x=roughness，y=reflectance，z=metalness，w=保留 | 保留（WE 的 refraction 砍掉） |
| 4 | `normalStrength_alphaRef_texMulAddXY` | `uint2` | half4 | x=法线强度，y=alphaRef，zw=UV mul | 合并 WE 的字段 2 与 9 的 xy |
| 5 | `texMulAddZW_pad` | `uint2` | half4 | zw=UV add | 拆出来避免 half 精度问题（UV add 常是 0.x，half 够用）[推断] |
| 6 | `flags_shaderType` | `uint` | 位域 | 低 16=shaderType，高 16=flags | 合并 WE 的 13+15 两个 uint（**刻意合并，但 flags 独立 16 位，不再与 stencil 挤**） |
| 7 | `textures[5]` | `TextureSlot[5]` | 每槽 8B | `descriptor(int) + uvset_flags(uint)` | 5 槽；**砍掉 SVT 的两个 sparse 描述符**（每槽省 8B） |

**总大小**：5×8 + 4×8 + 4 + 4 = **80 字节**（含对齐）→ 比 WE 的 384B 小 4.8 倍 [推断]。

> **必须保留的 WE 细节**（不保留会出错）：
> - **0 号描述符 = null**（`globals.hlsli:22-26`）[实测]；
> - **-1 表示无贴图**（`ShaderInterop_Renderer.h:216-219`）[实测]；
> - **`descriptor_index(x) = max(0, x)`** 的防御包装（`globals.hlsli:26`）[实测]。
>
> **必须砍掉的 WE 细节**（对本项目是负收益）：
> - stencil ref 与 flags 挤一个 uint（§2.1.1）；
> - `layerMask`（无分层需求）；
> - `sampler_descriptor`（采样器走 StaticSampler，见 `Common.hlsli:19-26`）[实测]；
> - `userdata`（无自定义 shader）。

### 7.5 后处理参数建议（落在 WP8）

采纳 WE 的「32B 万能 CB」（§2.2.5）但补 CPU setter：

```
// Shader/Shared/PostProcessCB.h
CBUFFER(PostProcessCB, 2)
{
    float2 resolution;      // offset 0
    float2 resolution_rcp;  // offset 8
    float4 params0;         // offset 16
    float4 params1;         // offset 32
};
```

C++ 侧禁止「直接写 params0.x」，必须通过命名 setter：

```
struct PostProcessParams {
    PostProcessCB cb{};
    void SetSSAO(float range, float power, float sampleCount) {
        cb.params0 = { range, sampleCount, power, 0 };
    }
    void SetBloom(float threshold, float exposure) {
        cb.params0 = { threshold, exposure, 0, 0 };
    }
};
```

> **这样做的价值**：保留 WE 的「一个 CB 槽跑所有后处理」的根签名优势，同时把「宏名→字段」的不可检关系搬到 C++ setter 里变成**可 grep 的代码**。WE 的做法在 `ShaderInterop_Postprocess.h:22-76` 有 **33 条** `#define` [实测]，一旦改字段顺序，引用这些宏的 shader 会静默出错；setter 方案下错误会在 setter 处集中暴露。

### U1 `SHADERTYPE_BIN_COUNT = 12` 与 `SHADERTYPE_COUNT = 12` 的同步是否只靠那一处 static_assert

- **影响**：若两者失配，`PSTYPE_OBJECT_PERMUTATION_BEGIN + shaderType` 的索引会越界到 `PSTYPE_OBJECT_TRANSPARENT_PERMUTATION_BEGIN` 区间，**选中错误的 shader 而不报错**。

### U5 本项目 `irradianceConvolutionCS.hlsl` 的归一化约定未确认

- **已确认**：`irradianceConvolutionCS.hlsl:29-41` 用 Hammersley + 余弦加权采样，最后 `irradiance /= sampleCount` [实测]，**没有乘 π 也没有除 π**。
- **未确认**：这个积分对应的是 $\int L\cos\theta\,d\omega$ 还是 $\frac{1}{\pi}\int L\cos\theta\,d\omega$。因为 Hammersley 采样是**均匀分布**（`:31-33` 的 `cosTheta = sqrt(1-Xi.y)` 是余弦加权分布的逆变换），所以 `irradiance /= sampleCount` 得到的是**余弦加权平均**，即 $\frac{1}{\pi}\int L\cos\theta\,d\omega$ [推断]。若此推断成立，则 `LightingPS.hlsl:151` 的 `diffuseIBL = irradiance * baseColor` **正确**（不需要再除 π）。
- **影响**：若推断错误，IBL 漫反射会偏亮或偏暗 π 倍（3.14×，肉眼明显）。
- **验证方式**：用一个已知均匀环境（全白 HDRI，radiance=1）渲染一个 albedo=1、metallic=0 的球。正确结果应为球面亮度 ≈ 1（余弦加权的半球积分归一化后）。若得到 π 或 1/π，则约定的方向相反。（本块未执行——需要构建运行，违反「禁止构建」铁律。）

### U6 WE 的 `Surface::load_internal` 是否在所有变体下都能正确越界保护

- **已确认**：`preload_internal`（`surfaceHF.hlsli:343-383`）有 4 处越界检查 [实测]。
- **未确认**：`load_internal`（`:384-1086`）内部对 `material.textures[...]` 的访问是否有额外保护。从代码看它依赖 `IsValid()`（`texture_descriptor >= 0`），而 `descriptor_index(max(0,x))` 会把 -1 变成 0 → 读 null 描述符。**这意味着「无贴图」时会采到 null 纹理而不是跳过**——除非上层有 `if (IsValid())` 包裹。
- **影响**：若某条路径漏了 `IsValid()`，会采到 null 描述符（返回 0 或未定义），表现为「黑色贴图」而非崩溃。
- **验证方式**：grep `load_internal` 里所有 `textures[` 访问，逐一确认外层有 `IsValid()`。（本块抽查了 `:586`/`:609`/`:660`/`:695`/`:895` 五处，均有包裹 [实测]；实测 384-1086 行区间内 `material.textures[` 出现 **70 次**、`.IsValid()` 出现 **15 次**、`.GetTexture()` 也是 **15 次** —— 数量不匹配说明**有约 55 次访问不经过 IsValid 检查**，但其中 18 次是 `.GetUVSet()`、1 次是 `.texture_descriptor`（这两类不需要 IsValid），剩余约 36 次是 Sample/SampleGrad/SampleLevel —— 需要确认这些是否都在外层 `if (IsValid())` 内。**本块未逐一核对，列为未确认** [实测]）
