## 3. 证据规则

### 3.1 结论必须可追溯

1. 每条技术结论附 `文件相对路径:行号`。函数/结构体签名原样引用。
2. 区分**实测**（读过该行）与**推断**（由命名/调用点推测）。推断必须标注「推断」，并写明确认它需要读哪个文件。
3. 禁止只罗列目录树或类名。约束文档明确：不得只复制 WE 的目录/类名/接口形式；每条借鉴必须说明**解决的问题、设计依据、替代方案、实际收益**。
4. 对 WE 的每个设计，必须给出 **必需 / 可选 / 规模不匹配** 三选一的适用性判断并说明理由（约束文档要求：WE 设计不适合当前规模或学习目标时必须明确说明）。

### 3.2 审计基线：HEAD，而非工作树

**这是本文件集的 P0 前提。** 审计开始时工作树存在未提交改动，其中若干源码文件被截断成残缺状态（例如 `DeferredRenderer.cpp` 638 行 → 30 行，`DeferredApp.cpp` 143 行 → 30 行），mtime 集中在 2026-10-24 17:22–17:25。**后续实测（2026-10-24 20:1x）确认这不是一次性中断残留，而是另一个并行开发会话在持续改写工作树**：`git status --porcelain` 从会话初 17 项增至 55 项，且其中 5 条旧 P0 结论已被并行会话修掉（`LightingPS.hlsl` 硬编码分辨率、`StaticMeshVS.hlsl` 切线还原、`RayTracingApp` 的 `RequiresRaytracingSupport`、`Utility.h` 的 `RELEASE` 宏、`Display.cpp` resize 链），另有 2 处路径迁移导致行号失效（`ModelConvert.cpp`、`ModelLoader.cpp` → `Engine/05_Scene/Model/`）。**因此必须区分两个基线：审计基线 = HEAD（本文件集全部结论的基准）；施工基线 = 收编后的工作树（阶段 0/WP0 的产物）。** 逐条复核见 `09_升级实施建议.md` 附录 A。

因此：

- **审计基线 = 最后一次一致提交 HEAD = `51c09d09917a507e33ff7e468e824e34963339c5`**（`1`，2026-10-16 19:38）。
- 涉及被改动文件的结论，以 `git show HEAD:<file>` 的内容为准；同时如实记录工作树当前状态与两者差异。
- 详细清单与影响分析见 `02_架构现状审计_audit-tooiyume.md` 的 P0 章节；工作树复核结果见 `09_升级实施建议.md` 附录 A。

### 3.3 重要事实：本地 WE 版本与约束文档的假定不一致

约束文档 §2.1 询问「WE 中 Forward / Deferred / Tiled Rendering 和 Path Tracing 的组织方式」。**本地 WE 版本并不存在 `RenderPath3D_Deferred` / `_Forward` / `_Tiled` 这三条 RenderPath 子类**，唯一的 3D 路径子类是 `RenderPath3D_PathTracing`。因此该问题的真实答案必须由读码得出，不能套用旧版 WE 的分文件印象。结论见 `01B_WE_公共渲染功能与后处理链.md`。

**6 条目标架构原则**（摘自约束文档，本文件集统一编号引用）：

1. 应用层与渲染路径分离
2. 渲染路径与公共渲染功能分离（但不强迫所有算法共用不合理接口，允许专用实现）
3. 场景/材质与底层 RHI 解耦，避免 D3D12 细节无约束泄漏
4. 后处理明确输入输出约定，区分 HDR / Tonemapping / LDR，按需 Ping-Pong
5. 资源生命周期与 GPU 执行同步（禁止用抽象隐藏同步关系）
6. 为未来管线保留扩展（Forward / Deferred / DXR PathTracing / Neural Rendering 如 3DGS；Neural 初期独立 Demo，不强耦合进 RHI）

| 渲染路径（RenderPath） | 一条完整渲染色序：确定用哪些 RT、按什么顺序、调用哪些公共渲染功能，产出最终图像。WE 对应 `wi::RenderPath3D`。 |
| 公共渲染功能 | 被多条渲染路径共享的、与具体路径编排无关的绘制能力（画场景、画天空、画阴影图、后处理单效果）。WE 对应 `wi::renderer` 命名空间。 |
| 场景与资产系统 | 场景数据（实体/组件/材质/相机/光照）与其来源（模型/纹理导入、解析、缓存）。 |
| RHI | 对 D3D12 的工程化封装：设备、命令、描述符、资源、屏障、同步。 |
| 后处理链 | 从 HDR 场景颜色到 LDR 呈现图像之间的一系列全屏处理步骤。 |

### 三条新增硬结论（均可回源）

1. **后处理链权威顺序**：tonemap 在 `wiRenderPath3D.cpp:2473`，是第 20 步，**唯一的 HDR→LDR 分界**；AO/SSR/SSGI 在第 8–10 步（TAA 之前），DoF/MotionBlur 在第 18–19 步（TAA 之后、tonemap 之前）。
2. **π 归一化的落点**（2026-10-24 机器复核后更正，以 `A_勘误与基线校正.md` 为准）：`PI` 定义于 `shaders/globals.hlsli:793`。**GGX/Charlie 的 `1/PI` 在 NDF 内部**（`brdf.hlsli:15` / `:30` / `:39`），那是法线分布自身的归一化，**与漫反射能量无关**；`brdf.hlsli:189 BRDF_GetDiffuse` **不含 `/PI`**（`:203` 直接 `return diffuse * surface_to_light.NdotL_sss;`）。**漫反射真正的 `/PI` 在光照累加处**：`lightingHF.hlsli:49` `half3 diffuse = lighting.direct.diffuse / PI + lighting.indirect.diffuse * ...`。→ 施工含义：抄 `BRDF_GetDiffuse` 时**不要自己再除 π**，否则漫反射暗 3.14 倍；反之删掉 `ApplyLighting` 的 `/PI` 而不在别处补回，则亮 3.14 倍。
3. **资产压缩的分层**：`AddDeferredBlockCompression`（`wiRenderer.cpp:19366`）与 `AddDeferredMIPGen`（`:19360`）在资产层只**登记**，渲染层帧首**执行** —— 这是本项目 WP3 修「模型贴图 100% 未压缩」时该照搬的唯一结构（而非其 GPU 队列）。
