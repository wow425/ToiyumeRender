### C2 发现的真实缺口

**缺口 G-C2-1：帧线性上传分配器（`AllocateGPU` / 动态常量缓冲）在 RB4 的 RHI 草案中缺失。**

- **RB2 侧需求**`[文档核对]`：`CameraCB` 用 `BindDynamicConstantBuffer`(`wiRenderer.cpp:11335`)，语义是「在帧环形上传区切一块、写进去、绑上去」（RB2 §5.1 记为「动态 = 环形分配」`[实测]`）；实例指针数组同样走 `AllocateGPU`(`wiRenderer.cpp:3170`)。
- **RB4 侧状态**`[实测]`：RB4 §7.1 的 21 方法清单为 `Init / CreateSwapChain / Present / CreateBuffer / CreateTexture / CreateShader / AllocateDescriptor×2 / CreatePipelineState / BeginCommandList / Submit / BindPipeline / BindConstantBuffer / BindDescriptorTable / PushConstants / DrawIndexed / DrawIndexedInstanced / Dispatch / CopyBuffer / Barrier / WaitForFence`（Lead 逐个数过 = 21，与 RB4 自检「3+3+2+1+2+4+4+2=21」一致）。**其中没有任何环形分配 API。**
- **但 RB4 §2.4-A 第 14 行明确说「只留 `AllocateGPU(size, cmd)`」** —— 即 RB4 的意图是保留它，只是**没有把它写进 21 方法清单**。这是 RB4 文档**内部的清单不一致**，不是概念分歧。

**Lead 的裁定（避免把 `AllocateGPU` 塞进 RHI 虚接口）**：

> **不在 RHI 加 `AllocateGPU`；改为在 `BufferDesc` 上补两个字段，把帧分配器放到 L4（RenderFeatures/Shared）实现。**
>
> 具体：
> 1. `BufferDesc` 必须能表达 **堆类型**（DEFAULT / UPLOAD / READBACK）与 **是否持久映射**；
> 2. `CreateBuffer` 成功后，`GpuBuffer` 提供一个**非虚** `void* GetMappedPtr()`；
> 3. L4 的 `FrameUploadAllocator` 在初始化时创建**一个** `UPLOAD` 大 buffer（如 8MB）并持久映射，每帧 `Reset()` 归零 offset，`Allocate(size, align)` 返回 `{offset, cpuPtr}`；
> 4. 绑定时调用 RHI 的 `BindConstantBuffer(cmd, slot, buffer, offset)` —— **21 个虚方法一个都不用加**。
>
> **理由**：帧线性分配是**策略**（多大块、何时重置、双缓冲几帧）而非**物理事实**（创建/绑定/绘制）。WE 把它放进 `GraphicsDevice` 是因为它要服务 4 条队列 + 多线程录制（RB4 §4.3 的**无锁**环形分配）；本项目单线程录制、双缓冲，一个朴素 bump allocator 就够（RB4 §6.3 已独立给出同样判断：「4096 槽 + 无锁都不需要」）。
>
> **代价**：L4 需要知道「一帧何时结束」（重置时机）——这本来就是 WP4 帧资源环的职责，不新增耦合。

### C2 结论

**通过（含一处需修正的清单）**。B1/B3/B4/B5/B7 直接覆盖；B8 覆盖但归属在 `CmdList` 非虚成员；**B2/B6 暴露 RB4 清单漏列 `AllocateGPU`** ——已由 Lead 裁定为「移出 RHI、下沉到 L4」，因此**不需要修改 21 方法数量**，但 **RB4 §7.1 的清单应补一句说明**（已在本文件记录，后续修订 RB4 时并入）。

## C3：RB5（延迟销毁判据） × RB1（路径切换时旧 RT 的释放时机）

**状态：✅ 通过（含一条对 RB5 的修正 + 一条对 01A 未确认项的闭合）。**

### 校验依据（Lead 全部亲自回源 [实测]）

**A. RB5 侧：判据与时间轴**
- 判据（10 个销毁队列统一）：`entry.tag + BUFFERCOUNT < FRAMECOUNT`，实现 `wiGraphicsDevice_DX12.h:582-636`；
- `tag` 来源：`~Resource_DX12()` 里 `uint64_t framecount = allocationhandler->framecount;` 然后 `destroyer_resources.push_back(std::make_pair(resource, framecount));`（`wiGraphicsDevice_DX12.cpp:1466-1474`）→ **tag = 析构那一刻的 `allocationhandler->framecount`**；
- `framecount` 的更新点：`AllocationHandler::Update()` 的**第一行** `framecount = FRAMECOUNT;` 然后才做 10 个 `while (front().second + BUFFERCOUNT < FRAMECOUNT)`（`wiGraphicsDevice_DX12.h:582-636`）；
- `Update` 的唯一常规调用点：`SubmitCommandLists` 末尾，顺序为 `FRAMECOUNT++`（`:5531`）→ 帧首阻塞循环（`:5534-5546`）→ `allocationhandler->Update(FRAMECOUNT, BUFFERCOUNT)`（`:5548`）→ 复制队列 worklist 回收（`:5550-5558`）。

**Lead 独立复核的推导**：帧 G 录制期 `allocationhandler->framecount == G`（由帧 G−1 帧末的 `Update(G, 2)` 写入），故帧 G 退役的 RT 得 `tag = G`。帧 m 帧末调 `Update(m+1, 2)`，判据 `G + 2 < m + 1` ⟺ `m ≥ G + 2` ⟹ **帧 G+2 帧末释放**。与 RB5 §4.2 结论一致 ✔

**B. RB1 侧：路径切换做了什么**
- `ActivatePath` 的 fade 回调里只做 `activePath->Stop(); component->Start(); activePath = component;`（`wiApplication.cpp:74-77`）—— **从不 delete 路径对象** ✔（与 01A §2.1/§2.2 一致）
- `RenderPath3D::Stop()` 函数体只有 `DeleteGPUResources();`（`wiRenderPath3D.cpp:1816-1819`）
- `RenderPath3D::DeleteGPUResources()`（`wiRenderPath3D.cpp:17`）先逐个 `rtMain = {}; rtVelocity = {}; …` 清掉约 40 个 RT，**函数最后一行**才调基类 `RenderPath2D::DeleteGPUResources();`（`wiRenderPath3D.cpp:93`）

### 关键事实 1：`FlushDeallocations` 的调用点是 `DeleteGPUResources()`，不是析构函数

RB5 §3 步骤 20 写的是「全仓唯一调用点在 `~RenderPath2D`（`wiRenderPath2D.cpp:21`）」。Lead 回源实测**函数名写错了**，`file:line` 本身是对的：

`@

→ 全仓**确实只有这一个调用点**，但宿主函数是 **`RenderPath2D::DeleteGPUResources()`**（`wiRenderPath2D.cpp:10-22`），**不是** `~RenderPath2D`。
→ 这个差别是实质性的：`DeleteGPUResources()` 会被 `Stop()` 与 `ResizeBuffers()` 调用（`wiRenderPath3D.cpp:99`，`ResizeBuffers` 开头也调 `DeleteGPUResources()`），所以「排空」是被**路径切换/尺寸变更**直接触发的；若它真在析构函数里，路径切换就不会触发排空。

### 关键事实 2：`FlushDeallocations` 排不掉「当前帧」退役的条目（RB5 §4.5 有 off-by-one）

`FlushDeallocations` 的实现是 `for (uint32_t i = 0; i < BUFFERCOUNT; ++i) SubmitCommandLists();`（`wiGraphicsDevice.h:438-445`）。设它在帧 F 调用、且当帧刚退役的 RT 满足 `tag = F`（`allocationhandler->framecount == F`）：

| 第几次 `SubmitCommandLists` | `FRAMECOUNT` 变为 | `Update` 收到的 `FRAMECOUNT` | 实际排空条件（`tag + 2 < FRAMECOUNT`） |
|---|---|---|---|
| 1 | F+1 | F+1 | `tag ≤ F−2` |
| 2 | F+2 | F+2 | `tag ≤ F−1` |

⟹ **`tag = F`（本帧退役）两次之后仍不满足**。

RB5 §4.5 的原文是「任意 `tag ≤ FRAMECOUNT_now` 的条目都满足 `tag + 2 < FRAMECOUNT_now + 2`」——**正确形式应为 `tag ≤ FRAMECOUNT_now − 1`**。这不是概念分歧，是一个会影响「排空是否即时」结论的等式偏差，已记入本文件，修订 RB5 时并入。

**兜底在哪**：`~AllocationHandler` 里调 `Update(~0ull, 0)`（`wiGraphicsDevice_DX12.h:578`，注释 `// destroy all remaining`）。`BUFFERCOUNT = 0` 使判据恒真 ⟹ **连当前帧条目一并释放**；这才是「进程退出前一定放干净」的保证，而不是 `FlushDeallocations`。

### 关键事实 3：C3 要求的确定答案

> **旧 RT 在帧 F 被标记删除，会在帧 F+2 帧末被真正 Release。最大 = 2 帧；最小 = 2 帧（在路径切换这条路径上）。**

- **下界（为什么不能更早）**：由精确判据，帧 G 的条目最早在 `m ≥ G+2` 满足，即帧 G+2 帧末。**唯一**的加速通道是「在**严格晚于** G 的某一帧 F′ 再调一次 `FlushDeallocations`」——那时 `tag = G ≤ F′−1` 会被立刻排空（代价是两次阻塞提交，每次都等帧首 fence）。而路径切换的 `FlushDeallocations` 与退役发生在**同一个帧 F 内**，所以对刚退役的那批 RT **没有加速效果**。
- **上界（为什么不会拖更久）**：只要帧循环继续，每帧帧末的 `Update` 都会推进判据，2 帧后必然命中。若之后再也不提交任何帧，则由 `~AllocationHandler` 的 `Update(~0ull, 0)` 一次性放干净。
- **安全性（为什么 `Stop()` 立即置空是安全的）**：`DeleteGPUResources()` 只把**上层句柄**置空（`rtMain = {}`），被置空对象的 `~Resource_DX12` 会把 COM 引用搬进销毁队列；**COM 引用比上层句柄多活 2 帧**。帧 G+2 录制期的帧首保证是「GPU 已完成帧 ≤ G 的全部非空队列工作」（RB5 §4.1），而该 RT 只可能在帧 ≤ G 被引用 ⟹ 释放时其使用已完成。

⟹ 无矛盾，且 01A 的两处待确认项都被 RB5 + C3 收紧。

### C3 → 本项目 WP4 / WP6 / WP7 的三条推论

1. **本项目没有「2 帧」这个上界**，语义必须显式写进 WP6 文档。本项目采纳 RB5 §7.1 的 fence 完成值判据，`tag` 是「最后一次引用该资源的提交返回的 fence 值」，释放时刻 = GPU 越过该值。因此路径切换后旧 RT **可能当帧就被释放**（GPU 已越过）**也可能延迟到队列排空**——与 WE「恒定 2 帧」完全不同。WP6 的验收不能写「延迟 2 帧」，只能写「不早于最后一次引用」。
2. **WP4 必须先于 WP6 是硬依赖**（与 05 §5.1 一致），理由是正确性的：现在 `~GpuResource → Destroy() → m_pResource = nullptr` 是**立即 Release**（`Engine/02_RHI/Resource/GpuResource.h:28-36`，RB5 §6.1 [实测]）。若在今天这条路径上做 WP6 的路径切换，`Stop() → DeleteGPUResources()` 会立刻释掉仍被上一帧命令引用的 RT = **必然 UAF**。WE 能这么写，是因为它有销毁队列兜着。
3. **resize 与路径切换应共用同一个排空入口**。WE 的 `ResizeBuffers()` 开头就调 `DeleteGPUResources()`（`wiRenderPath3D.cpp:99`）→ 同一个 `FlushDeallocations`；本项目只需要一个 `DeferredReleaseQueue::FlushAll()`，在 `Display::Resize`（`ResizeBuffers` 之前）与 `GameCore::TerminateApplication` 两处调用（RB5 §7.6/§7.7 已给顺序）。**不要**为 resize 和路径切换各写一套排空。

### C3 结论

**通过**。给出确定答案（**旧 RT：帧 F 标记 → 帧 F+2 帧末真正 Release，恒 2 帧**），与 01A 的 `ActivatePath` 行为不矛盾；同时产出 **1 条修正**（RB5 §3 步骤 20 的宿主函数名应为 `DeleteGPUResources` 而非 `~RenderPath2D`）、**1 条等式修正**（RB5 §4.5 的排空条件应为 `tag ≤ FRAMECOUNT_now − 1`）、**1 条闭合**（01A §12 的 `Stop()` 安全性未确认项）与 **1 条推测修正**（01A §5.1 第 124 行对 `FlushDeallocations` 作用的判断）。
