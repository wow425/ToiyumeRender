## 5.0 迁移的总原则

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **先解环，再分层** | 依赖成环（G1）是所有结构性问题的根因。不解环就抽公共层，会因为 include 关系再造新环 |
| 2 | **先抽共享，再拆路径** | 若先拆 DeferredRenderer 而不先把 PSO/材质绑定抽出去，拆出来的路径会再写一份一样的代码（重演 G3） |
| 3 | **每包必须能独立构建通过** | 约束文档要求渐进式；任何一包结束都必须是「绿的、可运行的」 |
| 4 | **每包必须能独立回退** | 以 git revert 单提交即可回退为设计目标 |
| 5 | **不动 6 段空壳的功能语义** | 架构迁移期只搬位置、不改行为。空壳保持空壳（约束：禁止大规模新增特效） |
| 6 | **文档是交付物** | 每包必在 docs/AIWorkLogs/ 生成施工文档，未写文档不算完成 |

## 5.1 依赖图与总顺序

```text
WP0 基线冻结与工作树隔离  ------------------------------+ (前置，非架构)
                                                        |
WP1 解环：场景层去依赖  <-------------------------------+
      |
      +--> WP2 共享渲染约定抽取（RootBindings / PSOFactory / DescriptorAllocator）
      |         |
      |         +--> WP3 Scene 容器落地（Material 数据迁入 Scene）
      |         |         |
      |         |         +--> WP5 DrawScene 提取（公共渲染功能层诞生）
      |         |                   |
      |         |                   +--> WP6 DeferredPath 收编
      |         |                             |
      |         |                             +--> WP7 ForwardPath + 注册表接入
      |         |
      |         +--> WP4 帧资源环与同步协议（可与 WP3 并行）
      |                   |
      |                   +--> WP8 后处理语义与链框架（需要 WP6 的 RT 所有权）
```

**串行主链**：WP0 -> WP1 -> WP2 -> WP3 -> WP5 -> WP6 -> WP7
**可并行支线**：WP4（依赖 WP1，可与 WP2/WP3 并行）、WP8（依赖 WP6）

**为什么必须是这个顺序**（三条硬依赖，违反会造成返工）：

| 依赖 | 原因 | 违反的后果 |
|---|---|---|
| WP1 必须先于全部 | 不解环时，任何向 Scene 搬东西的动作都会因为 Scene → Renderer 的反向 include 失败 | 编译错误，或被迫把新代码也放进 Renderer 层，加深 G1 |
| WP2 必须先于 WP5 | DrawScene 内部要用 PSOFactory 解析 PSO；若先写 DrawScene 再抽 PSOFactory，DrawScene 要写两遍 | 重复劳动 + 中间态不可用 |
| WP4 必须先于 WP6 | 路径收编要处理 RT 生命周期；没有帧资源环与延迟销毁，「销毁后 GPU 仍在用」会成为新 bug | resize/shutdown 崩溃 |

### WP4 帧资源环与同步协议

| 项 | 内容 |
|---|---|

## 5.5 完成状态判定

每个 WP 只能用以下状态之一（总控流程第三部分）：

| 状态 | 判定条件 |
|---|---|
| `DONE` | 目标实现 + 构建/测试/运行验证通过 + 代码审查完成 + 施工文档已写 |
| `IMPLEMENTED_UNVERIFIED` | 代码已改，但关键验证未执行（必须列出未验证项） |
| `PARTIAL` | 只完成部分目标，余项与原因明确 |
| `BLOCKED` | 因依赖/环境/信息缺失无法继续，需写明解除条件 |
| `REJECTED` | 审查发现方案不正确，已撤销或保留为失败记录 |

**禁止**：把「编译通过」当「GPU 正确」，把「画面看起来对」当「生命周期正确」，把「文档写了」当「代码通过」。

## 5.6 与约束文档「完成标准」的对照

约束文档 §六：最终目标不是让目录像 WE，而是让项目具备清晰的应用层、渲染路径、公共渲染功能、场景与资产系统、底层 RHI 及**可验证的资源生命周期**。

| 完成标准 | 由哪个 WP 达成 | 可验证证据 |
|---|---|---|
| 清晰的应用层 | WP6 | 应用层只调 `Render(FrameContext&)` 一次；Demos 中无 pass/RT 逻辑 |
| 清晰的渲染路径 | WP6、WP7 | 两条路径共存；新增路径不改 Features 层 |
| 清晰的公共渲染功能 | WP2、WP5 | Features 层不含路径/应用层 include；两条路径共用同一 DrawScene |
| 清晰的场景与资产系统 | WP1、WP3 | Scene 层不 include L4/L5/L6；存在单一 Scene 容器 |
| 清晰的底层 RHI | WP4 | RHI 不反向依赖上层（R2 为绿） |
| **可验证的资源生命周期** | WP4 | resize/最小化/关闭三用例 + Debug Layer 零 warning + PIX 事件 |

## 5.7 迁移期间禁止的事

| 禁止 | 理由 |
|---|---|
| 新增大规模渲染特效（SSAO/Shadow/DOF/MotionBlur/Bloom…） | 约束文档 §六明令 |
| 引入 RenderGraph / FrameGraph | 04 §4.6：会把同步关系藏进框架，违反原则⑤ |
| 引入完整 ECS | 04 §4.6：规模不匹配 |
| 为对齐 WE 而改目录名/类名 | 约束文档 §一明令禁止形式复制 |
| 一次性重写 DeferredRenderer | 约束文档 §四：不允许一次性重写 |
| 顺手修 6 段空壳 | 会把「架构迁移」与「功能实现」混在一个提交里，无法独立回退 |
| 在未冻结工作树时施工 | WP0 前置；02 §1 已证明并行写入会造成基线漂移 |

## 5.8 建议的下一步

**下一步只做 WP0**。理由：

1. 02 §1 证明工作树在审计期间持续被另一会话写入——**任何在漂移基线上的施工都不可信**。
2. WP0 不改任何源码，风险最低，却解除了后续全部工作包的基线风险。
3. WP0 同时产出「可重复构建」证据，这是后续每个 WP 验收的基准。

WP0 完成后，按 WP1 → WP2 → WP3 → WP5 → WP6 主链推进；WP4 可在 WP2/WP3 期间并行。

**不要**在 WP1 完成前开始 WP5（会因反向 include 失败而返工），也**不要**在 WP4 完成前开始 WP6（会在 resize 上崩）。
