1. `shadertype` 只在 MAIN pass 有意义（`:3312-3315`），初始化期同样只对 MAIN 展开 `SHADERTYPE_COUNT` 个变体（`:1947`：`materialtype_differentiation = renderPass == RENDERPASS_MAIN ? SHADERTYPE_COUNT : 1`）[实测]。→ **PSO 组合爆炸被这一行从 8×12 压到 1×12 + 7×1**。
2. `sample_count` 是**唯一一个「读运行时状态」的位**（`:3320`）。它不是材质属性，而是「当前绑定的 RT 有几个 sample」。→ 同一个材质在 MSAA on/off 下拿到的 PSO 不同，这是 DX12 的硬约束，不是设计选择。

#### 它在运行时如何被组装（3 步）

1. **初始化期预烘焙**：`:1945-2233` 五重循环 `renderPass × shaderType × mesh_shader × blendMode × cullMode(0..3) × tessellation(0..1) × alphatest(0..1) × msaa{1,2,4,8}`，逐组合构造 `PipelineStateDesc`，在后台 job 里 `CreatePipelineState`，结果通过 `EVENT_THREAD_SAFE_POINT` 回调写回 `*GetObjectPSO(variant)`（`:2157-2159`）[实测]。同时带**剪枝**：
   - `tessellation && renderPass > RENDERPASS_PREPASS_DEPTHONLY` → skip（`:1959-1960`）
   - `(PREPASS || PREPASS_DEPTHONLY) && transparency` → skip（`:1964-1965`）
   - `mesh_shader && tessellation` → skip（`:1971-1972`）
2. **运行时按对象组装**：`:3310-3321`，8 个字段按 2.2 表的来源逐个赋值。
3. **查表**：`GetObjectPSO(variant)` = `PSO_object[renderpass][shadertype][mesh_shader][variant.value]`（`:364-368`）[实测]。**注意前三层是数组、第四层是 `unordered_map`**：数组维度对应「初始化期已枚举的轴」，map 维度把 25 位剩余组合当 hash key——这是「预烘焙 + 懒创建」的混合体（DX12 后端另有一层 JIT PSO，见 §5.4）。

```cpp
inline void Create(uint _instanceIndex, uint camera_index = 0, float dither = 0)
{
    data  = _instanceIndex & 0xFFFFFF;          // 24 bit 实例下标
    data |= (camera_index & 0xF) << 24u;        //  4 bit 相机/级联下标
```

### 2.5 `sort_bits` —— 由 Scene 侧预先算好的「材质签名摘要」

`wiScene.cpp:4675-4730` [实测]

```cpp
union SortBits {
    struct {
        uint32_t shadertype  : 6;   // 位掩码：1 << material->shaderType
        uint32_t blendmode   : 3;   // 位掩码：1 << GetBlendMode()
        uint32_t doublesided : 1;
        uint32_t tessellation: 1;
        uint32_t alphatest   : 1;
        uint32_t customshader: 8;
        uint32_t sort_priority: 4;
        uint32_t unused      : 8;
    } bits;
    uint32_t value;
};
```
逐 subset 累积（`:4718-4721`：`sort_bits.bits.shadertype |= 1 << material->shaderType` 等）[实测]，最终通过 `object.sort_bits` 传给 `RenderBatch.sort_bits`（`wiRenderer.cpp:7243`）[实测]。

> **它解决的问题**：排序时希望「相同 PSO 的对象挨在一起」以减少 PSO 切换，但 PSO 是运行时才解析的（要先过 flags/renderPass），排序阶段拿不到。`sort_bits` 是一个**廉价的材质相似度摘要**，让排序至少把「材质类型相同」的对象归堆。**注意它是「近似」而非「精确」**：一个对象可能有多个 subset 用不同材质（`:4718` 是 `|=` 累积），所以它不能当真 key 用。

## §4 算法与公式

### 4.1 抖动（dither）淡出 —— 半透明对象的 LOD 交叉渐变

`wiRenderer.cpp:3452` [实测]：

```cpp
const float dither = std::max(
    instance.GetTransparency(),
    std::max(0.0f, batch.GetDistance() - instance.fadeDistance) / instance.radius
);
```

- 第一项 `instance.GetTransparency()`：对象自身透明度（0=不透明）
- 第二项：**进入 fadeDistance 之后的线性淡出**，分母是包围球半径（所以半径越大淡出越慢，视觉上按「物体尺寸归一化」）
- 若 `dither > 0.99` → **整个实例跳过**（`:3453-3456`）
- 若 `dither > 0` → 本批置 `forceAlphatestForDithering = 1`（`:3457-3460`）→ 进而影响步骤 23 的 `variant.bits.alphatest`（`:3319`）
- 若 `instance.alphaRef < 1` → 同样强制 alpha test（`:3461-3464`）

**量化**：`dither` 被打包成 **4 bit**（`ShaderInterop_Renderer.h:816`：`(uint(dither*15.0f) & 0xF) << 28`），shader 侧 `GetDither() = half(data>>28 & 0xF)/15.0`（`:828-831`）[实测]。→ **只有 16 级**，配合 blue-noise 阈值比较用（`FrameCB.texture_bluenoise_index`，`wiRenderer.cpp:4424`）[推断：由字段名与 4 bit 量化推断其用途为阈值比较]。

### 4.2 两种排序键（精确的位布局）

`RenderBatch::operator<`（opaque，`wiRenderer.cpp:243-269`）[实测]：

```cpp
union SortKey { struct {
    uint64_t distance  : 16;   // 最低优先级
    uint64_t lod       : 8;
    uint64_t meshIndex : 16;
    uint64_t sort_bits : 24;   // 最高优先级
} bits; uint64_t value; };
return a.value < b.value;
```

`RenderBatch::operator>`（transparent，`:274-300`）[实测]：

```cpp
union SortKey { struct {
    uint64_t lod       : 8;
    uint64_t meshIndex : 16;
    uint64_t sort_bits : 24;
    uint64_t distance  : 16;   // 最高优先级
} bits; uint64_t value; };
return a.value > b.value;
```

**优先级推导**（位域从低位起 = 低优先级，源码注释 `:249, :280` 明确写了「order of members … sort priority (low to high)」）[实测注释 + 推断推论]：

| 模式 | 优先级 低 → 高 | 最终顺序 | 目的（源码注释） |
|---|---|---|---|
| **opaque** `<` | distance → lod → meshIndex → **sort_bits** | 按 sort_bits 主导；同 sort_bits 内 **meshIndex 主导**（同网格聚成一批），再按 lod，最后前→后 | `:239-242`：「Priority is set to mesh index to have more instancing … distance is second priority (front to back Z-buffering)」[实测] |
| **transparent** `>` | lod → meshIndex → sort_bits → **distance** | **远→近**（`>` + 最高位是 distance），同距离内按 sort_bits/meshIndex 归堆 | `:270-273`：「Priority is distance for correct alpha blending (back to front)」[实测] |

> **为什么 opaque 用 `<` 而 transparent 用 `>`**：因为 opaque 希望「网格聚批」优先于「前后」，transparent 希望「前后」绝对优先（否则混合错）。两者都用**同一个 64 位整数比较**，只是位序和比较方向不同——**没有两次比较、没有 tuple，一个 `std::sort` 搞定**。这是本项目可以直接借的工程技巧（§6 判「可选」，理由见该节）。

### 4.3 indexOffset 的两种算法

`wiRenderer.cpp:3381-3394` [实测]：

```cpp
const MeshComponent::BufferView& ibv = provokingIBRequired ? mesh.ib_provoke : mesh.ib;
const size_t ib_stride = provokingIBRequired ? mesh.GetProvokingIndexStride() : mesh.GetIndexStride();

if (mesh.generalBufferOffsetAllocation.IsValid())
    indexOffset = uint32_t(((uint64_t)mesh.generalBufferOffsetAllocation.byte_offset + ibv.offset) / ib_stride)
                + subset.indexOffset;

```

- **情况 A（suballocated）**：IB/VB 被塞进一个大的 general buffer，所以 offset 要加上子分配的 `byte_offset`，再除以 stride 换算成「索引个数」
- **情况 B（standalone）**：IB 是独立 buffer，offset 相对自己

## §6 可迁移性判定（逐项：必需 / 可选 / 规模不匹配 + 理由 + 替代方案）

> **标注口径**：「WE 机制」列描述与所引 file:line = **[实测]**；「判定 / 理由 / 替代方案」三列 = **[推断]**（基于实测机制 + 本项目规模约束的分析，非源码事实）。此声明覆盖全表。
> 三选一定义：**必需** = 缺它则 WP5/WP7 做不成；**可选** = 有收益但有可接受替代；**规模不匹配** = 机制正确但复杂度成本 > 本项目收益。

> 判定口径：本项目 = 1–3 万行、单 D3D12 后端、教学为主、现有 `BaseRenderer` + Deferred/Forward 两条路径、已有 `MeshSorter`/`PipelineStateCache`。
> 「规模不匹配」= 机制本身正确，但其**复杂度成本**（行数/状态空间/调试难度）对本项目不划算。

## §7 对本项目 WPx 的具体建议（可直接施工）

> **标注口径**：本章设计建议全部为 **[推断]**；其中引用的「本项目实测现状」行号与代码为 **[实测]**（见 §9 #130-137）。

### 7.1 给 WP5（DrawScene 提取）—— 边界与签名

**建议 S5-1：函数签名按「已准备态」设计，不按「WE 同构」设计**

WE 的签名 `DrawScene(const Visibility&, RENDERPASS, CommandList, flags)`（`wiRenderer.h:282-287`）[实测] 能成立，是因为 `Visibility` 里塞了 `scene` 指针（`:128`），而 `Scene` 里塞了已算好的 GPU 描述符索引（`ShaderScene`）[实测]。→ **这是一个「隐式全局」而非「显式参数」**。本项目若照抄，会在 Features 层引入对 Scene 内部 GPU 布局的依赖，违反 B3。

建议：

```cpp
// 04_Renderer/Features/DrawScene.h
namespace Renderer::Features {

enum class DrawSceneFlags : uint32_t {
    None            = 0,
    Opaque          = 1u << 0,
    Transparent     = 1u << 1,
    OcclusionCulling= 1u << 2,
    ForegroundOnly  = 1u << 3,
};

enum class PassType : uint8_t { ZPrepass, GBuffer, Shadow };   // 只 3 个值

// 绘制需要的 GPU 侧「只读世界视图」——由调用者装配，Features 不知道 Scene 的内存布局
struct SceneDrawData {
    D3D12_GPU_VIRTUAL_ADDRESS materialBuffer;  uint32_t materialCount;
    D3D12_GPU_VIRTUAL_ADDRESS geometryBuffer;  uint32_t geometryCount;
    D3D12_GPU_VIRTUAL_ADDRESS instanceBuffer;  uint32_t instanceCount;
    const uint32_t* visibleObjects;            uint32_t visibleCount;
    // 每个对象的 mesh 索引 + sort_bits 由调用者提供（MiniEngine 的 ModelInstance 已有等价物）
};

void DrawScene(GraphicsContext& gfx,
               const SceneDrawData& world,
               const ObjectDrawDesc* objects,   // {meshIndex, instanceIndex, center, radius, sortBits, filterMask}
               uint32_t objectCount,
               PassType pass, DrawSceneFlags flags,
               PSOFactory& psoFactory,
               TransientAllocator& frameAlloc);   // 实例数组环形分配（M7）

} // namespace
```

- **解决什么问题**：让 Features 层「不知道 Scene 是什么」，只依赖 POD 视图；同时保留 WE 的 flags/pass 双轴与实例化批处理
- **替代方案**：直接传 `const Scene&` —— 否决，因为 Features 会被迫 include `05_Scene` 头，B3 的 R1 规则（Scene 不得泄漏 D3D12 细节）会反向破裂
- **规模适配**：`SceneDrawData` 只有 5 个字段；`ObjectDrawDesc` 每对象 32 B（对比 WE 的 16 B `RenderBatch`，多的是过滤所需字段，本项目对象数 << WE）

**建议 S5-2：把「二次过滤」与「排序」显式拆成两个函数**

WE 把它们揉在 `DrawScene` 里（`:7220-7254`）[实测]，导致无法单测。建议：

```cpp
uint32_t CullObjects(const ObjectDrawDesc*, uint32_t count, const CullInputs&, uint32_t* outIndices);
void     SortObjects(ObjectDrawDesc*, uint32_t count, bool transparent);
```

- **解决什么问题**：这两步是纯 CPU 逻辑、零 GPU 依赖，可以脱离 D3D12 单测（本项目教学场景下这是关键收益）
- **替代方案**：保持内联 —— 否决，会把 `DrawScene` 撑到 300+ 行（WE 的 DrawScene 104 行 + RenderMeshes 353 行 = 457 行，`01B` 已记录其可读性问题）

**建议 S5-3：实例批处理必须保留，但用「两遍」而非 WE 的「单遍 + lambda flush」**

WE 的做法：单遍遍历 renderQueue，边遍历边累积 batch，遇到分组键变化就调 `batch_flush()` lambda（`:3426-3484`）[实测]。问题：`batch_flush` 是个 227 行的 lambda（`:3196-3422`），捕获了 10+ 个外部变量 [实测]，极难调试。

建议：**第一遍算分组边界（纯数据），第二遍按边界逐批发 draw**：

```cpp
// pass 1: 算 {firstInstance, instanceCount, meshIndex, lod} 分组
std::vector<InstanceGroup> groups = BuildInstanceGroups(sortedObjects, count);
// pass 2: 每组的实例指针写进环形 buffer
WriteInstancePointers(groups, frameAlloc);
// pass 3: 每组逐 subset 发 draw
for (auto& g : groups) for (auto& subset : g.subsets) EmitDraw(subset, g);
```

- **解决什么问题**：`batch_flush` lambda 的捕获列表不可审计；拆成显式三遍后每遍都可独立验证
- **替代方案**：照抄 lambda —— 否决，因为本项目 `GraphicsContext` 是 MiniEngine 风格（`context.DrawIndexed(...)` 直接调用，`DeferredRenderer.cpp:318`）[实测]，本来就没有「延迟 flush」的需求
- **规模适配**：三遍都是 O(n) 线性扫描，n 在本项目 < 1 万，开销可忽略

### 7.2 给 WP5/WP6 交界 —— `PipelineDesc` 的语义修正（必须做，否则 WP5 建不起来）

**实测现状**：`Engine/04_Renderer/Pipeline/PipelineDesc.h:23-30` [实测]

```cpp
enum class RenderPassType { Depth, Forward, Deferred, Shadow, Transparent };
```

**问题**：这五个值混了**两个正交的轴**：
- `Depth / Shadow` = 输出目标（等价于 WE 的 pass 轴）
- `Forward / Deferred` = 着色路线（WE 用**另一条轴**表达：同一个 `RENDERPASS_MAIN` 下靠 flags 与 RT 格式区分，`wiRenderPath3D.cpp:1562 vs :1392` 都是 MAIN [实测]）
- `Transparent` = 对象属性（WE 里是 `BLENDMODE`，`ObjectRenderingVariant` 的 bit 12-15）

后果：`PipelineDesc::operator==`（`:40-45`）把这三个轴混在一个枚举里比较，**必然产生语义重复的 PSO**（例如 `Forward+Transparent` 与 `Transparent` 会算成两个不同 PSO）。而 `GetPSOIndex` 用「暴力遍历已建 PSO 比较 `ID3D12PipelineState*`」去重（`DeferredRenderer.cpp:605-609`）[实测]——这是**在用运行时指针相等掩盖 key 设计缺陷**。

**建议**：把 `PipelineDesc` 拆成 WE 的三轴形态：

```cpp
struct PipelineDesc {
    uint32_t VertexFlags;     // 已有
    uint32_t MaterialFlags;   // 已有
    RenderOutput Output;      // {ZPrepass, GBuffer, Shadow}  ← pass 轴（3 值）
    bool     DoubleSided;     // 从 MaterialFlags 里提出（WE: cullmode 位）
    bool     AlphaTest;       // 从 MaterialFlags 里提出（WE: alphatest 位）
    BlendMode Blend;          // {Opaque, Alpha, Additive}      ← 取代 PassType 里的 Transparent
    bool operator==(const PipelineDesc&) const;  // 逐字段
};
```

- **解决什么问题**：① 消除语义重复 PSO；② 让 `GetPSOIndex` 不需要暴力遍历（改成 `unordered_map<PipelineDesc, uint16_t, Hash>`）；③ 为 WP7 的 ForwardPath 铺路——Forward 与 Deferred 的差异**不体现在 PipelineDesc 里**，而体现在「传入的 RT 格式/着色器」上
- **替代方案**：保留现有 5 值枚举，新增 `Deferred_Transparent` 等 —— 否决，会让枚举变成笛卡尔积
- **规模适配**：字段从 3 个变成 6 个，但组合数反而下降（因为删掉了不可达组合）；hash 一次算完，比遍历 N 个 PSO 快
- **证据强度**：这条建议的依据是**本项目实测代码**，不是 WE 类比 —— WE 的做法（`ObjectRenderingVariant` 把 pass/blend/cull/alphatest 分位）恰好印证了这个拆分方向

### 7.3 给 WP7（ForwardPath）—— 用「DrawScene 是否需要改」当边界验收

WE 的 `visibility_shading_in_compute` 是**反面教材**（`01B` §4.2 已述）：它在 `RenderPath3D` 里用 `if` 分叉，导致 `DrawScene` 被调用两次、且其中一次只画 impostor（`wiRenderPath3D.cpp:1544-1553`）[实测]。

**建议 S7-1**：ForwardPath 只在**两处**与 DeferredPath 不同：
1. `RenderOutput` 传的值不同（Deferred 传 `GBuffer`，Forward 传 `GBuffer` 但 **RT 是最终颜色**）—— 差异由**路径持有 RT 的格式**吸收（B1：RT 由路径拥有）
2. Lighting 段：Deferred 有全屏 draw，Forward 没有

→ **Features 层（DrawScene）一行不改**。这就是 WP7 验收标准「新增路径未修改 Features 层任何文件」的可执行解释。

**建议 S7-2**：不要在 `DrawScene` 里加 `if (forward)`。若发现必须加，说明 `SceneDrawData`/`PSOFactory` 的输入不完整，应该补输入而不是加分支。

### 7.4 给 WP6（DeferredPath 收编）—— 现在就能改的 3 处

基于 `DeferredRenderer.cpp:249-432` [实测]：

| 现状 | 问题 | 建议 |
|---|---|---|
| `Render()` 里同时做 GBuffer 绘制（`:251-324`）与 RT 管理（`:256-271`） | 违反 B2（路径不该管绘制细节，Features 不该管 RT） | 把 `:285-322` 整段（排序消费 + PSO 绑定 + DrawIndexed 循环）搬进 `Features::DrawScene`；RT 段（`:256-271`）留在路径 |
| 遍历 `for (; CurrentPass <= pass; ...)`（`:290`）—— 这是 MiniEngine `DrawPass` 遗留 | 一次 `Render` 调用会**顺带画完之前所有 pass**（因为 `CurrentPass` 从 sorter 的当前值开始递增）。这在「一帧一次调用」的新形态下会重复绘制 | WP6 删除这个循环；`DrawScene` 只画 `pass` 指定的那一类 |
| `GetPSOIndex` 暴力遍历去重（`:605-609`） | 每次新组合 O(N) 比较，且 N 是运行时增长的 | 见 §7.2：换 `unordered_map` |

### 7.5 不要做的事（防止过度设计）

| 不要做 | 理由 |
|---|---|
| 不要引入 7 值 `RENDERPASS` 枚举 | 本项目只 3 个 pass，多出来的 4 个值永远为假（§6 M2） |
| 不要实现 describe/barrier 声明系统 | WE 连声明都没有（§5.2 实测 0 barrier），本项目按 04 §4.4-B2 的「只声明读写意图」即可，不要引入 `ResourceState` 自动推导 |

| 不要把 `ClearWorld` 放进 Features | 它是 Scene 的职责，WE 自己也只是转发（§6 M20） |

## §8 未确认项（≥3 条，每条给出「确认需读哪个文件哪一段」）

> **标注口径**：每条中「已看到的事实」= **[实测]**（附 file:line）；「推测原因 / 风险」= **[推断]**。6 条全部为真实未闭合项。

**U1｜`ObjectRenderingVariant` 的位域比特位置是否为 MSVC 的低位起分配？**
本文 §2.2 表的「位置」列标为 [推断]。C++ 标准只保证「相邻位域打包进同一存储单元」，**不保证从低位还是高位开始**。WE 依赖 `variant.value` 作为 hash key（`wiRenderer.cpp:367`），若换编译器（Clang/GCC）位序不同，**PSO 会错配到别的组合**且不报错。
→ 确认方式：读 `wiRenderer.cpp:348-363` 的 `union` 定义 + 任一 MSVC 编译产物；或查 WE 是否有针对非 MSVC 的 `#ifdef`（本次 grep 未见于该区域）。**这是复制该机制前必须闭合的风险**。

**U2｜`renderQueue`/`renderQueue_transparent` 是 `thread_local`，`RenderMeshes` 是否因此不可重入？**
`wiRenderer.cpp:346-347` 定义两个 `static thread_local RenderQueue` [实测]，`DrawShadowmaps`（`:6748-6749`）与 `DrawScene`（`:7222`）都直接 `init()` 它们。若同一线程上两个 `RenderMeshes` 嵌套（`DrawWireframeOverlay` → `DrawScene` 就是嵌套，`:8721`），内层 `init()` 会清掉外层队列。
→ **本文未能确认这是否真的安全**：`DrawWireframeOverlay` 只在 `RENDERPASS_MAIN` 且独立调用（不在 `RenderMeshes` 内部），所以实际不嵌套。但**契约是隐式的**。确认方式：读 `wiRenderPath3D.cpp` 全部 `DrawWireframeOverlay` 调用点，确认它们都不在任何 `RenderMeshes` 的调用栈里。

**U3｜`ShaderMeshInstance::SetUserStencilRef`（存进 `flags` 高 8 位）与硬件 `BindStencilRef` 是两条独立通路，shader 侧如何使用前者？**
`ShaderInterop_Renderer.h:781-788` 把 stencil 写进 `flags` 高 8 位 [实测]，但 `ObjectPushConstants`（`:835-845`）没有 stencil 字段。推测供软光栅化/描边在 PS 里读实例的 stencil 值。**未读任何 PS 的 stencil 用法**。
→ 确认方式：`grep -rn "GetUserStencilRef" shaders/`，逐个看调用点的语义（本次未做，属 RB6 范围）。

**U4｜`drawscene_flags` 是 `static const`（`wiRenderPath3D.cpp:929`），意味着 flags 在路径生命周期内不可变——运行期切换 wireframe/tessellation 如何生效？**
`static` 意味着只初始化一次 [实测]。但 `DRAWSCENE_TESSELLATION` 位在 `RenderMeshes` 里还与 `GetTessellationEnabled()` 与设备能力再与一次（`wiRenderer.cpp:3152-3156`）[实测]——说明运行期开关走的是**全局 setter**（`wi::renderer::SetTessellationEnabled`）而非 flags。
→ 确认方式：读 `wiRenderer.h:96-250` 的 setter 区，确认哪些「看起来是 flags 的能力」实际由全局开关控制。**这直接影响本项目 `DrawSceneFlags` 该不该做成运行期可变**。

**U5｜`GetObjectPSO` 的 4 维数组第一维是 `RENDERPASS_COUNT`=8，但 `shadertype` 维度是 `SHADERTYPE_COUNT`=12——非 MAIN pass 的 11 个空槽是否真的不被访问？**
`wiRenderer.cpp:366` 声明 `PSO_object[8][12][2]` [实测]，初始化期只对 MAIN 填 12 个 shadertype（`:1947`）[实测]。运行时 `:3312-3315` 保证非 MAIN 的 `shadertype` 恒为 0 [实测]。**逻辑上闭合**，但数组白白浪费 7×11×2 = 154 个 `unordered_map` 实例（每个至少 40+ B 头部）。
→ 确认方式：读 `wi::unordered_map` 的实现（`wiVector.h`/`wiArchive.h` 区），确认空 map 的开销。**对本项目的启示**：不要复制这个 4 维数组形态（§6 M3 已改为单层 map）。

**U6｜子分配（suballocated）索引缓冲的 `indexOffset` 公式中，`mesh.ib`/`mesh.ib_provoke` 的 `BufferView.offset` 语义未核对**
`wiRenderer.cpp:3381-3394` 的两种分支 [实测] 依赖 `BufferView{offset, size}` 的 `offset` 是「相对于所属 buffer 起点」。若子分配的 IB 实际拥有独立 `GPUBuffer`（aliasing），公式里加 `byte_offset` 就是对的；若是同一 buffer 的不同区间，则可能重复加。
→ 确认方式：读 `MeshComponent::CreateRenderData`（`wiScene_Components.cpp`，约 `:1000-1400` 区）里 `generalBufferOffsetAllocation` / `generalBufferOffsetAllocationAlias` 的赋值处。**本项目不打算做 IB 子分配（§6 M12/M7），故此风险可规避**。
