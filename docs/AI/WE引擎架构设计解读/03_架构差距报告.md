# 03 架构差距报告（交付物 A）

> 本文对照 WickedEngine（下称 WE）与本项目 TooiyumeRender 的真实源码，给出**架构层面的差距**，并分析其根因。
> 结论全部可回溯到 `01A`/`01B`/`01C`（WE 侧证据）与 `02`（本项目现状）中的 `文件:行号`。
> 本文只做诊断，不给施工方案；施工顺序见 `05_迁移顺序与工作包.md`，目标形态见 `04_目标架构与模块边界.md`。
>
> 审计基线：HEAD = `51c09d09917a507e33ff7e468e824e34963339c5`。工作树在审计期间被**另一并行会话**持续写入（见 `02` §1），不作基线。

## 3.1 一句话结论

**本项目并不缺「渲染功能」，缺的是「分层」。**

具体地：PBR/IBL 数学是对的、GBuffer+Lighting 是真跑的、RHI 主干是成链可用的、构建是绿的。这些在 `02` 中都被复核为**可保留的高价值资产**。真正的问题是四条**结构性**缺陷：

| # | 缺陷 | 本质 | 关键证据 |
|---|---|---|---|
| G1 | **依赖是循环的，不是分层的** | 声明的 Application→Renderer→Scene/Asset→RHI→Core 只在目录名上成立；实测存在 3 条反向边 + 1 条越级直连 | Scene/Model/Model.h:5-12 include 04_Renderer 与 02_RHI；CameraController.h:3 include 01_Application（02 §3.0） |
| G2 | **没有「渲染路径」这个抽象** | 只有一个类同时兼任路径与功能；pass 调度权在应用层 | BaseRenderer::Render(..., DrawPass pass, ...) 由外部决定画哪个 pass；DeferredRenderer.h 同时持 GBuffer 枚举 + RT + RootSig + PSO cache（02 §3.2） |
| G3 | **公共渲染功能层不存在** | 项目层面**零共享实现** | Forward 与 Deferred 各写一份 Initialize/Shutdown/OnResize/BuildRootSignature/GetPSOIndex/BindRenderState/BindMaterial（02 §3.2 逐段比对） |
| G4 | **后处理链与 HDR/LDR 约定不存在** | 无 HDR 中间 RT、无链、tonemap 被塞进光照 shader | 交换链 R8G8B8A8_UNORM（RendererConfig.h:17）；六段空壳后直接 CopyBuffer（02 §0） |

**G1 是根因，G2/G3/G4 是它的表现。** 因为依赖成环，「场景」无法独立于「渲染器」演化，渲染器只能越长越大（G2/G3）；因为渲染器是唯一的组织中心，后处理也就没有独立的落点（G4）。

## 3.2 六条目标原则的差距总表

打分口径：**0 = 完全缺失；1 = 有雏形但未成体系；2 = 基本满足但有明确缺口；3 = 满足**。分数由 `02` 的证据支撑，本文只做归纳。

| 原则 | 现状分 | WE 的做法（可借鉴部分） | 差距性质 |
|---|---|---|---|
| ① 应用层与渲染路径分离 | **1** | 薄 RenderPath 基类（12 个非纯虚钩子）+ ActivatePath 持 activePath；应用层唯一提交（wiApplication.cpp:388） | **接口有雏形、边界错位**：IGameApp::RenderScene() 让应用层成为渲染驱动者 |
| ② 渲染路径与公共渲染功能分离 | **1** | namespace wi::renderer 自由函数 + 按效果 Resources POD；wiRenderer 中 grep RenderPath 为 0 次 | **几近缺失**：有 4 块公用雏形（MeshSorter / BufferManager / Material / PipelineStateCache），但 Forward 与 Deferred **8 段逐字重复**（02 §3.2.3） |
| ③ 场景/材质与 RHI 解耦 | **0** | 单一 Scene 世界；可见性归渲染器（wiRenderer.h:150 visibleObjects） | **反向依赖 3 条**：Scene→Renderer、Scene→RHI、Scene→Application |
| ④ 后处理明确 HDR/Tonemap/LDR | **0** | RenderPostprocessChain：HDR 段 → 唯一 tonemap → LDR 段；rt_read/rt_write 加 swap | **完全缺失**：无 HDR RT、无链、tonemap 位置错 |
| ⑤ 资源生命周期与 GPU 同步 | **1** | 显式 GPUBarrier + 帧计数延迟销毁 + AllocateGPU ring | **局部正确、局部必现断裂**：屏障攒批设计正确，但 resize 断链、OnResize 零调用 |
| ⑥ 为未来管线保留扩展 | **1** | PathTracing 证明「另一条路径」可行，但它整体重写 Render() | **无扩展机制**：加一条路径要复制后处理链 |

**加权结论**：①③④⑥ 四项为结构性缺失（0–1 分），② 几近缺失（1 分：仅 4 块公用雏形，两条路径 8 段逐字重复）。这不是靠修 bug 能解决的量级。

> **交叉印证**：本表与 `02` §7 的独立评分完全一致（1 / 1 / 0 / 0 / 1 / 1）。两条互不知情的分析路径得出同一组分数，提高了该结论的可信度。

## 3.3 逐层差距详表

### 3.3.1 L6 应用层

| 维度 | WE | 本项目（HEAD） | 差距 |
|---|---|---|---|
| 路径持有方式 | RenderPath* activePath 裸指针不拥有（wiApplication.h:27）；切换只调旧路径 Stop()，**从不 delete**（wiApplication.cpp:74-77） | 三个 Demo 各自 new / 全局定义渲染器对象（DeferredApp.cpp:57） | **本项目更原始**：无 ActivatePath、无生命周期回调 |
| 帧驱动 | 27 步固定帧序（wiApplication.cpp:89-390），路径只被调用 | Demo 自己在 Update/RenderScene 里 GraphicsContext::Begin/Finish 两次 | **渲染流程裸露在应用层**，正是原则①要消除的 |
| 提交点 | **应用层唯一提交** wiApplication.cpp:388 | Demo 每帧提交两次 | 两者都可接受；本项目应把提交收进路径（04 §4.4-B2） |
| 输出契约 | 路径以 getter 暴露结果（GetRenderResult3D/GetDepthStencil/GetGUIBlurredBackground） | Demo 直接把 Display::SceneColorBuffer 指到渲染器内部 RT（DeferredApp.cpp:76） | **应用层知道路径内部 RT**，强耦合 |
| resize 通知 | 每帧尺寸比较（wiRenderPath2D.cpp:90-94）→ 路径 ResizeBuffers | OnResize 有声明有实现、**全仓 0 调用点**；ResizeDisplayDependentBuffers 只有声明无实现且被注释（Display.cpp:167） | **必现断裂** |

**WE 可借鉴点**：Start() 触发 ResizeBuffers() / Stop() 触发 DeleteGPUResources() 把「路径切换」与「资源生命周期」绑定（wiRenderPath3D.cpp:1816-1824，仅 4 行）。这恰好补上本项目的 resize 断链。

**WE 不可借鉴点**：fade 过渡、Lua 绑定、4 队列并行，01A §10.2 判定为规模不匹配。

### 3.3.2 L5 渲染路径

| 维度 | WE | 本项目（HEAD） | 差距 |
|---|---|---|---|
| 抽象形态 | 薄基类 RenderPath（12 个非纯虚钩子，wiRenderPath.h:17-40） | BaseRenderer 除 ModelSort() 外**无任何共享实现** | 本项目是「接口」不是「基类」，无复用价值 |
| pass 调度权 | 路径内部决定（RenderPath3D::Render() 内按序调用） | **外部决定**：Render(context, frame, pass, batchType) | **原则①的直接违反** |
| 路径内是否含功能 | **含**（WE 自身缺陷）：编排 + 40 RT + ~60 开关 + 25 Resources 结构体 | **也含**，且更重：连 RootSignature/DescriptorHeap/PSO cache 都在类里 | 两边都错，**不能靠抄 WE 来修** |
| 结果暴露 | getter + 默认 nullptr 的最小契约 | 具体类型 DeferredBuffer GetDeferredBuffer() | 应用层需知道具体路径类型 |

**关键发现（WE 侧，反直觉）**：`01B` 证明 WE **不存在** Forward/Deferred/Tiled 三条路径，只有**一套 tiled forward+ 光照** + 两个执行模型（光栅化 PS / visibility-buffer CS，由运行期 bool visibility_shading_in_compute 切换，wiRenderPath3D.h:208）。

这条发现改变了本项目的设计前提：

- 约束文档 §2.1 假定 WE 用不同 RenderPath 组织 Forward/Deferred —— **该假定在本地 WE 版本上不成立**。
- 因此「给 Deferred 和 Forward 各建一个 RenderPath 子类」**不能从 WE 抄现成结构**。
- 但 WE 的收敛方向值得学：**把多条管线的差异收敛为「同一套光照 + 一个执行模型开关」**，而不是让每条管线各长一套。
- 对本项目的启示：Forward 与 Deferred 的**共享面远大于差异面**（同一套 PBR、IBL、阴影、后处理），差异只在「几何信息怎么落到像素」。这正是原则②要抽出的部分。

### 3.3.3 L4 公共渲染功能（本项目最大的空白）

**WE 的形态**（01B §2.2）：namespace wi::renderer 全自由函数，参数显式传入 Scene/Visibility/CameraComponent/CommandList；实测其源码中 grep RenderPath = **0 次**、grep Application = **0 次**、grep GetScene() = **0 次**——不依赖路径、不依赖应用层、不取全局单例。

**本项目的形态**（02 §3.2）：

| 功能 | Forward | Deferred | 是否共享 |
|---|---|---|---|
| Initialize / Shutdown / OnResize | 各一份 | 各一份 | 否 |
| BuildDescriptorHeaps | 各一份 | 各一份 | 否 |
| BuildRootSignature | 各一份 | 各一份 | 否 |
| GetPSOIndex | 各一份 | 各一份 | 否 |
| BindRenderState | 各一份 | 各一份 | 否 |
| BindMaterial | 各一份 | 各一份 | 否 |
| MeshSorter | 共用 | 共用 | **是（唯一共享）** |

**差距量化**：7 项中 6 项零共享。这不是「重构一下」的量级，是「公共层尚未存在」。

**本项目代码里已有的自白**（BaseRenderer.h:1-8）：作者写道——PSO 绑定方法是通用的，但放在抽象类缺数据、放在具体类又不合适。`01B` 的实测证明 WE 的答案是：**把它放到一个不依赖路径的自由函数层，数据全部作为参数传入**。这条自白因此不是「待解决的问题」，而是「已经找到答案但尚未实施」的问题。

### 3.3.4 L3 场景与资产

| 维度 | WE | 本项目（HEAD） | 差距 |
|---|---|---|---|
| 世界容器 | 单一 wi::scene::Scene（ECS + 组件管理器） | **不存在 Scene 类**，只有 Model + LightingSystem + Camera 松散组合；grep class Scene 仅命中 glTF.h:217（解析用） | **结构性缺失** |
| 可见性 | 归渲染器：wiRenderer.h:150 visibleObjects（uint32 索引数组） | 无可见性列表；Demo 持 ModelInstance Models[10] 直接传渲染器 | 无剔除基础设施 |
| 场景↔GPU 边界 | **未真正隔离**（WE 自身缺陷）：MeshComponent 同时含 CPU 顶点数组 + GPUBuffer + 裸 int 描述符索引 + BLASes（wiScene_Components.h:728-770） | **也未隔离**：Model.h:5-11 直接 include RHI 头 | 两边同病，**不必向 WE 学这一点** |
| 材质→PSO | 32 位位域 key ObjectRenderingVariant（wiRenderer.cpp:348-362）+ 二维缓存 + 后台全变体预热 | 各渲染器自建 std::vector<GraphicsPSO> m_PSOCache + GetPSOIndex | **有雏形无共享** |
| 反向依赖 | 1 条（资产层登记延迟 MIP → 渲染层执行，wiResourceManager.cpp:942 → wiRenderer.cpp:3603） | **3 条**（Scene→Renderer / Scene→RHI / Scene→Application） | 本项目更严重 |

**WE 唯一的反向依赖值得学其处理方式**：资产层只**登记意图**，渲染层每帧统一**执行**（ProcessDeferredTextureRequests）。它承认「有些事必须由渲染层做」，但把依赖压成「数据登记」而非「直接调用」。本项目应换成队列/回调，而不是 include。
### 3.3.5 L1 RHI

| 维度 | WE | 本项目（HEAD） | 差距 |
|---|---|---|---|
| 抽象层次 | 多后端（DX12/Vulkan/Metal），wiGraphicsDevice 统一接口 | 单 D3D12，MiniEngine 血缘（见 06） | **WE 属规模不匹配，不应照搬** |
| 同步可见性 | 双轨：pass 内 barrier 由后端按 LoadOp/StoreOp 自动生成（wiGraphicsDevice_DX12.cpp:6114-6137）；pass 外必须显式 GPUBarrier | 显式 barrier 攒批（CommandContext.cpp:385-409），无自动生成 | 本项目**更符合原则⑤**（同步关系始终可见） |
| 延迟销毁 | 10 个 destroyer_* 队列，判据 = 队首帧号 + BUFFERCOUNT < FRAMECOUNT（wiGraphicsDevice_DX12.h:581-638） | 无延迟释放队列，Destroy 立即置空 ComPtr | **缺失**（原则⑤硬伤） |
| 上传 | AllocateGPU ring + 独立 COPY 队列 | 线性分配器 + UploadBuffer | 基本对等，无 COPY 队列（可接受） |
| 资源状态跟踪 | 无运行时断言（01B §8） | 无 | 两边都缺，可后补 |

**结论**：RHI 是**本项目相对最健康的一层**（`02` 复核为可保留资产）。差距集中在两点：**缺延迟销毁队列**、**缺 pass 级资源状态约定**。这两点是原则⑤的可施工落点，不需要重写 RHI。

## 3.4 WE 有哪些**不能**抄（明确说明，防止形式复制）

约束文档要求：WE 设计不适合当前规模/学习目标时必须明确说明。以下 8 项经 01A/01B/01C 判定为**不适用**：

| # | WE 的做法 | 判定 | 依据 | 本项目替代方案 |
|---|---|---|---|---|
| 1 | RenderPath3D 作为「编排 + 40 RT + ~60 开关 + 25 Resources」全家桶基类（3326 行） | **规模不匹配** | 01A §0-7、§10.2；PathTracing 只能「跳过 + 重写」 | 路径基类**只做生命周期与结果契约**，RT 由具体路径自持（04 §4.2.2） |
| 2 | 多后端 wiGraphicsDevice（三份后端实现） | **规模不匹配** | 单 D3D12、教学用途；会淹没学习目标 | 单后端，保留具名 Transition（06 §A.6） |
| 3 | 显存别名 AliasingAllocator + offset_* + Barrier(Aliasing) | **规模不匹配** | 01A §10.2：每处 offset 都要与 barrier 配对，是原则⑤风险最大来源 | 不引入；需要时用普通 RT 复用 |
| 4 | 15+ 命令列表 / 4 队列并行（含 WaitCommandList 依赖语义） | **规模不匹配** | 01A §10.2；使 Render() 长达 955 行 | 1–2 个命令列表，单队列 |
| 5 | tiled/clustered light culling（lightCullingCS + Harada 2.5D） | **暂不需要** | 当前光源数极少（旧审计记 MaxLights=1，待 02 复核） | 直接光照；光源增多后再评估 |
| 6 | 完整 ECS（wi::ecs + 组件管理器） | **规模不匹配** | 教学项目、实体数量小 | 轻量 Scene::Scene 容器（04 §4.4-B3） |
| 7 | fade 过渡 / Lua 绑定 / 事件系统 / 资源流送 | **规模不匹配** | 01A §10.2 逐条判定 | 保留接口位，暂不实现 |
| 8 | 场景组件同时持有 GPU 句柄与裸 int 描述符索引（wiScene_Components.h:728-770） | **不应学**（WE 自身缺陷） | 01C §2.1、§4 泄漏清单 15 条 | 场景只持资源句柄，不持裸描述符索引 |

**一个必须点明的反直觉结论**：本报告发现「本项目在原则⑤上**部分优于** WE」——WE 把 pass 内 barrier 自动化了（01B §0-7），而本项目始终显式攒批 barrier。约束文档原则⑤明确「禁止为追求抽象而隐藏重要的 GPU 同步关系」，因此**这一点不要向 WE 靠拢**。

## 3.5 根因分析

为什么会出现 G1–G4？本报告给出四条根因，均有证据：

### 根因 R1：MiniEngine 的血缘没带来它的「分层意图」

`06` 已证明 Engine/ 是 MiniEngine 的直系后代。但 MiniEngine 的 Core/ **本身就不是分层架构**（RHI 与后处理同目录、靠命名空间约定）。本项目完整继承了它的文件，却自行重编了 00_Core…05_Scene 六层目录——**目录是新的，依赖关系是旧的**。

这解释了 G1：分层停留在目录名，没有落到 include 上。

### 根因 R2：MiniEngine 的「公共渲染功能」没有被一起搬过来

`06` §A.3.1 实测：上游 Core/{PostEffects, FXAA, SSAO, DepthOfField, MotionBlur, ImageScaling} **全部未被采纳**，唯一幸存者是 TemporalEffects 且被移入 04_Renderer。

也就是说：本项目的 Engine 只搬了**底盘**（RHI/资产/窗口），没搬**可复用的渲染功能层**。于是当需要第二条管线时，只能把第一条复制一遍——这直接解释了 G3（零共享）与 G2（路径与功能混居）。

### 根因 R3：MiniEngine 的管线本体未被采纳，本项目自研且无参考

`06` §A.3.2：上游 Model/Renderer.cpp + SponzaRenderer.cpp 未被采纳；本项目自研 BaseRenderer/DeferredRenderer/ForwardRenderer。

自研不是错，但**没有参考意味着边界只能靠试错**。BaseRenderer.h:1-8 那段自白就是试错的痕迹：作者已意识到 PSO 绑定「放哪都不对」，但当时没有「公共渲染功能层」这个概念可用。

### 根因 R4：功能推进优先于结构推进

从 git 历史看（TAA初步建设、IBL修补完毕、rt Sample1），项目按「加功能」推进。功能一多，DeferredRenderer 就从「路径」长成了「路径 + 功能 + 资源容器」。

`02` §0 的实测印证了后果：**3 段真实现 + 6 段空壳并存**。空壳（SSAO/Shadow/Transparent/PostProcess/TAA/Tonemap 六段只有成对 PIX 事件）正是「先占位、后填充」的产物——而这个顺序恰恰与「先立结构、再填功能」相反。
