## §1 三条总判断

### J1 本项目**不缺渲染功能，缺的是分层**

这是全阶段最重要的结论，由两条独立证据链交叉印证：

- **功能侧充分**：GBuffer + 延迟光照真跑、PBR BRDF 数学正确（RB6 逐项核对 `Engine/Shader/05_BRDF/BRDF.hlsl`）、IBL 预计算链完整、构建 83/83 全绿（`02` §1）。
- **结构侧缺失**：依赖成环（`02` §3）、无渲染路径抽象（`02` §4）、公共渲染功能层不存在（`02` §5）、无 HDR 与后处理约定（`02` §6）。

⇒ **推论**：本阶段之后任何「加特效」的动作，收益都会被结构债务按比例吃掉；而先做结构的收益是**复利**的（每多一个渲染路径，重复代码少一份）。这正是约束文档「架构迁移完成前禁止大规模新增无关渲染特效」的技术理由。

### J2 存在**两条独立战线**，混在一起做会互相阻塞

| 战线 | 内容 | 判据 | 与另一条的关系 |
|---|---|---|---|
| **A 结构** | WP0–WP8（解环 → 共享约定 → Scene 容器 → 帧资源环 → DrawScene 提取 → 两条路径 → 后处理框架） | 编译通过 + 六个 Demo 行为不回退 | 慢、需要连续投入 |
| **B 正确性** | 缺陷清单（§4.2） | 逐条可复现 → 修复 → 回归 | 快、可碎片化插入 |

两条战线**大部分可并行**，但有 **3 条硬交叉**（必须按顺序，见 §4.3）：

1. **B-01（显存释放）必须先于 WP6**：今天 `GpuResource::~GpuResource → Destroy() → m_pResource = nullptr` 是立即 Release（`Engine/02_RHI/Resource/GpuResource.h:28-36`），任何「路径切换销毁 RT」都会 UAF。
2. **B-04（PSO 语义重复）必须先于 WP5**：否则 `PassType` 枚举会把两个正交轴焊死，越晚拆越贵。
3. **B-07（材质纹理槽一致性）必须与 WP3 同批**：WP3 会重写材质数据布局，是唯一能一次性焊死护栏的时机。

### J3 **审计基线必须钉死，工作树不能当基线**

实测：工作树被**并行开发会话**持续改写，`git status --porcelain` 从会话初的 17 项增长到 **55 项**（2026-10-24 20:1x 实测），其中多条**恰好是本审计报告列出的 P0 缺陷已被修复**（详见附录 A）。

⇒ **规矩**：

- 所有「现状」结论以 **HEAD `51c09d0`** 为准，行号以各文档标注的基线为准；
- 任何施工**开工前**必须重跑一次复核（附录 A 的命令），确认该缺陷是否已被并行会话修掉，**避免重复修或改坏**；
- 建议 WP0 的第一步就是**把并行会话的成果收编为一个提交**，否则结构迁移与并行修改会持续冲突。

## §4 两条战线的排序

### 4.1 战线 A：结构迁移

**只做 WP0 是当前唯一正确的下一步**（05 的结论，本文确认）。理由：

- WP0 不改一行源码，但**决定了后续八个 WP 的成败**——现在有 55 项未提交改动、4 条反向依赖、一个活跃的并行会话，不先钉基线就动手必然冲突；
- WP0 的产出（基线提交 + 施工分支 + 复核脚本）可复用给每一个 WP。

**WP0 的具体动作清单**（可直接执行）：

1. 与并行会话确认其改动范围，**收编为一个提交** `chore: 收编并行会话改动`（当前 55 项脏改动，其中含本审计 5 条 P0 的修复，见附录 A）；
2. 打基线 tag：`git tag arch-baseline-2026-10`；
3. 建施工分支：`git switch -c arch/wp1-decouple`；
4. 落盘复核脚本 `scripts/audit_recheck.bat`（内含附录 A 的检查命令）；
5. 建 `docs/AIWorkLogs/`（本阶段已建）与每 WP 一份施工文档模板。


> **⚠ WP3 前置条件（附录 C-8 实测新增，2026-10-24 23:0x）**
> 任何贴图压缩/格式改造**必须先修** `Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:25` 的失效判据——它**只比对 mtime、不含 flag**。否则补了 `kDefaultBC` 之后已存在的 `.dds` 不会重编译，会静默沿用旧格式，表现为「代码改了但画面没变」。跳步会得到「假通过」。

### 4.3 为什么不能「先修完缺陷再动结构」

三个理由，每一个都被实测支撑：

1. **有 4 条缺陷的正确修法就是 WP 本体**（表下说明），单独修 = 写两遍；
2. **结构未解环前，修缺陷会加深耦合**：例如 B-07 若在旧布局上修好纹理槽，WP3 换布局时护栏必须重做一遍；
3. **并行会话正在修**：附录 A 实测已有 5 条（B-03/B-11 可能/B-16/B-17 等）被改掉，说明缺陷清单**会腐烂**——它必须配合 §1-J3 的复核机制使用，而不是当一次性任务清单。

## §6 不许抄清单（合并 03 §3.4 与各 RB §6 的「规模不匹配」）

本节存在的理由：约束文档明确禁止「只复制目录/类名/接口形式」，而 WE 的**规模是本项目的 10–30 倍**（WE 核心 15.2 万行 vs 本项目引擎约 2 万行）。下面每一项都写清「为什么不适用」，而不是「不采用」。

| # | WE 的做法 | 为什么不适用（理由） | 本项目替代 | 来源 |
|---|---|---|---|---|
| N1 | **多后端抽象**（`wiGraphicsDevice` 92 个虚函数，Vulkan 9,141 行 / Metal 5,245 行） | 50% 的接口面积对单后端是纯负担；本项目只有 D3D12 | **21 方法薄 RHI** | RB4 §6.1 |
| N2 | **bindless 全局描述符堆**（100 万 CBV/SRV/UAV + 2048 sampler） | 容量需求来自编辑器加载海量资产；WE 自己也要保留退化路径 | 有界 4096 槽 + **索引 0 永久 null**，不够再加 | RB4 §6.2 |
| N3 | **AliasingAllocator**（RT 别名复用） | 省约 32MB 换一类新的同步 bug；教学项目里认知成本大于收益 | **不做**；先做 RT 池复用（同尺寸同格式复用） | RB4 §6.4 |
| N4 | **四条队列 + 独立 COPY 队列** | 服务多线程录制与全平台；本项目单线程录制 | 单图形队列；帧内 copy 与绘制同队列 + 一次 fence | RB5 §6.3 |
| N5 | **帧计数延迟销毁法**（`entry.tag + BUFFERCOUNT < FRAMECOUNT`） | 依赖 4 条硬前提（每帧每队列恰 Signal / Signal 覆盖全部队列 / 帧尾互 Wait / 命令列表不跨帧），任一被破即静默泄漏；且隐式不可测 | **单队列 + 单调 fence 完成值**（项目已有 `ExecuteCommandList` 返回值与 `IsFenceComplete` 路由） | RB5 §7、C3 |
| N6 | **ECS + ComponentManager⟨T⟩**（`wiScene.h:33-68` 约 40 个管理器） | 40 个管理器模板样板；swap-and-pop 打乱索引（`wiECS.h:324-344`）让教学调试困难 | `std::vector` + 空闲槽表，**保留「稳定句柄 + 组件互引」语义** | RB3 §6.1 |
| N7 | **全局几何池 suballocation**（`wiScene_Components.cpp:1217-1234`） | 绘制侧引入三重偏移 + ALIASING_BUFFER，教学不直观 | 每 mesh 独立 `GpuBuffer`，保留 `Mesh::vbOffset/ibOffset` | RB3 §6.2 |
| N8 | **材质 384B 半精度打包 + bindless 数组** | 打包规律靠注释维护，位域语义无 static_assert 保护 | **显式结构体 + `static_assert(sizeof)`**；槽位枚举编译期钉死 | RB6 §2、C1 |
| N9 | **全局 Scene 单例 + 全局后缓冲** | 单例让「多场景/多视口」不可测，并隐藏数据流 | 可实例化 `Scene::Scene` + 默认访问器；后缓冲**显式传参** | RB9 §7.5、RB3 §7.3 |
| N10 | **编辑器与 UI 全家桶**（`wiGUI` 6,480+1,117 行、`wiFont`/`wiImage`、`wiBacklog` 屏幕控制台、`ModelImporter` 7,212 行 + 4 个第三方库） | 属于**编辑器可执行目标**，不是引擎层；抄进来会把工具链耦合进 RHI/Scene | **不引入编辑器**；只抄 `wiBacklog` 的「等级 + 落盘 + 崩溃无锁遍历」与 `wiProfiler` 约 200 行内核 | RB9 §6/§7.5 |
| N11 | **Lua 绑定 + 15+ 命令行表 + fade/多窗口** | 约 25,000 行脚本绑定层；本项目无脚本需求 | 不做；需要的开关走配置文件 | 01B §10.2 |
| N12 | **mesh shader / VRS / sparse / video 类 RHI 接口**（RB4 判定 28 个可砍虚函数） | 无硬件与需求支撑；留着就是永远不测的代码 | **砍掉**（或延后到有明确 Demo） | RB4 §2.3 |
| N13 | **GPU 端 MIP/BC/流送**（`IMPORT_STREAMING`、mip 反馈、后台线程） | 面向 GB 级开放世界资产 | 本期**离线**压缩 + 主线程烘焙；先消灭同步卡顿（B-20） | RB8 §7.7 |

| N15 | **后处理必须共用统一接口** | 约束文档原则②明确允许专用实现 | 只有 `src/dst + 参数结构` 是硬约定；DoF/TAA 等允许专用签名 | RB7 §7、原则② |

**反面提醒**：N15 是唯一一条「WE 没做错、但也不能照抄」的项——WE 的后处理签名五花八门（尤其 TAA 把双缓冲藏在资源包内部，`wiRenderer.h:888-897`），本项目**起步**应统一，但**不要**为了统一而把 TAA/DoF 硬塞进一个不合适的通用签名。

## 附录 C：WE 技术目录落地后的九条修正与闭合（2026-10-24 22:3x A4 卷 / 23:0x A5 卷实测回写）

### C-1 RTShadow 不是独立实现，是屏幕空间阴影的宏变体

`shaders/rtshadowCS.hlsl` 全文仅 3 行：

`@hlsl
#define RTAPI
#define RTSHADOW
#include "screenspaceshadowCS.hlsl"
`@

**影响**：§6 若把 RTShadow 与 ScreenSpaceShadow 当两套资产分别估工，会重复计算。实际是**一份着色器 + 两个宏**。遮罩打包共用：`screenspaceshadowCS.hlsl:9` 的 `MAX_RTSHADOWS = 16`，每光源 8 bit（`:298-301`），RTShadow 侧再压成 tile 位掩码（`:309-319`）。降噪不对称：前 4 个光源走完整时空降噪（含 velocity 补偿，`rtshadow_denoise_temporalCS.hlsl:116-119`），第 5–16 个只做 lerp。**归属**：WP8 成本按 1 份实现估。

### C-2 全部 GI 与后处理共用同一块常量表（WP8 的直接范本）

`shaders/ShaderInterop_Postprocess.h:43-67` 用宏把同一组 `params0/1` 在四类 GI 中取不同名字：`ssao_range` = `rtdiffuse_range` = `rtreflection_range`；`ssr_frame` = `ssgi_frame` = `rtdiffuse_frame`。

**影响**：WP8 的 `PostProcessConstants` 不需要每效果一张 CB，**一张 8-DWORD 表 + 字段宏别名**即可覆盖全部后处理与 GI，可省掉多个 CB 绑定槽。与 D15 一致。**归属**：WP8 按单表组织。

### C-3 GI 消费侧的三条硬规则（此前完全缺失）

GI 怎么用不在 GI 着色器里，在光栅着色器里（`objectHF.hlsli:1022-1036`、`shadingHF.hlsli:125-175`）：

| 规则 | 内容 | 证据 |
|---|---|---|
| R1 | **漫反射 GI 互斥**：第一个置位 `IsGIApplied()` 的 GI 整替换 `indirect.diffuse`，后续 DDGI/VXGI/Surfel 跳过 | `shadingHF.hlsli:125` |
| R2 | **镜面 GI 叠加**：`indirect.specular = gi.rgb * F + old * (1 - gi.a)`，alpha 混合并乘菲涅耳 | `objectHF.hlsli:1025` |
| R3 | **DDGI 无条件采样**：它顺带产出 `dominant_lightdir`，即使已被别的 GI 覆盖也要调用 | `shadingHF.hlsli:125-175` |

**影响**：WP5/WP6 接入任何 GI 之前，必须先有统一的 `indirect` 结构（diffuse / specular / occlusion / dominant_lightdir）与 `IsGIApplied` 位。**归属**：WP5 的材质光照输出必须预留这四字段。
