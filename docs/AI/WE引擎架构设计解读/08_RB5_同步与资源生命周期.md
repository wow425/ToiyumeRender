**核心研究问题的答案（先给结论）**：WE 保证"GPU 还在用的资源不会被释放"的手段**不是一个**而是**三套并存的机制**：
1. **帧计数延迟释放**（主机制）：资源析构时只把 COM 指针搬进 `AllocationHandler` 的 10 个 `deque`，真正的 `Release` 推迟到 `tag + BUFFERCOUNT < FRAMECOUNT` 成立的那一帧帧末（`wiGraphicsDevice_DX12.h:582-636` [实测]）。其正确性完全依赖 `SubmitCommandLists` 末尾的**无条件帧首 CPU 阻塞**（`wiGraphicsDevice_DX12.cpp:5534-5546` [实测]）。
2. **fence 完成值回收**（精确机制）：异步拷贝队列的 worklist 用 `fence->GetCompletedValue() >= entry.fenceValue` 回收（`wiGraphicsDevice_DX12.cpp:5550-5558` [实测]）、shader-visible 描述符堆环用自建 fence 判据（`wiGraphicsDevice_DX12.h:489-495`、`wiGraphicsDevice_DX12.cpp:1930-1943` [实测]）。
3. **帧内存 ring 的"不回收"策略**：`AllocateGPU` 只增 offset，靠每帧 `reset()` 归零（`wiGraphicsDevice.h:347-389`、`wiGraphicsDevice_DX12.h:230` [实测]），安全性同样来自机制 1 的帧阻塞。

## §1 职责边界

### 1.1 本机制负责（Yes）
- **资源销毁侧的延迟**：`~Resource_DX12` / `~QueryHeap_DX12` / `~PipelineState_DX12` / `~RTPipelineState_DX12` / `~VideoDecoder_DX12` 的 COM 对象不是立刻释放，而是入队等待"确定不再被 GPU 引用"`wiGraphicsDevice_DX12.cpp:1467-1474, 1495-1496, 1550-1552, 1578-1579, 1614-1616` [实测]。
- **帧环深度与生产-消费节流**：`BUFFERCOUNT=2` 决定 CPU 最多领先 GPU 几帧，以及销毁延迟的下界 `wiGraphicsDevice.h:72` [实测]。
- **GPU 可见的描述符堆环**：`DescriptorHeapGPU` 的 ring 分配与 wrap 前等待（自建 fence + 三级缓存检查）`wiGraphicsDevice_DX12.h:471-497`、`wiGraphicsDevice_DX12.cpp:1930-1943` [实测]。
- **帧内动态内存（上传堆）的分配与重置**：`GPULinearAllocator` / `AllocateGPU` / `UpdateBuffer` / `BindDynamicConstantBuffer` `wiGraphicsDevice.h:328-389` [实测]。
- **资源状态迁移的执行**：显式 `GPUBarrier` 的落地（`CommandList_DX12::Barrier`）与 RenderPass 隐式 barrier 的生成与提交 `wiGraphicsDevice_DX12.cpp:7197-7330, 6031-6050, 6300-6378` [实测]。

### 1.2 本机制不负责（No，明确排除，避免误迁移）
- **不管资源内容/描述符内容的生命周期**：延迟队列只推迟 COM `Release`；`destroy_subresources()` 里的 srv/uav/rtv/dsv 描述符是**立即**销毁的 `wiGraphicsDevice_DX12.cpp:1427-1458` [实测]。
- **不管时钟/呈现节流**：vsync/tearing 由 `Present` 参数决定 `wiGraphicsDevice_DX12.cpp:5472-5506` [实测]；`WaitForGPU` 是独立的"全停"工具且**不使用** `frame_fence` `wiGraphicsDevice_DX12.cpp:5813-5832` [实测]。
- **不管交换链 backbuffer 轮转**：`GetBufferIndex()`（帧环槽位）与 `SwapChain_DX12::GetBufferIndex()`（backbuffer 索引）是**两个不同函数**，WE 应用层把交换链设为 3 缓冲而帧环仍是 2 `wiGraphicsDevice.h:147`、`wiGraphicsDevice_DX12.cpp:1595`、`wiApplication.cpp:836` [实测]。
- **不管命令列表录制内容的正确性**：它只保证"提交边界"的可见性；同一帧内两个 pass 之间的状态翻转必须由上层显式 `PushBarrier` 表达 `wiRenderer.cpp:91-104` [实测]。
- **不做设备丢失后的优雅回收**：device removed 直接 `wi::platform::Exit()`，10 个销毁队列**不被排空** `wiGraphicsDevice_DX12.cpp:5809` [实测]。

## §3 调用链（入口 → GPU 命令，逐步骤 file:line）

**A. 创建**（资源本身不参与延迟机制；创建时只登记它不是"可立即释放"的）
1. 上层 `device->CreateTexture/Buffer/...` → `Resource_DX12` 构造；D3D12MA 分配落在 `allocation`，D3D12 资源落在 `resource`（`wiGraphicsDevice_DX12.cpp:1467-1474` 的析构里可见这两个成员的存在）[实测]。
2. 设备初始化时先建 10 把帧 fence，全部初值 0（`wiGraphicsDevice_DX12.cpp:2682-2706`）[实测]；注册设备移除回调（`wiGraphicsDevice_DX12.cpp:1644-1650`）[实测]。

**B. 使用（录制期，FRAMECOUNT == n）**
3. `BeginCommandList` → `commandlist.reset(GetBufferIndex())`（`wiGraphicsDevice_DX12.cpp:5299`）→ `CommandList_DX12::reset(bufferindex)` 里 `frame_allocators[buffer_index].reset()` 并清空各类 barrier 向量（`wiGraphicsDevice_DX12.h:224-260, 230`）[实测]。
4. 每帧开始时命令分配器与命令列表统一 Reset（`wiGraphicsDevice_DX12.cpp:5373-5378`）[实测]：⇒ **命令列表不跨帧存活**，这是"帧计数即可代表提交边界"的前提之一。
5. 动态上传：`AllocateGPU(dataSize, cmd)` 走 `GetFrameAllocator(cmd)`，只增 offset，空间不足时按 `(旧size+dataSize)*2` 对齐新建（`wiGraphicsDevice.h:347-389`）[实测]。
6. 状态迁移：`device->Barrier(barriers, count, cmd)` → `CommandList_DX12::Barrier` **只把转换过的 `D3D12_RESOURCE_BARRIER` 记进 `commandlist.frame_barriers`**（`wiGraphicsDevice_DX12.cpp:7197-7201`）[实测]；`layout_before == UNDEFINED` 时额外登记 `Discard` 并把 StateBefore 换成资源真实布局（`wiGraphicsDevice_DX12.cpp:7260-7285`）[实测]。
7. RenderPass：`RenderPassBegin(images, ...)` 生成隐式 begin barrier 并**立即** `ResourceBarrier(begin...)`（`wiGraphicsDevice_DX12.cpp:6079, 6300-6334, 6375-6378`）[实测]；`RenderPassEnd` 提交 end barrier（`wiGraphicsDevice_DX12.cpp:6336-6372, 6541-6546`）[实测]。

**C. 提交（帧 n 末尾，FRAMECOUNT 即将变成 n+1）**
8. `SubmitCommandLists()` 入口（`wiGraphicsDevice_DX12.cpp:5388`）→ `Close()` 本帧全部命令列表并按队列攒批（`wiGraphicsDevice_DX12.cpp:5394-5410`）[实测]。
9. `frame_fence_values[GetBufferIndex()]++`（`wiGraphicsDevice_DX12.cpp:5458`）→ 每个非空队列 `queue.submit()` 后 `queue->Signal(frame_fence[槽][q], frame_fence_values[槽])`（`wiGraphicsDevice_DX12.cpp:5462-5468`）[实测]。
10. 呈现（仅带 swapchain 的命令列表）：`Present`；失败码为 DEVICE_REMOVED/RESET 则 `OnDeviceRemoved()`（`wiGraphicsDevice_DX12.cpp:5472-5506`）[实测]。
11. **帧尾全队列互 Wait**：`queues[q1].queue->Wait(frame_fence[槽][q2], frame_fence_values[槽])`（`wiGraphicsDevice_DX12.cpp:5516-5528`）[实测]。
12. `descriptorheap_res/.sam.SignalGPU(graphics queue)`（`wiGraphicsDevice_DX12.cpp:5529`；实现 `wiGraphicsDevice_DX12.h:489-495`）[实测]。
13. **`FRAMECOUNT++`**（`wiGraphicsDevice_DX12.cpp:5530-5531`）——帧号在此翻转，"新帧槽位"从此可见。
14. **帧首 CPU 阻塞**：对全部非空队列 `if (fence->GetCompletedValue() < frame_fence_values[bufferindex]) SetEventOnCompletion(该值, nullptr)`（`wiGraphicsDevice_DX12.cpp:5534-5546`）[实测]——`nullptr` 事件句柄 = 立即阻塞等待。
15. `allocationhandler->Update(FRAMECOUNT, BUFFERCOUNT)`（`wiGraphicsDevice_DX12.cpp:5548`）→ 10 个队列统一判据 `front().second + BUFFERCOUNT < FRAMECOUNT` 后 `pop_front()`（`wiGraphicsDevice_DX12.h:582-636`）[实测]。
16. 异步拷贝 worklist 用**完成值**回收（`wiGraphicsDevice_DX12.cpp:5550-5558`）[实测]。

**D. 标记删除（任意帧 n）**
17. 上层把 `ComPtr`/`GPUBuffer` 值置空 → `~Resource_DX12` 抄起当前帧号 `framecount = allocationhandler->framecount`，把 `allocation`/`resource` **移动**进 `destroyer_allocations`/`destroyer_resources`（`wiGraphicsDevice_DX12.cpp:1467-1474`）[实测]；描述符四件套立即销毁（`wiGraphicsDevice_DX12.cpp:1427-1458`）[实测]。
18. 其他 8 个队列的入队点：queryheap（`:1495-1496`）、pipeline+rootsig（`:1550-1552`）、stateobject（`:1578-1579`）、video decoder heap/decoder（`:1614-1616`）、bindless index（`:1377, 1386`）[实测]。
19. **真正 `Release`**：发生在满足判据的那一帧的第 15 步——队列元素被 `pop_front()`，`ComPtr` 析构 ⇒ COM 引用计数递减 ⇒ D3D12MA 回收。**没有任何显式 `Release()` 调用**。

**E. 排空（仅两处）**
20. `FlushDeallocations()`：基类实现为"连续提交 `BUFFERCOUNT` 次 `SubmitCommandLists()`"（`wiGraphicsDevice.h:438-445`）[实测]；全仓唯一调用点在 `RenderPath2D::DeleteGPUResources()`（`wiRenderPath2D.cpp:21`）[实测]。⚑ **Lead 勘误（依据 10_交叉校验记录 C3，Lead 亲自回源）**：宿主函数是 `wiRenderPath2D.cpp:10-22` 的 `DeleteGPUResources()`，**不是** `~RenderPath2D`；该函数由 `RenderPath3D::Stop()`（`wiRenderPath3D.cpp:1816-1819`）与 `RenderPath3D::ResizeBuffers()`（`wiRenderPath3D.cpp:99`）调用 —— 所以"排空"是被**路径切换与尺寸变更**直接触发的，而不是析构触发的。
21. `~AllocationHandler` → `Update(~0ull, 0)`：判据恒真（`tag + 0 < ~0ull`）⇒ **无视 fence 全部立即释放**（`wiGraphicsDevice_DX12.h:581`）[实测]。等价于"析构时不再有 GPU 工作"的断言。
22. `WaitForGPU()`：建临时 fence，`Signal(0)` 复位后对每个队列（含额外的 copyAllocator 队列）`Signal(fence,1)`+`SetEventOnCompletion(1,nullptr)`（`wiGraphicsDevice_DX12.cpp:5813-5832`）[实测]；`~GraphicsDevice_DX12` 第一件事就是它（`wiGraphicsDevice_DX12.cpp:3089-3098`）[实测]。
23. 交换链 Resize：若已有贴图则 `WaitForGPU()`，再对每张 backbuffer `resource.Reset()`（"forced immediate reset"）并 `textures.clear()`（`wiGraphicsDevice_DX12.cpp:3100-3120`）[实测]；贴图数 = `desc.buffer_count`（`wiGraphicsDevice_DX12.cpp:3152-3153, 3191, 3237, 3296-3298`）[实测]。

## §4 算法与公式

### 4.1 帧号流水线（符号定义）
**[实测] 由 `wiGraphicsDevice_DX12.cpp:5458, 5462-5468, 5531, 5534-5546` 与 `wiGraphicsDevice_DX12.h:582-636` 推出：**
- 记"帧 n 录制期" = `FRAMECOUNT == n` 的代码区间。
- 帧 n 末尾的 `SubmitCommandLists` 顺序是：槽 `s = n mod 2` 的 `frame_fence_values[s]` 自增 → 每队列 `Signal(frame_fence[s][q], frame_fence_values[s])` → 跨队列互 Wait → `FRAMECOUNT++`（变 n+1）→ **等待槽 `(n+1) mod 2` 的 `frame_fence_values`** → `Update(n+1, 2)`。
- 因此帧 n+1 录制期的**入口等待**，等的是"上一次同槽位 Signal 的值"，即**帧 n-1 帧末**发出的信号。
- ⟹ **结论（帧首保证）**：进入帧 G 录制期时，GPU 已完成 {0, 1, …, G−2} 帧的全部非空队列工作。`[推断]`（由代码路径推出，未运行验证）

### 4.2 延迟销毁判据：精确公式
**[实测]** `wiGraphicsDevice_DX12.h:582-636`
```
释放条件（对 10 个队列统一）:
    entry.tag + BUFFERCOUNT < FRAMECOUNT
其中 entry.tag = 该资源被标记删除那一帧的帧号（allocationhandler->framecount）
     BUFFERCOUNT = 2, FRAMECOUNT = 本帧帧号 + 1（已自增）
```
**求释放时刻**：设资源在帧 n 被标记删除（`tag = n`），在帧 m 末尾的 `Update` 中比较，此时 `FRAMECOUNT = m+1`：
```
n + 2 < m + 1  ⟺  n < m − 1  ⟺  m ≥ n + 2
```
⟹ 该资源在**帧 n+2 帧末**被真正释放。

**安全性**：帧 n+2 录制期入口的帧首保证（§4.1）是"GPU 已完成帧 ≤ n"；而该资源只可能在帧 ≤ n 的录制期被引用（帧 n+1 及以后它已从上层句柄消失）。所以释放时其全部使用都已完成 ⇒ **不会 use-after-free**。

**紧性（为什么不是 +1）**：把判据换成 `tag + 1 < FRAMECOUNT`：
```
n + 1 < m + 1  ⟺  m ≥ n + 1   ⟹ 帧 n+1 帧末就释放
```
但帧 n+1 录制期入口只保证"GPU 已完成帧 ≤ n−1"（§4.1，把 G=n+1 代入得 G−2=n−1）。**帧 n 提交的命令此刻可能仍在执行**，而该资源正是在帧 n 被最后一次引用 ⇒ **必然有 use-after-free 窗口**。故 `+BUFFERCOUNT` 不是保守冗余，而是**正确性的下确界**：销毁延迟必须 ≥ 帧环深度。`[推断]`（推导，未运行验证）

| P2 | 帧首阻塞遍历**全部** `QUEUE_COUNT` 个队列（不是只等图形队列） | `wiGraphicsDevice_DX12.cpp:5539-5545` [实测] |
| P3 | 帧尾"每个队列对其他每个队列 `Wait`"，保证跨队列可见性（否则 A 队列完成不代表 B 队列看到 A 的写） | `wiGraphicsDevice_DX12.cpp:5516-5528` [实测] |
| P4 | 所有可能接触该资源的 GPU 工作都经由 `SubmitCommandLists` 提交，且命令列表**不跨帧存活**（每帧 Reset） | `wiGraphicsDevice_DX12.cpp:5299, 5373-5378` [实测] |

**一旦破坏任何一条，判据即失效**：P1 被破坏则 fence 值不再对应帧号；P2 被破坏则某些队列可以落后任意多帧；P3 被破坏则在多队列下"帧完成"不再是全局概念；P4 被破坏（例如持有一个命令列表录两帧再提交）则 tag 帧号低估了实际使用时刻。

### 4.4 帧首阻塞的位置与代价
- **位置**：`SubmitCommandLists` 的最后 1/3 处（`wiGraphicsDevice_DX12.cpp:5534-5546`），**在 `FRAMECOUNT++` 之后、`Update` 之前**，即"已经算作新帧，但还没让新帧跑起来"的时刻。`[实测]`
- **形式**：`fence->SetEventOnCompletion(value, nullptr)` —— 注释明写 `// nullptr event handle will simply wait immediately`（`wiGraphicsDevice_DX12.cpp:5538`）[实测]，**直接在调用线程上阻塞**，不是轮询也不是事件等待。
- **代价**：
  1. CPU 最多领先 GPU **2 帧**（帧环硬上限）；GPU 忙时 CPU 在 `SubmitCommandLists` 内被拖住 ⇒ 无法"提前录制下一帧"来填满 GPU 气泡。`[推断]`
  2. 帧尾**全队列互 Wait** 会把队列重叠限制在**帧内**，注释自己承认 `// Note: it disables overlapping queues into the next frame`（`wiGraphicsDevice_DX12.cpp:5517`）[实测] ⇒ 跨帧的 compute/copy 并行被牺牲，换来的是"帧完成"这个简单可靠的语义。
  3. 但帧首阻塞**不消耗额外线程/事件对象**（`nullptr` 事件），实现代价极低。`[实测]`
- 与之对比，`WaitForGPU` 走的是"临时 fence + 事件 + 1 次 signal"的独立路径，**完全不用 `frame_fence`**（`wiGraphicsDevice_DX12.cpp:5813-5832`）[实测] ⇒ 说明 WE 自己也把"帧环语义"和"全停语义"当作两套东西。

### 4.5 `FlushDeallocations` 的等价公式
```cpp
void FlushDeallocations() { for (uint32_t i = 0; i < BUFFERCOUNT; ++i) SubmitCommandLists(); }  // wiGraphicsDevice.h:438-445 [实测]
```
**推导（原推导有 off-by-one，⚑ Lead 已修正，依据 10_交叉校验记录 C3）**：`Update` 的判据是 `tag + BUFFERCOUNT < FRAMECOUNT`，而 `Update` **收到的是自增后的** `FRAMECOUNT`（`wiGraphicsDevice_DX12.cpp:5531` 先 `FRAMECOUNT++`，`:5548` 再调 `Update(FRAMECOUNT, BUFFERCOUNT)`）。设调用发生在帧 F（此时 `allocationhandler->framecount == F`，故当帧退役的资源 `tag = F`）：

| 第几次 `SubmitCommandLists` | `FRAMECOUNT` 变为 | `Update` 收到的值 | 实际排空条件 |
|---|---|---|---|
| 1 | F+1 | F+1 | `tag ≤ F−2` |
| 2 | F+2 | F+2 | `tag ≤ F−1` |

⟹ `FlushDeallocations` 能排空的是 **`tag ≤ FRAMECOUNT_now − 1`** 的条目（原文写成 `tag ≤ FRAMECOUNT_now`，多算了一帧）；**当帧刚退役的条目（`tag = F`）排不掉**，它们仍由 2 帧后的常规 `Update` 回收。

**真正的兜底是 `~AllocationHandler` 里的 `Update(~0ull, 0)`**（`wiGraphicsDevice_DX12.h:578`，注释 `// destroy all remaining`）：`BUFFERCOUNT = 0` 使判据恒真，连当前帧条目一并释放。同时也隐含"每次 `SubmitCommandLists` 都阻塞到帧首保证"，所以排空**同时**保证了 GPU 已追上。`[推断]`（公式推导，Lead 已按源码修正）

### 4.6 失效条件
1. **device removed**：帧 fence 永不前进，帧首 `SetEventOnCompletion(..., nullptr)` 会**永久阻塞**当前线程；WE 的处置是在 Present 返回 DEVICE_REMOVED/RESET 时 `OnDeviceRemoved()`（`wiGraphicsDevice_DX12.cpp:5472-5506, 5561`）→ 收集 DRED 面包屑与页错误分配信息并打日志（`wiGraphicsDevice_DX12.cpp:5694-5800`）→ **`wi::platform::Exit()`**（`wiGraphicsDevice_DX12.cpp:5809`）[实测]。⇒ 10 个销毁队列**不会被排空**，进程直接退出，由 OS 回收进程内存与 GPU 资源。
2. **多队列（超出 `QUEUE_COUNT` 的队列）**：帧计数法只覆盖 `frame_fence[buffer][QUEUE_COUNT]` 里的 5 个队列。WE **自己额外建了一个不在枚举内的 COPY 队列** `copyAllocator.queue`（`wiGraphicsDevice_DX12.cpp:1690-1706`，创建失败即 `wilog_messagebox(... [CopyAllocator] ...) + wi::platform::Exit()` `:1702-1703`）[实测]。这个队列**不参与**帧首阻塞与帧尾互 Wait 的循环，所以它的资源**只能用 fence 完成值回收**：`while (front().fence->GetCompletedValue() >= front().fenceValue)`（`wiGraphicsDevice_DX12.cpp:5550-5558`）[实测]，提交侧在 `CopyAllocator::submit` 里 `cmd.fenceValue++`→`Signal`→（若 `wait_cpu` 则直接等完成）否则让所有主队列 `Wait` 它并把它推入 `async_worklist`（`wiGraphicsDevice_DX12.cpp:1756-1795`）[实测]。
   ⟹ **结论**：`QUEUE_COUNT` 之外的队列一律必须走"完成值"路径，帧计数法对它们是**不安全**的（不是"不精确"，是**会提前释放**）。`[推断]`
3. **描述符槽位不在保护范围内**：延迟队列只推迟 COM `Release`；`destroy_subresources()` 里的 srv/uav/rtv/dsv 立即 `destroy()`（`wiGraphicsDevice_DX12.cpp:1427-1458`）、静态描述符分配器的 `free` 只是 `freelist.push_back(index)`（`wiGraphicsDevice_DX12.h:552-558`）[实测]。⇒ 如果 GPU 仍会读旧命令流里的描述符**内容**，这里没有任何保护。`[推断]`（见 §8 第 2 条）
4. **`present`/resize 的强停**：Resize 直接 `WaitForGPU()` + `resource.Reset()`（`wiGraphicsDevice_DX12.cpp:3100-3120`）[实测]，**绕过**帧计数机制 —— 因为它必须立即重绑交换链缓冲，等不起 2 帧。

## §5 资源与同步

### 5.1 帧环：BUFFERCOUNT / FRAMECOUNT / fence 完成值的流转
**三者的语义分工** `wiGraphicsDevice.h:72-73, 145-147`、`wiGraphicsDevice_DX12.h:134-135` [实测]：
- `FRAMECOUNT` = **提交计数**（设备全程单调），是"唯一时间轴"；`[实测]` `wiGraphicsDevice_DX12.cpp:5531`
- `BUFFERCOUNT` = **槽位数**（=2），把时间轴模成环形；`GetBufferIndex() = FRAMECOUNT % BUFFERCOUNT` `[实测]` `wiGraphicsDevice.h:147`
- `frame_fence_values[s]` = 槽 s 的**信号次数**；因为每帧只对当前槽 +1，所以它**恰好等于该槽上次使用时的帧号+1**，即"该槽最近一次提交的完成凭据"。`[推断]`（由 5458/5468/5534 三处推出）

**帧 n 末尾（`SubmitCommandLists`）发生的事，按执行顺序** `wiGraphicsDevice_DX12.cpp:5458-5548` [实测]：
| 序 | 动作 | 行号 |
| --- | --- | --- |
| 1 | 关列表、按队列攒批、有依赖先提交 | 5394-5410 |
| 2 | `frame_fence_values[槽]++` | 5458 |
| 3 | 每队列 `Signal(frame_fence[槽][q], frame_fence_values[槽])` | 5462-5468 |
| 4 | `Present`（仅 swapchain 命令列表） | 5472-5506 |
| 5 | 每队列 `Wait` 其他每队列的同槽 fence | 5516-5528 |
| 6 | `SignalGPU`（描述符堆 fence） | 5529 |
| 7 | `FRAMECOUNT++`（槽位翻转） | 5531 |
| 8 | **阻塞**到槽 `FRAMECOUNT%2` 的 fence ≥ `frame_fence_values[该槽]` | 5534-5546 |
| 9 | `Update(FRAMECOUNT, BUFFERCOUNT)` 排空到期的销毁队列 | 5548 |
| 10 | 按完成值回收异步拷贝 worklist | 5550-5558 |

**关键因果**：第 8 步等的值来自**两帧前**的第 3 步（同槽位）⇒ 第 9 步执行时，CPU 可以安全地认为"帧号 ≤ FRAMECOUNT−2 的那些帧已经跑完"。**销毁判据（§4.2）就是这句话的直接翻译**。

### 5.2 内存 ring：`AllocateGPU`
- **分配** `wiGraphicsDevice.h:347-389` [实测]：`dataSize==0` 直接返回无效；取 `GetFrameAllocator(cmd)`（per-CommandList × per-槽位）；`free_space = buffer.desc.size − offset`；不足时新建 UPLOAD buffer，`desc.size = align((旧size + dataSize) * 2, alignment)` ⇒ **几何式增长，永不缩小**；`data = mapped_data + offset`；`offset += align(dataSize, alignment)`。
- **回收**：**没有回收**。唯一重置点是 `GPULinearAllocator::reset()`（`offset = 0`，`wiGraphicsDevice.h:230`），由 `CommandList_DX12::reset(bufferindex)` 在每帧 `BeginCommandList` 时调用 `wiGraphicsDevice_DX12.cpp:5299` [实测]。
- **与帧资源的绑定**：绑定的是**槽位**（`GetBufferIndex()`），不是帧号 ⇒ 同一槽位在帧 n 与帧 n+2 复用同一批 buffer。`[实测]` `wiGraphicsDevice_DX12.h:466-469`
- **安全性来源**：复用槽位发生在帧 n+2 的 `reset`，而该时刻的帧首保证是"帧 ≤ n 已完成"（§4.1）⇒ 旧帧对这些上传数据的读取已结束。**⇒ `AllocateGPU` 不带任何 fence，完全寄生在 §4.3 的 P2/P4 上**。`[推断]`
- **失败/爆增行为**：单帧分配超过上一帧 buffer 大小则当帧就 realloc（不会失败到上层，可能一次申请 2×），旧 `GPUBuffer` 由 COM 管理（其释放走 `destroyer_* `? 注意：`GPUBuffer` 是引擎对象不是 `Resource_DX12`，其内部 ID3D12Resource 的释放路径未逐行确认，见 §8 第 5 条）。`[推断]`

### 5.3 描述符堆 ring：第二套"预算环"（按需等待，而非无条件阻塞）
- shader-visible 全局堆 `DescriptorHeapGPU`：`std::atomic<uint64_t> allocationOffset{0}` + 自建 `ID3D12Fence` + `fenceValue` + `cached_completedValue` `wiGraphicsDevice_DX12.h:471-497` [实测]。
- 每帧末 `SignalGPU(graphics queue)`：`fenceValue = allocationOffset.load(); queue->Signal(fence, fenceValue); cached_completedValue = fence->GetCompletedValue();` `wiGraphicsDevice_DX12.h:489-495`、调用点 `wiGraphicsDevice_DX12.cpp:5529` [实测]。
- 环分配前的**三级检查** `wiGraphicsDevice_DX12.cpp:1930-1943` [实测]：① 用缓存的 `cached_completedValue % wrap_effective_size` 做免锁快速判断；② 相交才真调 `fence->GetCompletedValue()` 复核；③ 仍相交才 `SetEventOnCompletion(heap.fenceValue, nullptr)` 实等。设计意图注释见 `wiGraphicsDevice_DX12.cpp:1900-1920` [实测]。
- **对比价值**：这是"**只在真正绕回时才阻塞**"的写法，与帧首阻塞（无条件）形成对照 ⇒ §7 建议本项目采用前者。`[推断]`

### 5.4 barrier 的两个来源、共存方式与责任划分
**来源 A：显式 `GPUBarrier`** `wiGraphics.h:683-762` [实测]
- 四个工厂：`Memory(resource=nullptr)`（UAV 屏障）、`Image(texture, layout_before, layout_after, mip, slice, aspect)`、`Buffer(buffer, state_before, state_after)`、`Aliasing(resource_before, resource_after)` `wiGraphics.h:683-762` [实测]。
- 落地：`CommandList_DX12::Barrier` **只做记录**，把转换后的 `D3D12_RESOURCE_BARRIER` 推进 `commandlist.frame_barriers` `wiGraphicsDevice_DX12.cpp:7197-7201` [实测]；`layout_before == UNDEFINED` 的 IMAGE 屏障会被额外登记为 `Discard`（并复制一份到 `renderpass_barriers_begin_after_discards` 语义）`wiGraphicsDevice_DX12.cpp:7260-7285` [实测]。
- 记录后会**按目标队列类型裁剪状态**：COMPUTE 队列清掉 PIXEL_SHADER_RESOURCE 位；COPY 队列把非 COPY_SOURCE/COPY_DEST 的状态压成 COMMON；VIDEO_DECODE 同理 `wiGraphicsDevice_DX12.cpp:7197-7330` [实测]。
- 上层辅助函数 `PushBarrier` 会**丢弃 `before == after` 的空屏障** `wiRenderer.cpp:99-104` [实测]；典型调用点：editTex 的 SRV↔UAV 翻转 `wiRenderer.cpp:3540, 3583`、3D_WIND/INDIRECT_DEBUG/帧常量缓冲 `wiRenderer.cpp:5187-5214, 5238`、`wiRenderer.cpp:5371` [实测]。

**来源 B：`RenderPassBegin/End` 隐式 barrier** `wiGraphicsDevice_DX12.cpp:6031-6050, 6079` [实测]
- images 版入口 `:6079`；swapchain 版自建 barrier 并**立即** `ResourceBarrier(1,&barrier)` `:6031-6050`。
- `LoadOp` → `BEGINNING_ACCESS_TYPE_{PRESERVE,CLEAR,DISCARD}`、`StoreOp` → `ENDING_ACCESS_TYPE_{PRESERVE,DISCARD}`，并转成 `D3D12_RENDER_PASS_RENDER_TARGET_DESC`/`DEPTH_STENCIL_DESC` `wiGraphicsDevice_DX12.cpp:6117` 起 [实测]。
- **begin barrier 生成规则** `wiGraphicsDevice_DX12.cpp:6300-6334` [实测]：`before = _ParseResourceState(image.layout_before)`、`after = _ParseResourceState(image.layout)`（RESOLVE 时取 RESOLVE_DEST）；**仅当 `before != after` 才生成**；`subresource >= 0` 时按 mip×slice **展开成多条**，否则用 `ALL_SUBRESOURCES`。
- **end barrier 生成规则** `wiGraphicsDevice_DX12.cpp:6336-6372` [实测]：`before = image.layout`（RESOLVE 时为 RESOLVE_DEST）、`after = image.layout_after`；推入 `renderpass_barriers_end`。
- 提交时机：begin 在 `RenderPassBegin` 内**立即** `ResourceBarrier(begin.size(), begin.data())` `wiGraphicsDevice_DX12.cpp:6375-6378`；end 在 `RenderPassEnd` `wiGraphicsDevice_DX12.cpp:6541-6546` [实测]。resolve 另有专表 `resolve_src_barriers` `wiGraphicsDevice_DX12.cpp:6491-6492, 6528, 6543-6546` [实测]。
- 命令列表上的五组记录容器 `wiGraphicsDevice_DX12.h:204-217` [实测]：`frame_barriers / discards / renderpass_barriers_begin / renderpass_barriers_begin_after_discards / renderpass_barriers_end / resolve_src_barriers`。

**共存方式与责任划分（结论表）**
| 场景 | 谁负责生成 | 证据 |
| --- | --- | --- |
| RTV/DSV 在 pass 开始/结束的状态迁移 | **框架**（RenderPassBegin/End 按 `layout_before/layout/layout_after` 自动生成） | `wiGraphicsDevice_DX12.cpp:6300-6378, 6541-6546` [实测] |
| 纹理被当作 SRV/UAV 读写时的翻转 | **上层显式 `GPUBarrier`** | `wiRenderer.cpp:3540, 3583, 5187-5214` [实测] |

⇒ **责任划分一句话**：**"pass 边界上的 RTV/DSV 布局"归框架，"资源作为 SRV/UAV/COPY 的角色与内存依赖"归调用者。** 框架只做 `before != after` 的机械转换，不做跨 pass 语义推导。`[推断]`

## §6 可迁移性判定（三选一 + 理由 + 替代方案）

### 6.1 延迟销毁队列 —— 判定：**必需**
- **理由**：本项目当前是"析构即 `Release`"：`~GpuResource(){Destroy();}` → `m_pResource = nullptr` `Engine/02_RHI/Resource/GpuResource.h:28-35` [实测]。GPU 仍在执行上一批命令时，任何上层释放（`Display::Resize` 里循环 `Destroy g_DisplayPlane[i]` `Display.cpp:142-168`、`StructuredBuffer::Destroy` 连带 `m_CounterBuffer.Destroy()` `GpuBuffer.h:116-125`、资源热重载/关卡切换）都会立刻把 D3D12 资源还给分配器 ⇒ 直接 UAF / DEVICE_REMOVED。这是本项目 RB5 级别**唯一的正确性缺口**，不是优化项。
- **不是照搬的理由**：WE 需要 10 个队列是因为它每类对象有**不同的回收附带动作**（bindless 索引回填 `wiGraphicsDevice_DX12.h:578-579`、video decoder heap/decoder 成对 `wiGraphicsDevice_DX12.h:576-577`、D3D12MA Allocation 与 ID3D12Resource 分离 `wiGraphicsDevice_DX12.h:570-571`）。本项目没有 bindless/video/D3D12MA，照搬 10 个队列只是重复模板代码。
- **本项目替代方案**：**1 个类型擦除队列**（`std::deque<std::pair<uint64_t /*fence*/, std::function<void()>>>`），或最多 2 个（资源 / 其余 COM）。回收动作在 lambda 里完成，天然覆盖 `StructuredBuffer` 这种"子对象也要一起延迟"的链式情况。规模判定：WE 的 `deque + pair + 10 份 while` ≈ 70 行模板；本项目等价物 ≈ 30 行。

### 6.2 帧计数判据（`tag + BUFFERCOUNT < FRAMECOUNT`） —— 判定：**可选**（不推荐照搬）
- **理由（可选而非规模不匹配）**：它在 WE 的语境里是正确的（§4.2 已证），并且**成本极低**（无需 fence 查询，只要一个整数比较）。本项目若也建帧环，这条判据同样可成立。**但**它要求三条本项目目前完全没有的设施：① 帧首无条件阻塞 `wiGraphicsDevice_DX12.cpp:5534-5546`；② 帧尾全队列互 Wait `wiGraphicsDevice_DX12.cpp:5516-5528`（WE 注释自认 `disables overlapping queues into the next frame`）；③ 命令列表不跨帧 `wiGraphicsDevice_DX12.cpp:5373-5378`。
- **本项目的更优选择**：项目**已经有**全局单调 fence（`m_pFence` + `m_NextFenceValue`，`CommandListManager.cpp:49-54, 112-122`）+ 队列类型高位编码（`CommandListManager.cpp:10-15`）+ 现成的完成值判据（`front().first <= CompletedFenceValue` `CommandAllocatorPool.cpp:31-58`；`IsFenceComplete(front().first)` `LinearAllocator.cpp:64-80`）。用"**提交时返回的 fence 值**"当 tag，比"帧号"**更精确**（精确到批次而非帧）、**无 2 帧硬节流**、**天然支持多队列**。
- **本项目替代方案**：`entry.tag = ExecuteCommandList(...)` 的返回值（`CommandListManager.cpp:112-122`），回收条件 `g_CommandManager.IsFenceComplete(tag)`（`CommandListManager.h:60-72`）。**只有当**将来因为性能原因确实需要"帧号即凭据"的免查询路径时，再引入帧计数法作为**快速路径**（fence 判据作为兜底）。

### 6.3 `AllocateGPU` ring —— 判定：**可选**
- **理由**：它解决的是"每帧大量动态常量/顶点数据"的分配抖动（`wiGraphicsDevice.h:347-389`，几何增长的 UPLOAD buffer）。本项目目前有 CPU 侧 `LinearAllocator`（`CleanupUsedPages(FenceID)`，`LinearAllocator.cpp:128-143`），但没有 GPU 侧按帧槽位的持久上传缓冲；若上层现在每次动态更新都新建/写整块 buffer，则这是**性能收益明确**的一项，但不是正确性必需项 ⇒ 可选。
- **本项目替代方案**：`GpuUploadRing`：`GPUBuffer` 数组，长度 = `MAX_FRAMES_IN_FLIGHT`（建议 2 或 3），每槽位一个 `offset`；每帧**取当前槽位**，**只在该槽位的 fence 未完成时**才等待（对照 WE 的无条件帧首阻塞 `wiGraphicsDevice_DX12.cpp:5534-5546` 与描述符堆的按需等待 `wiGraphicsDevice_DX12.cpp:1930-1943`，选后者），完成后 `offset = 0`。**不要**照搬"靠帧首阻塞保证安全"（§5.2 的寄生设计）。`[推断]`

### 6.4 Aliasing（`GPUBarrier::Aliasing` + placed resource 复用） —— 判定：**规模不匹配**
- **理由**：WE 的 aliasing 依赖两样本项目没有的东西：① 在同一个 `ID3D12Heap` 内做 placed resource 重绑的分配器（`CreatePlaced` 接口本项目已有 `GpuBuffer.h:16-25` [实测]，但没有任何 heap 复用/别名的调用方）；② `GPUBarrier::Aliasing(resource_before, resource_after)` 的静态别名规则 `wiGraphics.h:683-762`、落地 `wiGraphicsDevice_DX12.cpp:7197-7330`。本项目的规模（学习渲染器、资源数少）根本没有显存压力驱动这种复杂度 ⇒ **不建议现在引入**，引入即引入一整类难查的 bug。
- **本项目替代方案**：保留 `CreatePlaced(ID3D12Heap*, offset)` 作为将来切入点（不加任何新代码）；真需要省显存时先做**资源复用池**（同描述跨帧复用同一个 ComPtr），而不是 aliasing。

### 6.5 多队列 fence —— 判定：**可选**
- **理由**：本项目**已经有**三队列管理器与队列类型编码（Graphics/Compute/Copy，`CommandListManager.h:15-45, 60-80`、`CommandListManager.cpp:10-15`），fence 值里天然带队列类型 ⇒ "per-queue fence + 跨队列 wait"的**基础设施已具备**，只需在启用 compute/copy 队列执行时补两件事：① 资源 tag 取**所有**触碰它的队列 fence 的较大值；② 提交后若两队列间有依赖，用 `StallForFence/StallForProducer`（`CommandListManager.cpp:150-156`）显式表达。若本项目始终只用 graphics 队列，则本项可选、零收益。
- **不要照搬 WE 的做法**：WE 用"帧尾全队列互 Wait"（`wiGraphicsDevice_DX12.cpp:5516-5528`）来让帧计数法在多队列下成立，代价是禁掉跨帧重叠；本项目用**完成值判据**即可，不需要全互 Wait。`[推断]`
- **本项目替代方案**：`DeferredReleaseQueue` 的 tag 类型改为 `uint64_t`（已含队列类型）；若一个资源被多队列使用，入队时取 `max(fenceGraphics, fenceCompute)`（因为 `IsFenceComplete` 只查一个队列的类型位，`CommandListManager.h:60-72`，所以必须保证 tag 来自"最慢的那个队列"）。

## §7 对本项目 WP4 的建议（可施工粒度）

### 7.1 结论先行：用"单队列 + 单调 fence 完成值"，不照搬 WE 的帧计数法
三条理由（均已在 §6.2 给出证据）：① 本项目 fence 基础设施现成且是单调值，扩展成本≈0；② 帧计数法要求"帧首无条件阻塞 + 帧尾全队列互 Wait + 命令列表不跨帧"三件套，会把 CPU 硬性限制在 GPU 后面 2 帧，并禁掉跨帧队列重叠（WE 注释自认 `wiGraphicsDevice_DX12.cpp:5517`）；③ 完成值判据精确到"批次"，且 `IsFenceComplete` 已按队列类型路由，天然可扩展多队列。**代价**：需要一次 `GetCompletedValue()`（可用本地缓存缓解，参照 `CommandListManager.cpp:132-140` 的 `m_LastCompletedFenceValue` 写法）。

### 7.2 新增类型：`DeferredReleaseQueue`（建议放 `Engine/02_RHI/Memory/`）
```cpp
// 语义：持有"已完成提交的 COM 对象"，直到 GPU 越过给定 fence 值
class DeferredReleaseQueue
{
public:
    // fenceValue 必须来自一次已提交的 ExecuteCommandList（见 7.4 契约）
    void Enqueue(uint64_t fenceValue, std::function<void()> deleter);
    // 每帧调用一次：释放所有"提交 fence 已完成"的条目（FIFO，队首不满足即停）
    void Process();
    // resize / shutdown：无视 fence 全部立即释放
    void FlushAll();
    size_t Size() const;
    uint64_t OldestFenceValue() const;   // 用于诊断/断言
private:
    std::mutex m_Mutex;
    std::deque<std::pair<uint64_t, std::function<void()>>> m_Queue; // 单调不减的 fence 值
};
extern DeferredReleaseQueue g_DeferredReleaseQueue;
```
- **回收条件（精确形式）**：
  ```cpp
  while (!m_Queue.empty() && g_CommandManager.IsFenceComplete(m_Queue.front().first)) {
      m_Queue.front().second();   // 真正的 Release 在这里发生
      m_Queue.pop_front();
  }
  ```
  与项目既有判据同构：`CommandAllocatorPool.cpp:31-58`（`front().first <= CompletedFenceValue`）、`LinearAllocator.cpp:64-80`（`IsFenceComplete(front().first)`）[实测]。
- **队列数量**：**1 个就够**（判定与理由见 §6.1）。若追求可读性可拆 2 个：`ResourceRetireQueue`（ID3D12Resource）与 `MiscRetireQueue`（PSO/根签名/query heap）。**不要**照搬 10 个。

### 7.3 `GpuResource::Destroy` 改造（保持现有对外语义）
```cpp
// Engine/02_RHI/Resource/GpuResource.h（现 :28-35）
virtual void Destroy() override {
    if (m_pResource) {                                  // ComPtr<ID3D12Resource>
        ComPtr<ID3D12Resource> dying = m_pResource;     // 拷一份所有权
        g_DeferredReleaseQueue.Enqueue(
            m_RetireFenceValue,                          // 见 7.4
            [dying]() mutable { dying.Reset(); });       // GPU 越过 fence 后才真正 Release
        m_pResource = nullptr;                           // 对上层：立即失效（与今天一致）
    }
    m_GpuVirtualAddress = D3D12_GPU_VIRTUAL_ADDRESS_NULL;
    ++m_VersionID;                                       // 版本号语义不变
}
```
- `m_RetireFenceValue` 是新增成员（`uint64_t`），在资源**被绑定/提交**时由 `GpuResource` 记录"最后一次可能被 GPU 使用"的 fence 值；`Destroy` 时若它仍是 0（资源从未提交使用）⇒ 直接立即 `Release`，**不入队**（这是最常见的加载失败/临时资源路径，避免无谓延迟）。`[推断]`
- 子类只要沿用"先处理自己的成员再调基类"的现有写法即可自动继承延迟语义（范例：`GpuBuffer.h:116-125` 的 `StructuredBuffer::Destroy`）。

### 7.4 WP4 必须写清的契约（关键设计点，WE 没有显式表达）
**问题**：`Destroy` 可能发生在**命令还没提交**的时刻（帧内录制中）。此时"最后一次提交的 fence 值"是上一批的旧值，用它当 tag 会**提前释放**（因为当前正在录制的命令列表还没提交，但已经引用了该资源）。
**建议契约（三选一，取 A）**：
- **A（推荐）延迟取 tag**：帧内析构的资源不立即 `Enqueue`，而是登记到"本帧待退役列表"；帧末 `CommandContext::Finish` / `Display::Present` 之后再统一以**本帧最终提交 fence 值**入队。实现成本 ≈ 一个 `std::vector`。**正确性最强**：tag 必然 ≥ 引用它的那次提交。
- B：`Enqueue` 时若检测到"有未提交的 `GraphicsContext`"，则 tag 取 `m_NextFenceValue`（即"下一次提交将得到的值"），并保证该值确实会被提交出去（需要上层 `Finish`）。风险：若上层随后不提交，tag 永远不满足 ⇒ **泄漏而非崩溃**（可接受的失败方向）。
- C（不推荐）：要求 `Destroy` 只能在帧外调用。契约难维护，且与"PIXEL/资源热重载"的天然用法冲突。
**失败方向原则**：宁可**泄漏**（tag 过高）不可**崩溃**（tag 过低）⇒ 所有不确定场合一律取更大的 fence 值。

### 7.5 帧轮转（本项目版"帧资源环"，无阻塞版）
```cpp
constexpr uint32_t MAX_FRAMES_IN_FLIGHT = 2;                 // 建议 2；不要求等于 SWAP_CHAIN_BUFFER_COUNT(3)
uint64_t m_FrameFenceValues[MAX_FRAMES_IN_FLIGHT] = {};      // 每槽位最后一次 Signal 的 fence 值
uint32_t CurrentFrameSlot() const { return m_FrameIndex % MAX_FRAMES_IN_FLIGHT; }

// 进入新一帧时（Present 之后）：
uint32_t slot = CurrentFrameSlot();
if (m_FrameFenceValues[slot] != 0 &&
    !g_CommandManager.IsFenceComplete(m_FrameFenceValues[slot]))
{
    g_CommandManager.WaitForFence(m_FrameFenceValues[slot]);   // 只在真需要时阻塞
}
m_FrameFenceValues[slot] = /* 本帧最后一批提交返回的 fence 值 */;
```
- 与 WE 的差别（**本项目的设计选择，需在 WP4 文档里写明理由**）：WE 是**无条件**阻塞到"完成 2 帧前"（`wiGraphicsDevice_DX12.cpp:5534-5546`）；本项目是**按需**阻塞（只有当前槽位的 fence 尚未完成才等），代价是"最多 2 帧在飞"这个**弱保证**取代 WE 的"帧号即可信"强保证 ⇒ 但它与 fence 完成值判据配套，不需要强保证。
- `MAX_FRAMES_IN_FLIGHT` 与 `SWAP_CHAIN_BUFFER_COUNT`（=3，`Display.cpp:25`）**解耦**：前者管 CPU 领先与 per-frame 资源槽位；后者管 Present 队列深度。WE 同样是解耦的（帧环 2 `wiGraphicsDevice.h:72` vs 交换链 3 `wiApplication.cpp:836`）[实测]。
- **`g_CurrentBuffer` 的轮转必须补 fence 校验**：现在 `Display::Present` 是 `Present(0,0)` 后立刻 `g_CurrentBuffer = (g_CurrentBuffer+1)%3`（`Display.cpp:230-245`）[实测]，而 `PreparePresentSDR` 下一帧会 `TransitionResource(g_DisplayPlane[g_CurrentBuffer], COPY_DEST)` 并 `CopyBuffer` 进去（`Display.cpp:247-265`）[实测] ⇒ 若 GPU 仍在读这个 backbuffer，写它会与呈现竞争。修法：记录"每个 backbuffer 最后被写入的 fence 值"，轮转到它时先 `IsFenceComplete` 检查再写。

### 7.6 Resize 协议（`Display::Resize`，现 `Display.cpp:142-168`）
**必须顺序**（现有代码已有 `IdleGPU` 两次，只需插入排空）：
1. `g_CommandManager.IdleGPU();`（已有 `Display.cpp:144`）—— 停止所有队列。
2. `for (i) g_DisplayPlane[i].Destroy();`（已有）—— 现在会把 3 个 backbuffer **入队**（改造后语义）。
3. **`g_DeferredReleaseQueue.FlushAll();`（新增，位置必须在 `ResizeBuffers` 之前）** —— 理由：DXGI 要求 `ResizeBuffers` 时应用**不持有任何 backbuffer 引用**，否则返回 `E_INVALIDARG`；"`IdleGPU` 已完成"只说明 GPU 不用了，但 **COM 引用仍在延迟队列里**。这正是"延迟释放"与"resize 必须立即释放"的唯一冲突点，`FlushAll` 是它与 shutdown 的专用逃生门。
4. `s_SwapChain1->ResizeBuffers(SWAP_CHAIN_BUFFER_COUNT, w, h, SwapChainFormat, 0);`（已有）。
5. `GetBuffer(i)` + `CreateFromSwapChain` 重建 3 个 `g_DisplayPlane`（已有）、`g_CurrentBuffer = 0`（已有）、再 `IdleGPU()`（已有）。
6. **清零 `g_DisplayPlane[i]` 的 `m_RetireFenceValue`**，否则会拿旧交换链的 fence 值当 tag（无害但语义错）。`[推断]`

### 7.7 Shutdown 协议（`GameCore::TerminateApplication`，现 `GameCore.cpp:82-88`）
1. `g_CommandManager.IdleGPU();`（已有 `GameCore.cpp:83`）—— 等所有队列完成。
2. **`g_DeferredReleaseQueue.FlushAll();`（新增）** —— 此时队列里所有 tag 都已完成，立即释放；**不能让它们留到 device/队列析构之后**（否则会把资源还给一个已死的 device）。
3. `game.Cleanup();`（已有）—— 次生的 `Destroy` 也要再 `FlushAll` 一次（因为 Cleanup 会入队新条目）；或在 `DeferredReleaseQueue` 析构里做。
4. `GameInput::Shutdown();`（已有）。
**顺序铁律**：`IdleGPU` → `FlushAll` → 再析构任何 D3D12 对象。`DeferredReleaseQueue::~DeferredReleaseQueue()` 也应 `FlushAll()` 作为兜底。

### 7.8 Barrier 侧的最小建议（RB5 覆盖范围，WP4 只需知道边界）
- 保持现有 `CommandContext::FlushResourceBarriers()` 的"攒批→提交"写法（`CommandContext.cpp:86-113`）[实测]，**不要**照搬 WE 的 `frame_barriers` 记录-延迟提交（`wiGraphicsDevice_DX12.cpp:7197-7201`），除非将来引入 RenderPass 需要合并——WE 那套是为"同帧多次 Barrier 调用合并成一次 ResourceBarrier"服务的，本项目当前每帧 Barrier 数量不足以体现收益。`[推断]`
- 若将来做 RenderPass 抽象，照搬 WE 的**三态模型**（`layout_before / layout / layout_after`，`wiGraphicsDevice_DX12.cpp:6300-6372`）而不是照搬它的类名：责任划分（§5.4 的表）是真正有价值的结论。
- 已经明确的坑：**框架只做 `before != after` 的机械转换**（`wiGraphicsDevice_DX12.cpp:6300-6334`），所以"同一个资源在两个 pass 之间从 SRV 变 UAV"必须由调用者显式表达——这一条在本项目同样成立。`[推断]`

### U6. 异步拷贝队列由谁节流（循环集合已确认，节流来源未知）
- **已知（G3 抽查 2 回源核对后确证）**：帧首阻塞的循环上界是 `for (int queue = 0; queue < QUEUE_COUNT; ++queue)`，并对 `queues[queue].queue == nullptr` 直接 `continue` `wiGraphicsDevice_DX12.cpp:5534-5546` [实测]；而 `copyAllocator.queue` 是**额外**创建、**不在** `QUEUE_COUNT` 枚举内的 COPY 队列 `wiGraphicsDevice_DX12.cpp:1690-1706` [实测] ⇒ **帧首阻塞确实不覆盖它**——这也解释了为什么它必须自带一套完成值 worklist `wiGraphicsDevice_DX12.cpp:5550-5558` [实测]。
- **仍不确定**：除 worklist 之外是否还有任何节流（例如 `CopyAllocator::submit` 在 `async_worklist` 过长时反压、或某处调用 `frame_fence_values` 之外的等待）。若没有，则 CPU 可以**无限领先**异步拷贝队列：不会 UAF（worklist 用完成值判据），但 **worklist 与 fence 数量会无界增长**，且 `freelist` 里的拷贝分配器会被耗尽后触发新建。
- **确认方式**：完整读 `CopyAllocator` 的 `init / submit / incrementFence / update` 全部成员（`wiGraphicsDevice_DX12.cpp:1690-1830` 区间）与 `async_worklist` 的声明处（`wiGraphicsDevice_DX12.h`）。
