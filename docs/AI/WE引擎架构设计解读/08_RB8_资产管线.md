> 全部结论带 `文件:行号`，标注 `[实测]`（命令直接输出）或 `[推断]`（由代码推断，未运行验证）。

## 摘要

WE 的资产管线是**「弱引用缓存 + 双重延迟（IMPORT_DELAY / 帧末延迟队列）+ 单线程低优先级流送」**三段式：
文件名即缓存键，`unordered_map<string, weak_ptr<`ResourceInternal`>>` 只保存弱引用，最后一个 `Resource` 强引用析构即自动从表中清除（`WickedEngine/wiResourceManager.cpp:236`、`WickedEngine/wiResourceManager.cpp:1269-1287`）[实测]。
**从文件到 GPU 的完整路径**：`MaterialComponent::CreateRenderData()` → `resourcemanager::Load(name, flags)` → 弱引用查表 →（时间戳过期则重建）→ `helper::FileRead` → `LoadResourceDirectly` 按扩展名分派 → `device->CreateTexture/CreateBuffer2` → `ResourceInternal::texture` → 渲染层 `GetDescriptorIndex` 绑定（`WickedEngine/wiScene_Components.cpp:517-525`、`WickedEngine/wiResourceManager.cpp:1036-1144`、`WickedEngine/wiResourceManager.cpp:1129-1131`）[实测]。
**延迟 MIP 与 BC 压缩登记在资产层、执行在渲染层**：`wiResourceManager.cpp:942` 与 `:981` 调 `wi::renderer::AddDeferredMIPGen / AddDeferredBlockCompression`，渲染层在帧首 `ProcessDeferredTextureRequests` 用同一 CommandList 批量执行（`WickedEngine/wiResourceManager.cpp:942`、`WickedEngine/wiRenderer.cpp:3531-3617`、`WickedEngine/wiRenderPath3D.cpp:861`）[实测]。这是**反向依赖**：资产层 `#include "wiRenderer.h"`（`WickedEngine/wiResourceManager.cpp:2`）[实测]。
**流送**由 GPU 侧 mip 反馈驱动：像素着色器 `write_mipmap_feedback` 写入 `texturestreamingbuffer`，CPU 回读后转成 `StreamingRequestResolution` 原子或，下一帧主线程 `UpdateStreamingResources` 起一个低优先级 job 做部分文件读取 + 重建纹理（`Shaders/globals.hlsli:599-624`、`WickedEngine/wiScene.cpp:4391-4404`、`WickedEngine/wiResourceManager.cpp:1192-1407`）[实测]。

## §1 职责边界

### 负责（WE `wi::resourcemanager`）
- **按扩展名分派的通用资产加载器**：扩展名→数据类型查表 JE/PNG/BMP/DDS/TGA/HDR/HEIC/WAV/OGG/LUA/MP4/H264/TTF（`WickedEngine/wiResourceManager.cpp:257-273`）[实测]。
- **进程级弱引用缓存**：`static wi::unordered_map<std::string, wi::allocator::weak_ptr<ResourceInternal>> resources`（`WickedEngine/wiResourceManager.cpp:236`）[实测]，配 `std::mutex locker`（`WickedEngine/wiResourceManager.cpp:235`）[实测]。
- **文件时间戳失效检测与热重载**：`CheckResourcesOutdated` / `ReloadOutdatedResources`（`WickedEngine/wiResourceManager.h:118-122`）[实测]。
- **DDS 流送状态机**：记录全部 mip 的文件偏移/行距/层距，按需只上传子集 mip（`WickedEngine/wiResourceManager.cpp:563-587`）[实测]。
- **序列化内嵌资源**：`ResourceSerializer` 支持把资源二进制随场景一起存档（`WickedEngine/wiResourceManager.h:139-145`）[实测]。
- **纹理分辨率上限**：`SetTextureResolutionLimit`（`WickedEngine/wiResourceManager.h:104-106`）[实测]。

### 不负责
- **不做纹理解码后的 GPU 工作**：延迟 MIP 生成与 BC 压缩本身由渲染层执行，资产层只登记（`WickedEngine/wiResourceManager.cpp:942`、`WickedEngine/wiRenderer.cpp:3603-3616`）[实测]。
- **不做网格资产管线**：顶点/索引缓冲在 `MeshComponent::CreateRenderData` 里直接走 `renderer::SuballocateGPUBuffer` + `CreateBuffer2`（`WickedEngine/wiScene_Components.cpp:559`、`WickedEngine/wiScene_Components.cpp:1220-1234`）[实测]，不经过 resourcemanager。
- **不做模型格式导入（FBX/glTF/OBJ）**：全仓库 grep `assimp` **零命中**（`grep -rln assimp --include=*.cpp --include=*.h` 返回空）[实测]；运行时 `LoadModel2` 只打开 `.wiscene` 走 `wi::Archive`（`WickedEngine/wiScene.cpp:9230-9237`）[实测]。
- **不做纹理解码算法**：用 stb_image / dds.h / WIC（`WickedEngine/wiResourceManager.cpp:9-10`、`WickedEngine/wiResourceManager.cpp:708-766`）[实测]。

## §2 关键类型与数据结构

### 2.1 `wi::Resource`（句柄）
```cpp
struct Resource {
    wi::allocator::shared_ptr<void> internal_state;   // 类型擦除的共享句柄
    constexpr bool IsValid() const { return internal_state.IsValid(); }
    ...
    void SetOutdated();                       // 标记为「下次 Load 时重建」
    void StreamingRequestResolution(uint32_t);// 向流送系统请求分辨率
};
```
证据：`WickedEngine/wiResourceManager.h:20-50` [实测]。这是**拷贝即共享**的值语义句柄——拷贝 `Resource` 就增加强引用计数，无需显式 `AddRef`。

### 2.3 `StreamingTexture`
`streaming_data[16]`（每 mip 的 `data_offset/row_pitch/slice_pitch`）、`mip_count`、`min_lod_clamp_absolute`（`WickedEngine/wiResourceManager.cpp:45-56`）[实测]。
配套常量：`streaming_texture_min_size = 64 * 1024`（`WickedEngine/wiResourceManager.cpp:58`）[实测] —— 低于 64KB 不再降级，因为 D3D12 资源对齐不会因此省内存。

### 2.4 Flags（行为开关，可序列化，顺序不可改）
`IMPORT_COLORGRADINGLUT`、`IMPORT_RETAIN_FILEDATA`、`IMPORT_NORMALMAP`、`IMPORT_BLOCK_COMPRESSED`、`IMPORT_DELAY`、`STREAMING`（`WickedEngine/wiResourceManager.h:73-82`）[实测]。
注释明确「Order of these must not change as the flags can be serialized!」——**flag 会随 `.wiscene` 落盘**（`WickedEngine/wiResourceManager.h:72`）[实测]。

### 2.5 延迟队列（渲染层）
```cpp
wi::SpinLock deferredMIPGenLock;
wi::vector<std::pair<Texture, bool>> deferredMIPGens;      // (纹理, preserve_coverage)
wi::vector<std::pair<Texture, Texture>> deferredBCQueue;   // (未压缩源, BC 目标)
```
证据：`WickedEngine/wiRenderer.cpp:191-193` [实测]。用 `SpinLock` 而非 `mutex`，因为登记发生在任意加载线程、持锁区间极短。

### 2.6 流送反馈缓冲
`textureStreamingFeedbackBuffer`（UAV, R32_UINT）+ `textureStreamingFeedbackBuffer_readback[GetBufferCount()]`（READBACK）+ `textureStreamingFeedbackMapped`（`WickedEngine/wiScene.h:148-150`）[实测]。
大小 = `materialArraySize * sizeof(uint32_t) * 2`（*2 为快速扩容）（`WickedEngine/wiScene.cpp:197-206`）[实测]。**每材质一个 u32**：低 16 位 = uvset0 请求分辨率，高 16 位 = uvset1（`WickedEngine/Shaders/globals.hlsli:608`、`WickedEngine/wiScene.cpp:4394-4395`）[实测]。

## §3 调用链（文件 → GPU）

### 3.1 纹理主链（非流送、非延迟）
1. 场景反序列化把材质贴图相对名解析成绝对路径：`x.name = dir + x.name`（`WickedEngine/wiScene_Serializers.cpp:274-280`）[实测]，`dir` 来自 `archive.GetSourceDirectory()`（`WickedEngine/wiScene_Serializers.cpp:82`、`WickedEngine/wiArchive.cpp:187-190`）[实测]。
   - **[推断]** 路径解析策略 = 「存档内的相对名 + .wiscene 所在目录」，纯字符串拼接，**不做 VFS/挂载点/搜索路径**（无相关代码）。
2. 材质数据落地后立即异步建渲染数据：`wi::jobsystem::Execute(seri.ctx, [&]{ CreateRenderData(); })`（`WickedEngine/wiScene_Serializers.cpp:282-284`）[实测]。
3. `MaterialComponent::GetTextureSlotResourceFlags(slot)` 决定 flags：默认加 `IMPORT_BLOCK_COMPRESSED`（除非用户关掉）、默认加 `STREAMING`（除非关掉）、法线槽加 `IMPORT_NORMALMAP`（`WickedEngine/wiScene_Components.cpp:482-503`）[实测]。
4. `textureslot.resource = wi::resourcemanager::Load(textureslot.name, flags)`（`WickedEngine/wiScene_Components.cpp:517-525`）[实测]。
5. `resourcemanager::Load` 持 `locker`，用 `resources[name]` 取弱引用并 `lock()`（`WickedEngine/wiResourceManager.cpp:1045-1047`）[实测]。
6. 时间戳比较：`timestamp = helper::FileTimestamp(name)`（`WickedEngine/wiResourceManager.cpp:1056`），`last_write_time` 转 epoch 计数（`WickedEngine/wiHelper.cpp:1374-1380`）[实测]。
7. 命中且未过期 → 直接返回新 `Resource`（**不解码、不建 GPU 资源**）（`WickedEngine/wiResourceManager.cpp:1096-1101`）[实测]。
8. 未命中/过期 → `make_shared<ResourceInternal>()` 覆盖表项，记录 filename/container 参数（`WickedEngine/wiResourceManager.cpp:1061-1076`）[实测]；释放锁。
9. 取字节：`helper::FileRead(container_filename, filedata, filesize, offset)`，内部是 `std::ifstream` + `seekg(offset)` 支持部分读（`WickedEngine/wiResourceManager.cpp:1109`、`WickedEngine/wiHelper.cpp:1308-1332`）[实测]。
10. `LoadResourceDirectly` 按扩展名分派（`WickedEngine/wiResourceManager.cpp:343-361`）[实测]。
11. DDS 分支：读 header → 建 `TextureDesc` → DXGI 格式大表映射（`WickedEngine/wiResourceManager.cpp:366-464`）→ BC4/BC5 补默认 swizzle（`WickedEngine/wiResourceManager.cpp:466-479`）[实测]。
12. 分辨率上限 mip 裁剪：`while (desc.width > max_texture_resolution && ...) { ...; mip_offset++; }`（`WickedEngine/wiResourceManager.cpp:552-560`）[实测]。
13. 流送资源额外裁剪到 ≥64KB，并记录 `min_lod_clamp_absolute = mip_offset`（`WickedEngine/wiResourceManager.cpp:579-586`）[实测]。
14. `device->CreateTexture(&desc, initdata + mip_offset, &resource->texture)` + `SetName`（`WickedEngine/wiResourceManager.cpp:589-590`）[实测]。
15. SRGB 视图另建子资源（`WickedEngine/wiResourceManager.cpp:592-602`）[实测]。
16. PNG/JPG 等分支：先 `flags &= ~Flags::STREAMING`（`WickedEngine/wiResourceManager.cpp:700`）[实测]，stb_image 解码 → 按通道数选 format 与 `bc_format`（`WickedEngine/wiResourceManager.cpp:767-859`）[实测]。
17. 建纹理时 `mip_levels = GetMipCount(...)`、`usage = DEFAULT`、`bind_flags = SHADER_RESOURCE|UNORDERED_ACCESS`（为 MIP 生成留 UAV），注释直言「we don't fill the mips here correctly, just always point to the mip0 data」（`WickedEngine/wiResourceManager.cpp:910-923`）[实测]。
18. `device->CreateMipgenSubresources(resource->texture)`（`WickedEngine/wiResourceManager.cpp:927`）[实测]，然后 `wi::renderer::AddDeferredMIPGen(resource->texture, true)`（`WickedEngine/wiResourceManager.cpp:942`）[实测]。
19. 若带 `IMPORT_BLOCK_COMPRESSED`：把未压缩纹理 move 走，另建 BC 目标纹理（`bc_format`，法线强制 BC5_UNORM + swizzle R,G,ONE,ONE），再 `AddDeferredBlockCompression(uncompressed_src, resource->texture)`（`WickedEngine/wiResourceManager.cpp:944-982`）[实测]。
20. 清理：无 `IMPORT_RETAIN_FILEDATA` 且无 `IMPORT_DELAY` 时 `filedata.clear(); shrink_to_fit();`（`WickedEngine/wiResourceManager.cpp:1026-1031`）[实测]。
21. 渲染层帧首执行：`wi::renderer::ProcessDeferredTextureRequests(cmd)` 在 3D 路径第 861 行、2D 路径第 198 行，注释说明「Execute it first thing in the frame here, on main thread, to not allow other thread steal it and execute on different command list!」（`WickedEngine/wiRenderPath3D.cpp:861`、`WickedEngine/wiRenderPath2D.cpp:198`）[实测]。
22. 使用端绑定：`material.WriteShaderTextureSlot(...)` 写描述符索引到材质常量数组（`WickedEngine/wiScene.cpp:4360-4362`）[实测]，描述符来自 `device->GetDescriptorIndex(&texture, SubresourceType::SRV)`（`WickedEngine/wiScene.cpp:4370`）[实测]。

### 3.2 网格链（与纹理不同路）
`MeshComponent::CreateRenderData` → `renderer::SuballocateGPUBuffer(bd.size)` → `device->CreateBuffer2(&bd, init_callback, &generalBuffer, &suballoc.alias, suballoc.allocation.byte_offset)`（`WickedEngine/wiScene_Components.cpp:1220-1234`）[实测]；CPU 侧顶点数组直接存在 `MeshComponent` 里并由场景序列化落盘（`WickedEngine/wiScene.h:206`、`WickedEngine/wiScene_Serializers.cpp:2731`）[实测]。

### 3.3 模型链（`.wiscene`）
`LoadModel2` → `wi::Archive archive(fileName, true)` → `scene.Serialize(archive)`（`WickedEngine/wiScene.cpp:9230-9237`）[实测] → `Scene::Serialize` 先读一段 `reserved`，再读 `jump_before/jump_after` 跳到「资源区」读内嵌资源，然后跳回「实体区」读组件（`WickedEngine/wiScene_Serializers.cpp:2662-2717`）[实测]。

## §4 算法与公式

### 4.1 缓存键与失效
- 键：**原始文件名字符串**（含容器偏移不进键，见 §8 未确认项 U1）（`WickedEngine/wiResourceManager.cpp:1046`）[实测]。
- 失效：`resource->timestamp < FileTimestamp(name)`（`WickedEngine/wiResourceManager.cpp:1059`）[实测]。注意是**严格小于**：同一时间戳视为未变；`SetOutdated()` 直接把 `timestamp = 0`，从而 0 < 任何真实时间戳必然命中重建（`WickedEngine/wiResourceManager.cpp:213-221`）[实测]。
- 生命周期：表中只有 `weak_ptr`；表项由 `UpdateStreamingResources` 在流送轮询里发现 `x.second.expired()` 后 `resources.erase(*x)` 回收（`WickedEngine/wiResourceManager.cpp:1267-1288`）[实测]。**结论：缓存是「有强引用才存活」的，最后一个 `Resource` 句柄析构 = GPU 纹理随即释放**[推断]。

### 4.2 流送分辨率映射
着色器侧（`WickedEngine/Shaders/globals.hlsli:604-608`）[实测]：
```
lod_uvset = get_lod(65536, duv/dx, duv/dy)
resolution = 65536 >> clamp(uint(lod), 1, 16)
mask = resolution0 | (resolution1 << 16)
InterlockedOr(buffer[materialIndex], wave_mask)
```
CPU 侧把请求还原成 2 的幂：`requested_resolution = 1u << (31u - firstbithigh(requested_resolution))`（`WickedEngine/wiResourceManager.cpp:1300-1304`）[实测]。
内存压力：`memory_percent = usage / budget`，`memory_shortage = memory_percent > streaming_threshold`（默认 0.8）（`WickedEngine/wiResourceManager.cpp:1306-1308`、`WickedEngine/wiResourceManager.cpp:1177`）[实测]。
滞回：`target_unload_delay = memory_shortage ? 4 : 255` 帧，只有连续超时才降级（`WickedEngine/wiResourceManager.cpp:1310`、`WickedEngine/wiResourceManager.cpp:1328-1330`）[实测]。
流进：`desc.width <<= 1; desc.height <<= 1; desc.mip_levels++; mip_offset--`（`WickedEngine/wiResourceManager.cpp:1319-1324`）[实测]。
流出：`while (ComputeTextureMemorySizeInBytes(desc) > streaming_texture_min_size && desc.width > requested && desc.height > requested) { >>= 1; mip_levels--; mip_offset++; }`（`WickedEngine/wiResourceManager.cpp:1334-1340`）[实测]。
偏移换算：`mip_data_offset = streaming_data[mip_offset].data_offset`，再对每个 mip 反向减去基准得到相对指针（`WickedEngine/wiResourceManager.cpp:1345`、`WickedEngine/wiResourceManager.cpp:1373-1379`）[实测]。

### 4.3 min lod clamp 平滑过渡
`mip_offset = mip_count - desc.mip_levels`；`min_lod_clamp_absolute -= dt * streaming_fade_speed(=4)`，下限夹到 `mip_offset`；相对值 `= absolute - mip_offset` 传给 `CreateSubresource(..., min_lod_clamp_relative)`（`WickedEngine/wiResourceManager.cpp:1214-1250`、`WickedEngine/wiResourceManager.cpp:1178`）[实测]。
**[推断]** 这是防「突然清晰/突然模糊」的视觉跳变：lod clamp 每帧线性下移，mip 切换被抹成渐变。注意此路径每帧 `DeleteSubresources` + 重建 SRV，代价是每帧若干 D3D12 描述符操作（`WickedEngine/wiResourceManager.cpp:1224-1251`）[实测]。

## §5 资源与同步

### 5.1 锁与线程模型
| 锁 | 保护对象 | 策略 | 行号 |
|---|---|---|---|
| `static std::mutex locker` | `resources` 表 + 流送阈值 | `Load` 全程持锁到「复用」判断结束就释放；`UpdateStreamingResources` 用 `try_lock` 避免主线程卡 | `WickedEngine/wiResourceManager.cpp:235`、`WickedEngine/wiResourceManager.cpp:1206-1207` [实测] |
| `std::mutex streaming_replacement_mutex` | `streaming_texture_replacements` | 单流送线程 + 主线程；注释说明「can only be held by the single streaming thread, so we don't need to try_lock」 | `WickedEngine/wiResourceManager.cpp:1175`、`WickedEngine/wiResourceManager.cpp:1195` [实测] |
| `wi::SpinLock deferredMIPGenLock` | 两个延迟队列 | 登记方（任意线程）与渲染主线程 | `WickedEngine/wiRenderer.cpp:191-193`、`WickedEngine/wiRenderer.cpp:19362-19369` [实测] |
| `static std::mutex locker`（序列化） | `Serialize_READ/WRITE` 期间资源存活 | `seri_locker` | `WickedEngine/wiResourceManager.cpp:1573-1575` [实测] |

### 5.2 后台流送的三段握手
1. **提交**（主线程，帧内）：`if (wi::jobsystem::IsBusy(streaming_ctx)) return;` 保证同时只有一个流送 job；收集候选资源到 `streaming_texture_jobs`（强引用，防 job 期间被释放）；`locker.unlock()` 后才提交（`WickedEngine/wiResourceManager.cpp:1255-1289`）[实测]。
2. **执行**（低优先级线程）：`streaming_ctx.priority = wi::jobsystem::Priority::Streaming`，注释「One low priority thread will be responsible for streaming, to not cause any hitching while rendering」（`WickedEngine/wiResourceManager.cpp:1294-1296`）[实测]。job 内直接调 `device->CreateTexture(...)`（`WickedEngine/wiResourceManager.cpp:1385`）[实测]——**D3D12 资源创建在非主线程**。
3. **交换**（主线程，下一帧开头）：`for (auto& replace : streaming_texture_replacements) { replace.resource->texture = replace.texture; ... } ; clear()`（`WickedEngine/wiResourceManager.cpp:1194-1202`）[实测]。**纹理句柄替换只在主线程发生**，diffuse 帧内引用旧纹理，避免撕裂。
4. **释放**：旧纹理是 RAII 句柄，赋值即析构 → 走 GraphicsDevice 的延迟释放（`update_deferred_release(device->GetFrameCount(), device->GetBufferCount())`，`WickedEngine/wiRenderer.cpp:2854`）[实测]。

### 5.3 每帧调用点
`wi::resourcemanager::UpdateStreamingResources(dt)` 在应用主循环 `wiApplication.cpp:403` 调用[实测]。
`ProcessDeferredTextureRequests(cmd)` 在 3D/2D 渲染路径帧首调用（`WickedEngine/wiRenderPath3D.cpp:861`、`WickedEngine/wiRenderPath2D.cpp:198`）[实测]。
反馈缓冲清零点在场景 GPU 上传末尾（`WickedEngine/wiRenderer.cpp:5638-5641`）[实测]，回读在 `TextureStreamingReadbackCopy`（`WickedEngine/wiRenderer.cpp:5646-5660`）[实测]。

### 5.4 就绪可见性（渲染层如何知道资产已就绪）
- **没有 ready 标志位、没有 future/event**：`Resource::IsValid()` 只是「缓存里有一个活着对象」；`resource.GetTexture().IsValid()` 才是「GPU 资源在」（`WickedEngine/wiResourceManager.h:23`、`WickedEngine/wiResourceManager.h:26`）[实测]。
- **[推断]** 由于 `Load()` 在返回前同步完成解码与 `CreateTexture`（除非用 `IMPORT_DELAY`），普通调用方不需要等；流送降级纹理始终是**可用的低分辨率版本**，因此也不需要等。真正的「未就绪」只出现在 `IMPORT_DELAY` 与流送 job 完成前的中间态。
- `IMPORT_DELAY` 的接续语义：先以 `IMPORT_DELAY` 建对象并保留 filedata（`WickedEngine/wiResourceManager.cpp:1078-1084`），之后任一次不带 `IMPORT_DELAY` 的 `Load` 会清掉该 flag 并继续真正解码（`WickedEngine/wiResourceManager.cpp:1088-1093`）[实测]。

### 5.5 延迟队列的批量语义
`ProcessDeferredTextureRequests` 在同一 `cmd` 上：先按序 `GenerateMipChain(texture, MIPGENFILTER_LINEAR, cmd, mipopt)`，再按序 `BlockCompress(src, dst, cmd)`，最后整体 `clear()`（`WickedEngine/wiRenderer.cpp:3603-3616`）[实测]。**没有优先级/标签/依赖排序**，纯 FIFO[推断]。
`ProcessDeferredTextureRequests` 还顺手处理笔刷纹理（`painttextures`）并在其后为多 mip 目标补 `GenerateMipChain`（`WickedEngine/wiRenderer.cpp:3533-3600`）[实测]。

## §6 可迁移性判定

> 三选一口径：**必需**＝本项目当前缺此能力且已有可复用基础设施；**可选**＝有收益但需先补前置条件；**规模不匹配**＝WE 的写法依赖本项目没有的大前提，照搬会引入净复杂度。
> 每项附「理由」与「本项目替代方案」，并显式给出**不搬 WE 类名/目录名**后的落地形态。

### 6.1 weak_ptr 弱引用缓存（文件名 → weak_ptr<ResourceInternal>）
**判定：可选**

**理由**
- WE：缓存表只存弱引用，最后一个 `Resource` 强引用析构 → 表项自动 `expired()` → 由流送轮询 `erase`（`WickedEngine/wiResourceManager.cpp:236`、`WickedEngine/wiResourceManager.cpp:1267-1288`）[实测]。
- 本项目**已经是等价的「引用计数 + 缓存表」**，只是表用 `unique_ptr` **强**拥有（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:54`）[实测]，并在引用计数归零时**当线程立即** `erase`（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:177-178` → `Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:158-161` → `Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:104-111`）[实测]。
- 关键差距不在「弱引用」，而在**释放时机**：WE 的纹理句柄是 RAII，赋值/析构后走 GraphicsDevice 的 `update_deferred_release(device->GetFrameCount(), device->GetBufferCount())`（`WickedEngine/wiRenderer.cpp:2854`）[实测]，即**按帧数延迟释放**；本项目没有这一层 [推断] —— 最后一个 `TextureRef` 析构的线程就是 `ManagedTexture` 被 delete（`s_TextureCache.erase` 触发 `unique_ptr` 析构，`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:108-110`）[实测] 的线程，而 GPU 可能仍在读该资源。
- 也就是说：**照搬 weak_ptr 表并不能修掉本项目真正的风险**，收益仅为「表项自动清理」，而代价是键的语义要重新设计。

**替代方案（不搬 `Resource` / `ResourceInternal` 类型名）**
1. 保留 `std::map<std::wstring, ManagedTexture>`（值语义即可，不需要指针），键维持 `path + sRGB 后缀`（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:75-77`）[实测]。
2. 把 `DestroyTexture`（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:104-111`）从「立即 erase」改成「入待回收队列 + 按 frame fence 回收」，复用本项目既有的帧计数/围栏（RHI 层已有 per-context `FenceValue`）。
3. 于是「自动清理」与「GPU 安全」两步分离即可，不必引入 weak_ptr：引用计数归零 → 入队 → 帧围栏过后才真正析构。

### 6.2 延迟 MIP 生成（资产层登记、渲染层帧首执行）
**判定：可选（且对本项目当前形态无收益）**

**理由**
- WE 必须延迟，是因为 PNG/JPG 解码路径**只上传 mip0**：纹理描述里 `mip_levels` 已算好但数据未填——源码注释直言「we dont fill the mips here correctly, just always point to the mip0 data by default. Mip levels will be created using compute shader when needed!」（`WickedEngine/wiResourceManager.cpp:910-923`）[实测]，所以 `bind_flags` 必须带 `UNORDERED_ACCESS`（`WickedEngine/wiResourceManager.cpp:910-914`）[实测]，随后 `device->CreateMipgenSubresources` + `AddDeferredMIPGen`（`WickedEngine/wiResourceManager.cpp:927`、`WickedEngine/wiResourceManager.cpp:942`）[实测]。
- 本项目**mip 链在离线烘焙期就生成完了**：`if (info.mipLevels == 1) GenerateMipMaps(...)`（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:206-220`）[实测]，再由 `SaveToDDSFile` 写入 DDS（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:249-254`）[实测]；运行时 `CreateDDSTextureFromMemory` 直接按 DDS 里已有的 mip 层数创建（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:132`）[实测]。
- 结论：运行时不存在「有 mip 层数但没 mip 数据」的中间态，**引入延迟 MIP 是为一个不存在的问题付架构代价**（需要 UAV 可写纹理 + 帧首状态迁移 + 队列同步；本项目纹理目前常驻 `D3D12_RESOURCE_STATE_GENERIC_READ`，`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:135`）[实测]。

**替代方案**
- **不做**运行时延迟 MIP，保持「烘焙期生成 mip」不变。
- 若将来要支持运行时直读 PNG/JPG：仍在**烘焙期**用 DirectXTex `GenerateMipMaps` + `Compress` 产出 DDS（路径已存在，`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:206-254`）[实测]，运行时只做「读文件 → `CreateTexture`」。绝不引入 `AddDeferredMIPGen` 这类「资产层调渲染层」的登记 API。

### 6.3 BC 压缩调度（资产层打 flag、渲染层 compute 批处理）
**判定：BC 压缩本身 = 必需；「GPU 压缩调度」= 规模不匹配**

**理由**
- WE 在 GPU 上批处理 BC（`WickedEngine/wiRenderer.cpp:3611-3614`：`for (auto& it : deferredBCQueue) BlockCompress(it.first, it.second, cmd);`）[实测]，前提是它允许**任意格式运行时导入**并允许用户切换「优先未压缩」（`WickedEngine/wiScene_Components.cpp:485-488`：`if (!IsPreferUncompressedTexturesEnabled()) flags |= IMPORT_BLOCK_COMPRESSED;`）[实测] —— 即压缩与解压需要**运行时可选**。
- 本项目纹理**全部在烘焙期离线压缩**（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:223-243`：`Compress(..., cformat, TEX_COMPRESS_DEFAULT, 0.5f, ...)`）[实测]，运行时只读 DDS。
- 但**这条离线压缩实际上从未被触发**，这是本项目一个真实且可立即修的缺口：
  - `kDefaultBC = 16`（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.h:18`）[实测]；而 `TextureOptions(sRGB, hasAlpha, invertY)` **不会置 `kDefaultBC`**（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.h:23-26`）[实测]。
  - ModelConvert 对 5 个槽位分别传 `TextureOptions(true, bAlpha)` / `TextureOptions(false)`（`Engine/03_AssetSystem/Importers/Model/ModelConvert.cpp:367-376`）[实测] → 位掩码里只有 `kSRGB` 与 `kPreserveAlpha`，**`kDefaultBC` / `kNormalMap` / `kQualityBC` 永远为 0**。
  - 于是 `ConvertToDDS` 里 `bBlockCompress = GetFlag(kDefaultBC)` 恒为 false（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:38`）[实测] → 走 `cformat = tformat = R8G8B8A8(_SRGB)`（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:167`）[实测] → **模型贴图 100% 未压缩**（VRAM 约为 BC 的 4~8 倍）。
  - 唯一传压缩 flag 的调用点是环境 HDR：`CompileTextureOnDemand(HDRPath, kDefaultBC | kQualityBC)`（`Engine/04_Renderer/EnvironmentLightingManager.cpp:173`）[实测]；而 HDR 分支把 `cformat` 直接设为 `tformat = R16G16B16A16_FLOAT`（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:146-149`）[实测] 且 BC6H 被显式注释禁用（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:151-153`）[实测] → 该次 `Compress` 的目标格式不是 BC 格式 [推断]（见 §8 U2）。
  - 失败路径只 `Printf` 后保留未压缩图，**不报错、不中止**（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:233-242`）[实测] → 静默降级，这正是「贴图不走 BC」长期未被发现的原因。
- 本项目若开启 BC 还需补两处：①法线贴图应走 BC5（现在完全没传 `kNormalMap`，`Engine/03_AssetSystem/Importers/Model/ModelConvert.cpp:375-376`）[实测]；②尺寸非 4 倍数会被跳过（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:225-228`）[实测]。
- **「GPU 压缩调度」为何规模不匹配**：本项目纹理格式在**烘焙期定型且不再变化**，没有运行时切换压缩的需求；引入 compute `BlockCompress` 还要新写 UAV 纹理路径、帧首队列与 barrier 管理，收益只是省一次离线耗时。

**替代方案（保留离线压缩，修 flag 与失效键）**
1. 在 `Engine/03_AssetSystem/Importers/Model/ModelConvert.cpp:367-376` 的每个 `TextureOptions(...)` 上 OR 入 `kDefaultBC`；法线槽再 OR `kNormalMap`；BaseColor/Emissive 视需要 `kQualityBC`（BC7）。参数名沿用本项目已有的 `kDefaultBC/kNormalMap/kQualityBC`，**不引入** WE 的 `IMPORT_BLOCK_COMPRESSED` 命名。
2. 在 `Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:155-164` 确认三档 BC 分支（BC7 / BC3 / BC1）与 4 倍数对齐；非 4 倍数时**显式告警**而不是静默跳过（现在是 `Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:225-228`）[实测]。
3. 修失效键：`CompileTextureOnDemand` 现在只比较 mtime（`ddsFileStat.st_mtime < srcFileStat.st_mtime`，`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:25`）[实测]，**完全不含 flags** → 改了 `textureOptions` 也不会重建 DDS。建议让 flags 参与「比较值」（例如 DDS 侧旁挂一个版本/flag 标记，或把 flags 一起写进缓存标记），而不是只比 mtime。

### 6.4 .wiscene 思路（自描述场景存档 + 内嵌资源 + 相对路径）
**判定：规模不匹配**

**理由**
- `.wiscene` = **整个场景**的存档：带 `reserved` 段、`version >= 90` 的 `jump_before/jump_after` 双跳转区（先跳去读内嵌资源、再跳回读实体）、`componentLibrary` 驱动的组件顺序（`WickedEngine/wiScene_Serializers.cpp:2662-2740`）[实测]，配套 `wi::Archive` 与 30+ 组件的 `Serialize`。
- 本项目是 MiniEngine 血缘：没有 ECS 场景存档，`.ty` 承担的是**单个模型的烘焙产物**（展平几何 + 切线 + 索引优化 + 材质/纹理表）。入口 `BuildModel` 只做 3 件事：`BuildMaterials` → `WalkGraph` 展平 → return（`Engine/03_AssetSystem/Importers/Model/ModelConvert.cpp:412-431`）[实测]；`.ty` 的读取路径也不含任何实体/组件系统（`Engine/05_Scene/Model/ModelLoader.cpp:314-383`）[实测]。
- 把 `.wiscene` 那套（组件库 + 双跳转 + 内嵌资源 + 版本迁移）搬进来，等于在 MiniEngine 骨架上重建一个 ECS 场景系统，**收益（场景级存档）不是本项目当前目标**。

**替代方案（只借两条思想，落在 `.ty` 上）**
1. **相对路径**：`.ty` 已存纹理名（现在是 glTF `uri` 原样字符串，`Engine/03_AssetSystem/Importers/glTF.cpp:508-511` → `Engine/03_AssetSystem/Importers/Model/ModelConvert.cpp:262-265`）[实测]，加载时用 `.ty` 自身目录拼（本项目已是 `basePath + textureNames[ti]`，`Engine/05_Scene/Model/ModelLoader.cpp:62`）[实测]。保留即可，**不要**引入 `GetSourceDirectory` 这类 Archive 概念。
2. **版本号与不兼容即重建**：`.ty` 已有魔数 `"TY"`（`Engine/03_AssetSystem/Importers/Model/ModelConvert.cpp:440`）[实测] 与 `CURRENT_MINI_FILE_VERSION 2`（`Engine/05_Scene/Model/ModelLoader.h:12`）[实测]，校验点在 `Engine/05_Scene/Model/ModelLoader.cpp:251-265` [实测]。建议把「纹理槽位顺序 / MaterialTextureData 布局」纳入版本号语义——因为 `Engine/03_AssetSystem/Assets/Constants/ConstantBuffers.h:31` 的注释已指出「.ty 模型缓存按槽位顺序序列化 MaterialTextureData.stringIdx」[实测]，这是唯一会让旧缓存**静默读出错误贴图**的风险点（版本号不会因此变化，比版本不匹配更危险）。

### 6.5 后台流送（mip 反馈 + 单低优先级线程 + 主线程交换）
**判定：规模不匹配**

**理由（WE 的流送依赖四个本项目都不具备的前提）**
1. DDS 全 mip 的文件偏移/行距表与「按偏移部分读文件」：`streaming_data[16]` 记录每个 mip 的 `data_offset/row_pitch/slice_pitch`（`WickedEngine/wiResourceManager.cpp:45-56`、`WickedEngine/wiResourceManager.cpp:563-587`）[实测]，配合 `FileRead(container_filename, streaming_file, filesize, container_fileoffset + mip_data_offset)`（`WickedEngine/wiResourceManager.cpp:1351-1368`）[实测] 才能只读需要的 mip。
2. GPU 侧 mip 反馈：像素着色器 `write_mipmap_feedback` → `WaveActiveBitOr` → `InterlockedOr`（`WickedEngine/Shaders/globals.hlsli:599-624`）[实测]，UAV 缓冲 + READBACK 缓冲 + CPU mapping（`WickedEngine/wiScene.cpp:197-218`）[实测]。
3. 逐 uvset 的请求打包与解码（`WickedEngine/wiScene.cpp:4391-4404`）[实测]。
4. 单低优先级线程 + 主线程交换的三段握手（`WickedEngine/wiResourceManager.cpp:1255-1296`、`WickedEngine/wiResourceManager.cpp:1194-1202`）[实测]。
本项目对应实现：纹理管理器**没有 mip 偏移概念**，整块内存一次建纹理（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:121-150`）[实测]；`ReadFileSync` 是主线程同步全量读（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:97` → `Engine/00_Core/Utility/FileUtility.cpp:115-118` → `Engine/00_Core/Utility/FileUtility.cpp:16-32`）[实测]；连已写好的 `ReadFileAsync` **都没有任何调用点**（`Engine/00_Core/Utility/FileUtility.cpp:120-124`，全仓 grep `ReadFileAsync` 只有定义与声明）[实测]。

**替代方案（先做最小可用异步化，不做分级流送）**
1. **补齐最小异步**：把 `FindOrLoadTexture` 里的 `ReadFileSync`（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:97`）换成已有的 `Utility::ReadFileAsync`（`Engine/00_Core/Utility/FileUtility.cpp:120-124`）；`ManagedTexture::WaitForLoad` 语义已正确（自旋等 `m_IsLoading`，`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:152-156`）[实测]，但应改成条件变量或直接由 GPU 侧等待，避免主线程 `thread::yield` 空转（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:154-155`）[实测]。
2. **把烘焙挪出主线程**：`CompileTextureOnDemand`（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:9-30`）在主线程走完 `LoadFromWICFile` + `GenerateMipMaps` + `Compress` 全套（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:105-243`）[实测]，是启动卡顿主因 [推断]。挪到后台只需保证「同一 DDS 路径不被两个线程同时烘焙」。
3. **不做分辨率分级**：没有 mip 偏移表与 GPU 反馈的前提下谈流送没有立足点。

### 6.6 「资产层登记、渲染层执行」的反向依赖
**判定：可选（只借「帧首集中执行」这个时点，不借 include 方向）**

**理由**
- WE 让资产层 `#include "wiRenderer.h"`（`WickedEngine/wiResourceManager.cpp:2`）[实测] 换取「用渲染层的 CommandList 执行 compute」，renderer 侧暴露 `AddDeferredMIPGen` / `AddDeferredBlockCompression`（`WickedEngine/wiRenderer.cpp:19360-19371`）[实测]，并在帧首由渲染路径主动调用 `ProcessDeferredTextureRequests(cmd)`（`WickedEngine/wiRenderPath3D.cpp:861`、`WickedEngine/wiRenderPath2D.cpp:198`）[实测]。WE 这么做有硬理由：`CreateTexture` 可能发生在**流送线程**，不能让渲染线程之外的线程拿到 CommandList 串帧（帧首注释：to not allow other thread steal it and execute on different command list!，`WickedEngine/wiRenderPath3D.cpp:861`）[实测]。
- 本项目当前依赖方向是**渲染层 → 资产层**（`ModelLoader.cpp` include `TextureManager.h` 与 `TextureConvert.h`：`Engine/05_Scene/Model/ModelLoader.cpp:10-11`；`DeferredRenderer` 调 `TextureManager::Initialize`：`Engine/04_Renderer/Renderer/Deferred/DeferredRenderer.cpp:93`）[实测]，结构比 WE 干净。为「帧首批处理」而反向 include 是净负债。

**替代方案**
- 需要帧首集中执行时，**队列放渲染层**，资产层不 include 渲染头：在渲染器 `BeginFrame`（本项目已有每帧入口）里**显式调用** `TextureManager::ProcessPendingUploads()`，调用方向仍是「渲染层 → 资产层」。这与 WE 的**时机**相同（帧首、主线程、单一 CommandList），但**方向相反且不需要反向依赖**。

### 7.3 【P1】纹理释放按帧围栏延迟（修 GPU 使用中释放的风险）
- **问题**：`TextureRef` 引用计数归零 → `ManagedTexture::Unload()` → `DestroyTexture` → `s_TextureCache.erase`（`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:175-179`、`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:158-161`、`Engine/03_AssetSystem/Importers/Texture/TextureManager.cpp:104-111`）[实测]，**当场析构 D3D12 资源**，调用的线程可能是任意线程。

### 7.4 【P1】消除主线程同步烘焙（启动卡顿）
- **问题**：启动路径 `LoadModel` → `LoadMaterials` → `CompileTextureOnDemand`（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:9-30`，内部 `LoadFromWICFile` `:105-117` + `GenerateMipMaps` `:206-220` + `Compress` `:223-243`）**全在主线程同步执行**，而 `ModelLoader.cpp:359-360` 的注释却声称「贴图通常通过独立的异步 I/O 线程池去加载，避免阻塞主线程」[实测] —— **注释与实现不一致**，实际没有任何异步路径（`ReadFileAsync` 无调用点，`Engine/00_Core/Utility/FileUtility.cpp:120-124）[实测]。
- **改哪里**：
  1. 把 `Engine/05_Scene/Model/ModelLoader.cpp:359-360` 的失实注释改掉（**文档层面的正确性也是本任务要修的**）。
  2. `LoadMaterials`（`Engine/05_Scene/Model/ModelLoader.cpp:56-77`）的纹理循环里，把 `CompileTextureOnDemand` + `LoadDDSFromFile` 的**配对**提交到一个后台执行体（复用已有 `Utility::ReadFileAsync`，`Engine/00_Core/Utility/FileUtility.cpp:120-124`），主线程只负责后续 `s_TextureHeap` 描述符拷贝（`Engine/05_Scene/Model/ModelLoader.cpp:154-155`）——**描述符拷贝必须留主线程**。

- **验证**：给启动打点（`LoadModel` 前后），对比改动前后「到首帧」的耗时；`Assets/Model/**/*.dds` 全删后重跑，确认烘焙结果与同步版逐字节一致（可用 `fc /b` 比较）。

### 7.5 【P2】默认纹理与采样器表的健壮性（低成本）
- **问题 1（越界回退已有，但描述符泄漏没有）**：每个材质 `Renderer::s_TextureHeap.Alloc(kNumTextures)`（`Engine/05_Scene/Model/ModelLoader.cpp:91`）[实测]，而 `DescriptorHeap::Alloc` 是**单调 bump**、无 Free，容量断言在 `Engine/02_RHI/Descriptor/DescriptorHeap.cpp:84-95` / 堆大小 4096（`Engine/04_Renderer/Renderer/Deferred/DeferredRenderer.cpp:454`）[实测] → 每次 `LoadMaterials` 都吃 `5 × numMaterials` 个描述符，重复加载同一模型会**线性泄漏**，上限约 818 个材质 [推断]。
  - **改哪里**：`Engine/05_Scene/Model/ModelLoader.cpp:91-92`。把「每材质一张 5 槽表」改为「每材质一张、按材质去重缓存」，或使用 RHI 的 DynamicDescriptorHeap（`DescriptorHeap.h:19-48` 的 `DescriptorAllocator` 支持 256/堆的分页分配）[实测]。
- **问题 2（0xFF 默认值有毒）**：`textureOptions` 缺失项被填 `0xFF`（`Engine/03_AssetSystem/Importers/Model/ModelConvert.cpp:400`），加载侧缺失也填 `0xFF`（`Engine/05_Scene/Model/ModelLoader.cpp:64-68`）[实测]；而 `0xFF` 会同时点亮 `kSRGB | kNormalMap | kDefaultBC | kQualityBC | kFlipVertical`，直接撞上 `ASSERT(!bInterpretAsSRGB || !bContainsNormals)`（`Engine/03_AssetSystem/Importers/Texture/TextureConvert.cpp:43-44`）[实测]，Release 下则会「把 sRGB 图当凹凸图算法线 + 翻转 Y + 压缩」[推断]。
  - **改哪里**：`0xFF` 改成 `0`（无选项）或一个显式的 `kNoOptions`；并且不要让「缺项」走默认全开。
- **验证**：构造一个 `images` 数量 > 材质引用数量的 glTF（存在未被任何材质引用的 image），确认不再触发该 ASSERT 且该图按「无选项」编译。

### 7.6 【P2】材质纹理槽位顺序的一致性护栏
- **问题**：`MaterialTextureData.stringIdx[kNumTextures]` 是按槽位顺序**二进制落盘**的（`Engine/05_Scene/Model/ModelLoader.h:19`、`Engine/03_AssetSystem/Assets/Constants/ConstantBuffers.h:31`）[实测]，而 `kNumTextures` 与顺序定义在 `ConstantBuffers.h`；一旦顺序变化，旧 `.ty` 会**静默**把 Normal 当 Emissive 用（`CURRENT_MINI_FILE_VERSION` 不变，版本校验不会触发，`Engine/05_Scene/Model/ModelLoader.cpp:251-265`）[实测]。
- **改哪里**：做 7.2 的版本 bump；并在 `ModelLoader::LoadModel` 读 `FileHeader` 之后、读 `materialTextures` 之前（`Engine/05_Scene/Model/ModelLoader.cpp:361-362`）加一条硬校验：`header.numTextures` 与 `kNumTextures` 的期望关系、以及 `sizeof(MaterialTextureData)` 的编译期常量一起断言。
- **验证**：人为把 `header.version` 保持不变但改动 `MaterialTextureData` 字段数量，确认加载被断言拦住而不是静默出错。

### 7.7 【P3｜不建议现在做】GPU 端 MIP / BC / 流送
- 明确列为**不做**：`AddDeferredMIPGen` 式延迟 MIP、`BlockCompress` 式 GPU 压缩、mip 反馈流送。理由见 §6.2 / §6.3 / §6.5；触发条件：当出现「运行时导入未压缩图」或「场景纹理显存超出预算且需要分级」这两个真实需求之一时再评估。
