## §1 职责边界（WE 里这些模块各自负责什么，边界在哪）

### 1.1 结论先行：WE 是"一个引擎库 + 多个可执行目标"的三层结构

WE 仓库把引擎与编辑器放在**两棵平级目录**，各自独立构建：

- **引擎库**：WickedEngine\CMakeLists.txt:107 add_library(WickedEngine_common OBJECT <SOURCE_FILES> <HEADER_FILES>)，:136 add_library(WickedEngine ALIAS <TARGET_NAME>)；WICKED_DYNAMIC_LIBRARY 决定 STATIC/SHARED [实测]。**该目录只产出库，不产出应用**。
- 引擎目录内**唯一的可执行**：WickedEngine\CMakeLists.txt:286 add_executable(offlineshadercompiler ...) —— 离线着色器编译器，与编辑器无关 [实测]。
- **编辑器可执行**：Editor\CMakeLists.txt:6 file(GLOB SOURCE_FILES CONFIGURE_DEPENDS *.cpp)、:7-8 list(FILTER ... EXCLUDE main_.* / stdafx.*)、:9 list(APPEND SOURCE_FILES main_<PLATFORM>.cpp)、:18 add_executable(Editor WIN32 <SOURCE_FILES>)（Windows 分支；非 Windows 为 :34）、:20-22 target_link_libraries(Editor PUBLIC WickedEngine)（非 Windows 为 :36-38）、:56 target_precompile_headers(Editor PRIVATE "stdafx.h")、:59 add_dependencies(Editor Content)、:62-67 POST_BUILD 拷贝 dxcompiler 与 Editor/fonts [实测]。依赖方向**单向**：Editor → 引擎库。
- **开关**：CMakeLists.txt:27 option(WICKED_EDITOR "Build WickedEngine editor" ON)；CMakeLists.txt:199-201 if (WICKED_EDITOR) add_subdirectory(Editor) endif()；:203-205 if (WICKED_TESTS) add_subdirectory(Samples/Tests)；:223 区域 if (WICKED_WINDOWS_TEMPLATE) add_subdirectory(Samples/Template_Windows) —— 三个开关彼此独立 [实测]。→ **存在"不构建编辑器"的官方构建路径**（§7.5 的主证据）。

### 1.3 三条硬边界（有反例才成立，这里给反例）

1. **引擎不认识编辑器**。在 WickedEngine\ 全树 grep "Editor" 只命中 wiLua.cpp:59 IsThisEditor、:65 ReturnToEditor、:183/:753 调用、:376-377 RegisterFunc、:794 void EnableEditorFunctionality(wi::Application* application, wi::RenderPath* renderpath) 与 wiLua.h:204-206 的声明/注释 [实测]。参数类型是 wi::Application* / wi::RenderPath*，**不是 Editor 类型**，所以这条钩子不建立反向依赖。
2. **引擎不认识模型格式**。glTF/FBX/OBJ/PLY 解析器连同第三方库全部位于 Editor\ [实测]。引擎侧只认自己的场景序列化（wiScene_Serializers.cpp）。→ 在 WE 里，"资产导入"是**编辑器职责而非引擎职责**；引擎运行时只做资源（贴图/音频/脚本）加载，见 wiResourceManager.h:66-70 的 GetSupportedImageExtensions 等接口 [实测]。
3. **GUI 库不持有场景**。wi::gui::GUI 的私有成员只有 wi::vector<Widget*> widgets / bool focus / bool visible（wiGUI.h:235-237）[实测]，没有任何 Scene*/Renderer* 成员。GUI 只依赖"2D 绘制能力"，不依赖"世界状态"。

### 1.4 编辑器与引擎的耦合点到底在哪（一条）

编辑器把**自己的 Scene 实例注入渲染路径的指针**，而不是让渲染路径去查全局单例：
- Editor.cpp:6705（EditorComponent::SetCurrentScene 内）this->renderPath->scene = &scenes[current_scene].get()->scene;，:6706 同样注入 camera [实测]。
- 被注入方的成员声明是裸指针：wiRenderPath3D.h:202 wi::scene::Scene* scene = &wi::scene::GetScene();，wiRenderPath3D.h:197 wi::scene::CameraComponent* camera = &wi::scene::GetCamera(); [实测]。
- 默认值来自全局单例：wiScene.h:652 inline Scene& GetScene() [实测]。

即：**引擎提供"默认单例 + 可替换指针"两套入口**，编辑器用后者实现多标签页场景。这条设计让"无编辑器构建"只需保留单例路径即可工作，是解耦能落地（而非仅口号）的机制性证据。

### 1.5 任务要求的三个正面回答（本节给出，§6 再次落到决策）

**(a) WE 的编辑器是同一进程内的组件、独立可执行文件、还是两者都有？**
答：**以独立可执行文件为主，同时"编辑器 UI"在进程内是一个普通组件**。
- 独立 exe 的证据：Editor\CMakeLists.txt:18 add_executable(Editor WIN32 ...)（非 Windows :34）、:20-22 target_link_libraries(Editor PUBLIC WickedEngine)、Editor\main_Windows.cpp:9 自有 main 与消息循环 [实测]。
- 进程内组件的证据：class Editor : public wi::Application（Editor\Editor.h:288）+ EditorComponent : public wi::RenderPath2D（Editor.h:17）——UI 本身只是一个渲染路径组件，走 Load/Update/Render/Compose 生命周期（Editor.cpp:550/:1632/:3602/:4913）[实测]。
- 但**组件化不等于可嵌入**：Editor 类型定义在 Editor/ 子树、仅被 Editor 目标编译，引擎库不含它，因此没有"把编辑器作为库嵌进别的宿主"的路径 [实测；[推断]：未检查是否存在 Editor 的静态库目标，EDITOR\CMakeLists.txt 只有 add_executable，无 add_library]。

**(b) 若本项目不需要编辑器，WE 的哪些工具模块仍值得借鉴、哪些明确不该抄？**
- 值得借鉴（按性价比排序）：① CPU/GPU 区间计时（wiProfiler，679 行，可裁剪到 ~200 行）——因为 TR 的 RHI **已经**提供了时间戳原语但无人调用（CommandContext.h:168-169、:828-836）[实测]；② 有序异步初始化 + 就绪查询（wiInitializer.h:5-34，TR 目前在 GameCore.cpp:43-60 手写顺序初始化）[实测]；③ 日志的等级/落盘/崩溃兜底三件套（wiBacklog.h:28-35/:76-83/:96），TR 只有 Utility::Printf（Utility.h:45-57）+ LOG_INFO/LOG_TRACE（Utility.h:140/:142/:144）[实测]；④ 通用小工具按需点单（FileDialog（wiHelper.h:160）、GetSaveDataPath（:147）、Lossless Compress（:235））。
- 明确不该抄：wiGUI 全库与控件体系（6480+1117 行）、主题/本地化/停靠（wiGUI.h:110/:258/:260-261）、2D 文本渲染与 SDF 字体（wiFont 820 行）、backlog 的屏幕控制台与 Lua 阻塞（wiBacklog.h:39-48/:69-70）、模型导入器与第三方解析库（7212 行，且它们属于编辑器目标）[实测]。

**(c) WE 的日志/性能计时模块有多重？值不值得为 TR 引入轻量 profiler？**
- 规模数字（wc -l 实测）：wiProfiler.cpp 679 / .h 73（合计 752 行）；wiBacklog.cpp 787 / .h 97（合计 884 行）；对照：TR 全引擎 Engine\ 共 24332 行（其中 00_Core 2934、01_Application 1572、02_RHI 10523、03_AssetSystem 4758、04_Renderer 2947、05_Scene 1598，目录行数为逐目录实测 [实测]）。
- 结论：**值得，但只值得"计时器内核"，不值得"屏幕控制台"**。理由：TR 已具备全部前置条件——时间戳查询的声明与实现（CommandContext.h:168-169 声明、:828 inline EndQuery(..., D3D12_QUERY_TYPE_TIMESTAMP, ...)、:834-835 ResolveTimeStamps→ResolveQueryData）已存在且**全仓库无调用者**（grep "InsertTimeStamp" 仅命中声明与定义）[实测]；现有 Utility::Printf 已双通道输出（debugger + tooiyume_log.txt 追加写，Utility.h:32-57）[实测]。所以最小可行 profiler 是"在 RHI 之上加一个 ~200 行的区间采集器（含按帧槽位的回读缓冲）"，把结果打到既有日志通道，而不是复制 WE 的浮层显示（wiProfiler.cpp:381 的文本输出依赖 wiFont/wiImage）。

### §7.5 对本项目「不引入编辑器」的架构确认

结论：**TR "不做编辑器"的决策可以被 WE 的构建拓扑与运行期接口双重验证**——WE 自己就是"引擎库 + 可选编辑器 exe"，且官方维护了多个无编辑器宿主。证据链如下（全部 [实测]）：

1. **官方构建开关存在**：CMakeLists.txt:27 option(WICKED_EDITOR "Build WickedEngine editor" ON) 控制 CMakeLists.txt:199-201 if (WICKED_EDITOR) add_subdirectory(Editor) endif()。把它设为 OFF 后，编辑器目录根本不进构建；同级的 WICKED_TESTS（:203-205）与 WICKED_WINDOWS_TEMPLATE（:223 区域）是**独立开关**，互不牵连。
2. **引擎目标只产库**：WickedEngine\CMakeLists.txt:107 add_library(WickedEngine_common OBJECT ...)、:136 add_library(WickedEngine ALIAS <TARGET_NAME>)；引擎目录内唯一可执行是 :286 add_executable(offlineshadercompiler ...)（离线着色器编译器，与编辑器无关）。
3. **依赖单向且可 grep 验证**：Editor\CMakeLists.txt:20-22 target_link_libraries(Editor PUBLIC WickedEngine)（非 Windows 分支 :36-38）；反向在 WickedEngine\ 全树 grep "Editor" 只命中 Lua 钩子（wiLua.cpp:59 IsThisEditor、:65 ReturnToEditor、:794 EnableEditorFunctionality(wi::Application*, wi::RenderPath*)），参数类型不是编辑器类型。
4. **官方维护无编辑器宿主**：Samples\Template_Windows\main.cpp:3 wi::Application application;（直接实例化引擎基类）；同族还有 Template_Linux / Template_MacOS / Template_iOS，以及 Samples\Tests。模板工程只从 Editor\ 复制一个数据文件 startup.lua，**不存在代码依赖**。
5. **引擎内部用"可替换指针"而非"必须有编辑器"**：wiRenderPath3D.h:202 wi::scene::Scene* scene = &wi::scene::GetScene();（默认单例，wiScene.h:652）；编辑器仅在切标签页时改写它（Editor.cpp:6705-6706）。也就是说"编辑器模式"是对引擎接口的一种**使用方式**，不是引擎的一种**构建模式**。
6. **工具层挂在引擎帧循环，不在编辑器**：wi::profiler::BeginFrame/EndFrame（wiApplication.cpp:268/:387）与 wi::backlog::Update（:401）位于引擎的 Application::Run 内；编辑器只改外观（Editor.cpp:326-327 backlog::setFontColor/setBackgroundColor）。所以"不做编辑器"不会失去日志与计时能力。

**对 TR 的三条落地要求**（若采纳"不引入编辑器"）：
- **保留场景/相机的可替换接缝**：Scene 实例化 + 渲染侧持 Scene*（对应 WP3），否则将来若要接工具就得改渲染路径。
- **保留应用层 UI 挂点**：TR 已有 IGameApp::RenderUI(GraphicsContext&)（GameCore.h:24）[实测]——不要为了让"没有 UI"而删掉它，它是等价于 WE "UI 即 RenderPath 组件"的接缝。
- **诊断能力必须独立于编辑器存在**：按 §6 #1/#2/#3 在引擎层落地，而不是等有编辑器再说。

**反向确认（哪些"不做编辑器"会失去）**：资产导入（WE 的 glTF/FBX 导入器只在 Editor 目标里，§4.6）、可视化编辑与撤销历史（Editor.h:226-251 的 EditorScene.history）。TR 若不做编辑器，这两项必须用别的手段替代：离线转换工具 + 版本控制，而不是运行期导入。
