## 4. 设计概览

### 4.1 模块职责与依赖

| 模块 | 职责 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| `scripts/build.bat` / `run.bat` | **唯一构建/运行入口** | VS + VCPKG_ROOT | 直连 cmake --preset |
| `scripts/audit_recheck.bat` | 只读复核 13 项 | bash/pwsh + grep | 任何写操作 |
| `docs/AIWorkLogs/_TEMPLATE_WP_施工日志.md` | WP1–WP8 模板 | skill 模板 | 自造字段 |

### 4.2 调用链（构建路径，实测）

```
scripts/build.bat <Config> [clean]
  → vswhere 定位 VS → vcvars64.bat
  → 还原 caller 的 VCPKG_ROOT（vcvars64 会覆盖它）
  → 定位 cmake.exe / ninja.exe
  → cmake -S . -B out/build/<Config> -G Ninja -DCMAKE_TOOLCHAIN_FILE=<vcpkg>
  → cmake --build out/build/<Config>
产物：out/build/<Config>/Demos/<App>/<App>.exe
```

> **禁止 `cmake --preset`** 的原因（实测）：`CMakePresets.json` 的 `binaryDir` 是 `${sourceDir}/out/build/${presetName}`（如 `out/build/x64-debug`），与 `build.bat` 的 `out/build/<Config>`（如 `out/build/Debug`）**不是同一个目录**。两目录并存会出现「构建了但跑到旧 exe」。

### 4.3 数据流（基线证据链）

```
HEAD ──tag→ audit-legacy-51c09d0（02/09 附录A 的判定基准）
  │
  └─收编 K1/K2/K3──commit→ tag arch-baseline-2026-10
                              │
                              └─branch→ arch/wp1-decouple
                                                │
                        baseline 截图 + 构建日志 ←┘（后续 WP 的「不回退」判据）
```

### 4.4 关键设计决策与替代方案

| 决策 | 选择 | 替代方案（被否原因） |
|---|---|---|
| D-WP0-1 | 打**两个**标签 | 只打一个（审计基线与施工基线永久混淆，09 §1-J3） |
| D-WP0-2 | 收编为一个**提交** | 分散多提交（回滚粒度失控，且无法对应 §2.2 分类） |
| D-WP0-3 | 复核脚本**只读** | 允许脚本顺手修（违反 skill「不得覆盖未提交改动」） |
| D-WP0-4 | 构建走 `build.bat` | `cmake --preset`（产物目录分叉，见 §4.2） |

## 5. 关键实现讲解

### 5.1 复核脚本的 13 项检查（每项写明判据）

| # | 检查 | 判据 | 期望（当前树） |
|---|---|---|---|
| R01 | `LightingPS.hlsl` 硬编码分辨率 | 无 `1920`/`1080` 字面量 | PASS（已修） |
| R02 | `StaticMeshVS.hlsl` 切线 UNORM 还原 | 存在 `* 2.0 - 1.0` | PASS（已修） |
| R03 | `Utility.h` 的 `RELEASE` 宏 | 记录当前替代机制 | INFO |
| R04 | `Display.cpp` resize 链 | `Display::Resize` 存在且被 GameCore 调用 | PASS（已修） |
| R05 | `MaterialFlags.h` 空文件 | 行数/字节数 | **FAIL**（缺陷仍在） |
| R06 | `GBufferPS.hlsl` 的 `flags` 被消费 | 声明后有使用点 | **FAIL** |
| R07 | `SkyboxPS.hlsl` 无 tonemap/sRGB | 是否仍直接 return | **FAIL** |
| R08 | `DeferredRenderer.cpp` 空壳 Pass | PIX 事件后有无 GPU 命令 | **FAIL**（6 段空壳） |
| R09 | `ColorBuffer` 默认带 UAV | `ALLOW_UNORDERED_ACCESS` 存在 | INFO（有利事实） |
| R10 | `GpuResource::Destroy` 立即 Release | 是否已改入队 | **FAIL** |
| R11 | `PipelineDesc` PSO key 含 RT 格式 | key 位域清单 | **FAIL** |
| R12 | `PassType` 已拆分 | 枚举值清单 | **FAIL** |
| R13 | 描述符堆容量与占用 | 4096 槽剩余量 | INFO |

> **R05/R06/R07/R08 期望 FAIL 是有意的**：它们证明脚本**真的在读代码**而不只是返回成功。若某天变 PASS，说明并行会话修了它，此时应更新 `09` 附录 A，而不是改期望值。

### 5.2 脚本自身的硬约束

1. **只读**：不得修改任何文件；
2. 输出行格式固定：`[PASS]/[FAIL]/[INFO] Rnn 名称 证据`；
3. 退出码：无 FAIL → 0，有 FAIL → 1；
4. 末尾打印 `git rev-parse HEAD` 与 `git status --porcelain | wc -l`，保证复核可追溯。

### 5.3 边界条件

| 情况 | 处置 |
|---|---|
| 并行会话期间仍在写文件 | **停止 WP0**，记 BLOCKED，不 stash/checkout |
| 无 GPU 或驱动 | B6 记「环境受限，未执行」，状态最高 IMPLEMENTED_UNVERIFIED |
| `VCPKG_ROOT` 未设 | 先解决环境，不得把构建失败记成「通过」 |
| 构建超时被杀 | 记 FAILED/超时，**不得**写「运行通过」（AGENTS.md） |

## 12. 用户学习路线

### 12.1 建议阅读顺序

1. `09_升级实施建议.md` §1-J3（为什么要两个基线）
2. `09` §4.1（WP0 的 5 条动作）
3. `AGENTS.md` 构建与验证章节
4. `docs/AI/渲染器AI编程流程skill/references/03_build-verify-evidence.md`
5. 本文件 §8 的验证分层表

### 12.2 必须掌握的概念

- **审计基线 vs 施工基线**：前者是文档结论的锚点，后者是代码的起点；
- **收编 ≠ 修复**：WP0 只是把别人的改动变成一个提交，不改其内容；
- **只读复核**：脚本的价值是「能证明自己会失败」，不是「总是返回成功」。

### 12.3 关键机制如何连接

`build.bat` → 产物目录唯一化 → 截图证据可信 → 后续 WP 的「不回退」判据成立 → 结构迁移可验收。
