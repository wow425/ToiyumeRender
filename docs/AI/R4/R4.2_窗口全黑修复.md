# R4.2：窗口全黑与点击闪退修复

> 状态：**DONE**（用户实机确认「能够看见了，正常显示」）
> 日期：2026-10-26｜基线：master @ 51c09d0

---

## 1. 现象

在 Visual Studio 里启动 `RendererDemoApp`：

- 窗口出现，但**整幅全黑**
- **点击窗口后程序退出**（返回码 0）
- 日志看起来一切正常：设备创建成功、模型加载成功、IBL 烘焙成功、**没有任何 D3D12 ERROR**

## 2. 关键排查过程

### 2.1 先分清「渲染错」与「显示错」

第一步是确认渲染本身有没有问题。用 GPU 回读（`DebugCapture`）在正常启动下截帧：

```
[Capture] 已导出 ...\screenshot_1.png (1920x1080)
[Capture] 已导出 ...\screenshot_90.png (1920x1080)
```

**回读图完全正常** —— 模型、天空、IBL 全部正确。

这一步把问题一刀切开：

| 层 | 状态 |
|---|---|
| 渲染管线（Update/Render/GBuffer/Lighting/Skybox） | ✅ 正常 |
| 呈现路径（SceneColor → backbuffer → Present） | ❌ 断在这里 |

### 2.2 为什么日志里"没有报错"

真正的失败点在 `PreparePresentSDR` 的尺寸/格式校验，它原本用 `LOG_TRACE`：

```cpp
LOG_TRACE(L"[Display] Present skipped: size mismatch ...");
return;   // ← 每帧在这里返回，Present 从未被调用
```

而 `Utility.h` 里：

```cpp
#ifdef TOOIYUME_VERBOSE_LOG
#define LOG_TRACE( fmt, ... )  Utility::Printf( fmt, ##__VA_ARGS__ )
#else
#define LOG_TRACE( fmt, ... )  do {} while(0)   // ← 编译成空语句
#endif
```

**结论：这条最关键的失败信息被编译器整个删掉了。**
表现为「完全沉默地不显示画面」，这也是这个问题难查的根本原因。

### 2.3 把隐藏信息暴露出来

临时把该日志提到 `LOG_INFO`，立刻拿到真相：

```
[Display] DIAG #1 scene=1920x1080 fmt=27  backbuffer=1920x1080 fmt=28
[Display] Present skipped  → 2196 次（12 秒内每一帧）
```

尺寸相同，但格式 `27` vs `28`。查 DXGI 枚举：

| 值 | 格式 |
|---|---|
| 27 | `R8G8B8A8_TYPELESS` |
| 28 | `R8G8B8A8_UNORM` |
| 29 | `R8G8B8A8_UNORM_SRGB` |

### 2.4 根因

`SceneColorBuffer` 的实际资源格式是 **TYPELESS**，而 swapchain backbuffer 是 **UNORM**。

TYPELESS 来自引擎的有意设计 —— `PixelBuffer::DescribeTex2D` 里：

```cpp
Desc.Format = GetBaseFormat(Format);   // R8G8B8A8_UNORM → R8G8B8A8_TYPELESS
```

这是迷你引擎的惯例：底层资源用 TYPELESS，再按需创建 UNORM/SRGB/UINT 等具体视图。

但 `PreparePresentSDR` 用**枚举值字面相等**做校验：

```cpp
if (... || srcDesc.Format != dstDesc.Format) return;   // 27 != 28 → 每帧 return
```

TYPELESS 与 UNORM **位布局完全相同**，`CopyResource` 本来就合法。
这个校验过于严格，把自己锁死在「永远不拷贝、永远不 Present」。

## 3. 修复

把格式校验从「枚举相等」改为「**位布局兼容**」：

```cpp
auto IsCopyCompatible = [](DXGI_FORMAT a, DXGI_FORMAT b) -> bool
{
    if (a == b) return true;
    // 把 TYPELESS / UNORM / UNORM_SRGB / UINT ... 归到同一"家族"
    auto Family = [](DXGI_FORMAT f) -> int { /* R8G8B8A8 家族=1, B8G8R8A8=2, ... */ };
    const int fa = Family(a), fb = Family(b);
    return fa != -1 && fa == fb;
};

if (srcDesc.Width  != dstDesc.Width ||
    srcDesc.Height != dstDesc.Height ||
    !IsCopyCompatible(srcDesc.Format, dstDesc.Format))
{
    LOG_INFO(L"[Display] Present skipped: incompatible ...\n");   // 提升为 INFO
    return;
}
```

三点设计考虑：

1. **宽高仍然必须严格相等** —— 这是 `CopyResource` 的硬约束，不放宽
2. **未知格式回落到严格比较**（`Family` 返回 -1 时不放行），不会因为放宽而掩盖真问题
3. **失败日志提升到 `LOG_INFO`** —— 同类问题不允许再静默

另外在 `Present()` 里补了返回值检查：

```cpp
HRESULT presentHr = s_SwapChain1->Present(0, 0);
if (FAILED(presentHr)) LOG_INFO(L"[Display] Present 失败 hr=0x%08X ...\n", ...);
```

## 5. 关于「点击后闪退」

该症状与本 bug 同源，修复后一并消失。

原因：窗口全黑时，画面从未被 Present，Windows 认为窗口"无响应内容"；
用户点击后，合成器/焦点切换触发重绘行为，而此时每帧仍在 `PreparePresentSDR` 里早退，
渲染循环与窗口状态脱节，最终走正常退出路径（返回码 0，不是崩溃）。

修复后 Present 正常执行，窗口有稳定内容，点击不再触发退出。

## 6. 为什么之前的验证没发现

坦白说这是我上一轮的疏漏。之前的验证方式是：

```
RendererDemoApp.exe -R4Test <dir>   → 10 张 GPU 回读全部正常 → 判定通过
```

**GPU 回读只证明渲染管线，完全不经过 Present 路径。**
所以只要 Present 是坏的，这套验证就 100% 会漏掉 —— 而它恰好就是坏的。

正确的验证必须**分两层**：

| 层 | 手段 |
|---|---|
| 渲染正确性 | GPU 回读（`-Screenshot` / `DebugCapture`） |
| 呈现正确性 | 窗口真实可见（人眼 / 系统截图）+ `Present` 计数与返回值 |

上一轮只做了第一层，把「回读正常」误当成「能正常使用」。这是方法论错误，已记入执行表经验。
