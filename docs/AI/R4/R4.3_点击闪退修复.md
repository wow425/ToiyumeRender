# R4.3：点击鼠标导致程序退出的修复

> 状态：**DONE**（连点 10 次 + 右键 + WASD + Escape 全部实测）
> 日期：2026-10-26｜基线：master @ 51c09d0

---

## 1. 现象

上一轮修好黑屏后，用户报告：

> 渲染正常，但我一旦点击屏幕就自动闪退。

注意这次和上一轮的区别：

| | R4.2 黑屏 | R4.3 点击退出 |
|---|---|---|
| 画面 | 全黑 | **正常** |
| 点击 | 退出 | **退出** |
| 根因 | Present 路径断了 | **输入映射错了** |

两个问题**完全独立**，只是症状里都有"退出"，很容易被误认为同一个 bug。

---

## 2. 关键排查转折：它不是崩溃

第一反应是拿调试器抓崩溃调用栈。用了两层手段：

1. **cdb 附加**：设 `sxe av; sxe ch`（访问违例 / 立即数变更）→ 点击后**没有触发任何异常**
2. **代码里加 `SetUnhandledExceptionFilter`**：全局捕获未处理异常，把异常码、故障模块、调用栈写日志

结果：**日志里一条 `[CRASH]` 都没有**。

这推翻了我的初始假设。既然是"干净退出"，那只有一种可能：

> `UpdateApplication()` 返回了 `false`

而它返回 `!game.IsDone()`，`IsDone()` 的实现是：

```cpp
bool IGameApp::IsDone(void)
{
    return GameInput::IsFirstPressed(GameInput::kKey_escape);
}
```

**所以：点击鼠标 → 判定为按下 Escape → 正常退出。**

---

## 3. 根因：DIK 扫描码被当成 VK 虚拟键码用

### 3.1 两张码表本质不同

Windows 上"按键"有两套完全独立的编码：

| 体系 | 含义 | Escape 的值 | W 的值 |
|---|---|---|---|
| **DIK**（DirectInput 扫描码） | 物理按键位置 | 0x01 | 0x11 |
| **VK**（虚拟键码） | 逻辑按键含义 | 0x1B | 0x57 |

### 3.2 代码里的错位

`GameInput.cpp` 里原本只有**一张**映射表 `s_DXKeyMapping`，填的是 DIK：

```cpp
s_DXKeyMapping[GameInput::kKey_escape] = 1;    // DIK_ESCAPE = 0x01
s_DXKeyMapping[GameInput::kKey_w]      = 17;   // DIK_W = 0x11
```

而聚合键位时：

```cpp
const unsigned char vk = s_DXKeyMapping[i];              // ← 拿到的是 DIK
if (!down && windowActive && vk != 0)
    down = (::GetAsyncKeyState(vk) & 0x8000) != 0;       // ← 却当成 VK 用
```

### 3.3 致命巧合

```
DIK_ESCAPE = 0x01
VK_LBUTTON = 0x01        ← 鼠标左键！
VK_ESCAPE  = 0x1B
```

`GetAsyncKeyState(0x01)` 查询的是**鼠标左键**的状态。

于是形成这条链路：

```
鼠标左键按下
   → GetAsyncKeyState(0x01) 返回按下
   → s_Buttons[0][kKey_escape] = true
   → IsFirstPressed(kKey_escape) == true
   → IsDone() == true
   → UpdateApplication() 返回 false
   → 主循环 break → TerminateApplication → exit(0)
```

**整个过程没有任何错误**，所以日志干净、调试器也抓不到异常。

### 3.4 顺带被掩盖的第二个 bug

同一张错表还导致了字母键全部映射错误：

```
DIK_W = 0x11  →  实际查到的是 VK_CONTROL（左 Ctrl）
DIK_A = 0x1E  →  实际查到的是 VK_...（无关键）
```

所以相机 WASD 一直"时灵时不灵"——只有在 DirectInput 通路（`s_Keybuffer`）可用时才正常，
一旦回落到 `GetAsyncKeyState` 通路就全错。之前一直没查出来，是因为"有时能用"。

---

## 4. 修复

核心思路：**按用途拆成两张表**，而不是继续混用一张。

### 4.1 新增 VK 表

```cpp
unsigned char s_DXKeyMapping[GameInput::kNumKeys]; // DigitalInput -> DIK (扫描码)
unsigned char s_VKMapping[GameInput::kNumKeys];    // DigitalInput -> VK  (虚拟键码)
```

`s_VKMapping` 用标准 VK 宏填满：

```cpp
s_VKMapping[kKey_escape] = VK_ESCAPE;   // 0x1B，不再是 0x01
s_VKMapping[kKey_w]      = 'W';         // 0x57
s_VKMapping[kKey_a]      = 'A';
...
```

### 4.2 分开使用

```cpp
// 通路 1/3：DirectInput 的 s_Keybuffer 用 DIK 索引
const unsigned char dik = s_DXKeyMapping[i];
if (dik < 256 && (s_Keybuffer[dik] & 0x80) != 0)
    down = true;

// 通路 2：GetAsyncKeyState 必须用 VK
const unsigned char vk = s_VKMapping[i];
if (!down && windowActive && vk != 0)
    down = (::GetAsyncKeyState(vk) & 0x8000) != 0;
```

### 4.3 为什么保留 `vk != 0` 判断

未映射的键在表里是 0。但要注意 **VK 里 0x00 不是有效键码**，
而 `VK_LBUTTON = 0x01` 是有效值——所以不能用"非零即有效"去推断，
必须依赖显式填表 + 这个零值哨兵。

## 5. 验证

用**真实鼠标事件**（`SetCursorPos` + `mouse_event`，走完整输入路径），
而不是 `PostMessage` 模拟（后者不经过 `GetAsyncKeyState`）：

| 测试项 | 修复前 | 修复后 |
|---|---|---|
| 启动后存活 | ❌ 自己就退出了 | ✅ True |
| **连点 10 次左键**（10 个不同位置） | ❌ 第 1 次就退出 | ✅ **True** |
| 点击右键 | — | ✅ True |
| WASD 四个键 | — | ✅ True |
| **按 Escape** | — | ✅ **正常退出（exit 0）** |

最后一项很重要：**Escape 退出功能必须保留**，不能为了修 bug 把正常功能也弄坏。

---

## 6. 为什么前一版没发现

回看这个 bug 的潜伏条件：

1. **只在 `GetAsyncKeyState` 通路生效时才暴露**——如果 DirectInput 的
   `s_Keybuffer` 能正常提供按键，第一条通路已经 `down = true`，
   第二条通路会被 `if (!down && ...)` 短路，bug 不触发。
2. **R1 引入这条通路时是为了修"WASD 完全失效"**——当时只验证了
   "WASD 能动了"（因为字母键碰巧映射到了某个有效 VK），
   没有验证"Escape 是否还能正常触发"。
3. **点击退出这个现象太容易被归因为崩溃**——上一轮黑屏也在退出，
   很自然认为"同一个问题还没修干净"。

## 7. 方法论收获

### 7.1 "闪退"要先分类

| 类型 | 特征 | 排查手段 |
|---|---|---|
| **崩溃** | 非零退出码、有异常码 | 调试器 `sxe av`、`SetUnhandledExceptionFilter` |
| **主动退出** | **退出码 0**、无异常、日志干净 | 查退出条件（`IsDone` 之类） |

本次是后者。如果一开始就盯着"崩溃"找，会一直找不到——因为根本没有崩溃。

**判断依据很简单：看退出码。** 0 = 程序自己决定退出。

### 7.2 模拟输入要选对层级

```
PostMessage(WM_LBUTTONDOWN)
   → 走 WndProc → ImGui_ImplWin32_WndProcHandler
   → **不经过 GetAsyncKeyState**

mouse_event / SetCursorPos
   → 系统级注入 → 走完整的硬件输入路径
   → **会经过 GetAsyncKeyState**  ← 这才是本次需要验证的
```

我一开始用 `PostMessage` 复现不出来，就是这个原因。后来换 `mouse_event` 立刻复现。

### 7.3 遇到"无异常退出"，第一件事是读退出条件

不要急着加日志，先看 `while` 循环的判定条件。`IsDone()` 只有一行，
扫一眼就能看到它依赖 Escape——然后再去看 Escape 是怎么被置位的。
