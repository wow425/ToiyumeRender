# R4.1：Visual Studio 内可直接构建与运行

> 状态：**DONE**（VS 路径 / 脚本路径 / Release 全部实测）
> 日期：2026-10-26｜基线：master @ 51c09d0

---

## 1. 问题现象

在 Visual Studio 里打开本仓库（`D:\...\TooiyumeRender`）后，CMake 无法配置/构建。但
命令行执行 `scripts\build.bat Debug` 一直是成功的 —— 说明代码没问题，是**构建配置**的问题。

## 2. 四个真实根因（按严重度）

### 2.1 `CMakePresets.json` 有非法字段 → VS 连 presets 都读不出来

根对象里写了非法的 `_comment` 字段。CMake 的 presets 规范**不允许**未定义的根字段，
直接拒绝解析整个文件：

```
CMake Error: Could not read presets from ...
Error: @4,15: Invalid extra field "_comment" in root object
```

VS 的 CMake 集成正是通过 presets 决定配置的，因此这一步失败 = 项目在 VS 里完全无法配置。
命令行 `build.bat` 不走 presets，所以一直没暴露。

**修复**：删除 `_comment`（注释改为各字段的 `description`），并按规范补 `cmakeMinimumRequired`、
`buildPresets.configuration`。

### 2.2 依赖 hard-depend on `VCPKG_ROOT` 环境变量 → VS 不读 shell 变量

原 `CMakeLists.txt` 在拿不到 `CMAKE_TOOLCHAIN_FILE` 时要求 `VCPKG_ROOT`，否则 `FATAL_ERROR`。
VS 的 CMake 集成**不继承**用户在 cmd 里 `set VCPKG_ROOT=...` 的结果，于是必然失败。

**修复**：改为双路径，优先级从高到低：

| 路径 | 触发条件 | 行为 |
|---|---|---|
| A | 显式给了 `CMAKE_TOOLCHAIN_FILE` 或设了 `VCPKG_ROOT` | 尊重它，走标准 vcpkg manifest 流程（命令行/CI） |
| B | 都没有 | 把仓库内 `vcpkg_installed/x64-windows` 加进 `CMAKE_PREFIX_PATH` |

路径 B 成立的关键：vcpkg 生成的 `*-config.cmake` 用 `_IMPORT_PREFIX` **相对定位**自身，
不依赖 toolchain。实测无任何环境变量时，`directxtex` / `directxmesh` / `DirectX-Headers`
全部解析成功。

### 2.3 运行时 DLL 部署依赖 toolchain 副作用 → 走路径 B 就缺 DLL

`DirectXTex.dll` / `DirectXMesh.dll` 原先由 vcpkg toolchain 的 `VCPKG_APPLOCAL_DEPS` 自动拷贝。
路径 B 不加载 toolchain，这两个 DLL 就没人拷，exe 启动直接报缺 DLL。

**修复**：新增 `Engine/20_cmake/DeployRuntimeDlls.cmake`，提供函数
`tooiyume_deploy_runtime_dlls(<target>)`，显式部署 5 个 DLL
（DirectXTex / DirectXMesh / dxcompiler / dxil / WinPixEventRuntime），
并按 Debug/Release 选择正确变体（`debug/bin` vs `bin`）。

### 2.4 仓库内 `vcpkg_installed` 的 DirectXMesh 缺 `dx12` feature → 链接失败

这是最隐蔽的一条。前三条修完后仍报：

```
MeshConvert.cpp.obj : error LNK2019: 无法解析的外部符号
  DirectX::ComputeInputLayout(struct D3D12_INPUT_LAYOUT_DESC const &, ...)
MeshConvert.cpp.obj : error LNK2019: 无法解析的外部符号 DirectX::VBReader::Initialize
```

排查过程（值得记录）：

1. 两个构建的 `LINK_LIBRARIES` 完全相同 → 不是链接顺序或路径问题
2. 两个构建的 `DEFINES` 完全相同 → 不是宏差异
3. 直接对比两个 `DirectXMesh.lib` 的 md5 → **不同**
4. `grep D3D12_INPUT_LAYOUT_DESC` → 仓库根目录那份 **0 处**，旧构建目录那份 **5 处**

结论：仓库根目录的 `vcpkg_installed`（5 月生成）装的是**不带 `dx12` feature** 的 DirectXMesh，
其 `DirectXMesh.lib` 里只有 D3D11 重载；代码用的是 D3D12 重载，因此链接不上。
旧构建目录 `out/build/Debug/vcpkg_installed` 是后来重新解析的，带 `dx12`，所以能过。

**修复**：用 `vcpkg.json` 声明的 feature 重新装到仓库根目录：

```bat
F:\VS\rep\vcpkg\vcpkg.exe install --triplet x64-windows ^
  --x-install-root=D:\...\TooiyumeRender\vcpkg_installed
```

装完 `DirectXMesh.lib` 里 D3D12 符号从 0 处变为 5 处。

| 路径 | 命令（均在不设 VCPKG_ROOT 下执行） | 结果 |

| Release | `--preset x64-release` + `build-release` | **101/101** |
| 旧脚本回归 | `scripts\build.bat Debug` / `Release` | 均 exit 0（未破坏） |

### 3.2 从零复现（模拟 VS 打开项目）

完整流程：删除 `out/build/x64-debug` → `--list-presets` → `--preset x64-debug` → `--build`，
全程 `set VCPKG_ROOT=`（清空）。结果 `ALL_OK`，日志显示
`[deps] 使用仓库内依赖目录: .../vcpkg_installed/x64-windows`。

| 检查 | 结果 |

## 4. 变更文件

| 文件 | 改动 |
|---|---|
| `CMakePresets.json` | 删非法 `_comment`；补 `cmakeMinimumRequired` / `buildPresets.configuration` |
| `CMakeLists.txt` | vcpkg 依赖改双路径（toolchain 或仓库内 `vcpkg_installed`）；include 部署函数模块 |
| `Engine/20_cmake/DeployRuntimeDlls.cmake` | **新增**，运行时 DLL 部署函数 |
| `Engine/CMakeLists.txt` | 移除不可能生效的部署循环（Engine 早于 Demos，`if(TARGET)` 恒假） |
| `Demos/*/CMakeLists.txt` | 移除各自硬编码的 vcpkg DLL 拷贝（会覆盖 Debug 版），改为调用统一函数 |
| `vcpkg_installed/` | 用 `vcpkg.json` 的 `dx12` feature 重新安装（补齐 D3D12 符号） |

## 5. 关键设计决策

| 决策 | 选择 | 替代方案与代价 |
|---|---|---|
| 依赖解析 | 双路径：toolchain 优先，否则 `CMAKE_PREFIX_PATH` | 强制要求 `VCPKG_ROOT`：VS 里永远配不起来 |
| DLL 部署 | 显式函数 + 各 Demo 自调用 | 根目录集中循环：`add_custom_command(TARGET)` 跨目录直接报错 |
| DLL 变体 | Debug 用 `debug/bin`，Release 用 `bin` | 统一用 `bin`：Debug 构建会跑 Release 版 CRT，断言/迭代器行为不一致 |
| 第三方包位置 | 保留在仓库内 `vcpkg_installed`（68 MB，已在 `.gitignore`） | 迁到 `ThirdParty/`：违背 vcpkg 默认布局，且 `find_package` 路径要额外维护 |

## 6. 留在原地的说明

- **第三方包位置未迁移**：`vcpkg_installed/` 就在仓库根目录，正是 vcpkg 的默认位置，
  符合用户「已安装的包放 vcpkg_installed」的要求。没有再复制一份到 `ThirdParty/`
  —— 两份副本必然分叉（本次链接失败的根因之一就是两份不同步）。
- **未改动任何 VS 安装目录下的文件**（`F:\VS\Community\...`），只调用了它已有的
  `cmake.exe` / `ninja.exe` / `vcvars64.bat`。
