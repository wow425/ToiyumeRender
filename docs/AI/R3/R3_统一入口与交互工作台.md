## 1. 这一阶段到底做了什么

一句话：**Renderer 从「写死在 Demo 里的全局对象」变成「注册表里创建的实例」，并在同一个入口里做到运行时切换 + ImGui 工作台 + 参数唯一真源。**

四件事，缺一不可：

| # | 交付物 | 说明 |
|---|---|---|
| 1 | `Demos/RendererDemoApp` | 统一入口。`Renderer::RendererPtr m_Renderer` 可以整体替换，不再有 `DeferredRenderer DeferredRenderer;` 这种文件级全局对象 |
| 2 | `RendererRegistry` 真创建路径 | `CreateRenderer(name)` 返回 `unique_ptr<BaseRenderer>`，切换 = 销毁一整套 GPU 资源 → 创建另一整套 |
| 3 | Dear ImGui 1.91.9b | Win32 + DX12 后端，六个面板：Performance / Scene·Model / Renderer / Material·Lighting / Debug View / DevTools |
| 4 | `RenderParams` 唯一真源 | UI 直接写 `m_Params` → `LightingSystem::ApplyParams` 打包成 `LightData` → CB → `LightingPS.hlsl`。面板不持有参数副本 |

为什么顺序必须是「R2 之后、R4 之前」：切换 Renderer 与 ImGui 都在频繁触碰**资源重建**和**输出缓冲区重绑**，这两件事正是 R2 修的基础设施。R2 没通，R3 一上来就会踩在同一堆问题上。

## 2. 关键设计决定

### 2.1 为什么 Renderer 必须是 `unique_ptr` 实例

`DeferredApp.cpp` / `Tooiyume.cpp` / `RayTracingApp.cpp` 里的 Renderer 是**文件级全局对象**，生命周期等于进程。
但「切换 Renderer」的语义是「销毁旧的一整套 GPU 资源，再创建新的一整套」，全局对象做不到「销毁后再创建」——它只能 `Initialize` 一次。

所以统一入口里它是 `Renderer::RendererPtr m_Renderer;`（`Renderer::RendererPtr = std::unique_ptr<BaseRenderer>`，`Engine/04_Renderer/Renderer/Base/BaseRenderer.h:224`）。
旧 Demo 保持原样不改（路线图要求「先整合不删旧 Demo」），它们继续用全局对象，只是不参与切换。

### 2.2 切换顺序：七步，一步都不能省

```
SwitchRenderer(name)                                    Demos/RendererDemoApp/RendererDemoApp.cpp:286
  1. g_CommandManager.IdleGPU()                          :301  旧的 GPU 工作必须真正做完
  2. Display::SceneColorBuffer = nullptr                 :304  shared_ptr 会拦住旧 SceneColor 的析构
  3. UnloadModel()                                       :307  Model 持有 TextureRef，Shutdown 会清纹理缓存
  4. m_Renderer->Shutdown(); m_Renderer.reset()          :310  DestroyDeferredBufferTargets + 销毁全局堆 + TextureManager::Shutdown
  5. RendererRegistry::Instance().CreateRenderer(name)   :317  真创建路径（不是 if/else 拼名字）
     -> Initialize(RendererCreateDesc{g_DisplayWidth, g_DisplayHeight})  :326
  6. BindRendererOutput(); m_Camera.SetAspectRatio(h/w)  :338  重绑 Display::SceneColorBuffer + 相机宽高比归位
  7. LoadModelByIndex(reloadIndex, false)                :343  纹理缓存已空，必须重新走一遍
```

每一步失败的原因都很具体，写在这里免得后人重踩：

- 省第 1 步 → 在旧资源还被 in-flight 命令列表引用时销毁它 → `#921 OBJECT_DELETED_WHILE_STILL_IN_USE`
- 省第 2 步 → `Display::SceneColorBuffer` 撑住旧 SceneColor，`Shutdown` 之后它指向已析构对象 → Present 时崩
- 省第 3 步 → `Model` 的 `TextureRef::m_ref` 指向被 `s_TextureCache.clear()` 释放的 `ManagedTexture` → 换模型时读悬垂指针
- 省第 6 步 → `PreparePresentSDR` 的尺寸/格式校验会拒绝拷贝 → 画面停在上一帧（不会崩，更难查）

### 2.3 UI 只登记请求，真正的动作在下一帧帧首执行

`RenderUI` 执行时 `GraphicsContext` 是开着的（`Engine/01_Application/GameCore.cpp:125-134`）。
而 `SwitchRenderer` 内部会 `Shutdown()` + `Initialize()`，两者都要提交自己的命令列表（`LightingSystem::InitializeResources` 甚至会 `CommandContext::InitializeBuffer` → `Finish(true)` 强等 GPU）。
**在已打开的命令列表里再开上下文会打乱录制。**

所以六个面板里的按钮只写 `m_PendingRendererName` / `m_PendingModelIndex`，真正的执行点在 `RendererDemoApp::Update` 的最开头、任何 `GraphicsContext::Begin` 之前（`RendererDemoApp.cpp:704` 调 `ApplyPendingActions()`，实现见 `:418`）。

`-R3Test` 走的也是同一批函数（`SwitchRenderer` / `LoadModelByIndex`），所以脚本化验收验证的是**真实交互路径**，不是一条平行实现。

### 2.4 ImGui 画到 SceneColor，再被整体复制到 backbuffer

路线图 §6.2 给了两个选项，这里选 A：

```
方案 A（采纳）：                      方案 B（否）：
  Renderer::Render  -> SceneColor       Renderer::Render -> SceneColor
  ImGuiLayer::Render -> SceneColor      PreparePresentSDR: COPY_SOURCE -> COPY_DEST -> CopyResource
  PreparePresentSDR:                    ImGuiLayer::Render -> backbuffer(COPY_DEST)
    COPY_SOURCE -> COPY_DEST -> Copy      需要额外的 COPY_DEST -> RENDER_TARGET -> PRESENT 转换
```

选 A 的理由：不动 `Display.cpp` 的状态机。`PreparePresentSDR` 本来就要求 Source/Destination 尺寸格式一致（R2 加的校验），UI 画在 SceneColor 上对它是透明的。
代价：**ImGui 的绘制结果也会进入 `-Screenshot` 的 GPU 回读图**。这不是缺点——`r3_09_imgui_panels.png` 就是靠这个拿到的。

插入点在 `Engine/01_Application/GameCore.cpp:125-134`：`RenderScene()` 之后、`Display::Present()` 之前，由 `IGameApp::HasRenderUI()` 控制是否付这份代价（旧三个 Demo 不实现，返回 false，行为完全不变）。

### 2.5 GPU 时间：查询堆 + 回读堆 + 围栏，不许偷懒

`Graphics::GetFrameTime()`（`Engine/01_Application/Display.cpp:349-351`）是**两次 Present 的 CPU 间隔**，不是 GPU 时间。路线图 §6.3 明确要求 Performance 面板必须区分二者。

`Engine/04_Renderer/GpuTimer.{h,cpp}` 的做法：

```
Initialize:  ID3D12QueryHeap(TIMESTAMP, 2*N 槽) + ReadbackBuffer(2*N*8 字节) + GetTimestampFrequency
Begin:       EndQuery(heap, TIMESTAMP, slot*2 + 0)      —— 渲染命令列表内
End:         EndQuery(heap, TIMESTAMP, slot*2 + 1)      —— 同一个命令列表内
OnSubmitted: 记录 CommandContext::Finish() 返回的围栏值
TryGetElapsedMs: 围栏完成才 Map 回读堆，把 (t1-t0)/frequency*1000 填入
```

两个容易写错的地方：

1. **不能用 `CommandContext::ResolveTimeStamps`**（`Engine/02_RHI/Command/CommandContext.h:169`）——它把 `DestinationBufferOffset` 硬编码成 0，多槽轮换会互相覆盖。必须用 `GraphicsContext::ResolveQueryData(heap, type, StartIndex, NumQueries, readback, DestinationBufferOffset)`。
2. **Map 之前必须确认围栏完成**，否则读到的是上一轮的数据（或未定义内容）。

结果滞后 1~2 帧，这是查询回读的固有延迟，面板上显示的是「最近一次有效采样」。

### 2.6 参数链路：只有一条

```
ImGui 滑杆  ->  Renderer::RenderParams m_Params          Demos/RendererDemoApp/RendererDemoApp.cpp:214
            ->  RenderFrameDesc::Params = &m_Params     :728 / :747
            ->  BaseRenderer::Update 里 ApplyParams     DeferredRenderer.cpp / ForwardRenderer.cpp
            ->  LightingSystem::PackParams              Engine/05_Scene/Lighting/LightingSystem.cpp:30
            ->  m_LightGPUBuffer（StructuredBuffer）    WriteBuffer（Transition COPY_DEST -> GENERIC_READ）
            ->  LightingPS.hlsl cbuffer Light b0        96 字节：PostParams + DebugParams
```

`ApplyParams` 先用 `memcmp` 去重（`:111`），参数没变就不上传。面板上的 `Light param uploads` 就是 `GetUploadCount()`，可以直观看到「拖滑杆才上传」。

Forward 路径不消费这个 UBO（`DefaultPS.hlsl` 的 `MainPS` 只返回 baseColor），所以面板在非 Deferred 时 `BeginDisabled` 并写明原因（`RendererDemoApp.cpp:997-1004`）——路线图要求「未实现显示禁用或 Not Implemented」，不能让人拖了没反应还以为坏了。

## 3. 施工中真正踩到的坑（这一节最值钱）

八个问题，全部是「日志全绿、Debug Layer 不报错、但画面/行为不对」的那种。

### 3.1 注册表为空：静态库的静态初始化器根本没被链接

**症状**：`[R3] 已注册 Renderer 数量：0`，随后 `CreateRenderer` 返回空、进程 ASSERT 退出。

**根因**：`RendererAutoRegister<T>` 是 `DeferredRenderer.cpp:34` / `ForwardRenderer.cpp:34` 里的**文件级静态对象**，而这两个 TU 在静态库 `TooiyumeEngine.lib` 里。
MSVC 链接静态库只拉取「被引用的目标文件」。Demo 里的 `dynamic_cast<Deferred::DeferredRenderer*>` **不 odr-use 任何符号**（`GetDeferredBuffer` 是头文件内联函数），RTTI 类型描述符是 UNDEF，链接器没有理由把这两个 .obj 拉进来 → 静态初始化器从未运行 → 注册表空。

这一条用 `dumpbin` 看不出来（链接后的 exe 没有 COFF 符号表），最后是**直接扫二进制里的 UTF-16LE 字面量**确认的：修复前 `Deferred Texture Descriptors` 出现 0 次，修复后 1 次。

**修法**：不依赖静态初始化器的链接运气，在 `RendererRegistry::Instance()` 里做一次性显式注册（`Engine/04_Renderer/Renderer/Base/RendererRegistry.cpp:35-38`）。这个 TU 一定被链接，注册变成确定性的。原有的 `RendererAutoRegister` 静态对象保留（重复注册只是 map 覆盖，无害）。

**教训**：**注册表类的设计必须假设「静态初始化器可能不运行」。** 显式注册 + 惰性兜底，比 Elegant 的自动注册可靠。

### 3.2 `RESOURCE_BARRIER_INVALID_HEAP` #741：UPLOAD 堆资源不能转换状态

**症状**：第一帧 `DeferredRenderer::Update` → `LightingSystem::ApplyParams` → `WriteBuffer` → 直接抛 C++ 异常（`0x80000003`），进程当场终止。

```
D3D12 ERROR: ID3D12CommandList::ResourceBarrier: Certain resources are restricted to
certain D3D12_RESOURCE_STATES states, and cannot be changed. Resources on
D3D12_HEAP_TYPE_UPLOAD heaps requires D3D12_RESOURCE_STATE_GENERIC_READ.
[ RESOURCE_MANIPULATION ERROR #741: RESOURCE_BARRIER_INVALID_HEAP]
D3D12: **BREAK** enabled for the previous message
```

**根因**：`CommandContext::CopyBufferRegion`（`CommandContext.h:784`）无条件对**源**资源发 `COPY_SOURCE` 转换；而 `WriteBuffer` / `FillBuffer` 的源是 `LinearAllocator` 的上传堆页面（`LinearAllocator.cpp:113-116`）。UPLOAD / READBACK 堆上的资源状态在创建时就固定了，DX12 不允许转换。

**修法**（两处配合）：
1. `Engine/02_RHI/Resource/GpuResource.h:42` + `:60-70`：`Destroy()` 里复位缓存，新增 `GetHeapType()` 惰性查询 + `mutable D3D12_HEAP_TYPE m_HeapType`。
2. `Engine/02_RHI/Command/CommandContext.cpp:430-438`：`TransitionResource` 开头对 UPLOAD / READBACK 堆早退，只校正跟踪状态，不发屏障。

**教训**：**RHI 的「状态转换」是个抽象泄漏点**——上层以为所有资源都能转换，底层才知道有些堆类型不允许。这类错误 Debug Layer 会直接 BREAK，不是警告。

### 3.3 切换 Renderer 时 0xC0000005：Context 缓存了已销毁的堆指针

**症状**：`Deferred -> Forward` 时崩在 `D3D12Core!CGraphicsCommandList::SetDescriptorHeapsInternal` 读 `ds:feeefeee`（已释放内存的填充值）。

**根因**：`CommandContext::m_CurrentDescriptorHeaps` 是「本 Context 已经绑过哪些堆」的裸指针缓存，用来避免重复调用 `SetDescriptorHeaps`。
它的生命周期比堆长：`ContextManager` 把 CommandContext 放池子里复用，而堆（`s_TextureHeap` / `s_SamplerHeap`）归各 Renderer 所有。

```
Deferred 用过 Context -> 缓存里存着 s_TextureHeap.GetHeapPointer()
Deferred::Shutdown  -> s_TextureHeap.Destroy()  （内存标记 0xFEEEFEEE）
Forward::Initialize -> LightingSystem::InitializeResources -> CommandContext::Begin -> Reset()
                    -> BindDescriptorHeaps() 把 0xFEEEFEEE 塞给 SetDescriptorHeaps
```

**修法**：`Engine/02_RHI/Command/CommandContext.cpp:231`，`Reset()` 之后无条件 `ZeroMemory(m_CurrentDescriptorHeaps, ...)`。命令列表 Reset 之后旧的堆绑定本来就失效了，缓存必须作废。

没有选「让 Shutdown 不销毁全局堆」那条路——堆的所有权本来就该在 Renderer 手里，改所有权会把这个 bug 变成另一个 bug。

### 3.4 运行时换模型后模型凭空消失（最阴的一条）

**症状**：切到另一个模型后，画面里只剩天空和地面。日志全绿：sorter 对象数不变（16 个）、`DrawIndexed` 照常提交、Debug Layer 一声不吭。

**根因**：`ModelInstance::operator=(std::shared_ptr<const Model>)`（`Engine/05_Scene/Model/Model.cpp:82-104`）重建了 `m_MeshConstantsCPU/GPU`，但**没有重置 `m_IsDirty`**。
而 `ModelInstance::Update` 的第二守卫是 `if (!m_IsDirty) return;`（`:106-109`）。

```
第 1 帧：EndFrame 已 ClearDirty() -> m_IsDirty == false
运行时换模型：新的 m_MeshConstantsGPU 内容未定义，但 Update 早退
每次 draw 的 WorldMatrix / WorldIT 是垃圾 -> 顶点退化成零面积三角形
-> 画面里什么都没有，但所有 API 调用都合法
```

**修法**：`Engine/05_Scene/Model/Model.cpp:99` 加 `m_IsDirty = true;`。语义上「换了模型数据就是脏的」，这一行本该在写 `operator=` 的那天就有。

**教训**：`IsDirty` 这种门控是**双重记账**——任何修改状态的路径都必须同时置脏。R1 已经因为 sorter + IsDirty 的组合出过一次「只有第一帧有画面」，这是同一个坑的第二次。

这也解释了「为什么 Forward 在统一入口里画不出东西」：并不是 Forward 的问题，是切模型那一步已经把画面掏空了，之后切到哪个 renderer 都是空的。**现象的位置不等于原因的位置。**

### 3.5 `#921 OBJECT_DELETED_WHILE_STILL_IN_USE`：换模型没等 GPU

**症状**：`UnloadModel()` → `ModelInstance::operator=` → `Model::~Model` → `GpuBuffer::Destroy` → `ComPtr::InternalRelease` 时 Debug Layer 直接断死：

```
D3D12 ERROR: ID3D12Resource2::<final-release>: CORRUPTION: An ID3D12Resource object
(...:"Model Data") is referenced by GPU operations in-flight on Command Queue
(...:"CommandListManager::m_CommandQueue"). It is not safe to final-release objects
that may have GPU operations pending. [ EXECUTION ERROR #921: OBJECT_DELETED_WHILE_STILL_IN_USE ]
```

**修法**：`RendererDemoApp::UnloadModel`（`RendererDemoApp.cpp:373-385`）在析构旧模型前 `g_CommandManager.IdleGPU()`。换模型是低频操作，整条队列排空的代价可以接受。

注意这里有 `if (m_Model.IsNull()) return;` 提前返回——首次加载时没有旧模型，不该白白排空一次队列（否则启动会明显变慢）。

### 3.6 `GpuBuffer::Destroy` 只清资源不还描述符

`CreateDerivedViews` 用 `if (m_SRV.ptr == D3D12_GPU_VIRTUAL_ADDRESS_UNKNOWN)` 判断「要不要分配描述符」。
如果 `Destroy` 不把 ptr 复位成 UNKNOWN，二次 `Create` 就会**跳过分配、继续写旧描述符**——而那个槽位可能已经分给别人了。

`ColorBuffer` / `DepthBuffer` 在 R2 已经有了 `Destroy` override；`GpuBuffer` 这一支在 R3 补上（`Engine/02_RHI/Resource/GpuBuffer.h:29`）：非 UNKNOWN 时 `Free(handle, 1)` 再置 UNKNOWN。
同时恢复了 `TypedBuffer::CreateDerivedViews` 里被注释掉的两处守卫（`Engine/02_RHI/Resource/GpuBuffer.cpp:229` 等）——否则 Destroy 复位之后，Create 会往 `(D3D12_CPU_DESCRIPTOR_HANDLE)-1` 写描述符。

`LightingSystem` 是进程级全局 `StructuredBuffer`，两个 Renderer 的 `Initialize` 都会 `InitializeResources()` → 重复 `Create`。**这条修复直接决定了「切 Renderer 不泄漏描述符」。**

### 3.7 宽字符 printf 的 `%s` / `%hs` / `%ws`

`LOG_INFO` 走 `vswprintf_s`。同一个 `%s` 在这里期望 `wchar_t*`，而代码传的是 `std::string::c_str()`（`char*`），结果是 UTF-16 被当成宽字符逐字节解释：

```
实际输出：[R3]   - 敄敦牲摥敒摮牥牥촀췍...
期望输出：[R3]   - DeferredRenderer
```

规则：**wchar_t* 用 `%ws`，char* 用 `%hs`，中文不要走 `%hs`**（引擎的 Printf 没有 UTF-8 → UTF-16 转换，中文会显示成 `å·²é‡ç»‘` 这种字节串，不影响判读但不能当文档）。

### 3.8 `LightingSystem::Shutdown` 没有调用者

两个 Renderer 都调 `InitializeResources()` 重建 `m_LightGPUBuffer`，但都不调 `Shutdown()`。切 Renderer 时这块 GPU 缓冲会跨实例残留。
修法：`DeferredRenderer.cpp:141` 与 `ForwardRenderer.cpp:101` 的 `Shutdown` 末尾各加一行 `Scene::LightingSystem::Shutdown();`。

顺带修的同类问题：`EnvironmentLightingManager` 的 `m_Baked` / `m_Ready` 跨 Renderer 不清零（第二次 `Initialize` 重建了 4 张 cubemap 但不再烘焙，采样到未定义内容），在 `Initialize` 与 `Shutdown` 两处都复位（`EnvironmentLightingManager.cpp:45-47` / `:73-75`）。

## 4. 验收证据（路线图 §6.3 四项）

### 4.1 同一入口切换 Forward / Deferred

`-R3Test` 第 7 步切 Forward、第 8 步切回 Deferred，两次都打 `[R3] 切换完成：...（输出 已重绑）`。描述符计数呈闭合回路：

```
初始 Deferred      RTV=13 SRV=65 pool=8
换模型 saber_emiya  RTV=13 SRV=61 pool=8
切 Forward          RTV=4  SRV=29 pool=8
切回 Deferred      RTV=13 SRV=61 pool=8   <- 完全回到切换前的数值
```

`pool` 恒为 8（描述符堆池数量），说明 100+ 次资源创建/销毁没有触发新堆分配。这是「无持续泄漏」最硬的指标。

### 4.2 切模型无残留、无崩溃

`r3_06_model_saber.png`：运行时从 merlin 换成 saber_emiya，角色站在草地上，天空云层正常。
`r3_08_back_deferred.png` 与 `r3_06` **逐字节相同**（md5 `488a8074f730...`）——切到 Forward 再切回 Deferred，画面完全恢复，没有残留。

### 4.3 FPS / 帧时间 / Debug View

`r3_09_imgui_panels.png` 里 Performance 面板同时显示：

```
CPU frame: 3.60 ms        <- Graphics::GetFrameTime()，两次 Present 的 CPU 间隔
CPU FPS:   277.7
GPU frame: 2.346 ms       <- GpuTimer，TIMESTAMP 查询堆的真实 GPU 时间
GPU timer enabled         <- 可关闭，关闭后不再采样（面板显示 0）
```

以 `r3_00` 为基准做像素差分，变化区域 bbox 恒为 `(749,117,1138,577)`（就是模型所在区域），说明「参数影响的是光照结果，不是整幅图」：

## 6. 复现命令

```bat
rem 构建（唯一入口，禁止 cmake --preset）

scripts\build.bat Release clean

rem 交互运行（自己拖面板）
```
