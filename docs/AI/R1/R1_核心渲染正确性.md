# R1 施工记录：修复确定性渲染错误

> 阶段：**R1（核心渲染正确性）**
> 依据：`docs/AI/TooiyumeRender_升级路线图_2026-10-24.md` §4
> 结论：R1 的 7 项全部修复，另发现并修复 2 个计划外的关键缺陷。**画面从「模型消失」变为「模型稳定可见、材质正确」**。

## 0. 一句话总结

R1 开始前，Deferred 路径**实际上是坏的**：模型完全不显示，画面里只有天空盒。修复后模型正常渲染，BaseColor / Metallic 通道均已用 GPU 回读验证正确。剩余「整体偏白」是 IBL 过曝，属于 R4 的曝光/色彩管理范围。

## 1. 最重要的发现：模型为什么完全消失

这是 R1 期间最有价值的排查，值得完整记录。

### 1.1 现象

- 启动日志显示两个模型都加载成功
- `MeshSorter` 里有 56 个 opaque draw（15 + 41）
- 但画面上**只有天空盒和地形，没有任何角色**

### 1.2 排查过程中的三个陷阱

**陷阱一：外部截图工具不可信。**
最初用 `PrintWindow` + `CopyFromScreen` 抓窗口。后来发现：把 GBufferPS 改成输出纯红色、再改成输出纯蓝色，抓到的 PNG **字节完全相同**（md5 一致）。
→ 说明抓到的是陈旧窗口内容。**外部截图不能作为「画面正确」的证据**。

正确做法：用 `ReadbackBuffer` 把 GPU 上的 ColorBuffer 回读，再用 DirectXTex 的 WIC 编码器写成 PNG。这是渲染管线的真实输出。

**陷阱二：修改 HLSL 不生效，但没有任何报错。**
把 LightingPS 改成输出 AO 单通道，重新构建，截图却毫无变化。检查发现 `.cso` 和 `.h` 的时间戳都更新了，Shader 确实重编了。

真正原因是 **`DeferredRenderer.cpp` 没有重新编译**。它 `#include "LightingPS.h"`，但生成头没有登记为该源文件的编译依赖，所以 exe 里仍是上一次编译进去的旧字节码数组。

**陷阱三：日志格式错误导致误判。**
一度以为相机位置恒为 (0,0,0)，因为 `LOG_INFO(L"%.3f", p.GetX())` 打印出 0。实际相机位置是正确的 (0,0,5)——
`Vector3::GetX()` 返回 `Scalar` 类型，传给可变参数时没有隐式转成 `float`，读到的就是垃圾值。
→ 必须写 `(float)p.GetX()`。**用 printf 家族打印自定义类型前，务必显式转换。**

### 1.3 根因

排除以上三个陷阱后，真正原因是 **sorter 生命周期错误**，而且这是我（AI）在 R0/R1 期间引入的：

```cpp
// 原实现（有 bug）：EndFrame 不 Reset
// → sorter 跨帧累积，draw 数量随帧数增长

// 我最初"修复"成：EndFrame 里 Reset
// → 但 ModelSort 只在 IsDirty 时执行
// → 第一帧末清空 sorter，第二帧模型不再 dirty，于是再也不加进去
// → 表现：只有第一帧有物体，之后全空
```

**正确的修法**：把「重建渲染列表」和「重算变换数据」分开——

```cpp
void DeferredRenderer::Update(...)
{
    DefaultSorter.Reset();          // 每帧清空

    for (auto* model : frame.Models)
    {
        if (model->IsDirty())
            model->Update(gfxContext, dt);   // 昂贵：Map/Unmap + CopyBufferRegion

        this->ModelSort(*model);             // 轻量：纯 CPU 遍历
    }
}
```

### 1.4 为什么这样设计

| 方案 | 结果 | 评价 |
|---|---|---|
| A. 每帧重建 + 每帧清空 | 正确 | **采用** |
| B. 永不清空 + 仅 dirty 时追加（原实现） | draw 无限累积，模型销毁后留下悬空指针 | 错误 |
| C. 每帧清空 + 仅 dirty 时追加 | 只有第一帧有画面 | 错误（我最初踩的坑） |

关键认知：**sorter 的内容是「这一帧要画什么」，天然属于帧内数据**，每帧重建才是它的正确语义。而 `ModelInstance::Update` 做的是 CPU→GPU 的常量缓冲上传，那才是真正需要 dirty 门控的昂贵操作。两者生命周期不同，不能绑在一起。

## 2. R1.1 统一材质纹理槽语义

### 2.1 问题

工程里存在**两套互相冲突**的纹理槽枚举，而 GPU 侧用的是第三份"隐含约定"：

| 位置 | 顺序 |
|---|---|
| `glTF.h::Material` | BaseColor, MetallicRoughness, Occlusion, Emissive, Normal |
| `ConstantBuffers.h` | BaseColor, **Normal, Emissive, Occlusion**, MetallicRoughness |
| `GBufferPS.hlsl` 的 t0..t4 | BaseColor, MetallicRoughness, Occlusion, Emissive, Normal |

`ModelConvert.cpp` 里写的是未限定的 `kMetallicRoughness` 等，解析到 **ConstantBuffers 那套**，却用它去索引 **glTF 顺序**的数组：

| 代码 | 实际取到 | 应该是 |
|---|---|---|
| `srcMat.textures[kBaseColor]` | BaseColor | ✅ |
| `srcMat.textures[kMetallicRoughness]`(=4) | **Normal** | MetallicRoughness |
| `srcMat.textures[kOcclusion]`(=3) | **Emissive** | Occlusion |
| `srcMat.textures[kEmissive]`(=2) | **Occlusion** | Emissive |
| `srcMat.textures[kNormal]`(=1) | **MetallicRoughness** | Normal |

### 2.2 修复

统一到 **glTF/HLSL 顺序**（即 GPU 实际使用的顺序），并加静态断言：

```cpp
enum {
    kBaseColor,         // t0
    kMetallicRoughness, // t1
    kOcclusion,         // t2
    kEmissive,          // t3
    kNormal,            // t4
    kNumTextures
};
static_assert(kNumTextures == 5, "GBufferPS.hlsl 的 t0..t4 固定为 5 个槽");
```

调用点改用限定名 `glTF::Material::kBaseColor`，即使将来顺序再变也不会静默带偏。

### 2.3 顺带修正 BaseColor 的 sRGB

原先 BaseColor 用 `TextureOptions(false)` 编译成线性格式，但磁盘上的 PNG 是 sRGB 编码的——等于把 sRGB 值直接当线性值用，画面偏暗。

按 glTF 2.0 规范修正：

| 贴图 | 色彩空间 | 理由 |
|---|---|---|
| BaseColor | **sRGB** | 颜色数据，采样时硬件解码到线性 |
| Emissive | sRGB | 同上 |
| Normal | Linear | 方向数据，sRGB 解码会扭曲向量 |
| Occlusion | Linear | 遮蔽系数，非颜色 |
| MetallicRoughness | Linear | 物理参数，非颜色 |

> 注意：修改槽位顺序后 `.ty` 缓存失效，必须用 `-RebuildModels` 重新烘焙。

## 3. R1.2 修正默认纹理表

### 3.1 为什么这张表比想象中重要

实测 `saberCaster3NoArmor.gltf`：20 个材质里 **19 个只有 baseColorTexture**，没有 normal / occlusion / emissive / metallicRoughness。也就是说，**这四个通道全部走默认纹理表**。

### 3.2 修复前后

| 槽位 | 修复前 | 修复后 | 正确默认值的理由 |
|---|---|---|---|
| t0 BaseColor | 白 | 白 ✅ | 乘法单位元，保留 baseColorFactor |
| t1 MetallicRoughness | **纯白 (1,1,1,1)** | 白 ✅ | G=roughness=1, B=metallic=1，再乘 factor 才等于材质值 |
| t2 Occlusion | **透明黑 (0,0,0,0)** | 白 ✅ | AO=1 表示不受遮蔽 |
| t3 Emissive | 白 | **黑** ✅ | 无自发光 |
| t4 Normal | **纯白 (1,1,1)** | **平面法线 (0.5,0.5,1)** ✅ | 解码后是切线空间 +Z |

修复前的致命问题在 **t4 Normal 拿到纯白**：`(1,1,1)*2-1 = (1,1,1)`，这是一个非法的单位向量（长度 √3），归一化后所有表面法线都指向同一个斜角方向——整个模型的着色是错的。

## 4. R1.3 深度 VB per-draw 偏移

`CompileMesh` 里三行 memcpy：

```cpp
std::memcpy(uploadMem + curVBOffset + curVertOffset, ...);   // VB：有 per-draw 偏移
curVertOffset += ...;
std::memcpy(uploadMem + curDepthVBOffset, ...);              // ❌ DepthVB：用了 curDepthVBOffset，但没加 per-draw 增量
std::memcpy(uploadMem + curIBOffset + curIndexOffset, ...);  // IB：有 per-draw 偏移
curIndexOffset += ...;
```

同一 Mesh 含多个 draw 时，后一个 draw 的深度顶点会覆盖前一个。

修复：引入 `curDepthVertOffset` 并逐 draw 累加，同时加 `nullptr / empty` 防御。

> 触发条件：仅当同一 Mesh 有 ≥2 个 draw 时。单 draw 时起始偏移恰好正确，所以这个 bug 平时不易暴露——修复后需要用多 draw 模型专门验证。

## 5. R1.4 Tangent 解码

烘焙端用 `VBWriter` 的 `x2bias=true` 把 `[-1,1]` 映射到 `[0,1]` 存进 `R10G10B10A2_UNORM`。运行时必须 `*2-1` 还原。

原实现：

```hlsl
float3 Normal = vsInput.Normal * 2.0 - 1.0;                          // ✅ 还原了
float4 Tangent = vsInput.Tangent * 2.0 - 1.0;                        // 算了但没用（死代码）
...
vsOutput.TangentWS = float4(normalize(mul(vsInput.Tangent.xyz, ...)), vsInput.Tangent.w);  // ❌ 用了未还原值
```

切线基完全错误 → TBN 错误 → 法线贴图方向错乱。

修复：

```hlsl
float3 Normal      = vsInput.Normal * 2.0 - 1.0;
float3 Tangent     = vsInput.Tangent.xyz * 2.0 - 1.0;
float  TangentSign = vsInput.Tangent.w * 2.0 - 1.0;   // 手性也要还原

vsOutput.NormalWS  = normalize(mul(Normal,  (float3x3) WorldIT));
vsOutput.TangentWS = float4(normalize(mul(Tangent, (float3x3) WorldIT)), TangentSign);
```

同时补上 `.w`（手性符号）的还原——原来直接把 `[0,1]` 的 w 当作 ±1 用。

## 6. R1.5 移除分辨率硬编码

`LightingPS.hlsl` 里：

```hlsl
float2 renderResolution = float2(1920, 1080);   // ❌
float2 uv = (position.xy + 0.5) / renderResolution;
```

只要窗口不是 1920×1080，UV 就错，反投影出的世界坐标整体偏移，光照与视线方向全错。

修复：扩展 `CameraData` / `cbuffer Camera`（b1），把真实渲染目标尺寸传进去：

```cpp
// C++
CameraCB.RenderTargetSize    = XMFLOAT2(rtW, rtH);
CameraCB.InvRenderTargetSize = XMFLOAT2(1.0f/rtW, 1.0f/rtH);
```
```hlsl
// HLSL
float2 uv = (position.xy + 0.5) * InvRenderTargetSize;
```

传 `InvRenderTargetSize` 而不是每像素做除法，省一次除法。

## 7. R1.7 固定常量缓冲契约

### 7.1 分叉的三份声明

| 位置 | 内容 |
|---|---|
| `ConstantBuffers.h`（C++） | `Matrix4 ViewProjMatrix; Vector3 CameraPos; Vector3 SunDirection; Vector3 SunIntensity;` |
| `StaticMeshVS.hlsl` | `float4x4 ViewProjMatrix; float3 ViewerPos;` |
| `GBufferPS.hlsl` | `float4x4 ViewProj; float3 ViewerPos;` |

三处字段名、数量、类型全都不一样。因为 `ViewProjMatrix` 恰好在偏移 0，所以"碰巧能用"。

### 7.2 隐患：Vector3 vs float3 的对齐差异

- C++ `Math::Vector3` 是 12 字节（XMVECTOR 存 4 个 float，但语义上是 3 个）
- HLSL `float3` 在 cbuffer 里按 **16 字节**对齐

混用会导致后续字段整体错位。修复方式：全部改用 16 字节对齐的类型（`Vector4` / `float4`）：

```cpp
struct alignas(256) GlobalConstants
{
    Math::Matrix4 ViewProjMatrix;   // offset  0
    Math::Vector4 CameraPos;        // offset 64
    Math::Vector4 SunDirection;     // offset 80
    Math::Vector4 SunIntensity;     // offset 96
};
static_assert(sizeof(GlobalConstants) == 256, "CBV 需要 256 字节对齐");
```

HLSL 两侧同步为完全相同的布局。这样新增字段时不会再出现隐式填充歧义。

## 8. 计划外的两个关键修复

### 8.1 Shader 生成头 → 源文件的编译依赖

**问题**：`compile_shader` 用 `add_custom_target` 生成 `.h`，但该头**不是任何 .cpp 的登记依赖**。改 HLSL → `.cso`/`.h` 更新 → 但 `DeferredRenderer.cpp` 不重编 → exe 里仍是旧字节码。

这是最容易误判成"改了代码没生效"的坑，实测坑了我很久。

**修复**：新增 `shader_attach_header_dependency`，用 CMake 的 `OBJECT_DEPENDS` 把头挂到具体源文件：

```cmake
function(shader_attach_header_dependency SOURCE_FILE)
    set_property(SOURCE "${SOURCE_FILE}" APPEND PROPERTY OBJECT_DEPENDS "${ARGN}")
endfunction()

shader_attach_header_dependency(
    ".../DeferredRenderer.cpp"
    "${CMAKE_BINARY_DIR}/ShaderCache/GBufferPS.h"
    "${CMAKE_BINARY_DIR}/ShaderCache/LightingPS.h"
)
```

验证：改 `.hlsl` 后重建，日志同时出现 `Compiling Shader` 和 `DeferredRenderer.cpp.obj`。

### 8.2 WASD 无法移动相机（R0 引入的回归）

**问题**：R0 为了让 DirectInput 不可用时程序不崩，我加了：

```cpp
if (!s_KbmReady) { KbmZeroInputs(); return; }   // ❌
```

`KbmZeroInputs()` 每帧把整个 `s_Keybuffer` 清零——**连带把 Win32 消息写入的键位也擦掉**，于是 WASD 完全无响应。

**修复**：
1. 该分支只清鼠标状态，不清键盘
2. 新增 `GameInput::NotifyWin32Key`，由 `WndProc` 转发 `WM_KEYDOWN/WM_KEYUP`
3. 键位聚合改为**三路取或**：Win32 消息 ∪ `GetAsyncKeyState` ∪ DirectInput

**验证**：进程内 `PostMessage(WM_KEYDOWN, 'W')` 后，相机 Y 从 0 持续增长到 2.69，松开后因动量继续滑行。完整链路 `WndProc → NotifyWin32Key → s_Keybuffer → IsPressed → 相机` 打通。

## 10. 遗留问题

| 项 | 现状 | 归属 |
|---|---|---|
| **模型整体偏白** | BaseColor 正确但最终输出过曝 | **R4** |
| Resize / 最小化 | `OnResize` 仍零调用 | R2 |
| 相机 aspect 不更新 | `SetAspectRatio` 零调用 | R2 |
| 光照参数硬编码 | 已调整到合理量级，但仍无 setter | R4 |
| 分辨率：窗口拉伸 | 已传真实尺寸，但 Resize 链未接通 | R2 |

### 关于「整体偏白」

BaseColor 通道证明了材质数据是对的，所以偏白不是贴图问题。经排查，主因是 **IBL 直接采样 HDR 环境贴图**——HDR 值域远超 1.0（天空亮度可达几十），`irradiance * baseColor` 之后整体被推高，再经 ACES 压回。

正确修复需要**曝光系统**（exposure → tonemap → 输出色彩空间），这属于 R4「色彩管理」的范围。R1 阶段我只把明显过量的方向光（10）和点光（80）降到合理量级（3 / 4），避免在这个阶段引入不完整的曝光模型。

## 11. 给 R2 的提示

1. **Resize 是下一个必做项**。现在分辨率常量已经通了，但 `OnResize` 仍是零调用，窗口缩放后 RT 尺寸与 swapchain 不匹配。
2. **R1.5 的分辨率传递已经就位**，R2 接通 Resize 后会自动生效，无需再改 Shader。
3. **sorter 现在每帧重建**，Resize 后重建实例不会累积旧 draw——R2 可以放心做资源重建。

## 12. 方法论沉淀（这轮最有价值的经验）

1. **外部截图不可作为 GPU 画面证据**。必须回读 framebuffer。
2. **区分「代码改了」和「改动生效了」**。生成头、PCH、缓存都可能让改动悄悄失效。验证方式是看构建日志里对应的 `.obj` 是否重编。
3. **printf 打印自定义类型必须显式转 float**，否则可变参数会读出垃圾，导致误判。
4. **修复前先确认现象是真的**。这轮因为截图和日志两处失真，浪费了不少时间在不存在的问题上。
5. **一个"修复"可能引入新 bug**。sorter Reset 就是典型：局部看是对的，与 `IsDirty` 门控结合后产生"只有第一帧有画面"。**改生命周期相关代码后必须实际跑起来看**。
