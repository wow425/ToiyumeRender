## 1. 资产基线：从「黑屏」到「有明确诊断的降级」

### 1.1 做了什么

1. 把缺失的模型目录（`Saber` / `saberCaster` / `toneriko`）补齐到 `Assets/Model`，与已有的 `Merlin` / `leimiaier` / `Kyomachiya` / `摩根` 并列。
2. 不再要求「模型必须存在才能启动」——**模型缺失时程序继续运行**，但必须给出**能定位的**错误。

### 1.2 为什么这样设计

原实现把「资源缺失」和「程序崩溃」混在一起：`LoadModel` 返回 `nullptr`，上层 `ModelInstance` 静默接受，最后表现为黑屏。排查者无法区分是「路径错」「文件坏」还是「渲染管线错」。

改成的原则是：**资源缺失 = 可降级的运行时错误，不是致命错误**。
- 程序继续跑（还能验证渲染管线本身是否正常）
- 但日志必须说清：**哪个文件、在哪找、什么后果、怎么修**

实际输出（用 `TOOIYUME_ASSETS_ROOT` 指向一个没有模型的目录复现）：

```
[Asset] AssetsRoot = C:\Users\saber\AppData\Local\Temp\empty_assets\Assets\
[Asset] 错误：模型加载失败 —— 源文件与缓存文件都不存在
[Asset]   源文件 : ...\Assets\Model\Merlin\merlin.gltf
[Asset]   缓存   : ...\Assets\Model\Merlin\merlin.ty
[Asset]   后果   : 该模型不会渲染（通常表现为画面中缺少对应物体）
[Asset]   排查   : 确认上方 [Asset] AssetsRoot 是否指向本项目 Assets 目录；
[Asset]            若模型尚未下载，请参考 docs/AI/ 中的资产说明补齐。
```

对比改造前只有一行 `Error: Could not find merlin.gltf`——既没有路径也没有后果。

### 1.3 关键代码位置

| 文件 | 作用 |
|---|---|
| `Engine/05_Scene/Model/ModelLoader.cpp` | 模型不在时的分级诊断输出 |
| `Engine/04_Renderer/EnvironmentLightingManager.cpp` | 环境图加载失败的诊断（影响 Skybox/IBL，但不阻断） |
| `Engine/04_Renderer/Renderer/Deferred/DeferredRenderer.cpp` | 加载前先用 `Asset::Exists` 预检并提示后果 |

## 2. 资源路径：`AssetsRoot` 统一解析

### 2.1 问题本质

写死绝对路径的坏处不只是「换机器要改」，而是**错误的传播被延迟**：编译期完全正常，运行时才失败，而且失败点和错误源相距很远。

### 2.2 设计方案：五级回退

新增 `Engine/00_Core/Utility/AssetRoot.{h,cpp}`，解析优先级从高到低：

```
1. 命令行  -AssetsRoot <path>        ← CI / 脚本显式覆盖
2. 环境变量 TOOIYUME_ASSETS_ROOT     ← 部署 / 多机开发
3. exe 目录逐级向上找含 Assets 的祖先（最多 8 层）  ← 覆盖构建树布局
4. 工作目录逐级向上找（同样规则）      ← 覆盖 IDE 启动
5. 编译期注入 TOOIYUME_SOURCE_ASSETS_DIR  ← 最后兜底
```

**为什么是「向上找包含 Assets 的祖先」而不是查固定相对层级？**
因为同一份代码有两种运行位置：
- 开发期：`<repo>/out/build/Debug/Demos/DeferredApp/DeferredApp.exe` → 要上溯 4 层才到 `<repo>`
- 发布期：`<install>/DeferredApp.exe` + `<install>/Assets/` → 只需 0 层

「向上找标志性目录」这一条规则同时覆盖两者，且不需要为每种布局写死层级数。这是一个通用技巧：**用文件系统结构本身作为定位依据，而不是用路径字符串**。

### 2.3 一个容易踩的坑：静态初始化顺序

最初的实现写成：

```cpp
// Demo 顶层
static std::wstring saberCaster = Asset::Resolve(L"Model/...");  // ❌
```

这个变量在 `main` 之前就初始化，而 `Asset::Initialize()` 是在 `GameCore::InitializeApplication` 里调用的——**全局变量构造时 AssetsRoot 还是空的**，解析结果全错。

改成惰性求值：

```cpp
static std::wstring saberCaster() { return Asset::Resolve(L"Model/..."); }  // ✅
```

这是 C++ 里典型的 **static initialization order fiasco**。规律：**任何依赖运行时初始化状态的全局对象，都应该改成函数内求值**。

### 2.4 `Resolve` 的两个防御点

```cpp
// 1) 绝对路径识别要考虑盘符
if (rel.size() >= 3 && rel[1] == L':' && (rel[2] == L'\\' || rel[2] == L'/'))
    return rel;

// 2) 根没解析出来时不要静默拼相对路径
if (g_AssetsRoot.empty()) { /* 报一次错 */ return rel; }
```

第 2 点尤其重要：如果根为空还照常拼接，会得到一个相对路径，然后文件系统「找不到」，最终又变回「黑屏 + 无信息」——**把错误提前到错误源头，是诊断设计的核心原则**。

## 3. 构建系统可移植化

### 3.1 vcpkg 工具链：从写死路径到环境变量

**改造前**（`CMakePresets.json:16`）：

```json
"CMAKE_TOOLCHAIN_FILE": "F:/VS/rep/vcpkg/scripts/buildsystems/vcpkg.cmake"
```

**改造后**：

```json
"CMAKE_TOOLCHAIN_FILE": {
  "type": "FILEPATH",
  "value": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake"
}
```

同时在根 `CMakeLists.txt` 加了**早期失败**检查：如果既没传 `-DCMAKE_TOOLCHAIN_FILE` 也没设 `VCPKG_ROOT`，直接 `FATAL_ERROR` 并打印三种正确用法。

**为什么值得单独写这个检查？** 因为不写的话，失败会发生在后面的 `find_package(directxtex CONFIG REQUIRED)`，报「找不到包」，而真正原因是「工具链没加载」。错误信息与根因相距越远，排查成本越高。

### 3.2 删掉 `CMakeSettings.json`

原文件内容是：

```json
"variables": [
  { "name": "CMAKE_TOOLCHAIN_FILE", "value": "F:/VS/rep/vcpkg/..." }
]
```

**这不是合法 JSON**——顶层少了 `{ "configurations": [ ... ] }` 外壳。任何 JSON 解析器都会失败。它不是「配置有点旧」，而是「文件本身是坏的」。直接删除，让 `CMakePresets.json` 成为唯一配置入口。

### 3.3 `vcpkg.json` 补 `builtin-baseline`

新版 vcpkg 在 manifest 模式下**要求** baseline，否则报：

```
error: this vcpkg instance requires a manifest with a specified baseline
```

加上 `"builtin-baseline": "<vcpkg repo commit>"` 后，依赖版本被**钉死**，不同机器/不同时间构建结果一致。这也是可复现性的必要前提。

### 3.4 `RELEASE` 宏：一个「从来没生效过」的分支

源码里有 13 处 `#ifdef RELEASE`，但**全仓库从未定义过它**。后果：Release 构建仍然走 Debug 分支——断言照常 `__debugbreak()`，Debug Layer 照常开启，资源命名照常执行。

在 `Engine/CMakeLists.txt` 里补上：

```cmake
if(CMAKE_BUILD_TYPE STREQUAL "Release" OR CMAKE_BUILD_TYPE STREQUAL "MinSizeRel")
    target_compile_definitions(TooiyumeEngine PUBLIC RELEASE=1)
endif()
```

### 3.5 打开后会暴露真实缺陷——这正是它的价值

定义 `RELEASE` 后 Release 构建**立刻编译失败**，暴露出：

```cpp
// CommandContext.h:488
ASSERT(BufferData != nullptr && Math::IsAligned(BufferData, 16))   // 注意：没有分号

    DynAlloc cb = m_CpuLinearAllocator.Allocate(BufferSize);
```

Debug 版 `ASSERT` 展开成 `if (...) { ... }`，天然是一个完整语句，所以调用点不带分号也没事。但 Release 版原来是 `(void)(isTrue)`——**没有分号**，于是后面那行变成：

```cpp
(void)(cond) DynAlloc cb = ...;   // 语法错误
```

修复方式是把 Release 版宏改成自带分号：

```cpp
#define ASSERT( isTrue, ... ) (void)(isTrue);
```

这样两种写法都合法：带分号的变成 `;;`（空语句），不带的被正确终止。

**这个案例的教学价值**：一个「从未被编译过的分支」里可能藏着真实的语法错误。分支存在 ≠ 分支正确。R0 把 Release 纳入常规验证，就是为了不让这类问题继续潜伏。

## 4. Shader 编译链：让「改 HLSL 真的生效」

### 4.1 最隐蔽的坑：仓库里的旧字节码头

`ForwardRenderer.cpp` 原来这样引用 shader：

```cpp
#include "Shader/01_Default/DefaultVS.h"   // 命中仓库内文件，不是构建产物
```

而 `Engine/CMakeLists.txt` 的 10 个 `compile_shader()` **没有任何一个涉及 `01_Default`**。

于是：`Engine/Shader/01_Default/DefaultVS.h` 是 2026-05-04 某次手工导出的字节码，**从此再没被更新过**。改 `.hlsl` 完全无效，构建也不会报任何警告。

### 4.2 修复的三个步骤

1. **把 `01_Default` 纳入编译**：
   ```cmake
   compile_shader(DefaultVS Shader/01_Default/DefaultVS.hlsl MainVS vs_6_4)
   compile_shader(DefaultPS Shader/01_Default/DefaultPS.hlsl MainPS ps_6_4)
   ```
2. **改 include 指向构建产物**（`#include "DefaultVS.h"`，由 ShaderCache 目录解析）
3. **删除仓库里的旧 `.h`**，让它不可能再被误选

### 4.3 顺带解决的符号命名问题

生成的头部符号是 `DefaultVS_cso[]`（由 `BinToHeader.cmake` 按文件名生成），而旧头部是 `g_pDefaultVS[]`。改 include 后编译报 `未声明的标识符`——**这正是「确认真的用上了生成头」的证据**。把调用点改成 `DefaultVS_cso` 即可。

### 4.4 `.hlsli` 依赖追踪

原来 `compile_shader` 的 `DEPENDS` 只有主 `.hlsl`：

```cmake
DEPENDS ${SHADER_SOURCE}
```

意味着改 `DeferredCommon.hlsli`（被 3 个 shader 引用）**不会触发任何重编译**。

新增 `Engine/20_cmake/ShaderDeps.cmake`，递归扫描 `#include` 并收集真实存在的文件作为依赖。

**验证方式**（可复现）：
```bash
touch Engine/Shader/02_Deferred/DeferredCommon.hlsli
scripts\build.bat Debug
# 预期恰好重编 3 个：StaticMeshVS / GBufferPS / LightingPS
```
实测输出：
```
[1/6] Compiling Shader: Shader/02_Deferred/StaticMeshVS.hlsl
[2/6] Compiling Shader: Shader/02_Deferred/GBufferPS.hlsl
[3/6] Compiling Shader: Shader/02_Deferred/LightingPS.hlsl
```

精确命中，不多不少。

### 4.5 include 顺序也有讲究

```cmake
target_include_directories(TooiyumeEngine PUBLIC
    "${CMAKE_BINARY_DIR}/ShaderCache"   # 生成头优先
    ${CMAKE_CURRENT_SOURCE_DIR}
)
```

把 ShaderCache 放前面，即使将来有人又把旧 `.h` 提交回来，也不会被优先命中。**这是纵深防御，不只是修当下的 bug。**

## 5. 输入与日志：把「看不见的失败」变成「可读的证据」

### 5.1 DirectInput 失败不应致命

启动时 `DirectInput8Create` 返回 `E_FAIL`（0x80004005），原代码直接 `ASSERT(false)` + `__debugbreak()`——**程序在「键鼠输入不可用」这种非核心问题上直接退出，连渲染都没机会跑**。

两处修复：
1. **接口类型不一致**：原来用 `IID_IDirectInput8`（宽字符版）却存进 `IDirectInput8A*`（窄字符版）。两者是不同的 COM 接口，指针不能互换，后续调虚函数会走错槽位。改成 `IID_IDirectInput8A`。
2. **失败降级**：记录警告 + 设 `s_KbmReady = false`，`KbmUpdate` 提前返回，渲染链路继续。

设计原则：**区分「核心能力」与「辅助能力」**。渲染器跑不起来必须失败；键鼠不可用只是降级。

### 5.2 日志从「只有调试器可见」到「落盘」

原来 `Utility::Printf` 只调用 `OutputDebugString`——**双击 exe 运行时什么都看不到**，崩溃/资产缺失完全无法排查。

改为同时写入 `<exe目录>/tooiyume_log.txt`。

### 5.3 分级：LOG_INFO / LOG_TRACE

诊断期间插了大量 `[Boot]` 追踪，验证完成后收敛成两级：

```cpp
LOG_INFO(...)   // 默认输出：设备、交换链、资源根、模型加载、生命周期边界
LOG_TRACE(...)  // 仅定义 TOOIYUME_VERBOSE_LOG 时输出：函数级细粒度追踪
```

最终启动日志只剩 8 行，全部是关键事实：

```
[Asset] AssetsRoot = D:\...\TooiyumeRender\Assets\
Looking for a Nvidia GPU
Selected GPU:  NVIDIA GeForce RTX 4060 Ti (16109 MB)
[Boot] Graphics: device OK, RequireDXRSupport=0
[Boot] Graphics: InfoQueue break on ERROR/CORRUPTION only
[Boot] calling game.Startup()
[Boot] game.Startup() returned
Changing display resolution to 1920x1080
```

**这就是「可诊断基线」的样子**：一眼能看出设备选对了、资产根找对了、Startup 进出正常。

### 5.4 Debug Layer 的断点级别

原来把 `WARNING` 也设为中断：

```cpp
infoQueue->SetBreakOnSeverity(D3D12_MESSAGE_SEVERITY_WARNING, true);  // ❌
```

Debug Layer 会对大量「不影响结果但会刷屏」的情况（优化提示、资源重叠）报 WARNING，一旦设成 break，程序会在**合法路径**上被调试器打断，反而掩盖真正的 ERROR。改成只 break `ERROR` / `CORRUPTION`。

## 6. `forceRebuild`：让缓存真正生效

三个 Demo 都写死：

```cpp
bool forceRebuild = true;   // ❌ 每次都全量重烘焙
```

这直接废掉了 `ModelLoader` 里精心写的 mtime 缓存逻辑（重新解析 glTF、重算切线、重算优化索引、重转纹理）。

改为命令行开关：

```cpp
bool forceRebuild = CommandLineArgs::HasFlag(L"RebuildModels");
```

### 顺带修好一个真实 bug

实现 `HasFlag` 时发现原 `GatherArgs` 有缺陷：

```cpp
const wchar_t* key = pfnGet(i);
i++;                                    // 先自增
if (i < numArgs && key[0] == '-')       // 再判断
```

当 `-Flag` 是**最后一个 token**（`app.exe -RebuildModels` 这种最常见的写法），自增后 `i == numArgs`，条件不成立，flag 被静默丢弃。

改成「先看当前 token 是不是 `-key`，再决定要不要吃掉下一个 token」，末尾 flag 也能正确识别。

**验证**：`-RebuildModels` 让 `merlin.ty` 的 mtime 从 8-15 更新到 10-24；不带参数时 mtime 保持不变。

## 9. 给后续阶段的建议

1. **R1 优先修「输入数据」而不是「BRDF」**。审计已确认 `DeferredCommon.hlsli` 的 GGX/Smith/Schlick 实现是正确的；画面不对的原因在材质槽映射、默认贴图、切线解码等**数据链路**上。改 BRDF 公式只会掩盖真正的问题。
2. **R1.6（sorter Reset）要在接 ImGui 之前做**。原因是材质编辑会触发 `MarkDirty`，从而暴露 sorter 累积问题——那时再修，会被误判成「ImGui 的 bug」。
3. **保持 Release 构建常态化**。本次就是靠它发现了 `ASSERT` 宏的真实语法缺陷。建议 CI 或本地脚本同时跑 Debug 和 Release。
4. **新增文件后必须重新 configure**。`Engine/CMakeLists.txt` 用 `GLOB_RECURSE` 且没有 `CONFIGURE_DEPENDS`，新增 `.cpp` 不 reconfigure 不会进构建。这次新增 `AssetRoot.cpp` 就踩到了——`build.bat ... clean` 可以规避。
