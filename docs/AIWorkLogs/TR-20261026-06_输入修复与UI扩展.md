## 3. Resize 闪退的排查过程（本轮最难）

用 cdb 抓栈 + 逐层加打点，定位到三个独立缺陷：

**A. GpuTimer 断言终止进程**
```
Renderer::GpuTimer::TryGetElapsedMs+0x159
RendererDemoApp::Update
GameCore::UpdateApplication
```
与渲染资源无关 —— 是"性能统计拿不到样本"却用了 `ASSERT(false)`。

**B. ResizeBuffers flags 不一致**
```
ResizeBuffers FAILED hr=0x887A0005 (DXGI_ERROR_DEVICE_REMOVED)
```
创建用 `DXGI_SWAP_CHAIN_FLAG_ALLOW_MODE_SWITCH`，Resize 传 `0`。
这解释了"过几次才崩"的间歇性。

**C. backbuffer 索引未重置**
```
DXGI_ERROR_ACCESS_DENIED ... rendering to a texture while only having read access
[ EXECUTION ERROR #232: DEVICE_REMOVAL_PROCESS_AT_FAULT]
```
Resize 后 `g_CurrentBuffer` 仍是旧值，对错误索引的 buffer 发 COPY_DEST 屏障。

每修一个就露出下一个 —— 只修第一个会"看起来好了但下次还崩"。

## 4. 架构变更：单模型 → 多模型

`ModelInstance m_Model` → `std::vector<SceneModel>`，其中 `SceneModel` 用
`unique_ptr<ModelInstance>` 持有。

三个关键决策：

1. **为什么用 unique_ptr**：`ModelInstance` 无拷贝赋值（含 UploadBuffer 等），
   直接放值类型会让 `vector<SceneModel>` 编译失败（实际踩到）。
2. **为什么增删延迟到帧边界**：`RenderFrameDesc.Models` 存元素指针，
   vector 扩容会让指针失效。UI 只登记 pending，由 `ApplyPendingActions` 执行。
3. **为什么拖动可立即生效**：只改 `m_Locator` 并置脏，不动容器结构。

## 7. 方法论教训

### 7.1 断言不是错误处理

`GpuTimer` 两处 `ASSERT(false)` 直接导致闪退。判断标准：
**这个失败是否影响核心功能？** 不影响（性能统计）→ 必须降级。

### 7.2 间歇性崩溃意味着状态累积

ResizeBuffers flags 不一致"过几次才崩"。不要因为"这一把没崩"就认为修好了。

### 7.3 一个症状可能是多个缺陷叠加

本轮 4 号需求修了 4 个缺陷才彻底解决。**验证必须跑到底并重复多次**。

### 7.4 让编译期替你发现约束

`ModelInstance` 没有拷贝赋值这件事是编译器发现的（vector 编译失败）。
若写成裸指针数组，这个约束就消失了，运行时隐患更多。
