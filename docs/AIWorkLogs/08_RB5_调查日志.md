## 4. G3 抽查记录（抽 3 条，逐条回源核对）

**抽查 1 — 判据公式是否真的写的是 `+ BUFFERCOUNT`（亦或 `+1` / `+GetBufferCount()`）**
- 目标证据：``wiGraphicsDevice_DX12.h:582-636``，报告中用于 §4.2 的核心公式。
- 回源命令：`sed -n '582,600p' "$W/wiGraphicsDevice_DX12.h"`
- 命中输出（节选，**逐字**）：
  ```
  void Update(uint64_t FRAMECOUNT, uint32_t BUFFERCOUNT)
  {
      std::scoped_lock lck(destroylocker);
      framecount = FRAMECOUNT;
      while (!destroyer_allocations.empty() && destroyer_allocations.front().second + BUFFERCOUNT < FRAMECOUNT)
      { destroyer_allocations.pop_front(); /* comptr auto delete */ }
      while (!destroyer_resources.empty() && destroyer_resources.front().second + BUFFERCOUNT < FRAMECOUNT)
      { destroyer_resources.pop_front(); /* comptr auto delete */ }
  ```
- **结果：命中**。确认为 `entry.second + BUFFERCOUNT < FRAMECOUNT`，`BUFFERCOUNT` 是**函数形参**（由调用点 `Update(FRAMECOUNT, BUFFERCOUNT)` 传入，值为 `GetBufferCount()` 即 2），不是写死的 `+1`，也不是 `GetBufferCount()` 的间接调用——这一点比原先的推测更精确，已据此更新 §2.1 与 §4.2 的表述（"形参传入，值=BUFFERCOUNT 常量"）。

**抽查 2 — 帧首阻塞是否遍历**全部**队列、是否真的用 `nullptr` 事件（而非轮询）**
- 目标证据：``wiGraphicsDevice_DX12.cpp:5534-5546``，报告中用于 §4.4 与前提 P2。
- 回源命令：`sed -n '5534,5548p' "$W/wiGraphicsDevice_DX12.cpp"`
- 命中输出（**逐字**）：
  ```cpp
  const uint32_t bufferindex = GetBufferIndex();
  for (int queue = 0; queue < QUEUE_COUNT; ++queue)
  {
      if (queues[queue].queue == nullptr) continue;
      ID3D12Fence* fence = frame_fence[bufferindex][queue].Get();
      if (fence->GetCompletedValue() < frame_fence_values[GetBufferIndex()])
      {
          // nullptr event handle will simply wait immediately:
          //  https://docs.microsoft.com/...s e t e v e n t o n c o m p l e t i o n #remarks
          dx12_check(fence->SetEventOnCompletion(frame_fence_values[GetBufferIndex()], nullptr));
      }
  }
  allocationhandler->Update(FRAMECOUNT, BUFFERCOUNT);
  ```
- **结果：命中，且发现一处新的精确事实**：循环上界是 `queue < QUEUE_COUNT`（本帧枚举内的 5 个队列），`copyAllocator.queue`（额外创建的 COPY 队列）**不在**此循环内。这直接改变了 §8 U6 的表述：现在可确证"帧首阻塞不覆盖异步拷贝队列"，剩下的未知只剩"是否有别的节流"。已在报告中把 U6 从"是否覆盖"改写为"异步拷贝队列由谁节流"。
- 附带确认：`queue == nullptr` 时 `continue`（跳过未创建的队列，例如未用 compute/video decode 时），因此 P2 的"遍历全部"实际是"遍历全部**已创建**队列"。

**抽查 3 — 资源入队时 tag 到底取什么值**
- 目标证据：``wiGraphicsDevice_DX12.cpp:1467-1474``，报告中用于 §3-D、§4.2 的 `tag = framecount`。
- 回源命令：`sed -n '1465,1476p' "$W/wiGraphicsDevice_DX12.cpp"`
- 命中输出（**逐字**）：
  ```cpp
  ~Resource_DX12()
  {
      std::scoped_lock lck(allocationhandler->destroylocker);
      uint64_t framecount = allocationhandler->framecount;
      if (allocation) allocationhandler->destroyer_allocations.push_back(std::make_pair(allocation, framecount));
      if (resource) allocationhandler->destroyer_resources.push_back(std::make_pair(resource, framecount));
      destroy_subresources();
  }
  ```
- **结果：命中**。tag 确为 `allocationhandler->framecount`（**不是** `FRAMECOUNT`，也不是任何 fence 值）；且 `push_back` 的是 `std::make_pair(ComPtr, tag)`，印证"延迟的只是 COM 引用计数"。同时可见 `destroy_subresources()` 在**同一析构体内、无锁外地**立即执行 ⇒ 描述符不延迟（§5.5 / §8 U2 的依据）。

## 7. 踩坑
1. **任务书里的 `FlushDeallocations` 不在 DX12 后端**。它在基类 `wiGraphicsDevice.h:438-445`，且实现只是"提交 `BUFFERCOUNT` 次"。第一次 grep 只搜 `wiGraphicsDevice_DX12.*` 时找不到，容易误判"不存在"。教训：跨文件概念先全仓 grep 再定位。
2. **`GetBufferIndex` 有两个同名不同义的定义**。设备级（`wiGraphicsDevice.h:147`，帧环槽位 = `FRAMECOUNT % 2`）与 `SwapChain_DX12::GetBufferIndex`（`wiGraphicsDevice_DX12.cpp:1595`，backbuffer 索引）。`SubmitCommandLists` 里调用的是前者，若误按后者理解会推出完全错误的帧协议。判定方法：确认类作用域后再读。
3. **`frame_fence_values` 的自增点是 `5458`（`FRAMECOUNT++` 之前），等待点是 `5534`（之后）**。两处都写 `GetBufferIndex()`，但含义分别是"旧帧槽位"与"新帧槽位"，正是这两个**不同的槽位**构成了 2 帧的滞后。第一次读时若把两行视为同一槽位，会得出"等当前帧自己"的错误结论。
4. **`+BUFFERCOUNT` vs `+1` 的差不是"保守一帧"而是"是否 UAF"**。最初直觉认为 `+1` 只是保守度不同；实际推导（§4.2）表明 `+1` 会让释放时刻比安全边界早**恰好一帧**，而那一帧正是资源被最后引用的帧 ⇒ 必然 UAF。
5. **不要整读 `wiGraphicsDevice_DX12.cpp`**。本次最大单段 171 行（5388-5558），其余都在 20–60 行区间；全篇用行号锚点串联（5458 → 5462 → 5531 → 5534 → 5548）即可还原协议，不需要读 7000 行。
