## 1. 目标与不做清单

### 1.1 目标（路线图 §8 D3 逐条对应）

| D3 原文要求 | 本轮的落地方式 |
|---|---|
| 先做硬阴影射线 | `RayTracing.hlsl` 的 `ClosestHit` 里发 `ShadowPayload` 射线，`RAY_FLAG_ACCEPT_FIRST_HIT_AND_END_SEARCH \| SKIP_CLOSEST_HIT_SHADER` |
| 再做反射 | 同一 `ClosestHit` 里发一次 `RayPayload` 反射射线（`Depth=1`），Schlick Fresnel + 强度系数混合 |
| 每个算法有可比较的光栅/光追场景 | `RendererDemoApp` 运行时可在 Deferred/Forward/RayTracing 之间切换，模型与相机保持不变；`docs/AI/R6ctl/screenshot_90.png` 是光栅对照 |
| 明确采样与偏差策略 | 每像素 1 条主射线（无累积、无抖动）；**唯一偏差**是沿法线的 `RTShadowNormalBias`（默认 0.002 m），阴影与反射共用；阴影/反射各 1 次弹射，`MaxTraceRecursionDepth = 2` |
| 性能统计 | `RayTracingFrameStats`（primary/shadow/reflection/total 发射数 + 三角/BLAS/实例数）+ 面板显示 GPU 帧时间 |
| 开关 | `RenderParams::EnableRTShadow` / `EnableRTReflection` / `RTDebugView` + 独立「Ray Tracing (R6)」面板 |
| VS 启动项精简 | `.vs/launch.vs.json` 从 6 条降到 4 条（Deferred / Forward / RayTracing / RendererDemo） |

### 1.2 明确不做（避免被后续会话当成"漏了"）

- **不接材质**：D3 用中性灰 `albedo=(0.8,0.8,0.8)` + 几何面法线。原因见 §8 取舍 A。
- **不做软阴影 / 多次弹射 / 累积降噪**：D3 明确只要求硬阴影；采样策略是每像素 1 条，多于 1 条必须有累积缓冲与时间稳定性设计，属 D4+。
- **不做点光源与 IBL 的光追版本**：HLSL 里只有一个方向光 + 程序化 `SkyColor` 环境项。UI 上这两段在 DXR 下**保持禁用**（不放假控件）。
- **不动 `DiagnosticView`/`DebugView` 枚举**：见 §8 取舍 B。
- **不做命中率统计**：只报精确可算的发射数上界。

## 5. 关键改动与调用链

### 5.1 先修构建系统（否则后面全是假验证）

**症状**：R6 首跑日志 `[DXR] 光追开关：阴影=开 反射=开（偏差=0.0000 m，阴影距离=-0.0 m ...）` —— 新增的 6 个字段全读成 0，`EnableRTReflection` 默认 `false` 却打成「开」。

**根因**：`ninja -t deps` 显示 **74 个 .obj 全部 `#deps 0`** —— 改任何 `.h` 都不触发重编。
- `out/build/Debug/CMakeFiles/rules.ninja:17` 的 `msvc_deps_prefix` 是双重编码乱码（原文「注意: 包含文件: 」，被存成 `娉ㄦ剰: 鍖呭惈鏂囦欢:`）。
- 机理：`cl.exe /showIncludes` 按**控制台代码页**输出；CMake 在 configure 期抓这段前缀写进 `rules.ninja`；Ninja 之后用这个字节串去 grep cl 的输出。系统 ACP=936(GBK)、控制台当时是 65001(UTF-8) → 前缀乱码 → 一行都匹配不到 → **所有依赖静默丢失**。
- 后果是静默的：编译链接全绿，但改结构体后其他 obj 保留旧布局，运行时内存错位。

**修复**（`scripts/build.bat`，现纯 ASCII / 8565 B）：
1. 步骤 0 强制 `chcp 65001`，**同时包住 configure 与 build**（cl 是在 build 期打印前缀的）；
2. 代码页哨兵 `_tooi_codepage.txt`：构建树已存在但哨兵缺失/≠65001 → 整树 `rmdir /s /q` 重配（`CMakeCXXCompiler.cmake` 只有 clean configure 才重生成）；
3. 步骤 6b 依赖自检：`ninja -t deps` 输出到临时文件，`findstr /R "#deps [1-9]"`，结果文件字节数为 0 才警告；
4. 成功/fail 两条退出路径恢复原代码页。

**验证**：`msvc_deps_prefix` 恢复正确、「`RayTracingRenderer.cpp.obj` `#deps 53`」、全树 `#deps 0` 只剩 3 个天然无 include 的（`PCH.cpp` / `PSOBuilder.cpp` / `ShaderLibrary.cpp`）、`touch RenderParams.h` 后 `ninja -n` 报 9 个构建步骤。

### 5.2 HLSL：三种载荷 / 三条射线

```hlsl
struct RayPayload    { float3 Color; float HitDistance; uint Depth; uint _pad0; float2 _pad1; }; // 32 B
struct ShadowPayload { float Visible; float _pad0; };                                            //  8 B
```
`ShadowPayload` 用**独立的 miss 记录**（SBT miss 表第 2 条 = index 1）：
```hlsl
TraceRay(g_Scene, RAY_FLAG_ACCEPT_FIRST_HIT_AND_END_SEARCH | RAY_FLAG_SKIP_CLOSEST_HIT_SHADER,
         0xFF, 0, 1, 1, ray, shadowPayload);
```
关键理由（写在源码注释里）：DXR 的命中着色器签名按载荷类型绑定；若阴影射线也走主 hit group，`RayPayload` 的 `ClosestHit` 会把 `ShadowPayload` 当 `RayPayload` 解释、静默写坏字段。加 `SKIP_CLOSEST_HIT_SHADER` 后「命中 → 不调用任何着色器、载荷保持初值 0；只有完全未命中才调用 `ShadowMiss` 置 1」，因此「初值 0 = 被遮挡」成立。

递归闸门：
```hlsl
if (payload.Depth >= 1u) { /* 只做本地面 Lambert 着色 */ return; }
```
越界**不报错**，设备会直接把进程移除（`DEVICE_REMOVED 0x887A0005`）。

### 5.3 偏差策略（D3 要求"明确"）

- **唯一偏差**：沿法线抬起 `RTShadowNormalBias` 米（默认 0.002 m）。阴影射线与反射射线共用同一值。
- 为什么不沿光线偏移：沿法线抬起保证新起点仍在表面外侧；沿光线抬起在掠射角会把起点推到表面内侧，反而制造更多自遮挡。
- 为什么不给两个偏差滑杆：同时存在两个偏差时，出问题无法归因到哪一个。
- 反射射线的 `TMin` 也用这个偏差（从 0 起算会立刻命中自己所在三角形 → 全场条纹）。
- 敏感性实测：把偏差放大到 0.05 m 后，调试通道画面明显变白（接触阴影被漏掉）→ 证明这个参数真的在起作用（`r6_09_shadow_bias_large.png`）。

## 6. 资源生命周期与同步点

| 资源 | 创建 | 状态 | 释放 | 本轮变化 |
|---|---|---|---|---|
| BLAS × 15 | `CreateAccelerationStructure`（UAV flag + AS 初始状态） | 创建即 AS，**永不发 barrier** | `DestroyBlasBuffers` | 无 |
| TLAS | 同上 | 同上 | `Destroy` | 无 |
| Scratch | `GpuBuffer::Create` | COMMON → UAV，各段互不重叠故无需 UAV barrier | `Destroy` | 无 |
| InstanceDesc / InstanceData / SBT | `UploadBuffer`（UPLOAD 堆） | 常驻 GENERIC_READ | 同上 | SBT 192 B 不变但 miss 段语义变了 |
| 输出 UAV | `BufferManager::CreateColorBuffer` | UNORDERED_ACCESS → PIXEL_SHADER_RESOURCE | `DestroyOutputTargets` | 无 |

**同步点**：`DispatchRays` 不自动 flush 资源屏障（不像 `DrawInstanced`），所以 `Render` 里在 `DispatchRays` 前显式 `FlushResourceBarriers()`；`BuildRaytracingAccelerationStructure` 前同样（否则报 `EXECUTION ERROR #538 INVALID_SUBRESOURCE_STATE`）。

## 7. 与 WE 引擎的比较

| 维度 | WE（自研引擎） | 本项目 R6 | 差异是否合理 |
|---|---|---|---|
| 阴影 | Shadow Map（深度贴图 + PCF） | DXR 硬阴影射线 | 合理：本项目处于「两种算法并存比较」阶段，路线图 §9 明确先 Shadow Map 后 SSAO |
| 反射 | SSR（屏幕空间） | 单次光追反射 | 合理：光追反射能打到屏幕外，SSR 不能；但也更贵 |
| 阴影偏差 | 深度偏移 + 法线偏移（两参） | **只有法线偏移一个参数** | 简化：D3 阶段先保证可归因，D4+ 再引入第二个 |
| 采样 | PCF 多 tap / SSR 多次 | **每像素 1 条射线** | 简化：无累积缓冲时多次采样只会更慢不会更好 |
| 降噪 | 有独立 pass | 无 | 简化：硬阴影不需要；反射噪点明显，属 D4+ |

**结论：R6 在算法选择上比 WE 更"物理正确"但更"未经工程化"。这是刻意的 —— D3 的目标是证明算法链路通了，不是产出可用于生产的画质。**

## 8. 方案取舍

### 取舍 A：D3 用中性灰 albedo，不接材质 ✅ 采纳

| 方案 | 理由 |
|---|---|
| **A（采纳）中性灰 + 几何面法线** | D3 是为了让「阴影/反射是否真的在算」可被证明。接材质会引入贴图采样、UV 展开、sRGB 解码三条新的失败面，一旦画面不对无法判断是光追错还是材质错 |
| B 复用 Deferred 的 GBuffer 材质 | 需要把 GBuffer 从光栅管线里读出来，跨越两条渲染路径的资源依赖；且 GBuffer 的 Normal 是压缩格式，DXR 侧解压会引入第二套解码代码 |
| C 直接读 glTF 材质并做 Cook-Torrance | 没有材质系统时只是把同一份错误数据算得更贵；且 D3 不要求 |

**代价（已知并接受）**：低多边形刻面外观明显（用面法线不用顶点法线）、无贴图细节。这是 NEXT 阶段（D4 接材质）的输入。

### 取舍 B：新增 `RayTracingDebugView` 而不是扩展 `DebugView` ✅ 采纳

- `DebugView` 每项对应 Deferred 的 GBuffer（Metallic/Roughness/AO），DXR 没有 GBuffer。
- 塞进同一枚举会让同名选项在两条路径下含义不同 —— 语义陷阱，且 `DebugViewName()` 要处理两套语义。
- 代价：多一个枚举与一个 Combo。已在 `RenderParams.h` 注释里写明理由。

### 取舍 C：SBT miss 表两条记录，而不是加第二个 hit group ✅ 采纳

| 方案 | 理由 |
|---|---|
| **A（采纳）2 条 miss + `SKIP_CLOSEST_HIT_SHADER`** | 命中时不需要任何着色器参与，载荷保持初值 0 即「被遮挡」；一条 `ShadowMiss` 处理未命中 |
| B 第二个 hit group + 空 closesthit | 需要额外 hit group 记录、额外导出，且空 closesthit 仍会被调用，成本更高 |
| C 用 `RAY_FLAG_ACCEPT_FIRST_HIT_AND_END_SEARCH` 不带 SKIP | `ClosestHit` 会被调用，把 `ShadowPayload` 当 `RayPayload` 写坏（32B vs 8B，越界） |

### 取舍 D：单独开「Ray Tracing (R6)」面板，而不是塞进 Renderer 面板 ✅ 采纳

- Renderer 面板在 1080p 下已顶到屏幕底部，继续加会被裁（实测过）。
- 更重要：光追控件与上面四个光栅 `[stub]` 开关**性质完全不同**，放一起会让读者误以为它们也是空壳。

## 12. 主动回忆（8 题）

1. **为什么阴影射线要用 `SKIP_CLOSEST_HIT_SHADER`？** 因为命中着色器签名按载荷类型绑定；不加这标志，主 `ClosestHit`（按 `RayPayload` 32B 解释）会被调到只传了 `ShadowPayload` 8B 的射线上，越界写坏内存。加了以后命中不调用任何着色器，载荷保持初值 0 = 被遮挡，只有未命中才走 `ShadowMiss` 置 1。
2. **为什么 `MaxTraceRecursionDepth` 是 2 而不是 1？** 主射线（0）发反射射线（1），反射射线命中时若再发一条就是 2 —— 所以闸门设在 `Depth >= 1` 早退，深度上限 2 刚好够主+反射一次。若设 1，反射射线命中会直接越界移除设备。
3. **为什么 `SetConstantArray` 从 32 改成 48 DWORD？** 新增了 4 个 `Vector4`（LightDirection/LightColor/RTParams/RTParams2）。四处必须同步：HLSL cbuffer、`static_assert(sizeof==192)`、`InitAsConstants(0,48)`、`SetConstantArray(...,48,...)`。漏改任意一处 → 后续字段整体错位、画面异常但**不报错**。
4. **`SunDirection` 存的是传播方向还是指向光源？** 传播方向（从太阳射向场景）。光栅侧 `LightingPS.hlsl:118` 用 `normalize(-DirectionIntensity.xyz)` 取反；DXR 侧 `toLight = normalize(-g_LightDirection.xyz)` 同样取反。**两侧必须保持同一约定**，`RenderParams.h:57-60` 有注释警告。
5. **为什么反射射线的 TMin 要用 `RTShadowNormalBias`？** 反射射线起点与阴影射线都是 `hitPos + n*bias`，若 TMin=0 会立刻命中自己所在三角形 → 全场条纹（自相交）。
6. **`#deps 0` 是怎么被发现的，为什么它比任何渲染 bug 都危险？** R6 首跑所有新字段读成 0；查 `ninja -t deps` 发现全部 obj 都是 `#deps 0`。危险在于它**完全静默**：编译链接全绿，但改结构体后其他 obj 保留旧布局 → 运行时随机内存错位。根因是 `msvc_deps_prefix` 在 ACP≠控制台代码页时被双重编码。
7. **为什么 Debug 和 Release 的渲染图 md5 应该相同？** 因为渲染是确定性的（固定相机、固定参数、每像素 1 条射线、无抖动）。若不同，说明某处有未初始化内存或随机采样。实测 11 张图 md5 完全相同。
8. **`r6_00` 与 `r3_00_initial_deferred.png` 为什么同 md5？** 后者名虽叫 deferred，但在 `-R3Test` 第 0 步时渲染器还是 `RayTracingRenderer`（启动参数指定），且参数与 `r6_00` 相同，输出自然一致。

## 附：本轮踩到的坑（8 条）

1. **`msvc_deps_prefix` 双重编码** —— 见 §5.1。这是本轮最大发现，值得写进 AGENTS.md。
2. **`for /f ... in ('ninja ... | findstr ...')` 在 bat 里会挂死** → 必须先 `> 文件` 重定向再 `findstr` 文件再 `for %%A in (file) do set SIZE=%%~zA`。
3. **`findstr /R /C:"#deps [1-9]"` 语法错**（`/C:` 与 `/R` 不能混）→ 正确是 `findstr /R "#deps [1-9]"`。
4. **bat 里绝不能出现中文**（GBK 读入后拆成命令，报 `'xxx' is not recognized`）。
5. **`imgui.ini` 会覆盖 `ImGuiCond_FirstUseEver`** —— 改了 `SetNextWindowPos` 但画面没动，先删 exe 目录下的 `imgui.ini`。
6. **ImGui 滑块标签画在控件右侧**，面板靠近屏幕右缘时标签会被裁掉 → `PushItemWidth` 收窄控件。
7. **`cl.exe` 在 bash 里直接调用时 `/nologo` `/TP` 会被 MSYS 路径转换吃掉**（变成 `F:/DSH/.../nologo`）→ 必须写成 .bat 由 `cmd //c` 执行。
8. **统计滞后一帧** —— 统计在 `Render` 末尾写、`LogState` 在 `Update` 开头读，所以日志里的射线数与当前帧参数差一帧。这不是 bug，但会被误读。
