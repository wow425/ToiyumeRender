## 6. 踩坑

### 6.1 工具层面

1. **run_code 里写含反引号的 markdown 会语法错误**。
   现象：`Expected ';', '}' or <eof>`。
   原因：模板字符串里嵌了 markdown 反引号，Node 解析器把它当成模板串结束符。
   解法：先用哨兵（双波浪线）占位，写完再一次性还原成反引号。**本报告与本文档都用此法写成**。

2. **ops_bash 里用 heredoc / 长单引号串会 unexpected EOF**。
   现象：`unexpected EOF while looking for matching quote`（即使先 base64 编码仍失败）。
   解法：改用 node:fs 的 appendFileSync 直接写文件，绕开 shell 引号。

3. **base64 + printf 管道不可靠**：长串下单引号包裹本身易错。
   **最终结论：不要用 shell 写文件内容，用 fs。**

### 6.2 源码理解层面

4. **CreateSubresource 返回 -1 不是错误**。
   第一遍读到 return -1 以为是 fail，实际是"使用了默认视图"的约定（DX12.cpp:4825 与 GetDescriptorIndex :5195 对照才确认）。这是 WE 里最容易误读的 API 之一。

5. **PipelineStateDesc 不含 RT 格式**。
   初读以为 PSO 描述完整，直到看 CreatePipelineState 的 renderpass_info 参数（:4301）才明白是"半成品 + 运行时补全"。这是理解 PipelineHash 为什么需要 renderpass_hash 的关键。

6. **根签名不在引擎里**。
   grep CreateRootSignature 只在 :3911 出现一次，且输入是 shader 的 shadercode。这意味着"引擎创建根签名"这个先入为主的印象完全错误——布局是 **HLSL 宏 + 编译参数**。

7. **PUSH_CONSTANT_COUNT=22 与根签名 12 不一致**。
   两边都是实测，但数字冲突。列入报告 8 节 U4，未强行解释。

8. **RootSignatureOptimizer 在 CreateShader 里只对 CS/LIB init**。
   （:3920-3925）图形 PSO 的 init 在 CreatePipelineState :4193。两处初始化点不同，容易漏看后者。列入 8 节 U1。

### 6.3 与队友的边界

- 本块（RB4）与 **RB5**（同步/内存/生命周期）在"延迟销毁 10 条队列"（DX12.h:565-638）与"AllocateGPU ring"（wiGraphicsDevice.h:331-389）上重叠。本报告只给**判据公式**（4.5）与**接口形态建议**（6.6），不展开生命周期状态机——那是 RB5 的核心产出。
